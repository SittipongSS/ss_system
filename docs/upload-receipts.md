# ใบรับการอัปโหลด (`upload_receipts` · mig 0406) — ที่มาของ `driveFileId` ที่ client ส่งมา

> สถานะ: **กำลังดำเนินการ** · ตรวจกับโค้ดเมื่อ 2026-10-08 · **merge เข้า main แล้ว 2026-10-08** (#1885 `cf9c7b24`) · มติเจ้าของ 08/10/2569 · mig 0406 **รันบนฐานจริงแล้ว 2026-10-08** (เจ้าของรันบน SQL Editor · ยืนยันจากฝั่งแอป: คีย์ service อ่านตารางได้ · คีย์ anon ได้ `42501`) · เจ้าของสั่ง deploy คืน 2026-10-08 — **smoke test บน production ยังค้าง** (ดู §ลำดับขึ้นระบบ ข้อ 4) · รอบหนึ่งครอบ `POST /api/attachments` (สาขาไฟล์ธรรมดา) · `DELETE /api/upload` · ตัวปล่อยไฟล์ของแถวไฟล์แนบ — ปลายทางอื่นเป็นรอบสอง (§ยังไม่ครอบ) · ⚠️ ยังไม่ได้ลองกับ server / Drive จริง

**อ่านก่อนแตะสายอัปโหลด → แนบ → ลบไฟล์ หรือเพิ่มปลายทางใหม่ที่รับ `driveFileId` จาก client**

## ช่องที่ปิด

`driveFileId` ของไฟล์แนบ **มาจาก client** และไม่มีที่ไหนจดว่า id นั้นเป็นไฟล์ที่คนเรียกอัปเองจริง:

- **ปลูก id ของไฟล์คนอื่นเพื่ออ่าน/ทิ้ง** — แถว `attachments` คือกุญแจเปิดอ่านไฟล์ (proxy ดาวน์โหลดสตรีมตาม id ของแถว) และกุญแจทิ้งไฟล์ (ลบแถว = ระบบทิ้งไฟล์ลงถังขยะ Drive) · `POST /api/attachments` เคยรับ id อะไรก็ได้ ⇒ คนที่แก้ระเบียนไหนได้สักใบ แนบแถวที่ชี้สัญญาที่เซ็นแล้ว/บัตรประชาชนลูกค้าของคนอื่น แล้วเปิดอ่านหรือกดลบได้
- **`DELETE /api/upload` ทิ้งอะไรก็ได้** — ใครล็อกอินก็เรียกได้ เชื่อ id จากคำขอ ถามแค่สองตารางและทิ้ง error ของคำถาม ⇒ ส่ง id ของโฟลเดอร์ลูกค้า · ไฟล์ในเธรด · รูปของนัดช่าง แล้วระบบทิ้งให้ทันทีโดยไม่ต้องมีแถวสักแถว

## ทะเบียน: ตาราง `upload_receipts`

หนึ่งแถว = หนึ่งไฟล์ที่ **server อัปขึ้น Drive เอง** · id มาจาก Drive ไม่ใช่จากคำขอ ⇒ ออกใบรับให้ไฟล์ที่ตัวเองไม่ได้อัปไม่ได้

| ช่อง | ความหมาย |
|---|---|
| `driveFileId` text **PK** | CHECK `^[A-Za-z0-9_-]{1,200}$` (ตัวหนังสือเดียวกับ `DRIVE_FILE_ID_PATTERN` ใน [`lib/upload/receipts.js`](../webapp/src/lib/upload/receipts.js) — เทสต์เทียบให้) · id ซ้ำ (23505) = error · **insert ไม่ใช่ upsert** |
| `userId` text NOT NULL | คนอัป (id ผู้ใช้ทั้งระบบเป็น text · บัญชีทดสอบในเครื่องคือ `local-dev`) |
| `entityType` · `entityId` | ค่าที่ client ส่งตอนอัป **ยังไม่ผ่านด่านสิทธิ์ใด** — จดไว้ดูย้อนหลัง ห้ามใช้ตัดสินว่าไฟล์เป็นของระเบียนไหน |
| `createdAt` | อายุใบรับ **24 ชั่วโมง ตัดสินตอนอ่าน** (`UPLOAD_RECEIPT_TTL_MS` · ครบ 24 ชั่วโมงพอดียังใช้ได้) · แถวไม่ถูกลบในรอบนี้ |
| `claimedBy` · `claimedAt` | ปลายทางที่รับไฟล์ไปแล้ว เช่น `attachments:<id แถว>` · ว่าง = ยังไม่มีใครรับ |

ตารางฝั่ง server ล้วน: เปิด RLS **ไม่มี policy** · REVOKE จาก `PUBLIC`/`anon`/`authenticated` · GRANT `service_role` · ดัชนี `upload_receipts_created_idx` เตรียมไว้ให้งานเก็บกวาด · ไม่มี backfill · ขึ้นทะเบียน `upload_receipts: 0` ใน `scripts/check-row-cap.mjs` (ทุกจุดอ่านเป็น primary key `.maybeSingle()` หรือ `.limit(1)`)

### ทำไมเป็นทะเบียนฝั่ง server ไม่ใช่โทเคนที่เซ็น

- **ไม่ต้องแก้ client** — PR นี้ไม่มีไฟล์ฝั่งจอเลย · ผู้เรียกทุกจุดแกะ ref จากการอัปแล้วประกอบ payload เอง ช่องใหม่อย่างโทเคนจะหล่นหายจนกว่าจะแก้ครบทุกจุด
- **แท็บที่เปิดค้างยังใช้ได้** — จอรุ่นเก่าส่งแค่ `driveFileId` เหมือนเดิม server ถามทะเบียนของตัวเอง (ข้อยกเว้นเดียวดู §ลำดับขึ้นระบบ ข้อ 5)
- **ฟอร์มที่จำ ref ไว้แล้วกดส่งซ้ำ** ส่งได้แค่ id เดิมที่จำไว้ (ไม่ได้จำโทเคน) — ทะเบียนตรวจจาก id อย่างเดียวได้ · ใบรับของคนอัปเองใช้ได้ 24 ชั่วโมงตราบที่ยังไม่ถูกประทับ
- ทะเบียนตอบได้ด้วยว่า "ปลายทางรับไปแล้วหรือยัง" (`claimedBy`) ซึ่งเส้นถอยการอัปต้องใช้ · และใน `webapp/src` ไม่มีโค้ดเซ็น (HMAC) อยู่เลย — ทางโทเคนต้องตั้งกุญแจลับตัวใหม่

## ออกใบรับ — สองจุดเท่านั้น

`recordUploadReceipt(supabase, { driveFileId: uploaded.id, userId: user.id, entityType, entityId })` เรียกทันทีหลัง `uploadForEntity` สำเร็จ ใน `POST /api/upload/commit` และขา Drive ของ `POST /api/upload` (นอก `try` ของ Drive · ขาหลักฐานใน bucket ส่วนตัวไม่ออกใบรับ)

- ลองสองครั้ง (หน่วง 250 ms) · 23505 ตั้งแต่ครั้งแรก = error ทันที · 23505 ตอนครั้งที่สอง = อ่านแถวกลับ ถ้าเป็นของผู้ใช้คนเดียวกันถือว่าสำเร็จ · ไม่ throw
- **ออกไม่สำเร็จ = log `🔴 ออกใบรับการอัปโหลดไม่สำเร็จ` แล้วคืน ref ตามเดิม ไม่ล้มการอัป** — แต่ไฟล์ใบนั้นเก็บลงปลายทางของไฟล์ Drive ที่ไหนไม่ได้แล้ว (ไฟล์แนบ · ไฟล์ในเธรด · รูป/ลายเซ็นของนัดช่าง ตรวจใบรับทุกที่ — §รอบสอง) · การแนบเป็นไฟล์แนบปิดเองสองแบบ (เธรดและนัดช่างตอบ 400/503 แบบเดียวกัน):
  - ทะเบียนอ่านไม่ได้ / ยังไม่มีตาราง ⇒ แนบ **503** และถอยการอัปก็ **503**
  - พลาดชั่วคราวแต่ทะเบียนอ่านได้ ⇒ แนบ **400** · ถอยการอัป **403** ⇒ ไฟล์ค้างบน Drive ให้รายงานไฟล์กำพร้า (cron `drive-orphans`) ตามเก็บ ผู้ใช้อัปใหม่แล้วแนบอีกครั้ง

## `POST /api/attachments` — สาขาไฟล์ธรรมดา

ลำดับ: ด่านสิทธิ์ของระเบียน → กติกาชนิดไฟล์ของ docType → **ห้าด่านข้างล่าง** → เขียนแถว → ประทับใบรับ (คนไม่มีสิทธิ์ต้องไม่ได้ใช้เส้นนี้ถามว่า id ไหนมีใบรับ) · สาขาเอกสาร Google (`google: {…}`) ไม่ผ่านบล็อกนี้ เพราะ id มาจาก Drive

| # | ด่าน | ไม่ผ่าน |
|---|---|---|
| ① | `driveFileId` ต้องเป็นตัวหนังสือไม่ว่าง (แถวที่มีแต่ `fileUrl` คือทางอ้อมข้ามทุกด่าน) | 400 `แนบไฟล์ไม่สำเร็จ — ไม่พบไฟล์ที่อัปโหลด ลองอัปโหลดไฟล์แล้วแนบอีกครั้ง` |
| ② | รูปร่าง id (`DRIVE_FILE_ID_PATTERN`) | 400 `แนบไฟล์ไม่สำเร็จ — รหัสไฟล์ไม่ถูกต้อง ลองอัปโหลดไฟล์แล้วแนบอีกครั้ง` |
| ③ | `parseDriveId(fileUrl)` ถ้าแกะ id ได้ ต้องตรงกับ `driveFileId` | 400 `แนบไฟล์ไม่สำเร็จ — ลิงก์ของไฟล์ไม่ตรงกับไฟล์ที่อัปโหลด ลองอัปโหลดไฟล์แล้วแนบอีกครั้ง` |
| ④ | ใบรับของคนเรียกเอง อายุไม่เกิน 24 ชั่วโมง (`uploadReceiptStatus` → `requireUploadReceipt`) | ไม่มี/ของคนอื่น/หมดอายุ: 400 `ไฟล์นี้ไม่ได้มาจากการอัปโหลดของคุณในช่วง 24 ชั่วโมงที่ผ่านมา — อัปโหลดไฟล์ใหม่แล้วแนบอีกครั้ง` · ตรวจไม่ได้: 503 `ตรวจที่มาของไฟล์ไม่ได้ในขณะนี้ — ลองแนบอีกครั้ง` |
| | ใบรับถูกประทับแล้ว (`claimedBy`) | 400 `ไฟล์นี้ถูกแนบไว้กับเอกสารอื่นแล้ว — อัปไฟล์ใหม่แล้วแนบอีกครั้ง` |
| ⑤ | ไม่มีที่ไหนอ้างไฟล์นี้ (`driveFileReferenced`) | อ้างอยู่: 400 ข้อความเดียวกับแถวบน · ตรวจไม่ได้: 500 |

- ⑤ ไม่ถามกับรูปของแถว checklist (`spec_item_image`) — บล็อกเดิมของ docType นั้นถามแถว `attachments` เอง (`driveFileHeld`) พร้อมข้อความของมัน และถูกเทสต์ตรึง · เธรด/หลักฐาน Won ของ docType นั้นกันที่ตัวปล่อยไฟล์ชั้นเดียว
- **ประทับ** หลัง insert: `claimUploadReceipt(…, { claimedBy: 'attachments:<id แถว>' })` เขียนเฉพาะใบที่ `claimedBy` ยังว่าง (ประทับแรกชนะ) · best-effort — พังแค่ log `[attachments] ประทับใบรับการอัปโหลดไม่สำเร็จ` ไม่ล้มคำขอ

## `DELETE /api/upload` — ขา Drive

ไม่ล็อกอิน = 401 · ขา `storagePath` (หลักฐาน Won ใน bucket ส่วนตัว) ไม่ได้แก้ · ไม่ส่ง `driveFileId` = `{ ok: true }` · ผู้เรียกทุกจุดยิงแบบไม่รอผล — สถานะมีไว้ให้คนไล่ log

| # | ด่าน | ไม่ผ่าน |
|---|---|---|
| ① | รูปร่าง id | 400 `ลบไฟล์ที่อัปไม่สำเร็จ — รหัสไฟล์ไม่ถูกต้อง` |
| ② | ใบรับของคนเรียกเอง ≤ 24 ชั่วโมง | ตรวจไม่ได้: 503 `ตรวจที่มาของไฟล์ไม่ได้ในขณะนี้ จึงยังไม่ลบไฟล์ — ลองอีกครั้ง` · ไม่มี/ของคนอื่น/หมดอายุ: 403 `ลบได้เฉพาะไฟล์ที่คุณอัปโหลดเองในช่วง 24 ชั่วโมงที่ผ่านมา` |
| ③ | ใบรับถูกประทับแล้ว | 409 `ไฟล์นี้ถูกแนบไว้กับเอกสารแล้ว — ลบผ่านหน้าของเอกสารนั้น` |
| ④ | `driveFileReferenced` — อ้างอยู่ **หรือถามไม่ได้** | 409 `ไฟล์นี้ถูกใช้อยู่ในระบบ (หรือตรวจไม่ได้) จึงไม่ลบ` |
| ⑤ | ชนิดจริงบน Drive (`driveFileTrashable`) | โฟลเดอร์/ไฟล์ของ Google: 409 `ไฟล์ชนิดนี้ลบผ่านเส้นนี้ไม่ได้ (โฟลเดอร์หรือเอกสาร Google)` · ถาม Drive ไม่ได้: 502 `ตรวจไฟล์กับ Google Drive ไม่สำเร็จ จึงยังไม่ลบไฟล์ — ลองอีกครั้ง` · อยู่ในถังขยะแล้ว: `{ ok: true }` |

ผ่านครบจึง `deleteFile` · สวิตช์ `UPLOAD_RECEIPT_MODE` **ไม่มีผลกับเส้นนี้** (ปฏิเสธผิดเสียแค่ไฟล์กำพร้าหนึ่งใบ ปล่อยผิดคือไฟล์ของคนอื่นลงถังขยะ)

## ปล่อยไฟล์อย่างปลอดภัย ([`lib/master/attachments.js`](../webapp/src/lib/master/attachments.js))

- **`driveFileReferenced(supabase, fileId, { excludeId, excludeIds })`** — รายชื่อแหล่งเดียวของสามผู้เรียก (`DELETE /api/upload` · `POST /api/attachments` · `releaseAttachmentFile`): ① แถว `attachments` ทั้งช่อง `driveFileId` และ `metadata.googleFileId` (`driveFileHeld`) ② `quotations.wonAttachments` ③ `entity_updates.attachments` · สองแหล่งหลังเป็น jsonb ถามด้วย `.contains(ช่อง, JSON.stringify([{ driveFileId }])).limit(1)` — 🐞 ส่ง array ของ JS ตรง ๆ ฐานตอบ 22P02 ทุกครั้ง · **ตรวจไม่ได้ = ถือว่ามีคนอ้าง** · รายชื่อต้องเดินตาม `collectReferencedIds` ใน `lib/driveMaintenance.js` (เทสต์ล้มเมื่อฟังก์ชันนั้นเริ่มอ่านตารางใหม่)
- **`driveFileTrashable(driveFileId)`** — ด่านชนิดไฟล์: `application/vnd.google-apps.*` (โฟลเดอร์ · Docs · Sheets) = `native` ไม่ทิ้ง · ถาม Drive ไม่ได้/ไม่พบ/ไม่บอกชนิด = `unverifiable` ไม่ทิ้ง · อยู่ในถังขยะแล้ว = `trashed`
- **`releaseAttachmentFile(att, deps)`** — ถอนสิทธิ์เอกสารร่วมก่อน (ลำดับเดิม) → ไม่มี `driveFileId` จบ → (ก) ยังมีที่อื่นอ้าง หรือตรวจไม่ได้ = **เก็บไฟล์ไว้** → (ข) ด่านชนิดไฟล์ → `deleteFile` · **ไม่ throw ทุกทาง** · ไม่ส่ง client = ใช้ admin client (ไม่ใช่ "ตรวจไม่ได้") · ไฟล์ที่ถูกเก็บไว้ให้รายงานไฟล์กำพร้าตามเก็บ
- **`purgeAttachments`** ปล่อยไฟล์ **ก่อน** ลบแถว ⇒ ส่ง `excludeIds` = id ทุกแถวของชุด ไม่งั้นสองแถวของ entity เดียวกันที่ชี้ไฟล์ใบเดียวเห็นกันเองแล้วไฟล์ค้างตลอดไป · `driveFileHeld` คัด `excludeIds` ออก **หลังอ่าน** (ไม่ต่อเข้าตัวกรอง — ตัวกรองยาวเกิน ~16 KB ตอบ error · อ่านไม่เกิน "จำนวนที่คัดออก + 1" เพดาน 1,000 · เต็มเพดานแล้วเจอแต่แถวที่คัดออก = ถือว่ามีคนถือ)
- **`revokeTwinDocGrants(list, deps)`** — เรียกหลังลบแถวทั้งชุดสำเร็จ: เอกสาร Google ที่ชุดเดียวกันผูกซ้ำมากกว่าหนึ่งแถวถูกส่งไปถอนสิทธิ์อีกรอบ (จับคู่กับกติกาแถวพี่น้องของตัวถอนสิทธิ์ใน PR `claude/google-link-rule` · ก่อน PR นั้นเข้า รอบสองแค่ถอนซ้ำของที่ถอนไปแล้ว) · `deps.supabase` ต้องเป็น client ของ service_role

## สวิตช์ฉุกเฉิน `UPLOAD_RECEIPT_MODE`

ปกติ **ไม่ตั้ง** (= บังคับ) · รูปเดียวที่มีผล: `observe:YYYY-MM-DD` ตรงตัวเป๊ะ (`uploadReceiptMode`)

- วันที่นับตาม **เวลาไทย** — มีผลจนสิ้นวันนั้น แล้วกลับมาบังคับเองแม้ลืมถอด
- **ไกลกว่า 7 วันนับจากวันนี้ (วันตามปฏิทินไทย · `OBSERVE_MAX_AHEAD_DAYS`) = บังคับ** — กันพิมพ์ปีผิด/`9999-12-31` · ⚠️ ค่าที่ไกลเกินจะเริ่มมีผลเองเมื่อวันนั้นเข้ามาอยู่ในระยะ 7 วัน
- `observe` เฉย ๆ · ตัวพิมพ์ใหญ่ · มีช่องว่าง · วันที่ไม่มีจริง · วันที่ผ่านแล้ว = บังคับทั้งหมด

## รอบสอง — เธรดอัปเดตและนัดช่าง

> สถานะของหัวข้อนี้: **รอตรวจ** · ตรวจกับโค้ดเมื่อ 2026-10-09 · แบรนช์ `claude/thread-visit-receipts` · ไม่มี migration · ⚠️ ยังไม่ได้ลองกับ server / Drive จริง — หลักฐานมีแค่เทสต์ในรีโป (ตัวปลอมของฐานและซอร์สของ route) · 🔴 **ห้าม merge ก่อนรอบหนึ่งถูกใช้จริงบน production** (ดู "ขึ้นระบบของรอบสอง" ข้อ 1)

**ช่องที่ปิด** — `POST /api/updates` กับ `PATCH /api/updates/[id]` เก็บ `driveFileId` อะไรก็ได้ที่ client ส่งมา แล้ว `/api/updates/[id]/file` สตรีมไฟล์ตาม id นั้น · `PATCH /api/service/visits/[id]` · `POST /api/service/visits/[id]/photos` · `POST /api/service/visits` เก็บ URL อะไรก็ได้ แล้ว `/api/service/visits/[id]/file` สตรีมไฟล์ตาม id ในสตริงนั้น ⇒ คนที่โพสต์ในเธรดไหนได้สักเธรด หรือแก้นัดของตัวเองได้ เปิดอ่านไฟล์ Drive ของคนอื่นผ่านแถวของตัวเองได้ · ตัวกวาดไฟล์กำพร้าไม่รู้จักไฟล์ของนัดช่าง

### ด่านกลาง ([`lib/upload/driveRefGate.js`](../webapp/src/lib/upload/driveRefGate.js))

- **`strictDriveId(url)`** — คืน id เมื่อลิงก์ชี้ไฟล์ **ใบเดียวแบบไม่กำกวม**: https · host ของ Google ตามรายการของ `attachmentUrlError` (ไม่มี `user:pass@` · ไม่มีพอร์ต) · id มาจาก `/d/<id>` ใน pathname **หรือ** พารามิเตอร์ `id` อย่างใดอย่างหนึ่ง อย่างละไม่เกินหนึ่งตัว · ไม่มี `/d/` ใน query หรือหลัง `#` · ผลต้องตรงกับ `parseDriveId(url)` (ตัวอ่านไฟล์ของนัดใช้ตัวนั้นกับสตริงที่เก็บ — `parseDriveId` ต้องการ id ยาวอย่างน้อย 10 ตัว) · ไม่งั้น `null`
- **`verifyDriveRefs(supabase, { refs, userId, storedIds, ownClaim, refuseClaimed, route, logContext })`** — ไล่ทีละตัวตามลำดับที่ส่งมา **ตัวแรกที่ไม่ผ่านปฏิเสธทั้งคำขอ** (ผู้เรียกไม่เขียนอะไรเลย) · คืน `{ error: { status, error, code?, index } }` หรือ `{ claimable: [id…] }`

- ข้อความ: `REF_SHAPE_TEXT` = `ไฟล์แนบต้องเป็นไฟล์ที่อัปโหลดผ่านระบบ — ลบไฟล์ออกแล้วแนบใหม่อีกครั้ง` · `REF_IN_USE_TEXT` = `ไฟล์นี้ถูกใช้กับรายการอื่นไปแล้ว — ลบไฟล์ออกแล้วแนบใหม่อีกครั้ง`
- **`code: 'file_ref'` (`FILE_REF_ERROR_CODE`) ติดเฉพาะคำตอบ 400** — ตัวอ้างอิงใช้ไม่ได้ ส่งซ้ำกี่ครั้งก็ไม่ผ่าน จอจึงต้องลืม ref แล้วอัปใหม่ · **503 ไม่ติด `code`** — ตัวอ้างอิงเดิมลองใหม่แล้วอาจผ่าน · route ตอบด้วย `Response.json({ error, ...(code ? { code } : {}) }, { status })` · `index` (ลำดับของตัวที่ไม่ผ่าน) ใช้ภายใน route ไม่ออกไปถึง client
- `refs` ที่ไม่ใช่ array หรือมีตัวที่ไม่ใช่ object = 400 (ผู้เรียกส่งผิดต้องไม่กลายเป็น "ไม่มีอะไรให้ตรวจ") · `[]` ผ่านโดยไม่ถามฐาน
- **สวิตช์ `UPLOAD_RECEIPT_MODE` ผ่อนได้ขั้น ⑥ ขั้นเดียว** (ตัดสินใน `requireUploadReceipt` — ด่านกลางไม่อ่าน env เอง) · ①②④ และ ⑦ บังคับทุกโหมด · ตัวที่ผ่านเพราะสวิตช์เท่านั้นถูกเก็บลงแถวได้แต่ **ไม่เข้า `claimable`** (ไม่มีใบรับของคนเรียกให้ประทับ)
- ด่านกลาง **ไม่เรียก `driveFileReferenced`** โดยเจตนา (อยู่บนทางร้อนของทุกโพสต์ — ใบรับที่ถูกประทับกันการใช้ซ้ำให้แล้ว)
- **`claimDriveRefs(supabase, { ids, claimedBy })`** — เรียกหลังเขียนแถวสำเร็จ · best-effort: ลองซ้ำหนึ่งครั้ง ยังพัง log `🔴 [upload-receipt] ประทับใบรับการอัปโหลดไม่สำเร็จ claimedBy=… driveFileId=…` แล้วเดินต่อ ไม่ throw ไม่ล้มคำขอ

### เธรดอัปเดต

- **`POST /api/updates`** — ลำดับ: ดูไม่ได้ 404 → โพสต์ไม่ได้ 403 → `sanitizeUpdateAttachments` (ไม่ได้แก้) → "ต้องพิมพ์ข้อความหรือแนบไฟล์" → **ด่านไฟล์** → งานที่เหลือ → `appendUpdate` · ไฟล์ทุกตัวต้องมีทั้ง `driveFileId` และ `fileUrl` เป็นตัวหนังสือไม่ว่าง (ตัวที่มีแต่ลิงก์ไม่มีใบรับให้ถาม — 400 `REF_SHAPE_TEXT` + `code`) แล้วเข้า `verifyDriveRefs` ด้วย `storedIds` ว่าง · `refuseClaimed: false` · ไม่มี `ownClaim`
- **เธรดไม่ประทับใบรับ** — ไม่มีเส้นไหนทิ้งไฟล์ของเธรด และรอบหนึ่งทำให้ `POST /api/attachments` กับ `DELETE /api/upload` ปฏิเสธไฟล์ที่แถวของเธรดถืออยู่แล้ว (`driveFileReferenced` แหล่ง ③) · ใบรับที่ปลายทางอื่นประทับไปแล้วจึงไม่ถูกตีกลับที่นี่ — จอส่งซ้ำหลังคำตอบหายต้องยังผ่าน
- ด่านอยู่ที่ route ไม่ใช่ใน `appendUpdate` — ผู้เรียก `appendUpdate` ฝั่ง server ที่เหลือไม่ส่งไฟล์ (เทสต์ทะเบียนตรึงไว้)
- **`PATCH /api/updates/[id]` action `edit`** — เมื่อส่งคีย์ `attachments`: รับได้เฉพาะ **ชุดย่อยของไฟล์ที่แถวถืออยู่** จับคู่ด้วย `driveFileId` (ตัวที่แถวเก็บไว้โดยไม่มี id จับคู่ด้วย `fileUrl` ที่ตรงกันทุกตัวอักษร) · ของที่เขียนกลับคือ **ตัวที่แถวเก็บไว้ทั้งก้อน** เรียงตามที่ส่งมา ไม่มีช่องไหนของคำขอถูกเก็บ · ส่งตัวที่แถวไม่มี / ส่งซ้ำ / ไม่ใช่ array = 400 `REF_SHAPE_TEXT` + `code` · `[]` = ถอดไฟล์ทั้งหมด · ไม่ส่งคีย์ = คงไฟล์เดิม · **ไม่ถามใบรับ** (ไม่มีไฟล์ใหม่เข้ามาทางนี้) · ไม่มีจอไหนส่งคีย์นี้วันนี้
- **จอ (ลืม ref)** — `postUpdateWithFiles` ([`lib/master/updatePost.js`](../webapp/src/lib/master/updatePost.js)) โยน error ที่ติดธง `refRejected` เฉพาะเมื่อ server ตอบ **400 พร้อม `code === 'file_ref'`** · `UpdateThread` เห็นธงแล้วล้าง `ref` ของไฟล์ที่ค้างในช่องพิมพ์ (`forgetUploadRefs` — ไฟล์ ภาพตัวอย่าง และข้อความที่พิมพ์ยังอยู่) ⇒ กดส่งครั้งถัดไป **อัปไฟล์ใหม่** แทนการส่ง ref เดิมไปโดนตีกลับซ้ำ · ล้มแบบอื่นทุกแบบ (ต่อไม่ติด · 503 · 400 เรื่องอื่น) **ไม่ลืม ref** — กติกาห้ามอัปซ้ำเดิมยังใช้เต็ม · ไม่มีการส่งซ้ำอัตโนมัติ · ค่า `'file_ref'` ฝั่งจอเป็นตัวหนังสือของตัวเอง (ไม่ import ด่านฝั่ง server) เทสต์เทียบสองฝั่งให้ · `ReportIssueModal` และหน้าลีดไม่ได้จำ ref จึงไม่ได้แก้

### นัดช่าง

รูปที่เก็บ **ไม่เปลี่ยน** (`attachments[] = { url, name, kind }` · `customerSignatureUrl` เป็นตัวหนังสือ) · `normalizeAttachment` ไม่ได้แก้ · ไม่มีการแก้ฝั่งจอ

- **กติกาต่อ URL หนึ่งตัว** (ทั้ง `attachments[].url` และ `customerSignatureUrl`): ตรงกับ URL ที่นัดนี้เก็บอยู่แล้ว **ทุกตัวอักษร** ⇒ ผ่าน ไม่ถามฐาน (แผ่นปิดงานส่งทั้งชุดซ้ำทุกครั้งที่บันทึก) · ตัวใหม่ `strictDriveId(url)` ต้องได้ id (ไม่งั้น 400 `REF_SHAPE_TEXT` — ตรวจรูปร่างทั้งชุดก่อนถามฐานตัวแรก) แล้วเข้า `verifyDriveRefs` ด้วย `storedIds` = id ของทุก URL ที่นัดเก็บอยู่ (`strictDriveId` ถอยไป `parseDriveId`) · `ownClaim: 'service_visits:<id นัด>'` · `refuseClaimed: true`
- **ประทับหลังเขียนสำเร็จ**: `claimDriveRefs(…, { claimedBy: 'service_visits:<id นัด>' })` ⇒ ใบรับหนึ่งใบใช้ได้กับนัดเดียว และเส้นถอยการอัป (`DELETE /api/upload` ด่าน ③) ไม่ทิ้งไฟล์ที่นัดรับไปแล้ว
- **`PATCH /api/service/visits/[id]`** — ถามจาก `patch` (ของที่กำลังจะลงแถวจริง) เฉพาะคีย์ที่ body ส่งมา · อยู่หลังด่านสิทธิ์และด่านของงานทุกตัว เป็นด่านสุดท้ายก่อน `update` · คำขอที่ไม่แตะรูป/ลายเซ็นไม่ถามฐานเลย · ข้อความ 400 บอกช่างว่าไฟล์ไหนและต้องทำอะไร: `รูป "<ชื่อไฟล์>": <เหตุ> — ปิดแล้วเปิดแผ่นปิดงานใหม่ แล้วแนบไฟล์นั้นอีกครั้ง` หรือ `ลายเซ็นลูกค้า: <เหตุ> — …` (เหตุ = ท่อนหน้าของข้อความด่านกลาง) · 503 = `<ไฟล์ไหน>: ตรวจที่มาของไฟล์ไม่ได้ในขณะนี้ — ลองแนบอีกครั้ง` ไม่ติด `code`
- **`POST /api/service/visits/[id]/photos`** — ด่านเดียวกันกับรูปหนึ่งรูป (ข้อความของด่านกลางตรง ๆ) · งานที่แนบรูปไม่ได้แล้วตอบ 409 เดิมก่อนถามทะเบียนใบรับ · ประทับเมื่อแถวเปลี่ยนจริง
- **`POST /api/service/visits`** (สร้างนัด) — เขียน `attachments: []` และ `customerSignatureUrl: null` เสมอ ค่าที่ส่งมาถูกทิ้ง (ไม่มีจอไหนส่ง)
- ไม่มีตัวปล่อยไฟล์ของนัดในรอบนี้ (ถอดรูปออก = ไฟล์ค้างบน Drive)

## ความเสี่ยงที่เหลือ

- **ประทับไม่ atomic กับ insert** — สอง POST พร้อมกันจากคนเดียวกันด้วยใบรับใบเดียว เขียนได้ทั้งสองแถว · ผลคือสองแถวชี้ไฟล์ใบเดียว ไม่ข้ามผู้ใช้ และตัวปล่อยไฟล์เก็บไฟล์ไว้ตราบที่ยังเหลือแถวใดแถวหนึ่ง
- **คำถาม jsonb สองตัวไม่มี index** — ไฟล์หนึ่งใบ = สามคำถาม (attachments 1 + jsonb 2 พร้อมกัน กวาดทั้งตาราง `quotations` และ `entity_updates`) · `purgeAttachments` = 3 × จำนวนแถวที่มีไฟล์ เรียงทีละแถว · ⚠️ ไม่ใช่แค่เส้นลบ — ด่าน ⑤ ของ `POST /api/attachments` ก็ถามชุดเดียวกันทุกครั้งที่แนบ · ตารางโตเมื่อไรต้องเพิ่ม GIN index เป็น migration แยก
- **แถวที่ถูกปลูกไว้ก่อนแก้** — ไม่มีการตรวจย้อนหลังแถว `attachments` เดิม · แถวปลูกที่ชี้ไฟล์ของแถวอื่นจะทำให้ไฟล์นั้นถูกเก็บไว้เมื่อแถวจริงถูกลบ (ไม่หาย แต่ยังเปิดอ่านผ่านแถวปลูกได้) · ไฟล์ที่ถูกอ้างเฉพาะจากแหล่งนอกรายชื่อสามแหล่ง (§ยังไม่ครอบ) ยังถูกทิ้งผ่านแถวปลูกได้ — โฟลเดอร์และเอกสาร Google กันไว้ด้วยด่านชนิดไฟล์แล้ว
- คำตอบจริงของ PostgREST ต่อตัวกรองรูปสตริง มีแค่บันทึกในคอมเมนต์ (`ลองกับฐานจริง 08/10/2569: รูปสตริงตอบ 200`) — เทสต์ในรีโปพิสูจน์แค่ URL ที่ client ประกอบ
