## 1. โจทย์

ออกสัญญาจากในระบบได้ ๓ ชนิด แล้วติดตามได้ว่าใบไหนอยู่ขั้นไหน

| ชนิด | คีย์ | คู่กับงานแบบไหน |
| --- | --- | --- |
| สัญญาจ้างออกแบบกลิ่นและการพัฒนาสินค้า | `scent_design` | ดีลประเภท `SCENT` |
| สัญญาจ้างผลิต | `manufacturing` | ดีลประเภท `NPD` / `RE-ORDER` **สาย `PRODUCT`** |
| สัญญาบริการ | `service` | ดีลประเภท `NPD` / `RE-ORDER` **สาย `SERVICE`** |

มติผู้ใช้ 2026-08-20 — สี่ข้อที่ตัดสินไปแล้ว ห้ามเดาใหม่:

1. **ด่านออกสัญญา = ใบเสนอราคาผ่านการอนุมัติภายใน** (`quotations.approvalStatus = 'approved'`)
   ไม่ต้องรอลูกค้าตอบรับ (ไม่ต้องรอ `status = 'accepted'` หรือดีลขึ้น Won)
2. **คู่ชนิดสัญญากับงาน** ตามตารางด้านบน — สายธุรกิจอ่านจาก **ดีล** ก่อน (mig 0275)
   แล้วค่อยตกไปที่โครงการสำหรับดีลเก่าที่ยังไม่ระบุ
3. **การลงนามทำนอกระบบ** — พิมพ์ออกไปเซ็น แล้วอัปโหลดไฟล์ที่เซ็นแล้วกลับเข้าใบ
   ไม่มีการเซ็นดิจิทัลของลูกค้าในระบบ
4. **ระบบเจนเนื้อสัญญาเอง** จากแม่แบบ + ช่องกรอก แล้วออกเอกสารตรึงฉบับ
   ไม่ใช่ทะเบียนที่แนบไฟล์ Word ที่ทำนอกระบบ

## 2. ของอยู่ตรงไหน (กฎสามชั้น)

สัญญาเป็น **เอกสารของฝ่ายขาย** — ฝ่ายขายเป็นคนเริ่ม ⇒ บ้านอยู่ใน "บริหารงานขาย"
(`/sa/contracts`) ตาม `docs/module-ownership-rule.md` ชั้นที่ 2 เหมือนใบเสนอราคา/ใบสั่งขาย
ไม่สร้างโมดูลใหม่ และไม่เอาไปไว้ใต้ `/database`

## 3. โครงข้อมูล (migration 0278)

ตาราง `sales_contracts` — หนึ่งแถวคือหนึ่งฉบับ

| คอลัมน์ | ความหมาย |
| --- | --- |
| `id` `contractNo` | รหัสภายใน · เลขที่สัญญา `CT-YYMMXXXX` (ออกตอนกด "ออกสัญญา" เท่านั้น) |
| `kind` | `scent_design` · `manufacturing` · `service` |
| `dealId` `quotationId` `customerId` `team` `ownerId` | ดีลต้นทาง · ใบเสนอราคาที่ปลดล็อก · ลูกค้า · ทีม/เจ้าของ (สำเนาจากดีล ใช้เป็นด่านรายแถว) |
| `status` | `draft` → `awaiting_signature` → `signed` · แยกสาย `revised` · `cancelled` |
| `baseNumber` `revisionNo` `revisedFromId` | สายฉบับแก้ไข (mig 0280) — เลขฐานเดียวกันทั้งสาย |
| `fields` (jsonb) | ค่าที่กรอกลงแม่แบบ (คู่สัญญา ราคา จำนวนครั้งแก้ไข ระยะเวลา ฯลฯ) |
| `templateKey` `templateVersion` | แม่แบบและรุ่นที่ใช้ |
| `issuedAt` `issuedBy` `issuedHtml` | เวลาออกเลข + **เนื้อเอกสารที่ตรึงไว้** |
| `signedAt` `signedDate` `signedFileId` `effectiveDate` `expiryDate` | หลักฐานการลงนามและวันที่ที่ติดตามต่อ |
| `cancelledAt` `cancelReason` | การยกเลิก (ต้องมีเหตุผล ≥ 10 ตัวอักษร) |

**ฉบับแก้ไข (Rev.) — กติกาเดียวกับใบเสนอราคา** (มติผู้ใช้ 2026-08-21)
ร่างลบได้ตลอดจนกว่าจะกดออกสัญญา · พอออกเลขแล้วแก้เนื้อไม่ได้ ต้อง **ออกฉบับแก้ไข** ซึ่งเป็น
แถวใหม่ที่ถือเลขฐานเดิม เลขฉบับถัดไป (`CT-YYMMXXXX-1`) ส่วนใบเดิมกลายเป็น `revised`
อ่านอย่างเดียว (ฉบับตรึงยังพิมพ์ซ้ำได้) · ทะเบียนโชว์เฉพาะฉบับล่าสุดของแต่ละสาย

⚠️ **ใบที่ลงนามแล้วออก Rev. ไม่ได้** — ข้อ 3.2 ของตัวสัญญาเขียนไว้เองว่าการแก้ไขเพิ่มเติม
ต้องทำเป็นลายลักษณ์อักษรและลงนามทั้งสองฝ่าย ⇒ ของแบบนั้นคือ "บันทึกเพิ่มเติมสัญญา"
ซึ่งเป็นเอกสารคนละใบ ไม่ใช่การออกฉบับแก้ไขทับของเดิม

**ทำไมสถานะมีแค่ ๔ ค่า** — โจทย์คือ "ง่ายและติดตามได้" คำถามที่ฝ่ายขายถามจริงมีสามข้อ:
ร่างเสร็จหรือยัง · ส่งไปให้เซ็นหรือยัง · เซ็นกลับมาหรือยัง ⇒ หนึ่งคำถามหนึ่งสถานะ
ขั้นย่อยอย่าง "ส่งไปรษณีย์แล้ว" เก็บเป็นวันที่/หมายเหตุบนใบ ไม่ใช่สถานะเพิ่ม

**FK เป็น RESTRICT ทั้ง `dealId` และ `quotationId`** — สัญญาเป็นเอกสารผูกพันตามกฎหมาย
ห้ามหายตามดีล/ใบเสนอราคา ⇒ `forceDelete` บล็อกการลบพร้อมบอกเลขที่สัญญาที่ขวางอยู่
(ถ้าไม่บล็อก การลบจริงจะตายกลางทางด้วย error ดิบจาก Postgres)

**เลขที่สัญญาไม่ได้อยู่ในทะเบียน "มาตรฐานเอกสาร"** โดยเจตนา — ทะเบียนนั้นบังคับให้มี
รหัสแบบฟอร์มควบคุม (FM-xx-nn) ซึ่งสัญญายังไม่มี · รูปแบบอยู่ที่ `CONTRACT_NUMBER_PATTERN`
ใน `lib/sales/contracts.js` และตัวนับใช้ `entity_number_counters` scope `CT`

## 4. ด่านออกสัญญา (logic ล้วน ทดสอบได้)

`lib/sales/contracts.js` — `contractKindsForDeal(deal, project)` และ
`contractEligibility({ kind, deal, project, quotations })` คืนเหตุผลเป็นข้อความไทยเมื่อออกไม่ได้:

- ดีลยังไม่มีใบเสนอราคาที่อนุมัติ (หรือใบที่อนุมัติถูกยกเลิก/ตีกลับไปแล้ว) → ออกไม่ได้
- ดีลยังไม่ระบุสายธุรกิจ → `NPD`/`RE-ORDER` ออกไม่ได้ (ห้ามเดาสายให้เอง)
- ชนิดที่ขอไม่เข้าคู่กับดีล → ปฏิเสธพร้อมบอกชนิดที่ออกได้

ด่านตัวเดียวกันถูกเรียกทั้งจาก `/api/sales-planning/contracts/options` (จอใช้ตัดสินว่าจะ
โชว์อะไร) และจาก `POST /contracts` + `POST /contracts/[id]/issue` (ด่านจริง) ·
ตอนกด "ออกสัญญา" ระบบ **ตรวจสถานะอนุมัติของใบเสนอราคาซ้ำ ณ วินาทีนั้น** เพราะใบอาจถูก
ถอนอนุมัติระหว่างที่ร่างค้างอยู่

— รุ่นก่อนหน้าคือ Ver.20260708 ต่างกันจุดเดียวที่ข้อ 2.9 (เติมคำว่า "ใบรับแจ้ง")

⚠️ **สัญญาตัดหน้าด้วยการ "วัดจริง" ไม่ใช่ประมาณเป็นมิลลิเมตร** — PDR/ใบแจ้งชำระคำนวณ
ต้นทุนแต่ละบล็อกเป็น มม. แล้วตัดแผ่นล่วงหน้า ซึ่งใช้กับสัญญาไม่ได้: ความสูงของย่อหน้าไทย
เดาไม่ได้ และ `.sheet` เป็น `overflow: hidden` ⇒ เดาพลาดเมื่อไร **ข้อสัญญาหายเงียบจากกระดาษ**
⇒ เอกสารเขียนออกมาเป็น "สายเนื้อหา" ที่อ่านครบได้เองก่อน แล้วสคริปต์ที่ฝังในไฟล์ย้ายบล็อก
ลงแผ่น A4 ทีละใบโดยวัด `scrollHeight > clientHeight` จริงจากเบราว์เซอร์ · หัวเอกสารขึ้น
เฉพาะแผ่นแรก · ทุกแผ่นมีท้ายกระดาษ (ชื่อบริษัท · เลขที่สัญญา · หน้า n / m) · บล็อกที่สูง
เกินหนึ่งแผ่นได้แผ่นยืดแทนการถูกครอบตัด · สคริปต์พัง = ยังเห็นเนื้อครบ เสียแค่การแบ่งหน้า

🪤 **กับดักที่เสียเวลาไปหนึ่งรอบ:** `.sheetContent` ของเปลือกเป็น flex column ซึ่ง *บีบ*
บล็อกลูกให้พอดีแผ่นแทนที่จะล้น ⇒ เงื่อนไข "ล้นไหม" ไม่มีวันเป็นจริง แล้วทุกอย่างไปกอง
อยู่แผ่นเดียวโดยตัวหนังสือทับกัน · เอกสารนี้จึงบังคับ `display: block` ให้ `.sheetContent`

**หน้าตากระดาษ (มติผู้ใช้ 2026-08-20):** ระยะขอบ 20/20/15 มม. (กว้างกว่าเอกสารชนิดอื่น
เพราะต้องเซ็นและเย็บเก็บ) · ย่อหน้าความนำ/ปิดท้ายเข้าย่อหน้าแรก 12 มม. ตามต้นฉบับ ·
**หัวเอกสารโชว์ภาษาเดียว** — ชื่อบริษัทและชื่อเอกสารภาษาอังกฤษถูกตัดออก ตัวสัญญาเป็นไทย
ทั้งฉบับ (ทำฉบับภาษาอังกฤษเมื่อไร ให้สลับ *ค่า* ที่ส่งเข้าหัวเอกสาร ไม่ใช่พิมพ์คู่กัน)

**การตรึงฉบับ:** ตอนกด "ออกสัญญา" ระบบออกเลขก่อน (RPC) แล้วเรนเดอร์ HTML เก็บลง
`issuedHtml` ทันที — หลังจากนั้นการเปิดเอกสารจะเสิร์ฟฉบับที่ตรึงเสมอ ไม่ใช่ข้อมูลสด
เรนเดอร์ล้มกลางทาง = ใบมีเลขแต่ยังไม่มีเนื้อ ซึ่งเส้นทางเปิดเอกสารจะเรนเดอร์ซ้ำให้เอง
(idempotent) ไม่ใช่ใบเสีย

## 5.1 จุดที่ตั้งใจต่างจากต้นฉบับ — อย่า "แก้ให้ตรง"

ตรวจเทียบตัวอักษรทั้งฉบับกับต้นฉบับล่าสุด (`สัญญาจ้างออกแบบกลิ่นและการพัฒนาสินค้า.pdf`
ฉบับ 13 ส.ค. 2569) เมื่อ 2026-08-21 — ข้อสัญญา 23/23 ข้อและทุกส่วนนอกข้อตรงกันหมด
เหลือสามจุดที่ต่าง และ **มติผู้ใช้คือคงแบบปัจจุบัน**:

| จุด | ต้นฉบับ | ระบบ |
| --- | --- | --- |
| ข้อ 1.1 | "ไม่มีการตอบกลับภายใน **ภายใน** 7 วัน" (พิมพ์ซ้ำ) | พิมพ์ "ภายใน" ครั้งเดียว |
| ช่องเซ็น | `ลงชื่อ……ผู้ว่าจ้าง` แล้วขึ้นบรรทัดใหม่เป็นวงเล็บชื่อ | คำว่าผู้ว่าจ้าง/ผู้รับจ้างอยู่บรรทัดของตัวเองใต้วงเล็บชื่อ |
| ที่อยู่ผู้รับจ้าง | หน้าแรกไม่มี "ถนนเพชรเกษม" · ย่อหน้าปิดท้ายมี | ใช้ค่าจากทะเบียนบริษัทค่าเดียวทั้งใบ |

⚠️ ใครมาตรวจรอบหน้าแล้วเห็นสามจุดนี้ **ห้ามแก้ให้ตรงต้นฉบับ** โดยไม่ถามเจ้าของเรื่องก่อน —
ทั้งสามผ่านการตัดสินไปแล้ว (สองข้อแรกเป็นการเก็บกวาดที่ตั้งใจ ข้อสามคือต้นฉบับไม่ตรงกันเอง)

**ส่วนที่ระบบเพิ่มจากต้นฉบับโดยตั้งใจ:** หัวเอกสาร (โลโก้ · ข้อมูลบริษัท · เลขที่/วันที่สัญญา ·
อ้างอิงใบเสนอราคา) และท้ายกระดาษพร้อมเลขหน้าทุกแผ่น

## 5.2 บันทึกเพิ่มเติมสัญญา (mig 0282)

มติผู้ใช้ 2026-08-21 — ต้นฉบับ `บันทึกเพิ่มเติมสัญญาจ้างออกแบบกลิ่นน้ำห.pdf`

- **ออกจากสัญญาหลักที่ลงนามแล้วเท่านั้น** · สัญญาที่ยังไม่เซ็นให้ใช้ Rev. แทน
- **ต้องอ้างคำร้องพัฒนากลิ่นที่ปิดเรื่องแล้ว** (`kind=scent_dev` · `status=closed`) เพราะ
  ตารางสูตรในบันทึก (ชื่อสูตร · รหัสสูตร · วันที่สูตร) ดึงจากแถวคำร้องที่ผลิตสูตรออกมาแล้ว
  (`producedFormulaId` → ทะเบียนสูตร) แล้ว **ตรึงลงใบตั้งแต่ตอนสร้าง**
- เลขที่ = เลขสัญญาแม่ + `-A{ครั้งที่}` (เช่น `CT-26080001-0-A1`) — ไม่มีตัวนับของตัวเอง
  ครั้งที่ถูกจองด้วย `UNIQUE (contractId, addendumNo)` ⇒ กดพร้อมกันก็ไม่ได้เลขซ้ำ
- ตารางแยก `sales_contract_addenda` ไม่ใช่ `kind` ใหม่ของสัญญา — `kind` ของสัญญาหมายถึง
  *ชนิดสัญญา* ยัดรวมกันเมื่อไร ทุกด่านที่ถาม "สัญญาชนิดไหน" ต้องมาแยกกรณีเพิ่ม
- ⚠️ **ต่างจากต้นฉบับหนึ่งจุดโดยตั้งใจ** (มติผู้ใช้ 2026-08-21): ต้นฉบับแยกวันที่เป็นบรรทัด
  ใต้หัวเรื่อง แล้วประโยคแรกขึ้นต้นว่า "บันทึกฉบับนี้ทำขึ้นที่ …" ⇒ ระบบย้ายวันที่เข้ามาใน
  ประโยคเป็น **"บันทึกฉบับนี้ทำขึ้นเมื่อ … ที่ …"** ให้อ่านจบในประโยคเดียว
- ⚠️ **จุดที่สองที่ตั้งใจต่าง** (มติผู้ใช้ 2026-08-21): ความนำของต้นฉบับใส่เลขทะเบียนนิติบุคคล
  ให้ฝั่งผู้ว่าจ้างฝ่ายเดียว ⇒ ระบบเติมของฝั่งผู้รับจ้างด้วย ให้ครบทั้งสองฝ่ายเท่าสัญญาหลัก
  (แม่แบบ `version: 20260821b`)
