ตอนที่รื้อ ฐานจริงมีใบสเปค 2 ใบ (ร่างเปล่า) มีเอกสาร 0 ใบ และยังไม่มีตัวนับ ⇒ รื้อได้โดยไม่ต้องย้ายข้อมูลเอกสาร

## ตาราง (mig 0370)

### `product_specs` — สเปคของสินค้า (คงไว้ ปรับรูป)
- 1 แถวต่อสินค้า (`productId` UNIQUE) ตามเดิม
- **เพิ่มคอลัมน์เนื้อหา** ย้ายมาจาก `product_spec_revisions`: `texture` `standardPackaging` `targetGroup`
  `keySellingPoint` `pricingTier` `productBenefit` `longevity` `dosagePerUse` (ความยาวเท่า CHECK เดิม) +
  `certifications jsonb '[]'` + `updatedBy` `updatedByName`
- **ถอด `currentRevNo`**
- checklist ย้ายไป `product_spec_items` (คีย์ `specId`) ซึ่งเป็นตารางใหม่
- `products.texture` / `products.standardPackaging` ยังเป็นกระจก · **ซิงก์ตอนบันทึกสเปค** (ไม่มีขั้นอนุมัติให้รอแล้ว) · ลบสเปคแล้วล้างสองช่องนี้เป็นค่าว่าง
- รูปประกอบยังเป็น `attachments` (`entityType='product'`, `docType='spec_illustration'`) ตามเดิม

### `product_spec_documents` — เอกสาร 1 ใบต่อบรรทัด SO
`id` (`PSD…`) · `docNo` UNIQUE แก้ไม่ได้ · `specId` → product_specs **RESTRICT** · `productId` → products **RESTRICT** ·
`salesOrderId` / `salesOrderLineId` → **SET NULL** (ย้ายได้ตอน SO ออก Rev) · `status` `active|void` ·
`currentRevNo` (Rev ล่าสุดที่อนุมัติขั้นสุดท้ายแล้ว · `NULL` = ยังไม่เคยอนุมัติ) · `voidedAt/By/ByName/voidReason` ·
`customerSignedAt/Name/customerSignFiles` (เก็บไว้ใช้ทีหลัง ยังไม่มีจอ) · `createdBy/ByName/At` · `updatedAt`
- partial unique: บรรทัด SO หนึ่งบรรทัดมีเอกสารที่ยังไม่ void ได้ใบเดียว
- trigger: `docNo` · `specId` · `productId` · `createdAt` แก้ไม่ได้ · ลบแถวไม่ได้ (เลขที่ออกนอกบริษัทแล้ว) — **mig 0375 ผ่อนช่องเดียว**: ร่างที่ยังไม่เคยยื่น ลบได้ผ่าน RPC `delete_product_spec_document_draft` ซึ่งเปิด "ประตู" ด้วย session flag `app.spec_doc_draft_delete` ที่เก็บ **id ของใบนั้นใบเดียว** (ไม่ใช่ `'1'`) · ยามยังตรวจทุกข้อเอง ไม่เชื่อ flag

### `product_spec_document_revisions` — Rev ของเอกสาร
`id` (`PSDR…`) · `documentId` → documents **RESTRICT** · `revNo` ≥ 0 · UNIQUE(`documentId`,`revNo`) ·
`status` `draft | pending_ae | pending_ae_supervisor | approved | rejected | superseded` ·
`reason` (บังคับเมื่อ `revNo > 0` — เหตุผลที่แก้) · `snapshot jsonb` (NULL ตอนเป็นร่าง · ถ่ายตอนยื่น) ·
`illustrationIds text[]` (ตัวชี้รูปในภาพนิ่ง ไว้กันไฟล์หาย) ·
`firstSubmittedAt` (**mig 0375** — รอยการยื่นที่ลบไม่ได้ · trigger ประทับตอนเข้า `pending_ae` · เคลียร์/แก้ไม่ได้ ⇒ แยกร่างที่ "เคยยื่นแล้วดึงกลับ" ออกจากร่างที่ไม่เคยยื่น) · `submittedAt/By/ByName` (AC) · `aeApprovedAt/By/ByName` · `supApprovedAt/By/ByName` ·
`rejectedAt/By/ByName` · `rejectionReason` · `rejectedStage` (`ae|ae_supervisor`) · `supersededAt` ·
`frozenHtml` · `frozenAt` · `rendererVersion` · `createdBy/ByName/At` · `updatedAt`
- partial unique: เอกสารหนึ่งใบมี Rev ที่ยังไม่จบ (`draft|pending_ae|pending_ae_supervisor|rejected`) ได้ทีละหนึ่ง
- trigger: Rev ที่ `approved/superseded` ห้ามแก้ `snapshot` `illustrationIds` `frozenHtml`(เมื่อมีค่าแล้ว) และตราประทับอนุมัติ · สถานะเปลี่ยนได้ทางเดียวคือ `approved → superseded` · ลบแถวไม่ได้ **ยกเว้นทางเดียว**: ลบพร้อมเอกสารแม่ผ่าน RPC ของ 0375 (ดูข้างล่าง) · constraint trigger แบบ DEFERRED กันไม่ให้ Rev หายเดี่ยว ๆ (เอกสารแม่ยังอยู่ตอน COMMIT = ล้มทั้งก้อน)

### RPC `create_product_spec_document`
ออกเลข (ตัวนับ `entity_number_counters` scope `FMSA04` · month = YYMM ค.ศ. · seed ด้วย LIKE ที่ปิดตาช่องวัน — ตรรกะเดียวกับ 0364 ข้อ ⑦ / 0271)
แล้ว INSERT เอกสาร และ INSERT Rev.00 `draft` **ในคำสั่งเดียว** · SECURITY DEFINER · ให้สิทธิ์เฉพาะ service_role

### RPC `delete_product_spec_document_draft` (mig 0375)
> 🔴 **ลำดับขึ้นระบบสำคัญ: รัน 0375 บน Supabase SQL Editor ให้เสร็จ *ก่อน* deploy โค้ดชุดนี้**
> โค้ดฝั่งอ่านใส่ `firstSubmittedAt` ไว้ในชุดคอลัมน์ของ Rev แล้ว (`REVISION_COLUMNS` + `REVISION_SUMMARY_COLUMNS`)
> และ PostgREST ล้มทั้งคำสั่งเมื่อเจอคอลัมน์ที่ไม่มีจริง (42703) ⇒ deploy ก่อนรัน = **พังพร้อมกันสามจอ**:
> หน้าเอกสาร `/sales-planning/spec-documents/[id]` · การ์ดเอกสารบนหน้าใบสั่งขาย · รายการเอกสารบนหน้าสเปคสินค้า
> ⚠️ `npm run check:columns` **จับเคสนี้ไม่ได้** — ตัวจับของมันอ่านเฉพาะ `.select('ชื่อคอลัมน์ตรง ๆ')` และข้าม
> `.select(CONSTANT)` ทุกจุด ⇒ CI เขียวไม่ใช่หลักฐานว่าคอลัมน์มีจริง · หลังรันแล้วเช็คด้วยตาว่า
> `select "firstSubmittedAt" from product_spec_document_revisions limit 1` ตอบ แล้วค่อยเปิดสามจอนั้นดู
> *อัปเดต:* ข้อความข้างบนเป็นจริงถึง 2026-09-23 — ตั้งแต่ #1795 ด่านแกะ `.select(CONSTANT)` ได้แล้ว
> และตั้งแต่ 2026-09-24 ตรวจคอลัมน์ใน embed `alias:table(...)` ด้วย ⇒ คอลัมน์ที่ยังไม่มีบนฐานทำให้ CI แดง
ลบ **เอกสาร + Rev.00** ของร่างที่ยังไม่เคยยื่น ในทรานแซกชันเดียว · `SECURITY DEFINER` · ให้สิทธิ์เฉพาะ service_role ·
รับ `p_document_id text` (คีย์ของชุดนี้เป็น text ทั้งระบบ — `PSD-…`/`PSDR-…` ออกจากฝั่งแอป · uuid จะเรียกไม่ได้เลย)
- **ลำดับล็อก: Rev ก่อน → เอกสารทีหลัง** เหมือนทางยื่น (ทางยื่น UPDATE แถว Rev แล้ว trigger ล็อกเอกสาร `FOR SHARE`)
  ⇒ ไม่มีวงจร deadlock และคนที่กด "ยื่น" แทรกกลางจะถูกเห็นเสมอ ⇒ RPC **ปฏิเสธ** แทนที่จะลบทับ
- ตรวจซ้ำที่ฐานทุกข้อ: ใบ `active` · `currentRevNo IS NULL` · มี Rev แถวเดียว · แถวนั้นเป็น Rev.00 `draft` ·
  ไม่มีรอยการยื่นสักช่อง (`firstSubmittedAt` `submittedAt` `aeApprovedAt` `supApprovedAt` `rejectedAt` `frozenHtml`)
  - ⚠️ ฝั่งจอ (`draftDeleteBlock`) ตรวจชุดเดียวกัน **ยกเว้นช่องสุดท้ายใช้ `frozenAt` แทน `frozenHtml`** — `frozenHtml`
    คือกระดาษทั้งแผ่น `REVISION_COLUMNS` จึงไม่ดึงมา ⇒ `frozenAt` คือตัวแทนที่อ่านได้ · เพี้ยนกันแล้วอย่างมากคือ
    ปุ่มโผล่แล้ว RPC ปฏิเสธพร้อมเหตุจริง (409) ไม่มีทางลบของที่ไม่ควรลบ · **คำตัดสินสุดท้ายอยู่ที่ RPC เสมอ**
- ปฏิเสธด้วยคำนำหน้าเดียว `product_spec_document_draft_delete_forbidden: <docNo> — <เหตุไทย>` (API ตัดเหตุไทยมาขึ้นจอ ⇒ 409)
  · ไม่พบใบ = `product_spec_document_not_found` ⇒ 404
- **ห้ามแตะ `entity_number_counters`** · คืน `{ docNo, document, revision }` (แถวเต็มที่ลบไป) — **ไม่ใช่ตัว `before` ของ audit**
  แต่เป็น**หลักฐานว่าแถวหายไปจริงทั้งคู่**: store ปฏิเสธที่จะตอบว่าสำเร็จถ้าไม่ได้ก้อนนี้ (แล้ว `docNo` ตัวจริงกลับไปในคำตอบ JSON ของ `DELETE` — **toast ไม่ใส่เลข** เพราะโมดัลที่เพิ่งกดผ่านบอกเลขที่ที่จะถูกเผาไปแล้ว · แก้ 23/09 ให้ตรงโค้ด) ·
  `audit_logs.before` เขียนจากแถวที่เราต์อ่านมา **ก่อน** เรียก RPC เสมอ (ลบก่อนเขียนทีหลัง = จังหวะที่แถวหายโดยไม่มีสำเนา
  และ `recordAudit` กลืน error เอง เราต์จึงไม่มีทางรู้ว่าต้องหยุด)
- 🔴 **ประตูจริงคือ session flag ไม่ใช่ตัว RPC** — ทางของแอปมีประตูเดียวจริง (PostgREST ตั้ง GUC ชื่อนี้เองไม่ได้ ⇒ ถือ service key
  แล้วยิง `DELETE` ตรงก็ยังชนยาม) แต่คนที่ต่อ SQL ตรง (SQL Editor) ตั้ง flag เองแล้วลบเองได้ · ยามยังคุม **ว่าอะไรหายได้**
  ครบทุกข้อตามมติ แต่ไม่คุม **ว่าใครเขียน audit** ⇒ ลบทางนั้น = ไม่มีแถว `audit_logs` เลย และกู้ไม่ได้ · รับไว้แบบเดียวกับ

## เส้นสถานะของ Rev

```
            ยื่น (AC)            AE เจ้าของดีลอนุมัติ           AE Sup อนุมัติ
  draft ─────────────▶ pending_ae ────────────────▶ pending_ae_supervisor ──────────▶ approved
    ▲                     │  │                          │  │                            │
    │   ดึงกลับ (ผู้ยื่น/admin)  │  └─ ตีกลับ ─┐          ดึงกลับ ─┘  └─ ตีกลับ ─┐   แก้ไขเอกสาร (AC/ผู้อนุมัติ)
    └─────────────────────┘             ▼                               ▼          ▼
                                     rejected ◀────────────────────────┘     Rev+1 draft
                                        │ AC แก้แล้วยื่นใหม่ (Rev เดิม)            (Rev ก่อนเป็น superseded
                                        └──────▶ pending_ae                  ตอน Rev ใหม่ได้ approved)
```

| `submit` | AC / admin | draft, rejected | SO ต้องอนุมัติ · ถ่ายภาพนิ่ง (สเปค + checklist + สินค้า + บรรทัด SO + รูป) ⇒ pending_ae · ล้างรอยตีกลับ |
| `withdraw` | ผู้ยื่น / admin | pending_ae, pending_ae_supervisor | ⇒ draft · ล้างตราประทับ submit/AE |
| `ae_approve` | AE เจ้าของดีลของ SO (`sales_deals.ownerId`) / admin | pending_ae | ⇒ pending_ae_supervisor |
| `sup_approve` | ผู้จัดการฝ่ายขาย `SALES_MANAGER_ROLES` (CD · CM · AE Sup — ผังตำแหน่ง 24/09) / admin | pending_ae_supervisor | ⇒ approved · Rev ที่ approved ก่อนหน้าเป็น superseded · `currentRevNo` = revNo · เรนเดอร์ `frozenHtml` |
| `reject` | ผู้มีสิทธิ์อนุมัติของขั้นนั้น | pending_ae, pending_ae_supervisor | เหตุผล 10–500 ตัวอักษร ⇒ rejected + `rejectedStage` |
| `revise` | AC / admin · **+ ผู้อนุมัติของใบนี้** (AE เจ้าของดีล · CD/CM/AE Sup — มติ 24/09 · `canReviseProductSpecDocument`) | Rev ล่าสุด approved | SO ต้องอนุมัติ · เหตุผลบังคับ ⇒ Rev+1 draft (Rev ที่อนุมัติแล้วยังเป็นฉบับที่ใช้ จนกว่า Rev ใหม่จะอนุมัติ) · **ยื่น Rev ใหม่ยังเป็นของสาย AC** · แจ้ง `product_spec_doc_revise` ⇒ ผู้ยื่นฉบับที่อนุมัติ + ผู้ออกเอกสาร · Rev ที่เปิดแล้วลบ/ปิดไม่ได้ (ทางออก = ยื่นจนอนุมัติ หรือยกเลิกทั้งใบ) |
| `void` | AC / admin ทุกใบ · **+ ผู้อนุมัติ เฉพาะใบที่เคยอนุมัติแล้ว** (มติ 24/09 · `canVoidProductSpecDocument`) | เอกสาร active **ที่เคยยื่นแล้ว** (ไม่ใช่ร่างที่ลบได้ — มติ 23/09/2569 "ซ่อนปุ่มยกเลิกช่วงร่าง") | เหตุผลบังคับ ⇒ document `void` · ทุกการกระทำอื่นปิด · แจ้ง `product_spec_doc_void` ⇒ ผู้ยื่น (Rev ล่าสุด + ฉบับที่อนุมัติ) + ผู้ออกเอกสาร + AE เจ้าของดีล · ยิง `void` ใส่ร่างที่ยังไม่เคยยื่น = 409 `FRESH_DRAFT_VOID_BLOCK` (บอกให้ใช้ลบร่าง ไม่ใช่ "สถานะเปลี่ยนแล้ว") · ผู้อนุมัติยิงใส่ใบที่ไม่เคยอนุมัติ = 403 (บอกให้ใช้ตีกลับ) |
| `delete` (ลบร่าง · **DELETE** ไม่ใช่ PATCH) | AC / admin | เอกสาร active + **Rev.00 `draft` ฉบับเดียวที่ไม่เคยยื่น** (`currentRevNo` ว่าง · ไม่มีรอยการยื่นสักช่อง) | ไม่ต้องมีเหตุผล ⇒ แถวเอกสารและ Rev **หายจากระบบ** (ไม่มีถังขยะ — กู้ได้จาก `audit_logs.before` เท่านั้น) · **เลขที่ไม่นำกลับมาใช้** · บรรทัด SO ว่างและออกใบใหม่ได้ทันที **เลขใหม่** · ไม่แจ้งเตือนใคร (ยังไม่เคยเข้าคิวผู้อนุมัติ) · ช่วงนี้ **ไม่มี** `void` ให้เลือก (มติ 23/09) — เป็นปุ่มปลายทางตัวเดียวของใบ |

- 🪤 **"ดึงกลับ" ล้างตราประทับการยื่นจนหมด** (`revisionPatch('withdraw')` เขียน `submittedAt/By/ByName = NULL` + `snapshot = NULL`)
  ⇒ ร่างที่เคยยื่นแล้วดึงกลับ **หน้าตาเหมือนร่างที่ไม่เคยยื่นทุกช่อง** · รอยที่แยกสองอย่างนี้คือ `firstSubmittedAt` (mig 0375)
  ⇒ ตัวตัดสินของ `delete` อ่านช่องนั้น ⇒ **ทุกทางที่ `select` แถว Rev ต้องดึงคอลัมน์นี้มาด้วย** (ตกหล่น = `undefined` = "ไม่เคยยื่น" = ปุ่มลบโผล่ผิดใบ)
- `delete` **ไม่เช็คสถานะ SO** — ลบร่างของตัวเองคือถอย ไม่ใช่เดินหน้า (กติกาเดียวกับ `withdraw`/`void`) · SO ที่ถูกย้อนการอนุมัติยิ่งต้องเก็บกวาดร่างที่ค้างได้
- ทุกการอนุมัติ/ยื่นต้องเช็คว่า SO ยัง `approved` อยู่ (ถ้าถูกย้อนการอนุมัติ ⇒ ติดด่าน บอกเหตุ)
  - ฐานตรวจซ้ำด้วย trigger ของ Rev: เมื่อ Rev จะเปลี่ยนไปเป็น `pending_ae` `pending_ae_supervisor` หรือ `approved` trigger ล็อกแถวเอกสารและแถว SO แบบ FOR SHARE แล้วตรวจว่าเอกสารยัง active และ SO ยัง approved ถ้าเอกสารถูก void หรือ SO ถูกย้อนการอนุมัติระหว่างคำขอ ฐานจะปฏิเสธ และ API ตอบ 409
- "admin" = `role === 'admin'` เท่านั้น — **ไม่ใช้ `isSuperuser`** เพราะ `ae_supervisor` นับเป็น superuser แล้วจะกดขั้น AE ข้ามเจ้าของดีลได้
- UPDATE ที่เปลี่ยนสถานะต้องมี `.eq('status', เดิม)` และ **เช็คว่าโดนแถวจริง** (`select().maybeSingle()` แล้วไม่ใช่ null) ไม่งั้นตอบ 409 "สถานะเปลี่ยนแล้ว กรุณาโหลดใหม่"

## จังหวะจาก SO (hook ใน `sales-orders/[id]/route.js`)
- **cancel** (ทั้งทางยกเลิกเฉย ๆ และทาง `cancel_sales_order_with_reversal_atomic`) ⇒ void เอกสารทุกใบของ SO นั้น เหตุผล `ใบสั่งขาย <เลข> ถูกยกเลิก`
- **revise** ⇒ บรรทัดใหม่ id = `'SOL-' || md5(<newSoId> || ':' || <oldLineId>)` (ดู RPC 0346/0363) ⇒ ย้าย `salesOrderId/LineId` ไปใบใหม่
  - Rev ล่าสุด approved ⇒ สร้าง Rev+1 draft เหตุผล `ออก Rev. ใบสั่งขาย <เก่า> → <ใหม่>`
  - Rev ล่าสุด pending_* ⇒ ถอยเป็น draft (Rev เดิม)
  - draft / rejected ⇒ คงไว้
- hook ทำงาน **หลัง** RPC ของ SO สำเร็จ · ถ้า hook ล้ม SO ยังสำเร็จ แต่ต้องตอบ `warning` และเขียน audit (ไม่เงียบ)
- เอกสารที่บรรทัด SO หายไป (`salesOrderLineId` เป็น NULL เพราะถูกถอดบรรทัด) โผล่ในการ์ดหน้า SO เป็นแถว "บรรทัดถูกถอด" พร้อมปุ่มปลายทางของใบ — ยกเลิกเอกสาร หรือ **ลบร่างเอกสารถาวร** ถ้ายังไม่เคยยื่น (มติ 23/09/2569 · API ส่ง `voidAction` + `removeAction` จาก `documentActions` ก้อนเดียว ⇒ ได้ตัวเดียวพอดี · ลบใช้เส้น `DELETE` และโมดัล `docConfirmPrompt('remove', { orphan: true })` ชุดเดียวกับหน้าเอกสาร) · เหตุบนปุ่มเดินหน้า/แถบเตือนบนหน้าเอกสารชี้ปุ่มที่ใบนั้นมีจริง (`lineRemovedBlock` / `lineRemovedNotice`)
  - ลบจากการ์ดแล้วไม่ได้คำตอบว่าสำเร็จ ⇒ ดึงการ์ดใหม่แล้วตัดสินด้วย `orphanRemoveFailureOutcome`: ใบหายจากการ์ด + ไม่มีคำตอบให้เชื่อ
    (เน็ตหลุด/5xx) = **ลบสำเร็จ** (toast สำเร็จ ไม่ใช่ "เชื่อมต่อไม่ได้ ลองอีกครั้ง" — UAT 23/09) · เซิร์ฟเวอร์ตอบเหตุ (404/409) หรือใบไม่มีปุ่มลบแล้ว
    = ปิดโมดัล เหตุขึ้นแถบการ์ด · ยังลบได้/โหลดการ์ดไม่ขึ้น = คงโมดัลให้กดใหม่
  - คำเตือนตอน SO ออก Rev ที่ย้ายเอกสารไปแบบไม่มีบรรทัด ชี้ **ที่ที่ปุ่มอยู่** ("จัดการต่อ (ลบร่าง/ยกเลิก) ได้ที่การ์ดเอกสารต่อเนื่องบนหน้าใบสั่งขาย")
    ไม่ใช่ชื่อปุ่มตายตัว — คำเตือนออกก่อนอ่าน Rev ล่าสุด และใบกำพร้าอาจเป็นร่างที่ไม่เคยยื่น (ปุ่ม = ลบ)
  - ตอน SO ออก Rev เอกสารที่หาบรรทัดคู่ในใบใหม่ไม่เจอ ย้ายไปผูก SO ใบใหม่โดยไม่มีบรรทัด แล้วใช้กติกา Rev ดังนี้ (ตัดสิน 22/09/2569 ตอนแก้ผลรีวิว)
    - Rev ล่าสุด pending_* ⇒ ถอยเป็น draft เหมือนเอกสารใบอื่น เพื่อไม่ให้ค้างอยู่ในคิวผู้อนุมัติ
    - Rev ล่าสุด approved ⇒ **ไม่เปิด Rev+1** เพราะเอกสารที่ไม่มีบรรทัดเดินด่านต่อไม่ได้ ทางออกเดียวคือยกเลิก และ Rev ลบไม่ได้ ถ้าเปิด Rev+1 จะมี Rev ที่ยื่นไม่ได้ค้างในประวัติตลอดไป
    - draft / rejected ⇒ คงไว้
- **ผู้ดูแลระบบบังคับลบ SO** ⇒ void เอกสารที่ยัง active ของ SO นั้นก่อนที่ FK จะปลดลิงก์ เหตุผล `ใบสั่งขาย <เลข> ถูกลบถาวร` และพรีวิวก่อนลบต้องบอกจำนวนเอกสารที่จะถูก void
- โมดัลยืนยันการยกเลิก SO และการออก Rev ของ SO ต้องบอกผลที่เกิดกับเอกสาร FM-SA-04 ของใบนั้น (กฎ approval-confirm-modals)

## ภาพนิ่ง (snapshot) และการตรึงกระดาษ
- ถ่ายตอน `submit` ทุกครั้ง (ยื่นใหม่หลังตีกลับก็ถ่ายใหม่) · ร่างที่ยังไม่ยื่นแสดงสด จากสเปค + SO ปัจจุบัน
- `snapshot = { schemaVersion: 2, spec: {ช่องเนื้อหาทุกช่อง, certifications}, items: [...], product: {ทุกช่องที่กระดาษพิมพ์}, order: {orderNumber, quotationNumber, confirmDocType, confirmDocNo, confirmDocDate, qty, unit, qtySource, deliveryDueDate, customerName, docLanguage, dealOwnerId, dealOwnerName, dealOwnerEmail, dealOwnerPhone}, customer: {name, nameEn, taxId, branchCode, billingAddress, billingAddressEn, shippingAddress, shippingAddressEn, contactName, contactPhone}, illustrations: [{attachmentId, caption, sortOrder, fileName}] }`
  - `order.qty/unit` = "จำนวนผลิต" (มติผู้ใช้ 22/09 "ปริมาตรบรรจุ และ จำนวนผลิต ดึงมาจาก ข้อมูล FG และ QT SO") — บรรทัด SO ก่อน · บรรทัดไม่มีจำนวน/ถูกถอด ⇒ บรรทัดใบเสนอราคาที่ SO ผูก (ตัวที่ `sales_order_lines.quotationLineId` ชี้ก่อน **ถ้าเป็นสินค้าเดียวกัน** — ลิงก์ที่ชี้บรรทัดของสินค้าอื่นไม่นับ · บรรทัดพิมพ์เองที่ไม่มี productId ยังเชื่อลิงก์ · ถอยบรรทัดแรกของสินค้าเดียวกัน) · `qtySource` = `sales_order_line` | `quotation_line` | null · อ่านใบเสนอราคาล้ม = ยื่นไม่ผ่าน (ไม่พิมพ์ N/A แทนตัวเลขจริง) · คีย์เพิ่มแบบไม่บังคับ ⇒ schemaVersion ยัง 2
  - ปริมาตรบรรจุ = `product.volume` + `volumeUnit` ของสินค้า FG ในทะเบียน (ภาพนิ่งถ่ายไว้อยู่แล้ว) · ใบอังกฤษแปลหน่วยผ่าน `volumeUnitLabel` (ขวด → Bottle · package → Package · ml/g/kg คงเดิม) · ภาพนิ่งที่ไม่มีสองช่องนี้ถอยไป `volumeText`
  - v2 (22/09) เพิ่ม `order.docLanguage` (ภาษาของ SO · ไม่มี SO = null = ไทย) · `order.confirmDocType` · ก้อน `customer` (ทั้งสองภาษาดิบ — ตัวพิมพ์เลือกภาษาเอง) · ที่มาชุดเดียวกับ `salesOrderPrint`: ชื่อไทย = SO · คู่อังกฤษ = SO ก่อน ถอยใบเสนอราคา · เลขผู้เสียภาษี/สาขา/ที่อยู่ไทย/ผู้ติดต่อ = ใบเสนอราคาที่ SO ผูก (`sales_orders.quotationId`) · อ่านใบเสนอราคาไม่ได้ = ยื่นไม่ผ่าน (ไม่พิมพ์กล่องว่าง)
  - ภาพนิ่ง v1 ไม่มีคีย์ใหม่ ⇒ ตัวพิมพ์ถอยเป็นใบไทย ช่องที่ไม่มีเป็นขีด (ภาพนิ่งห้ามเขียนทับ ต้องอ่านของเก่าได้เสมอ)

## audit
ทุกการกระทำลง `audit_logs` `entityType = 'product_spec_document'` · `before/after` เป็น **แถวเต็มทั้งเอกสารและ Rev**
(ทางตามรอยทางเดียวว่าใครเซ็นอะไรเมื่อไร) · คำเตือนที่เกิดหลังการอนุมัติตามไปใน `after.warnings` + `summary` ด้วย

🔴 **`delete` (ลบร่าง) เขียน audit ก่อนลบเสมอ** — ระบบไม่มีถังขยะ `audit_logs.before` คือทางกู้ทางเดียว
([[deleted-data-recovery]]) · ลบก่อนแล้วค่อยเขียน = มีจังหวะที่แถวหายโดยยังไม่มีสำเนา และ `recordAudit`
กลืน error ของตัวเอง ⇒ เราต์ไม่มีทางรู้ว่าต้องหยุด · ลบไม่ผ่านหลังจากนั้น เราต์เขียนแถว audit แก้กลับ
(`after.deleteFailed`) ไม่ปล่อยให้บันทึกโกหกว่าลบไปแล้ว
