"(ซ่อนไว้ N ภาพ)" เหมือนเดิม · ของกลางที่แตะ: `AttachmentsPanel.handleDelete` เมื่อเส้นลบตอบ `retired` จะโหลดรายการใหม่แทนการตัดแถวทิ้ง (แถวยังอยู่ในฐาน — เดิมภาพที่เพิ่งถูกซ่อนหายจากรายการที่แจ้งผู้เรียก เลขซ่อนไว้ขาดไปหนึ่งจนกว่าจะโหลดหน้าใหม่) · ปุ่มของการ์ด (บันทึกคำบรรยาย · เลื่อน · ลบภาพซ่อน) ล็อกด้วยธงเดียวและปล่อยเฉพาะของตัวเอง · - **`id` ของแถวคงเดิมข้ามการบันทึกแล้ว** (เดิมออก `PSI-…` ใหม่ทุกแถวทุกครั้ง) — จอส่ง `id` ของแถวเดิมกลับมา · `prepareSpecItemRows` เดินสองรอบ แถวเดิมหนึ่งแถวให้ `id` ได้ **ครั้งเดียว**: ① `id` ที่ส่งมา คงไว้เฉพาะเมื่อเป็นของแถวที่เก็บอยู่ **ในสเปคนี้** และยังไม่มีแถวก่อนหน้าใช้ไป นอกนั้นตัดทิ้ง (PK เป็นของทั้งตาราง ไม่ใช่รายสเปค — `id` จาก client ที่หลุดเข้าไป = ชน PK ของสเปคอื่นได้) · ② แถวที่ยังไม่มี `id` (จอรุ่นก่อน/แท็บที่เปิดค้างข้าม deploy ไม่ส่ง `id` มาเลย) รับ `id` ของแถวเดิมที่ยังว่างซึ่ง `itemKey` ตรงกัน ไม่มีค่อยแถวที่เพิ่มเอง (`itemKey` ว่างทั้งคู่) ที่ `itemLabel` ตรงกันเป๊ะ — รอบ ① จบก่อนเสมอ (`id` ที่ส่งมาชนะ) · ที่เหลือ store ออก `id` ใหม่ · ตอนสร้างสเปค `id` จาก client ไม่ถึง RPC เลย
- **ถอย (rollback)** อยู่ท้ายไฟล์เป็นคอมเมนต์: ถอยโค้ดก่อน → วางตัวฟังก์ชัน 8 คอลัมน์ของ 0370 หัวข้อ ⑨ข ทับกลับ (ห้ามถอด RPC ทิ้ง — โค้ดทุกรุ่นตั้งแต่ 0370 เรียกทุกครั้งที่บันทึก checklist) → ถอด index/constraint/คอลัมน์ · ⚠️ ราคาทุนที่กรอกไว้กับตัวชี้รูปของทุกแถว **หายถาวร** (ไฟล์รูปใน `attachments` ยังอยู่แต่ไม่มีแถวชี้)

### RPC `replace_product_spec_items`
บันทึก checklist ของสเปคแบบทับทั้งชุดในคำสั่งเดียว (ล็อกแถวสเปค → ลบชุดเดิม → เขียนชุดใหม่) · คนที่อ่านพร้อมกัน (เช่นการยื่นที่ถ่ายภาพนิ่ง) เห็นชุดเก่าหรือชุดใหม่ชุดใดชุดหนึ่งเท่านั้น ไม่มีจังหวะที่สองชุดซ้อนกัน · SECURITY DEFINER · ให้สิทธิ์เฉพาะ service_role
- **ตัวฟังก์ชันปัจจุบันคือของ mig 0405** (มติ 08/10/2569 · `CREATE OR REPLACE` ทับตัวของ 0370 ⑨ข — ลายเซ็น `(p_spec_id text, p_rows jsonb) RETURNS integer` · `SECURITY DEFINER` · `search_path` เดิม · `REVOKE` จาก PUBLIC/anon/authenticated + `GRANT` ให้ service_role ประกาศซ้ำ) · ลำดับ: ล็อกแถวสเปค `FOR UPDATE` → **เก็บแถวเดิมของสเปคนั้นลงตัวแปร jsonb** (`id` · `itemKey` · `itemLabel` · `sortOrder` · `costPrice` · `imageAttachmentId`) → ลบ → เขียน · แถวละ 10 คีย์ (8 ตัวของ 0370 + `costPrice` + `imageAttachmentId`) · คีย์ที่ไม่ได้ประกาศในชุดคอลัมน์ที่แกะถูกทิ้งเงียบ (`productSpecItemCostImageMigration.test.mjs` เทียบกับที่ store ส่ง)
- ⭐ **ยกค่าเดิมข้ามการทับ** — แถวที่ผู้เรียก **ไม่ได้ส่งคีย์** `costPrice` / `imageAttachmentId` มา ได้ค่าของแถวเดิมหนึ่งแถว จับคู่สามขั้น: ① **`id` เดียวกันก่อน** → ② **`itemKey` เดียวกัน** (ที่ไม่ใช่ NULL — แถวของแบบฟอร์ม) → ③ แถวที่เพิ่มเอง (`itemKey` เป็น NULL ทั้งคู่) ที่ **`itemLabel` ตรงกันเป๊ะ** · หลายแถวเข้าข่าย = แถวบนสุดตาม `sortOrder`, `id` (ผลนิ่ง) · แถวที่มี `itemKey` ไม่เข้าขั้น ③ · ตัดสินแยกทีละคีย์ (ส่งมาคีย์เดียว = อีกคีย์ถูกยก) · ส่งคีย์มาเป็น `null` = ล้างจริง · จับคู่ไม่ได้ = `NULL` · ไม่อ่านแถวของสเปคอื่น
  - ทำไมต้องมีขั้น ③: ผู้เรียกที่ไม่รู้จักสองคีย์ใหม่ก็ **ไม่ส่ง `id`** มาด้วย (โค้ดรุ่นก่อนออก `id` ใหม่ทุกแถวทุกครั้ง) ⇒ แถวที่เพิ่มเองไม่มีทั้ง `id` ทั้ง `itemKey` ให้จับ — ไม่มีขั้นนี้ ราคาทุน/รูปของแถวที่เพิ่มเองหายทุกครั้งที่ผู้เรียกแบบนั้นกดบันทึก · ผู้เรียกที่ผ่าน server รุ่นนี้ได้ `id` เดิมตั้งแต่ `prepareSpecItemRows` (กฎจับคู่เดียวกัน · แถวเดิมหนึ่งแถวใช้ได้ครั้งเดียว) แล้วถึง RPC ด้วยขั้น ① — ขั้น ②③ ของ RPC คือตาข่ายของผู้เรียกที่ไม่ผ่านฟังก์ชันนั้น (โค้ดรุ่นก่อนที่ยังรันอยู่ · worktree อื่นบนฐานเดียวกัน)
  - ⚠️ **ที่ยังหลุด (ยอมรับ)**: ผู้เรียกที่ไม่ส่งทั้งคีย์ใหม่และ `id` **แก้ชื่อ** แถวที่เพิ่มเอง = ไม่เหลืออะไรให้จับ ⇒ แถวนั้นได้ `NULL` ทั้งราคาทุนและรูป (เทสต์ตรึงไว้ทั้งที่ store และ PGlite) · ไฟล์รูปไม่ถูกลบตอนนั้น (คำขอที่ไม่ส่งคีย์รูปไม่ทำให้เก็บกวาด) แต่ไม่มีแถวชี้แล้ว จึงไปกับกฎอายุในการบันทึกครั้งถัดไปจากจอรุ่นใหม่
  - "ส่งคีย์มาไหม" ถามจาก **ก้อน jsonb ของแถว** (`elem ? 'costPrice'`) ไม่ใช่จากค่าที่แกะแล้ว — แกะแล้วคีย์ที่ไม่ส่งกับคีย์ที่ส่ง `null` เป็น NULL เหมือนกัน แยกไม่ออกว่า "ไม่แตะ" หรือ "ล้าง"
  - 🐞 **ทำไมต้องมี**: RPC นี้ลบทั้งชุดแล้วเขียนใหม่ ⇒ ผู้เรียกที่ไม่รู้จักสองคีย์นี้ — โค้ดรุ่นก่อน · แท็บที่เปิดค้างข้าม deploy · dev server/worktree อื่น (ทุกตัวชี้ฐาน production เดียวกัน ไม่มีฐาน dev แยก) — จะล้างราคาทุนกับรูปของทุกแถวทุกครั้งที่กดบันทึก แล้วตอบว่าบันทึกสำเร็จ
  - ฝั่งโค้ดเดินกลไกเดียวกัน: `normalizeSpecItems` คง **สามสถานะ** (ไม่มีคีย์ ≠ `null` — ห้ามเติมค่าตั้งต้น) · store ใส่สองคีย์ลง `p_rows` **เฉพาะเมื่อแถวมีคีย์** · คนที่แก้ราคาทุนไม่ได้ถูกตัดคีย์ `costPrice` ก่อนถึง RPC (`prepareSpecItemRows`) ⇒ ราคาเดิมคงอยู่
  - ⚠️ ขอบที่รู้: ผู้เรียกที่ไม่ส่งคีย์ ส่งแถวหนึ่งด้วย `id` ของแถวเดิม และอีกแถวด้วย `itemKey` ของแถวเดิมตัวเดียวกัน ⇒ สองแถวได้ค่าที่ยกมาชุดเดียวกัน (ไม่มี unique บนตัวชี้รูป) · จอปัจจุบัน (ส่งคีย์รูปทุกแถวเสมอ) และโค้ดรุ่นก่อน (ไม่ส่ง `id` · `itemKey` ไม่ซ้ำในชุด) ไม่สร้างรูปคำขอแบบนี้ · ทำนองเดียวกัน ผู้เรียกที่ยิง RPC ตรง (ไม่ผ่าน `prepareSpecItemRows`) ส่งแถวที่เพิ่มเอง **ชื่อซ้ำกันสองแถว** โดยไม่มี `id` ⇒ ทั้งสองแถวได้ค่าของแถวเดิมแถวบนสุด (ไม่ล้ม · ผลนิ่ง — PGlite ยืนยัน) · server รุ่นนี้ไม่เกิดเพราะจับ `id` ให้แบบแถวเดิมหนึ่งแถวใช้ได้ครั้งเดียว
- error ของ RPC แปลที่ store (`specItemsRpcFailure`) ด้วย **SQLSTATE ก่อนข้อความ** เป็นข้อความไทยที่ไม่มีข้อความดิบของ Postgres + status ที่ส่งถึงเราต์จริงทั้งทางบันทึกและทางสร้าง: `22P02`/`22003` (รูปแบบ/เกินช่วง) · `23503` (รูปถูกลบไปแล้ว) · `23514` (เกิน CHECK) · `23505` (รหัสแถวซ้ำ) ⇒ 400 · `product_spec_not_found` ⇒ 404 · ที่ไม่รู้จัก = ไม่มี status (500 พร้อมข้อความเดิม)

  ⇒ ร่างที่เคยยื่นแล้วดึงกลับ **หน้าตาเหมือนร่างที่ไม่เคยยื่นทุกช่อง** · รอยที่แยกสองอย่างนี้คือ `firstSubmittedAt` (mig 0375)
  ⇒ ตัวตัดสินของ `delete` อ่านช่องนั้น ⇒ **ทุกทางที่ `select` แถว Rev ต้องดึงคอลัมน์นี้มาด้วย** (ตกหล่น = `undefined` = "ไม่เคยยื่น" = ปุ่มลบโผล่ผิดใบ)
- `delete` **ไม่เช็คสถานะ SO** — ลบร่างของตัวเองคือถอย ไม่ใช่เดินหน้า (กติกาเดียวกับ `withdraw`/`void`) · SO ที่ถูกย้อนการอนุมัติยิ่งต้องเก็บกวาดร่างที่ค้างได้
- ทุกการอนุมัติ/ยื่นต้องเช็คว่า SO ยัง `approved` อยู่ (ถ้าถูกย้อนการอนุมัติ ⇒ ติดด่าน บอกเหตุ)
  - ฐานตรวจซ้ำด้วย trigger ของ Rev: เมื่อ Rev จะเปลี่ยนไปเป็น `pending_ae` `pending_ae_supervisor` หรือ `approved` trigger ล็อกแถวเอกสารและแถว SO แบบ FOR SHARE แล้วตรวจว่าเอกสารยัง active และ SO ยัง approved ถ้าเอกสารถูก void หรือ SO ถูกย้อนการอนุมัติระหว่างคำขอ ฐานจะปฏิเสธ และ API ตอบ 409
- "admin" = `role === 'admin'` เท่านั้น — **ไม่ใช้ `isSuperuser`** เพราะ `ae_supervisor` นับเป็น superuser แล้วจะกดขั้น AE ข้ามเจ้าของดีลได้
- UPDATE ที่เปลี่ยนสถานะต้องมี `.eq('status', เดิม)` และ **เช็คว่าโดนแถวจริง** (`select().maybeSingle()` แล้วไม่ใช่ null) ไม่งั้นตอบ 409 "สถานะเปลี่ยนแล้ว กรุณาโหลดใหม่"

## จังหวะจาก SO (hook ใน `sales-orders/[id]/route.js`)
- **cancel** (ทั้งทางยกเลิกเฉย ๆ และทาง `cancel_sales_order_with_reversal_atomic`) ⇒ void เอกสารทุกใบของ SO นั้น เหตุผล `ใบสั่งขาย <เลข> ถูกยกเลิก`
- **revise** ⇒ บรรทัดใหม่ id = `'SOL-' || md5(<newSoId> || ':' || <oldLineId>)` (ดู RPC 0346/0363) ⇒ ย้าย `salesOrderId/LineId` ไปใบใหม่
  - Rev ล่าสุด approved ⇒ สร้าง Rev+1 draft เหตุผล `ออก Rev. ใบสั่งขาย <เก่า> → <ใหม่>`
  - Rev ล่าสุด pending_* ⇒ ถอยเป็น draft (Rev เดิม)
  - draft / rejected ⇒ คงไว้
- hook ทำงาน **หลัง** RPC ของ SO สำเร็จ · ถ้า hook ล้ม SO ยังสำเร็จ แต่ต้องตอบ `warning` และเขียน audit (ไม่เงียบ)
- เอกสารที่บรรทัด SO หายไป (`salesOrderLineId` เป็น NULL เพราะถูกถอดบรรทัด) โผล่ในการ์ดหน้า SO เป็นแถว "บรรทัดถูกถอด" พร้อมปุ่มปลายทางของใบ — ยกเลิกเอกสาร หรือ **ลบร่างเอกสารถาวร** ถ้ายังไม่เคยยื่น (มติ 23/09/2569 · API ส่ง `voidAction` + `removeAction` จาก `documentActions` ก้อนเดียว ⇒ ได้ตัวเดียวพอดี · ลบใช้เส้น `DELETE` และโมดัล `docConfirmPrompt('remove', { orphan: true })` ชุดเดียวกับหน้าเอกสาร) · แถวประกอบที่ `specDocOrphanRow` ตัวเดียว (มี `currentRevNo`) และการ์ดแปลงเป็นก้อนโมดัลด้วย `orphanDocPromptInput` ⇒ โมดัลยกเลิก/ลบบนการ์ดพูดเท่าหน้าเอกสารทุกตัวอักษร รวม "ฉบับ Rev.XX ที่อนุมัติแล้วใช้ไม่ได้อีก" · toast ยกเลิกใช้ `docActionDoneMessage('void', { docNoText })` บอกว่าแจ้งเตือนใคร (ผลตรวจ 25/09 ของงานมติ 24/09 — ผู้อนุมัติกดยกเลิกจากการ์ดได้) · เหตุบนปุ่มเดินหน้า/แถบเตือนบนหน้าเอกสารชี้ปุ่มที่ใบนั้นมีจริง (`lineRemovedBlock` / `lineRemovedNotice`)
  - ลบจากการ์ดแล้วไม่ได้คำตอบว่าสำเร็จ ⇒ ดึงการ์ดใหม่แล้วตัดสินด้วย `orphanRemoveFailureOutcome`: ใบหายจากการ์ด + ไม่มีคำตอบให้เชื่อ
    (เน็ตหลุด/5xx) = **ลบสำเร็จ** (toast สำเร็จ ไม่ใช่ "เชื่อมต่อไม่ได้ ลองอีกครั้ง" — UAT 23/09) · เซิร์ฟเวอร์ตอบเหตุ (404/409) หรือใบไม่มีปุ่มลบแล้ว
    = ปิดโมดัล เหตุขึ้นแถบการ์ด · ยังลบได้/โหลดการ์ดไม่ขึ้น = คงโมดัลให้กดใหม่
  - คำเตือนตอน SO ออก Rev ที่ย้ายเอกสารไปแบบไม่มีบรรทัด ชี้ **ที่ที่ปุ่มอยู่** ("จัดการต่อ (ลบร่าง/ยกเลิก) ได้ที่การ์ดเอกสารต่อเนื่องบนหน้าใบสั่งขาย")
    ไม่ใช่ชื่อปุ่มตายตัว — คำเตือนออกก่อนอ่าน Rev ล่าสุด และใบกำพร้าอาจเป็นร่างที่ไม่เคยยื่น (ปุ่ม = ลบ)
  - ตอน SO ออก Rev เอกสารที่หาบรรทัดคู่ในใบใหม่ไม่เจอ ย้ายไปผูก SO ใบใหม่โดยไม่มีบรรทัด แล้วใช้กติกา Rev ดังนี้ (ตัดสิน 22/09/2569 ตอนแก้ผลรีวิว)
    - Rev ล่าสุด pending_* ⇒ ถอยเป็น draft เหมือนเอกสารใบอื่น เพื่อไม่ให้ค้างอยู่ในคิวผู้อนุมัติ
    - Rev ล่าสุด approved ⇒ **ไม่เปิด Rev+1** เพราะเอกสารที่ไม่มีบรรทัดเดินด่านต่อไม่ได้ ทางออกเดียวคือยกเลิก และ Rev ลบไม่ได้ ถ้าเปิด Rev+1 จะมี Rev ที่ยื่นไม่ได้ค้างในประวัติตลอดไป
    - draft / rejected ⇒ คงไว้
- **ผู้ดูแลระบบบังคับลบ SO** ⇒ void เอกสารที่ยัง active ของ SO นั้นก่อนที่ FK จะปลดลิงก์ เหตุผล `ใบสั่งขาย <เลข> ถูกลบถาวร` และพรีวิวก่อนลบต้องบอกจำนวนเอกสารที่จะถูก void
- โมดัลยืนยันการยกเลิก SO และการออก Rev ของ SO ต้องบอกผลที่เกิดกับเอกสาร FM-SA-04 ของใบนั้น (กฎ approval-confirm-modals)

    - **รูป** — แถวละรูป ไม่บังคับ (`SpecItemImageCell`): แนบ · เปิดดู (รูปย่อเป็นลิงก์แท็บใหม่) · เปลี่ยน · เอาออก · คอลัมน์นี้ไม่ผูกกับสิทธิ์ราคาทุน (โหมดอ่านอย่างเดียว = รูปย่อหรือขีด) · **ยังไม่มีสเปค = ปุ่มขึ้นแต่กดไม่ได้ พร้อมเหตุ "สร้างสเปคก่อน จึงแนบรูปของแต่ละแถวได้" พิมพ์ครั้งเดียวเหนือตาราง** (ปุ่มถือประโยคเดียวกันเป็น `title` · รอบแรกพิมพ์ใต้ปุ่มทุกแถว = 17 บรรทัดซ้ำและแถวสูง 53→82px ⇒ ย้ายขึ้นเหนือตาราง) (`canAttachItemImage` = แก้สเปคได้ + มีสเปคแล้ว) · **ระหว่างหน้ากำลังสร้าง/บันทึก/ลบ ปุ่ม "แนบรูป" และ "เปลี่ยนรูป" กดไม่ได้** (ลากวาง/วางก็ปิดด้วย) พร้อม `title` "กำลังบันทึก — รอสักครู่แล้วแนบรูปอีกครั้ง" — ดูข้อ "ระหว่างกำลังบันทึก" ข้างล่าง · ปุ่ม "เอารูปออก" ไม่ถูกปิด (ไม่สร้างไฟล์ค้าง) · **หลังแนบสำเร็จ/เอารูปออก โฟกัสคีย์บอร์ดกลับเข้ากล่องของแถวนั้น** (ปุ่มแรกที่กดได้ — ปุ่มที่กดถูก React ถอดเมื่อค่าเปลี่ยน ไม่คืน = โฟกัสตกไป `<body>` และ Ctrl+V ต่อไม่ติด) · ไม่แย่งโฟกัสถ้าผู้ใช้ย้ายไปช่องอื่นระหว่างรูปกำลังขึ้น · แนบไม่สำเร็จไม่คืนโฟกัส · **เปิดจอลองแล้ว 08/10** (devBypass บท AC · ดักคำขอเขียน): กด "เอารูปออก" แล้วโฟกัสไปอยู่ที่ปุ่ม "แนบรูป" ของแถวเดิม · ระหว่างคำขอบันทึกค้างอยู่ ปุ่ม "แนบรูป" กดไม่ได้พร้อม `title` ข้างบน และกลับมากดได้เมื่อคำขอจบ · ⚠️ ทาง "แนบสำเร็จ" ยังไม่ได้ลองบนจอ (ต้องอัปไฟล์จริงขึ้น Drive — เครื่อง dev คุยกับ Drive ไม่ได้ ⇒ ลองบน production หลัง deploy)
      - ไฟล์ = แถว `attachments` ของ **ตัวสินค้า** `docType='spec_item_image'` แนบผ่าน `uploadAttachment` ทางเดียวของระบบ · แถว checklist เก็บแค่ตัวชี้ · รับเฉพาะรูป (JPG · PNG · WEBP · GIF) **ไม่เกิน 5 MB** (`SPEC_ITEM_IMAGE_MAX_BYTES` — จอโหลดรูปต้นฉบับแถวละรูป ไม่มีตัวย่อรูป) ตรวจทั้งที่จอและที่ `POST` · ⚠️ ฝั่ง server เชื่อ `sizeBytes` ที่ client รายงาน ไม่ได้วัดไบต์จริง
      - **ไม่ขึ้นแผงเอกสารของสินค้า**: ไม่เป็นการ์ด (`productDocTypes()` กรองออก ⇒ ไม่เข้าด่าน "ยังขาดเอกสาร") และ `AttachmentsPanel` ตัดออกจากกอง "เอกสารอื่นๆ" · ตัวนับที่หัวแผง · ด่านแผงว่าง · รายการ inline (`PANEL_HIDDEN_DOC_TYPES` — แผงที่ขอชนิดนี้มาเองผ่าน `docTypes` ยังเห็น · `onItemsChange` ยังได้รายการดิบ) — ปล่อยให้ลบจากแผงนั้นได้ แถวจะเสียรูปเงียบ ๆ ตาม FK SET NULL โดยไม่มี audit และไม่ขยับ `updatedAt` ของสเปค
      - **แนบได้ทุกคนที่แก้สเปคได้ — ช่องแคบ `canAttachSpecItemImage`** (`lib/master/attachmentAccess.js`): ด่านรวมของไฟล์แนบสินค้า = แก้ทะเบียนสินค้า ซึ่งผูกกับทีมที่ดูแลลูกค้าเจ้าของสินค้า แต่สเปคแก้ได้ทั้งฝ่ายขาย ⇒ ไม่มีช่องนี้คนแก้สเปคนอกทีมกรอกได้ทุกช่องยกเว้นรูป (403) · แคบเป๊ะ: entity สินค้า + docType รูปประจำแถวเท่านั้น (ถามด้วย docType **ที่จะเก็บจริง** ตอนแนบ · **ของแถว** ตอนลบ/แก้) · ไฟล์อื่นของสินค้ายังผ่านด่านเดิม · ต่อเป็นประโยคแยกทั้งใน `POST /api/attachments` และ `guardAttachmentWrite` (ประโยคเดิมของรูปปฏิทินวางบิลถูกเทสต์ตรึงทั้งประโยค)
      - `POST` ของชนิดนี้: ไม่รับเอกสาร Google · ต้องมี `driveFileId` · ไฟล์ชนิดนี้ระบบลบเอง (ปล่อยให้ชี้ไฟล์ของคนอื่นได้ ตัวเก็บกวาดจะทิ้งไฟล์นั้นลงถังขยะ Drive) ⇒ ตรวจสองชั้นหลังด่านสิทธิ์ ก่อนเขียนแถว:
        - ① ฐาน — `driveFileHeld` (`lib/master/attachments.js`): **มีแถว `attachments` ไหนถือไฟล์นี้อยู่ = 400** ถามทั้งช่อง `driveFileId` และ `metadata.googleFileId` (เอกสาร Google ที่ใช้ร่วมกันเก็บ id ไว้ช่องหลัง และ `driveFileId` เป็น null — 🐞 รอบแรกถามแค่ช่องแรก ⇒ ชี้ Google Sheet ของดีลคนอื่นได้) · id ต้องเป็น `[A-Za-z0-9_-]+` เท่านั้น ผิดรูป = 400 โดยไม่ยิงคำถาม (ค่านี้ถูกต่อลงตัวกรอง `.or()`) · ตรวจไม่ได้ = 500
        - ② Drive — อ่าน `id, mimeType, trashed` ของไฟล์จริง (`getFileMeta`): อยู่ในถังขยะ · เป็นของ Google (`application/vnd.google-apps.*` = โฟลเดอร์/Docs/Sheets) · ไม่ใช่ชนิดรูปตามกติกาของ docType = 400 · **อ่านไม่ได้ (รวมไฟล์ที่ไม่มีอยู่) = 502** ไม่ปล่อยผ่าน · `mimeType` ที่เก็บลงแถวยังเป็นค่าที่ client ส่ง (ค่าจาก Drive ใช้ปฏิเสธอย่างเดียว) · ⚠️ ชั้นนี้ยังไม่เคยวิ่งกับ Drive จริง (เทสต์ตรึงลำดับในซอร์ส) — หลัง deploy ต้องลองแนบจริงหนึ่งครั้ง
        - ⚠️ **ที่ยังไม่ปิด (พูดตรง ๆ)**: ไม่ตรวจว่าไฟล์อยู่ในโฟลเดอร์ของสินค้านี้ ⇒ **ไฟล์รูปบน Drive ที่ไม่มีแถว `attachments` ไหนชี้** และ service account มองเห็น ยังแนบผ่านเส้นนี้ได้ แล้วถูกตัวเก็บกวาดทิ้งลงถังขยะ Drive ได้ (กู้จากถังขยะได้) · ที่มาของ `driveFileId` ที่ client รายงานใน `POST /api/attachments` เป็นช่องโหว่ทั่วไปที่มีมาก่อนของทุก docType — อยู่นอกรอบนี้ (งานแยก)
      - **ลบตรง ๆ ไม่ได้ขณะมีแถวชี้อยู่**: `DELETE /api/attachments/[id]` ของรูปที่ยังมีแถว checklist ชี้ = **409** "รูปนี้ผูกกับแถว checklist ของใบสเปค — เอารูปออกที่หน้าสเปคแล้วกดบันทึก" · อ่านไม่ได้ = 500 (ไม่ใช่ถือว่าไม่มีใครชี้) · รูปที่ไม่มีแถวชี้ลบได้ตามปกติ — แต่ก่อนทิ้งไฟล์บน Drive ถาม `driveFileHeld` เหมือนตัวเก็บกวาด: ยังมีแถวอื่นถือไฟล์เดียวกัน/ตรวจไม่ได้ = ลบแค่แถว เก็บไฟล์ไว้ (log) ตอบสำเร็จ (🐞 รอบแรกเส้นนี้ทิ้งไฟล์เลยโดยไม่ถาม = ทางลัดข้ามด่านของตัวเก็บกวาด)
        - ⚠️ ด่าน 409 **กันได้เท่าที่ทำได้ ไม่ใช่กันขาด**: ตรวจแล้วค่อยลบเป็นสองคำสั่งไม่มีล็อก — การบันทึกสเปคที่ commit ตัวชี้แทรกระหว่างสองคำสั่งพอดี แถวนั้นเสียรูป (FK ตั้งตัวชี้เป็น NULL) โดยไม่มี 409 · ยอมรับได้เพราะไม่มีจอไหนยิง `DELETE` กับชนิดนี้ (การเอารูปออกเดินผ่านการบันทึกสเปคเท่านั้น — ต้องเป็นคนที่แก้สเปคได้ยิง API เองให้ชนจังหวะ) และ FK SET NULL ทำให้ฐานไม่มีตัวชี้ค้าง เสียแค่รูปภายในหนึ่งรูป แถวกับราคาทุนอยู่ครบ · ปิดขาดต้องย้ายการลบไปไว้ใน RPC ที่ล็อกแถวสเปคตัวเดียวกับ `replace_product_spec_items` (ยังไม่ทำ)
      - **เปลี่ยน/เอาออกบนจอแตะแค่ตัวชี้ในร่าง** — ไม่ลบไฟล์จากจอ (ทิ้งร่างแล้วรูปเดิมต้องยังอยู่) · ไฟล์ที่ไม่มีแถวชี้ server เก็บกวาดเองตอนบันทึก (ดู "เก็บกวาดรูปประจำแถว" ข้างล่าง)
      - วาง (Ctrl+V) รับเฉพาะตอนโฟกัสอยู่ในกล่องของแถวนั้น — `useFileIntake` ตัวเลือกใหม่ `paste: "focused"` (ค่าตั้งต้น `"auto"` เหมือนเดิม): กล่องแบบนี้ไม่เข้าคิว paste ลอย ๆ ของหน้า จึงไม่ลงแถวแรกเงียบ ๆ และไม่แย่งแผงภาพประกอบ · กดเลือก/ลากวางเหมือนเดิม · ข้อความไฟล์ใหญ่เกินพิมพ์เพดานที่กล่องนั้นใช้จริง
    - **ระหว่างรูปของแถวกำลังขึ้น** (`rowUploads > 0`): ปุ่มบันทึก/สร้างกดไม่ได้พร้อมเหตุ "กำลังแนบรูปของแถว — รอให้เสร็จก่อนบันทึก" · ไม่โหลดทับร่าง · ไม่ลบสเปค · กันออกจากหน้า (`useUnsavedChanges`) — ทั้งสามทางทิ้งร่าง ⇒ ผลการแนบที่กลับมาทีหลังจะไม่มีแถวให้ลง แล้วไฟล์ค้างโดยไม่มีใครชี้
    - **ระหว่างกำลังบันทึก** (กลับกัน · หน้า `busy` = สร้าง/บันทึก/ลบ → `saving` ของ `ProductSpecForm`): เริ่มแนบรูปของแถวไม่ได้ — ผลบันทึกที่กลับมาสร้างร่างใหม่ทั้งก้อน ⇒ รูปที่ขึ้นเสร็จก่อนถูกร่างใหม่ทับ · รูปที่ขึ้นเสร็จทีหลังบนแถวที่เพิ่งเพิ่ม (`_uid` เปลี่ยนจาก `~new-N` เป็น id ของฐาน) ไม่มีแถวให้ลง · ทั้งสองทางไฟล์ค้างและผู้ใช้ไม่ได้ข้อความอะไร
    - แถวบนจออ้างกันด้วย `_uid` (`withRowUids` — แถวจาก server ใช้ `id` ของตัวเอง · แถวใหม่ได้ `~new-N` ซึ่งชนกับ id ของฐานไม่ได้) ไม่ใช่เลขลำดับ: ผลการแนบที่กลับมาหลังแถวถูกลบ/ร่างถูกโหลดใหม่ = ไม่ลงแถวไหน และไม่ปักว่ามีของค้าง · `_uid` ไม่ถูกส่งไป server
    - **ก้อนบันทึกของแถว** (`specSaveBody`): `id` ของแถวเดิม (ถ้ามี) + เจ็ดช่องเดิม + `imageAttachmentId` **ส่งทุกแถวเสมอ** (สตริงหรือ `null`) + `costPrice` **เฉพาะคนที่ `canEditItemCost`** · คำตอบของ GET/POST/PATCH: `spec.items[]` = แถวจากฐาน (หลังรัน 0405 มี `id` · `imageAttachmentId` ทุกแถว — ว่าง = `null` · และ `costPrice` เฉพาะคนที่เห็นได้) · `permissions` เพิ่ม `canSeeItemCost` · `canEditItemCost` · `canAttachItemImage`
  - **ด่านก่อนเขียน checklist** (store · ผ่านก่อนคำสั่งเขียนตัวแรกเสมอ — เนื้อสเปคเข้าไปแล้วค่อยรู้ว่ารูปไม่ผ่าน = บันทึกครึ่งเดียว):

**สเปคของสินค้า** (ไม่ใช่เอกสาร) ลง `audit_logs` `entityType = 'product_spec'` ทุกการสร้าง/บันทึก/ลบ · `before/after` เป็น **แถวสเปคเต็มพร้อม `items`** ·
ตั้งแต่รอบสิบ (mig 0405 · 08/10/2569) `after` ของการสร้าง/บันทึกที่ส่ง checklist มา คือแถวที่ **อ่านกลับจากฐานหลังเขียน** ⇒ ราคาทุน/ตัวชี้รูปที่ RPC ยกมาจากแถวเดิมอยู่ครบ
และ **ไม่ถูกลบคีย์ `costPrice`** — เราต์ลบคีย์ให้คนดู *หลัง* ลง audit เสมอ (เทสต์ตรึงลำดับใน `specDocumentRoutes.test.mjs`) ⇒ คนที่ถือ `audit:view` อ่านราคาทุนรายแถวได้ (ดู §มติ — ผู้ลงมือเลือก รอเจ้าของค้าน)
· การเก็บกวาดรูปประจำแถว (ตอนบันทึก/ตอนลบสเปค) **ไม่เขียนแถว audit ของตัวเอง** — ร่องรอยของรูปที่เคยมีแถวชี้คือ `imageAttachmentId` ใน `before` ของสเปค · รูปที่แนบแล้วไม่เคยบันทึกไม่มีร่องรอยใน audit

🔴 **`delete` (ลบร่าง) เขียน audit ก่อนลบเสมอ** — ระบบไม่มีถังขยะ `audit_logs.before` คือทางกู้ทางเดียว
([[deleted-data-recovery]]) · ลบก่อนแล้วค่อยเขียน = มีจังหวะที่แถวหายโดยยังไม่มีสำเนา และ `recordAudit`
กลืน error ของตัวเอง ⇒ เราต์ไม่มีทางรู้ว่าต้องหยุด · ลบไม่ผ่านหลังจากนั้น เราต์เขียนแถว audit แก้กลับ
(`after.deleteFailed`) ไม่ปล่อยให้บันทึกโกหกว่าลบไปแล้ว
