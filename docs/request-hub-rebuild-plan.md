## 0. สรุปสั้นที่สุด

ระบบคำร้อง **โครงสร้างข้างในดีแล้ว** — สถานะชุดเดียว · ทะเบียนหัวข้อในโค้ด ·
ธง `needs` ต่อหัวข้อ · เธรด · แนบไฟล์ · ปักหมุดไทม์ไลน์ · เลขที่เอกสาร

สิ่งที่ขาดไม่ใช่ฟีเจอร์ แต่เป็น **ขอบเขต 3 ข้อที่ถูกตีกรอบไว้ตั้งแต่ตอนที่มันยังเป็น
"ระบบขอราคาวัสดุ" และไม่มีใครถอดกรอบออกหลังเปลี่ยนชื่อ**

| # | กรอบที่ยังติดอยู่ | ผลที่เกิดจริง |
|---|---|---|
| 1 | เมนูอยู่หลังด่าน **ต้นทุน** (`canViewCosting`) | ฝ่ายที่ไม่ใช่ RD/PC **เปิดเมนูไม่ได้เลย** |
| 2 | `dept` มี CHECK แค่ `RD`/`PC` | **ขอ Invoice จากบัญชียังทำไม่ได้** ทั้งที่ผู้ใช้สั่งไว้ตั้งแต่รอบธุรกิจบริการ |
| 3 | คิวเห็นแค่สถานะที่ยังเปิด | **RD/PC มองย้อนหลังไม่ได้** และไม่มีช่องค้นหา |

⭐ **ทั้งสามข้อคือ "เมนูกลางที่ยังไม่กลาง"** — ตอนนี้ประสานได้ 2 ฝ่ายจาก 13 ฝ่ายที่มีในระบบ

## 2. ข้อเสนอ

### R-1 🔴 ด่านของเมนูผิดตั้งแต่ต้น — แยก "อ่านคำร้อง" ออกจาก "เห็นต้นทุน"

**ปัญหา** เมนูคำร้องยืมด่านของระบบขอราคาผลิตมาใช้ ซึ่งด่านนั้นมีไว้ปกป้อง**ตัวเลขต้นทุน**
ไม่ได้มีไว้ปกป้องการสนทนา ⇒ คนที่จะตอบ *"สอบถามข้อมูล"* ธรรมดา ต้องมีสิทธิ์เห็นต้นทุนก่อน

**เสนอ** แยกเป็นสองชั้น แล้ว **ปิดที่เนื้อ ไม่ใช่ปิดที่เมนู**

| ชั้น | ใคร | เห็นอะไร |
|---|---|---|
| `requests:view` | ทุกฝ่ายที่เป็นผู้ขอหรือผู้ตอบได้ | เมนู · คิวของฝ่ายตน · คำร้องที่ตัวเองเกี่ยวข้อง |
| `costing:view` (เดิม) | RD · PC · EX · admin | **บรรทัดวัสดุและราคา**ในใบขอราคา |

🪤 **กับดักที่ต้องระวังที่สุดของทั้งแผน** — ปลดด่านผิดวิธีแล้วต้นทุนรั่วทันที
เพราะทุกวันนี้ "ไม่เห็นเมนู" คือสิ่งที่กันไว้อยู่ · เงื่อนไขบังคับ:
- บรรทัดราคาต้องถูกตัดที่ **API** ไม่ใช่ซ่อนที่จอ
- เธรดของคำร้องขอราคาต้องพิจารณาแยก — ราคาถูกพิมพ์ในเธรดได้
- ⚠️ `/api/sa/requests/mentionable` ตอบรายชื่อโดยยึด `canViewCosting`
  (บันทึกไว้แล้วว่า *"ถ้าด่านนั้นเปลี่ยนไปดูตัวแถว เส้นนี้ตอบกว้างเกินจริงทันที"*) —
  **ข้อนี้คือสิ่งที่กำลังจะเปลี่ยนพอดี ต้องแก้พร้อมกัน**

**ขนาด** 1 PR กลาง · ไม่มี migration

### R-2 🔴 ฝ่ายผู้รับต้องเกินกว่า RD/PC — เริ่มที่ `FN` (บัญชี)

**ปัญหา** ผู้ใช้สั่งไว้เองตั้งแต่รอบธุรกิจบริการ: *"บางที SA จะต้องมาขอ Invoice จากบัญชี"*
และ *"SA ต้องกดว่าลูกค้าจ่ายแล้ว บัญชีต้องคอนเฟิร์ม"* · ทั้งสองอย่างเป็น **คำร้อง**
ตามนิยามทุกประการ แต่วันนี้ส่งถึงบัญชีไม่ได้ เพราะ **บัญชีไม่มีตัวตนในระบบเลย**

**เสนอ** 3 ก้าว ตามลำดับ

1. เพิ่ม `FN` เข้า `DEPARTMENTS` + `DEPARTMENT_NAMES_TH` (`'ฝ่ายบัญชีและการเงิน'`)
2. **ผ่อน CHECK ของ `dept` ออก** แล้วให้ทะเบียนฝ่ายผู้รับอยู่ในโค้ด
   ⭐ แพตเทิร์นเดียวกับ `kind` ที่ `0173:50` **จงใจไม่ใส่ CHECK** พร้อมเหตุผลเขียนกำกับไว้:
   *"ชุดชนิดเป็นเรื่องของงาน ไม่ใช่ของ schema"* — ฝ่ายผู้รับก็เรื่องเดียวกัน
3. หัวข้อใหม่ `invoice_request` → `FN` · `needs: ['deal']` (หรือ SO เมื่อมี)

⭐⭐ **ห้ามสร้างกลไกที่สอง** — ระบบธุรกิจบริการต้องการเส้น "SA แจ้ง → FN ยืนยัน" อยู่แล้ว
ถ้าไปทำเป็นโมดูลแยก จะกลายเป็นความผิดเดิมที่ `cross-department-requests-plan` เพิ่งแก้
(สอบถาม RD กับ ขอราคาวัสดุ เป็นคนละคิวทั้งที่เป็นเรื่องเดียวกัน)

**ขนาด** 1 PR เล็ก + migration 1 ใบ (DROP CHECK)
**⚠️ ขึ้นกับ R-1** — เพิ่มฝ่าย FN โดยไม่แก้ด่านก่อน = FN ยังเปิดเมนูไม่ได้อยู่ดี

### R-3 ⭐ สามตระกูล ไม่ใช่แปดหัวข้อแบน

**ปัญหา** ผู้ใช้พูดเองว่า *"ทั้งขอข้อมูล ขอเอกสาร ขอราคา"* = คิดเป็น **ตระกูล**
แต่ฟอร์มให้เลือกจาก dropdown แบน 8 ตัว และกำลังจะเพิ่มอีก (invoice · งานบริการ · ของเข้า)

**เสนอ** เพิ่มธง `family` บนทะเบียนหัวข้อ แล้วฟอร์มถาม **ฝ่าย → ตระกูล → หัวข้อ**

| ตระกูล | หัวข้อที่มี | สิ่งที่ต่างกันจริง |
|---|---|---|
| `ask` ขอข้อมูล | สอบถามข้อมูล · ติดตามของเข้า | จบด้วย**คำตอบในเธรด** |
| `doc` ขอเอกสาร | ขอเอกสาร · *(ขอใบแจ้งหนี้)* | จบด้วย**ไฟล์หรือเลขที่เอกสาร** |
| `price` ขอราคา | F · FB · PM | จบด้วย**ราคาเข้าทะเบียนวัสดุ** |
| `work` ขอให้ทำของ | บรีฟกลิ่น · Mock-up | จบด้วย**ของเข้าทะเบียน + รอบแก้** |

⚠️ **ไม่ใช่การแยกหน้า** — ยึดมติเดิมข้อ 4: *"สิ่งที่ทำให้แต่ละหัวข้อต่างกันจริงคือผลลัพธ์
ไม่ใช่หน้าตา"* ⇒ หน้ารายละเอียดหน้าเดียว เนื้อสลับตามหัวข้อ

⭐ ตระกูลยังเป็น**ตัวกรองบนคิว**ได้ฟรี ซึ่งเป็นของที่ R-4 ต้องใช้พอดี

**ขนาด** 1 PR เล็ก · โค้ดล้วน ไม่มี migration

### R-4 ⭐ แท็บ = มุมมองของคน · หัวข้อ = ตัวกรอง

**ปัญหา** แท็บวันนี้คือ `queue-RD` / `queue-PC` / `mine` และกรองด้วย
`REQUEST_OPEN_STATUSES` เท่านั้น ⇒
- **RD/PC มองย้อนหลังไม่ได้เลย** — ปิดเรื่องแล้วหายจากจอ ไม่มีทางกลับไปดู

### R-5 🔴 ปิดรูรั่ว `ON DELETE SET NULL` ก่อนข้อมูลจริงเข้า

**ปัญหา** พิสูจน์แล้วในข้อ 1 — ลบทะเบียนแล้วลิงก์บนคำร้องและบนราคาหายเงียบ
ไม่มี error ไม่มี warning และ audit log ที่เขียนว่า "ผูกกลิ่นในทะเบียน" กลายเป็นคำโกหก

**เสนอ** ตัดสินทีละตาราง **ไม่เหมารวม** เพราะความหมายไม่เหมือนกัน

| ที่ | เสนอ | เหตุผล |
|---|---|---|
| `dept_requests.scentId/formulaId` | `RESTRICT` เมื่อคำร้อง `closed` | ปิดเรื่องแล้ว = หลักฐานว่าราคานั้นของกลิ่นไหน |
| `material_prices.scentId/formulaId` | `RESTRICT` | ทะเบียนราคาไม่มีความหมายถ้าไม่รู้ว่าราคาของอะไร |
| `products.scentId/formulaId` | คง `SET NULL` | สินค้ามีตัวตนของตัวเอง กลิ่นเปลี่ยนได้ |

⚠️ `RESTRICT` แล้วปุ่มลบสูงสุดของ admin ต้องขึ้น `blocked` **ตั้งแต่พรีวิว** ไม่ใช่ไปตายตอนกด
— มาตรฐานนี้เขียนไว้แล้วใน `admin-force-delete-standard` ต้องต่อให้ครบ

🪤 `material_prices_identity_uk` ยังยึด `formulaCode` (text) อยู่ (`0171:145` เขียนเตือนไว้เอง)
⇒ **ตัวตนของราคาเป็น text ส่วน pointer เป็น id — สองตัวนี้ยังไม่รวมร่างกัน** ข้อนี้ค้างมาจาก
PR-5 ของแผนเดิมและยังไม่ได้ทำ

**ขนาด** 1 PR เล็ก + migration 1 ใบ
**⚠️ ควรทำก่อน R-6** — ยิ่งมีข้อมูลจริงมาก ยิ่งแก้ FK ยาก
