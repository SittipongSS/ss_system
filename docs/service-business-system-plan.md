## 0. ทำไมต้องทำ — ตัวเลขจากชีตที่ทีมใช้อยู่จริง

ในไฟล์ Excel มีชีต `ตรวจสอบ Service vs สัญญา` ที่เจ้าของไฟล์เขียนสูตรเอาสองโลกมาชนกัน แล้วได้ผลนี้:

| ผลตรวจ | จำนวน |
|---|---|
| ✅ สอดคล้อง | **42 / 166 = 25.3%** |
| ❌ ไม่พบลูกค้าในสัญญา | 62 |
| ⚠️ รหัสสินค้าไม่ตรง | 37 |
| 🔴 **สัญญาไม่มีผลแล้ว แต่ยังจัดคิวเข้าไป** | **25** |
| 🔴 **สัญญายังมีผล แต่ไม่มีคิวบริการเลย** | **102 จุด / 42 ลูกค้า** |

> **อ่านสองบรรทัดสุดท้ายรวมกัน:** วันนี้บริษัทส่งช่างไปที่ที่หมดสัญญา 25 จุด **และ** ไม่ได้ไปที่ที่จ่ายเงินแล้ว 102 จุด — พร้อมกัน

เพราะ **ตารางช่างกับทะเบียนสัญญาไม่มีอะไรเชื่อมกันเลย นอกจากคนที่จำได้**

⇒ "ไม่จ่ายห้ามออกไปให้บริการ" จึงต้องเป็น**ด่านในระบบ ไม่ใช่วินัยของคน**

### ตัวเลขประกอบ (ชีต Dashboard · ณ 2026-07-31)

- 380 จุดติดตั้ง · 148 ลูกค้า · มูลค่าสัญญารวม 24.6 ล้าน
- อยู่ระหว่างให้บริการ 135 · ใกล้หมด 47 · **หมดสัญญา 196** · ไม่ระบุวันที่ 2
- **Renewal rate ระดับลูกค้า 20.4% · ระดับจุดติดตั้ง 12.2%** · มูลค่าที่หลุดไปแล้ว 6.9 ล้าน

### 🔴 หลักฐานที่ชัดที่สุดว่าทำไมต้องเป็น DB ไม่ใช่ชีต

ชีต `ติดตามลูกค้าไม่ต่อสัญญา` มี 172 แถว มีคอลัมน์ ผู้รับผิดชอบ / สถานะติดตาม / วันที่ติดต่อล่าสุด / ผลลัพธ์ / วันนัดถัดไป

**คอลัมน์ "สถานะติดตาม" = "ยังไม่ติดต่อ" ทุกแถว**

ไม่ใช่เพราะไม่มีใครทำ — แต่เพราะชีตนี้ถูก generate ใหม่จากสูตรทุกครั้ง **สิ่งที่ SA พิมพ์ลงไปหายทุกรอบ** นี่คือของที่ต้องลง DB ก่อนอย่างอื่น

## 2. ⭐ ข้อค้นพบที่เปลี่ยนรูปโมเดล — สัญญา : ไซต์ = 1 : N

ในชีตหลัก **มูลค่าสัญญาอยู่ที่แถวแรกของกลุ่มเท่านั้น แถวที่เหลือเป็น 0**:

| ลูกค้า | รูปแบบจริง |
|---|---|
| เคพี อาร์ท เซ็นเตอร์ | `600,912` ครอบ 6 ห้องโถง · แล้ว `30,816` + `30,816` แยกอีก 2 ห้องน้ำ = **3 สัญญา 9 จุด** |
| มัลตี้ บิวตี้ | `480,601` ใบเดียวครอบ **4 สาขา** |
| Mali Clinic | `57,408` ที่สีลม · พิจิตร = `0` |

⇒ **งวดจ่ายต้องแขวนที่ "สัญญา" ไม่ใช่ที่ "ไซต์"**
⇒ ด่าน "ไม่จ่ายไม่เข้า" บล็อกทีเดียว **ทั้งกลุ่มไซต์ใต้สัญญานั้น**
⇒ ถ้าออกแบบเป็น 1 ไซต์ = 1 สัญญา จะได้มูลค่าซ้ำ 380 ใบทันที (Dashboard เองก็บวก 24.6M จากคอลัมน์ที่เป็น 0 เกินครึ่ง — ตัวเลขนั้นเชื่อไม่ได้อยู่แล้ว)

## 3. เทียบกับของที่มีอยู่จริงในระบบ

### มีแล้วและใช้ได้ (mig 0187–0188)

`service_sites` · `service_assets` · `service_plans` · `service_visits` · `service_visit_items`
หน้า `/service` · `/service/schedule` · `/service/sites` · `/service/my-visits` · ปิดงาน + ลายเซ็นลูกค้า

`service_visits.kind` = `install / refill / maintenance / repair / inspect / remove`
⇒ **ครบทั้ง 4 อย่างที่ผู้ใช้ระบุ** (เช็คพื้นที่=`inspect` · ติดตั้ง=`install` · เซอร์วิส=`refill`/`maintenance` · ซ่อม=`repair`) — ส่วนนี้ไม่ต้องแตะ

### 🔴 ไม่มีเลย 4 ก้อน

| ก้อน | สถานะวันนี้ |
|---|---|
| **สัญญาบริการ** | ไม่มีตาราง ไม่มีวันเริ่ม/หมด ไม่มีสถานะ ไม่มีต่อสัญญา · `service_plans.salesOrderId` เป็นช่องหลอก (ไม่มี FK ไม่มี UI) |
| **รอบจ่าย / สถานะการเงิน** | ไม่มี migration ที่เกี่ยวกับ billing/payment เลยทั้งระบบ ⇒ ด่านยังไม่มีที่ยืน |
| **แจ้งเตือนสัญญาใกล้หมด → SA** | มีตาราง `notifications` (0185) แต่ไม่มีต้นทางฝั่งสัญญา · ⚠️ Google Chat **ถูกถอดออกทั้งระบบแล้ว** (mig 0236 · 2026-08-12) กระดิ่งในแอปคือช่องทางเดียว |
| **Win-back** | ไม่มี |

### ⚠️ มีแต่รูปไม่ตรงของจริง 3 จุด

1. **`service_plans.everyDays` = "ทุก N วัน" แต่ของจริงคือ "วันที่ X ของเดือน"**
   หมายเหตุในตารางช่างเขียนชัด: `📅 วันที่ 17/เดือน` (8 ไซต์) · `📅 วันที่ 1-5/เดือน` (7) · `📅 วันที่ 3/เดือน` (3)
   ⇒ gen ด้วย `everyDays=30` จะ **เลื่อนสะสมเดือนละ 1-2 วัน** แล้วหลุดข้อผูกมัดกับห้างภายในไม่กี่รอบ โดยไม่มีใครเห็นว่าเลื่อน
2. **ไม่มีหน่วยวัดภาระงาน** — ตารางช่างนับเป็น **Package** (`Pkg STD` · `Pkg SM` = 0.5 STD · `Reed`) และหัวทุกวันมี `รวมวันนี้: 19.5 Package` = เพดานงานต่อวัน · schema มีแต่ `startTime/endTime` ซึ่งของจริงแทบไม่กรอก
3. **มอบหมายเป็นทีมหลายคนต่อนัด** — `Ta, Ice, Fluke` โผล่ 22 ครั้งจาก 167 · `assigneeId` + `assistantIds` รองรับได้แล้ว แต่ UI ยังไม่มี
   🐞 และ **prod ยังไม่มีบัญชีฝ่าย TS สักคน** ทั้งที่ช่างจริงมี 3 คน (ต้า · ฟลุ๊ค · ไอซ์)

## 4. ⭐ คำร้องขอเอกสารการเงิน — ไม่ต้องสร้างโมดูลใหม่

ระบบมี **`dept_requests`** (mig 0173) ที่แปลว่า "ขอให้ฝ่ายอื่นทำอะไรให้" ครบทุกชิ้นที่ต้องใช้:

| ต้องการ | มีแล้วใน `dept_requests` |
|---|---|
| ร่าง → ส่ง → บัญชีรับเรื่อง → ตอบ → ปิด | `draft → pending → acknowledged → answered → closed / cancelled` |
| เลขที่เอกสาร | `docNo` — **ออกตอนกดส่ง ไม่ใช่ตอนร่าง** (ร่างที่ทิ้งไม่กินเลข) |
| บัญชีส่งไฟล์ IV กลับ | เธรดกลาง + ไฟล์แนบ ต่อครบแล้ว |
| คิวของฝ่าย | `dept_requests_queue_idx (dept, status, "submittedAt")` |
| ผูกดีล / โครงการ / ลูกค้า | `dealId` · `projectId` · `customerId` |
| **เพิ่มชนิดใหม่** | ประกาศใน `lib/master/requestTypes.js` — **โค้ดล้วน ไม่ต้อง migration** |

⇒ เพิ่มชนิด **`billing_doc`** (`dept: 'FN'`)

🔴 **กำแพงเดียว**: `dept_requests.dept` มี `CHECK (dept IN ('RD','PC'))` (`0158:31`) — ต้องผ่อนรับ `FN`

### ข้อความที่ใช้จริงวันนี้ → ฟอร์ม

ตัวอย่างที่ทีมส่งกันในแชท:

```
ลูกค้า : เซนท์ สตูดิโอ (Scent Studio)
แบรนด์ : Scent Studio
AE: Fluke
AC: Gale
- ขอใบวางบิล 50 % ก่อนผลิต ออกใบกำกับภาษี (เป็นบรรจุภัณฑ์)
ใบเสนอราคา :  Q#260731-0006
ยอดเต็ม =  181,016.25 บาท
ยอด 50 % ก่อนผลิต = 90,508.125 บาท
```

| ในข้อความ | ลงช่องไหน |
|---|---|
| ลูกค้า / แบรนด์ | `customerId` ✅ มีแล้ว |
| `AE: Fluke` | เจ้าของดีล — **ดึงจากดีล ไม่ให้พิมพ์** |
| `AC: Gale` | Account Coordinate **ฝ่ายขาย** — ดึงจากดีล/ลูกค้า ไม่ให้พิมพ์ |
| `ขอใบวางบิล … ออกใบกำกับภาษี` | 🆕 `docKinds[]` ติ๊กหลายอัน (ใบวางบิล · ใบแจ้งหนี้ · ใบกำกับภาษี · ใบเสร็จ) |
| `(เป็นบรรจุภัณฑ์)` | `body` ✅ |
| `ใบเสนอราคา Q#260731-0006` | 🆕 `quotationId` — **ต้องเป็น id ไม่ใช่ข้อความ** |
| `ยอดเต็ม 181,016.25` | ไม่ต้องพิมพ์ — อ่านจากใบเสนอราคา |
| `ยอด 50% = 90,508.125` | 🆕 กรอก `%` หรือจำนวนเงิน แล้วระบบคูณให้ |

> ⚠️ **`AC` ในข้อความไม่ใช่ฝ่ายบัญชี** — `permissions.js:160` `ROLE_LABELS.ac = 'Account Coordinate'` เป็น role ในฝ่ายขาย และอยู่ใน `TEAM_ROLES` ด้วย
> ผู้รับเรื่องฝั่งบัญชีคือคนที่กด "รับเรื่อง" ในคิว `FN` ซึ่งยังไม่ปรากฏในข้อความเลย

### 🔴 ข้อสังเกตที่เปลี่ยนขอบเขต

**ตัวอย่างข้างบนเป็นงานบรรจุภัณฑ์ = สายสินค้า ไม่ใช่งานบริการ**

⇒ คำร้องขอเอกสารการเงินต้องอยู่ **นอกโมดูลบริการตั้งแต่วันแรก** (ตรงกับที่ผู้ใช้ยืนยันว่า *"ระบบนี้ได้ใช้ในส่วนขายแน่นอน"*) — ถ้าไปสร้างไว้ใต้ `/service` จะต้องรื้อภายในเดือนเดียว

⇒ และ **งวดจ่าย ↔ คำขอ IV ผูกกันได้แต่ไม่บังคับ** (`installment.billingRequestId` nullable) เพราะ *"บางทีขอ บางทีไม่ขอ"*

## 5. รอบจ่าย — หนึ่งงวด สองลายเซ็น

> **มติผู้ใช้ 2026-08-01:** *"SA ต้องกดว่าลูกค้าจ่ายแล้ว บัญชีต้องคอนเฟิร์ม"*

```
งวด:  pending ──[SA/AC กด "ลูกค้าจ่ายแล้ว" + แนบหลักฐาน]──> reported
                     ↑                                        │
                     └────[บัญชีตีกลับ + เหตุผล]───────────────┤
                                                              ↓
                                            [บัญชีคอนเฟิร์ม] confirmed ✅ ปลดด่าน
```

```
service_contract_installments
  seq · dueDate · amount · billingRequestId (null ได้)
  status: pending | reported | confirmed | rejected
  reportedById/Name/At  + evidence[]   ← SA / AC
  confirmedById/Name/At                ← FN
  rejectedReason                       ← FN
```

⚠️ **`reported` ห้ามปลดด่าน — ปลดเมื่อ `confirmed` เท่านั้น**
ไม่งั้น SA แจ้งเองปลดเองครบวงจร = เท่ากับไม่มีด่าน

### รอบจ่ายมาจากสัญญา

`billingCycle: monthly | quarterly | yearly | custom` + `startDate` + `termMonths` → gen งวดตอนสร้างสัญญา **แล้วแก้รายงวดได้เสมอ**

เพราะของจริงในชีตมี **29 รูปแบบที่พิมพ์มือ** รวมของที่ไม่ใช่รอบสม่ำเสมอเลย:
`แบ่งชำระ 30% ก่อนติดตั้ง / ชำระ 70% หลังติดตั้ง` · `ชำระ50%แรก 50%หลังจ่ายรายเดือน 3500บาท/เดือน 6เดือน`
และคำสะกดผิดซ้ำ (`แบ่งชำะ 2 งวด 50%`) กับของที่ควรเป็นสถานะไม่ใช่เงื่อนไข (`ชำระครบแล้ว 100%`)

⇒ **ต้องยุบเหลือ ~6 รูปแบบ + จำนวนงวด ก่อน import**

### ⚠️ ในระบบวันนี้ SO ยังไม่มีขั้นบัญชี

ผู้ใช้เทียบกับ *"SO ที่หลังอนุมัติแล้วต้องมีบัญชีกดด้วย"* — ตรวจแล้วในโค้ด `sales_orders.status` มีแค่
`draft → pending_approval → approved / rejected / cancelled` (`0107:13`)
แล้ววิ่งเข้า handoff queue ของ **LG (ยื่นภาษี)** ไม่ใช่บัญชี (`lib/sales/handoffQueue.js:38`)

⇒ **ขั้นบัญชีที่ผู้ใช้อธิบายเป็นกระบวนการจริงที่ยังไม่เคยลงระบบ** แผนนี้จะเป็นที่แรก · ถ้าใช้ได้ดี ค่อยพิจารณาย้อนไปใส่ให้ SO ทีหลัง (นอกขอบเขตแผนนี้)

| สถานะ | ความหมาย |
|---|---|
| `draft` | ใครก็สร้างได้ทุกเมื่อ · เห็นในรายการ "รอเข้าคิว" · **ไม่ขึ้นตารางจริง ไม่นับใน "งานของฉัน" ไม่นับภาระรายวัน** |
| `scheduled` | เข้าคิวจริง ขึ้นตาราง |

### เช็คลิสต์ `draft → scheduled`

| # | เงื่อนไข | ใครแก้ได้ | มาจากไหน |
|---|---|---|---|
| 1 | ไซต์ผูกสัญญาที่ **ยังมีผล ณ วันนัด** | SA | 25 จุดที่เข้าไปทั้งที่หมดสัญญา |
| 2 | **ไม่มีงวดเลยกำหนดที่ยังไม่ `confirmed`** | SA → FN | ข้อที่ผู้ใช้ขอ |
| 3 | มีช่างผู้รับผิดชอบ | TS | prod วันนี้ `assigneeId = null` ทุกใบ |
| 4 | วันนัดอยู่ในช่วงที่ไซต์ยอมให้เข้า | TS | `accessDays` / `accessFrom-To` มีแล้วใน `0187` |

ข้อ 1–2 = ด่านเงิน/สัญญา · ข้อ 3–4 = ด่านความพร้อมงาน

### ข้อบังคับ 3 ข้อของด่านนี้

1. **แสดงเป็นรายการติ๊กพร้อมชื่อคนที่แก้ได้ ไม่ใช่ปุ่มเทา** — ติดเงินให้มีปุ่ม "แจ้ง SA" ตรงนั้น · ติดช่างให้เลือกช่างตรงนั้น
   (บทเรียน [[supabase-masked-query-errors]] + หน้าอัปโหลดที่ผู้ใช้เห็นแค่ "ไม่สำเร็จ" ตลอด — ด่านที่ไม่บอกเหตุผลคือด่านที่คนหาทางอ้อม)
2. **ข้ามได้โดยหัวหน้า พร้อมเหตุผลบังคับ + ลงบันทึก** — ของจริงมี 25 จุดที่วิ่งอยู่ตอนนี้ ถ้าบล็อกแข็งวันแรก งานหยุดทันที
3. **บล็อกระดับสัญญา ไม่ใช่ระดับลูกค้า** — ลูกค้ารายเดียวมีหลายสัญญาเป็นเรื่องปกติ (เคพี อาร์ท 3 สัญญา 9 จุด) ค้างใบหนึ่งไม่ควรหยุดอีกใบ

### นิยาม "เลยกำหนด"

เลย `dueDate` แล้ว **และ** สถานะยังไม่ `confirmed` — **ไม่มี grace period**
(`reported` ที่บัญชียังไม่กดยืนยัน = ยังนับว่าค้าง ตามข้อบังคับใน §5)

## 7. โครงตาราง

```
deal (Won)
   └─ project (SERVICE)
        ├─→ production_jobs.projectId          ← มีแล้ว (สายบริการก็ผลิต)
        └─→ service_sites.projectId            ← ยังไม่มี (#868 §4)
              ├─ service_assets
              ├─ service_plans ──→ service_visits ──[ด่าน §6]
              └─ service_contract_sites ─┐
                                          ↓
                              🆕 service_contracts
                                    ├─ ownerId (SA)  · วันเริ่ม/หมด · สถานะ · ต่อ/ไม่ต่อ
                                    └─ 🆕 service_contract_installments
                                            └─ billingRequestId ──→ dept_requests (kind='billing_doc', dept='FN')
                                                                         ↑ ใช้ร่วมกับสายขายสินค้า
```

**`service_contract_sites` เป็น M:N** — ไซต์หนึ่งอาจถูกครอบด้วยสัญญาต่ออายุหลายใบตามช่วงเวลา และสัญญาหนึ่งครอบหลายไซต์ (§2)

| # | มติ |

| 3 | **งวดจ่าย 2 ลายเซ็น** — SA/AC แจ้ง + แนบหลักฐาน → FN คอนเฟิร์ม · `reported` ไม่ปลดด่าน |

| 6 | **สัญญา : ไซต์ = 1 : N** — งวดจ่ายแขวนที่สัญญา |
| 7 | บล็อก**ระดับสัญญา** · เลยกำหนด = เลย `dueDate` และยังไม่ `confirmed` ไม่มี grace |
