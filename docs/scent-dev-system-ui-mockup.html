พัฒนากลิ่น — ทั้งระบบของ SA และ RD

ฝ่ายขายทำงานที่ บริหารงานขาย · ฝ่ายวิจัยและพัฒนาทำงานที่ วิจัยและพัฒนา · ฐานข้อมูล เป็นศูนย์รวมข้อมูลของทุกระบบที่ทุกฝ่ายเข้าถึงได้แต่จำกัดสิทธิ์ — ใบนี้วาดว่าแต่ละฝ่ายเปิดระบบของตัวเองมาเจออะไร กดต่อไปไหน และ flow พัฒนากลิ่นวิ่งผ่านตรงไหน

SA ระบบบริหารงานขาย RD ระบบวิจัยและพัฒนา DB ฐานข้อมูล (ของกลาง) เสนอใหม่ ยังไม่มีในโค้ดวันนี้

00แผนที่ — ใครทำอะไร ที่ระบบไหน

สายเดียว 7 ก้าว ข้ามสองระบบสามครั้ง · ทุกครั้งที่ข้าม ใบยังเป็นใบเดิม — เปลี่ยนแค่ว่าใครเป็นคนเห็นปุ่ม

SA บริหารงานขาย

  1. เปิดคำร้อง จาก SO ที่อนุมัติแล้ว + กรอก PDR + วันที่คาดหวัง
  2. รอ RD — เห็นในคิว "รอฝ่ายตอบ"
  3. รับกลิ่น + วันที่ได้รับ
  4. ส่งให้ลูกค้า + วันที่จัดส่ง
  5. บันทึกคำตอบลูกค้า — คอนเฟิร์ม หรือ ขอให้แก้
  6. เห็นราคาที่ RD ใส่ (ม-41)

RD วิจัยและพัฒนา

  1. รับเรื่อง + ระบุวันกำหนดส่ง บังคับ · หรือ ตีกลับ
  2. รอหัวหน้าฝ่ายขายยืนยัน ยืนยันแล้ว 2026-08-08
  3. ส่งกลิ่น — สร้างแถวเองทีละ direction พร้อมรหัส ชื่อ วันที่ผลิต วันที่พร้อมส่ง
  4. ตอบคำถามในเธรด · เลื่อนกำหนดได้
  5. ใส่ราคา หลังลูกค้าคอนเฟิร์ม

DB ฐานข้อมูล

  1. ทะเบียนกลิ่น รับกลิ่นอัตโนมัติตอน RD กดส่ง (briefId + dealId + producedAt)
  2. รอบแก้ = กลิ่นตัวใหม่ ชี้กลับตัวเดิม (derivedFromScentId)
  3. ทะเบียนวัสดุ รับราคา RM_F ตอน RD ใส่ราคา
  4. เพิ่มตรงจากทะเบียน = กลิ่นเก่าที่เคยออกแบบแล้ว — ไม่มี briefId
กฎที่แบบนี้ยึด — คิวแยกตามฝ่าย แต่ ใบเป็นจอเดียว (ม-31) · /requests/[id] ไม่แยกตามฝ่าย มีแค่ปุ่มที่ย้ายตามคนดู · แยกใบเมื่อไรก็ได้สองก้อนที่เพี้ยนหากันในสามเดือน

การ์ดอยู่บนสุดของคอลัมน์ — สำหรับใบที่ขายบริการออกแบบกลิ่น นี่คือก้าวถัดไป ทันทีหลังอนุมัติ ยังไม่ใช่เรื่องของเข้า/แผนผลิต · ซ่อนทั้งการ์ดเมื่อใบไม่ใช่งานออกแบบกลิ่น — ใบขายสินค้าธรรมดาไม่ควรเห็นการ์ด ที่บอกว่า "เปิดไม่ได้" ตลอดไป นั่นคือ noise ไม่ใช่ข้อมูล
สามสถานะที่การ์ดต้องพูดต่างกัน — ตัดสินด้วย scentDesignOrderError() ตัวเดียวกับที่ API ใช้ ปุ่มกับ server จึงขัดกันไม่ได้
  • เปิดได้ — ปุ่ม accent พาไป /requests/new?kind=scent_dev&salesOrderId=…&returnTo=…
  • เปิดไปแล้ว — ขึ้นเลขที่ใบ + ปุ่มเงียบ "เปิดคำร้อง" พาไปใบนั้น (1 SO : 1 PDR · ม-37)
  • ยังเปิดไม่ได้ — ใบยังไม่ approved หรืออ่านจำนวนกลิ่นไม่ออก ⇒ ขึ้นเหตุผลเป็นข้อความ ไม่มีปุ่มจาง ปุ่มจางไม่บอกว่าต้องทำอะไรต่อ
ใบที่เปิดไปแล้วต้องถามด้วย service-role — ทะเบียนคำร้องมีขอบเขตของตัวเอง (ผู้ขอเห็นเฉพาะของตัวเอง) ⇒ ถามผ่านทางนั้นจะได้ "ไม่มีใบ" ทั้งที่เพื่อนร่วมทีม เปิดไปแล้ว แล้วปุ่มจะโชว์ให้กดจนไปตายที่ unique index ของ DB · คืนออกไปแค่ id / docNo / status

วันที่ SA รับของ dept_request_items.pickedUpAt มีแล้ว SA ช่วงที่ของค้างอยู่ที่ RD กับค้างอยู่ที่ SA เป็นคนละปัญหา (ม-50)
วันที่ส่งลูกค้า dept_request_items.sentAt มีแล้ว
scents.sentAt แก้ความหมาย		 SA ลูกค้าได้รับเมื่อไร · ทะเบียนกลิ่นแสดง ครั้งล่าสุด — ป้ายเดิมถูกอยู่แล้ว ผิดแค่ค่าที่เขียนลงไป
ปุ่ม "ส่งกลิ่น" ในทะเบียนอยู่ต่อ — RD ใช้มา 29 ครั้งบนของจริง · มันคือทางบันทึกวันส่งของกลิ่นที่ ไม่ได้มาจากคำร้อง (กลิ่นเก่า) · หลังแยกช่องแล้ว ปุ่มนี้เขียน scents.sentAt ตามป้ายเดิมเป๊ะ ๆ ส่วนกลิ่นที่มาจากคำร้องจะได้ sentAt จาก items.sentAt ตอน SA กดส่งลูกค้า
migration ที่ต้องรัน0224_scent_produced_at.sql
BEGIN;

-- วันที่ RD ผลิตกลิ่นตัวนี้เสร็จ — คนละวันกับวันพร้อมส่งและวันส่งลูกค้า
-- ไม่มี CHECK เรียงวัน: RD บันทึกย้อนหลังเป็นปกติ (เหตุผลเดียวกับ 0205)
ALTER TABLE public.scents
  ADD COLUMN IF NOT EXISTS "producedAt"     date,
  ADD COLUMN IF NOT EXISTS "producedById"   text,
  ADD COLUMN IF NOT EXISTS "producedByName" text;

-- แถวเดิมมีวันเดียว ซึ่งความหมายจริงคือ "วันที่ RD ส่งมอบ" ไม่ใช่วันที่ลูกค้าได้รับ
-- ⇒ ยกไปเป็นวันผลิต (ใกล้ความจริงที่สุดที่มี) แล้ว **เว้น sentAt ไว้เท่าเดิม**
-- ไม่ล้างทิ้ง เพราะกลิ่นเก่าที่ RD กดปุ่ม "ส่งกลิ่น" เองคือวันส่งลูกค้าจริง
UPDATE public.scents
   SET "producedAt" = "sentAt"
 WHERE "producedAt" IS NULL AND "sentAt" IS NOT NULL;

COMMIT;
