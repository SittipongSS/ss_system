# เพดาน 1,000 แถวของ PostgREST — ก่อนเขียน query ที่อ่านหลายแถว

> สถานะ: **กำลังดำเนินการ** · ตรวจกับโค้ดเมื่อ 2026-08-16 · แก้จุดที่คืนข้อมูลไม่ครบจริงแล้ว 3 จุด · เหลือหนี้ในเพดาน ratchet 180 จุด

## กฎ

**อ่านหลายแถวจากตารางที่โตตามการใช้งาน = ต้องมีเพดาน** — ใช้ `fetchAll` / `fetchAllResult`
จาก [`lib/supabaseFetchAll.js`](../webapp/src/lib/supabaseFetchAll.js) หรือใส่ `.range()` / `.limit()` เอง

```js
import { fetchAllResult } from '@/lib/supabaseFetchAll';

const { data, error } = await fetchAllResult(() => supabase
  .from('project_tasks').select('*')
  .order('stepOrder', { ascending: true })
  .order('id', { ascending: true }));   // ← ลำดับต้องนิ่ง
```

ด่าน `npm run check:rowcap` กันของใหม่ให้แล้ว (เพดานต่อตาราง ขึ้นไม่ได้ ลงได้อย่างเดียว)

## ทำไม

โปรเจกต์ตั้ง Supabase → Settings → API → **Max rows = 1000**

PostgREST ตัดผลลัพธ์ที่ 1,000 แถว **โดยไม่มี error** — โค้ดได้ array ที่สั้นกว่าความจริง
แล้วเดินต่อเหมือนไม่มีอะไรเกิดขึ้น ไม่มี log ไม่มีสัญญาณอะไรทั้งสิ้น

**นี่ไม่ใช่ความเสี่ยงเชิงทฤษฎี — มันเกิดขึ้นแล้ว** (พบตอนตรวจระบบ 2026-08-16):

| ตาราง | แถวจริง | อาการ |
|---|---:|---|
| `project_tasks` | 2,820 | คิวงานโครงการของผู้ดูแลเห็นแค่ 1,000 — และหาย **เป็นระบบ** เพราะเรียงด้วย `stepOrder` ⇒ ขั้นท้าย ๆ ของทุกโครงการหายก่อน |
| `notifications` | 1,194 | ไม่กระทบ (ทุก query กรอง `userId` + มี cursor อยู่แล้ว) |
| `personal_tasks` | 1,045 | ตัวเลข KPI ที่ใช้วัดผลคนคิดจากงานไม่ครบ |

ที่แก้ไปแล้ว: [`api/pm/project-tasks`](../webapp/src/app/api/pm/project-tasks/route.js) ·
[`api/pm/my-work`](../webapp/src/app/api/pm/my-work/route.js) ·
[`lib/pm/taskKpi.js`](../webapp/src/lib/pm/taskKpi.js)

ยืนยันกับฐานจริงหลังแก้: `project_tasks` 1000 → **2,820** (ไม่มี id ซ้ำ) · `personal_tasks` 1000 → **1,045**

## กับดักที่ต้องรู้

**⚠️ ต้องมี `.order()` ที่ให้ลำดับนิ่งเสมอ** — PostgREST ไม่การันตีลำดับถ้าไม่สั่ง
และคอลัมน์ที่ค่าซ้ำกันได้ (`stepOrder` · `createdAt`) ก็ยังไม่พอ ต้องพ่วง `id` ปิดท้าย

ลำดับไม่นิ่ง + ไล่ทีละหน้า = **ได้แถวซ้ำและแถวหายพร้อมกัน** ซึ่งแย่กว่าถูกตัด
เพราะจำนวนแถวดูเหมือนครบ

**⚠️ `fetchAll` รับ "ฟังก์ชันที่สร้าง query" ไม่ใช่ตัว query** — builder ของ supabase-js
ยิงซ้ำไม่ได้ ส่งฟังก์ชันมาเพื่อให้ทุกหน้าได้ builder ใหม่

**⚠️ หน้าเต็มพอดีแยกจาก "ยังมีต่อ" ไม่ได้** — ตารางที่มี 1,000 แถวพอดีจะยิง 2 ครั้ง
ครั้งที่สองได้ 0 แถว นั่นคือพฤติกรรมที่ถูก ไม่ใช่คำขอเสียเปล่า

## หนี้ที่เหลือ

`npm run check:rowcap` ตั้งเพดานไว้ที่ **169 จุด** (ณ 2026-08-16) — ส่วนใหญ่กรองด้วย
`projectId`/`dealId` ของใบเดียวซึ่งไม่มีทางแตะพันแถว จึงไม่ใช่บั๊กวันนี้ แต่เป็นกับดัก
ที่รอวันตารางโต

**เพดานขึ้นไม่ได้** — จะเพิ่มจุดใหม่ ต้องยกจุดเก่ามาแก้ให้เพดานพอดีเท่าเดิม
ตารางที่ควรรูดลงก่อนคือสามตัวที่เกิน 1,000 ไปแล้ว

## ทางเลือกที่ **ไม่** เลือก

ขึ้นค่า Max rows ใน Supabase ให้สูง ๆ — แก้เร็วแต่ไม่ใช่ทางแก้: ปัญหากลับมาเมื่อข้อมูล
โตข้ามเพดานใหม่ และระหว่างนั้น payload ใหญ่ขึ้นทุกหน้าโดยไม่มีใครตั้งใจ
