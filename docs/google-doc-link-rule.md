# ผูกเอกสาร Google (Doc/Sheet) เข้าระเบียน — กติกาผูก + สมุดสิทธิ์บน Drive

> สถานะ: **รอตรวจ** · ตรวจกับโค้ดเมื่อ 2026-10-08 · แบรนช์ `claude/google-link-rule` · มติเจ้าของ 08/10/2569 · ไม่มี migration · ไม่มีตัวแปร env · **ไม่มีสวิตช์ผ่อนด่าน** · 🔴 พฤติกรรมฝั่ง Drive พิสูจน์ด้วยตัวปลอมในเทสต์เท่านั้น (Drive จริงเรียกได้เฉพาะบน Vercel) — ต้องเดิน §เช็กลิสต์หลังขึ้น production และเฝ้า log ใน §สิ่งที่ลองก่อนขึ้นระบบไม่ได้

**อ่านก่อนแตะ `buildGoogleAttachment` · `ensureGoogleDocAccess` · `revokeAttachmentGrants` หรือเพิ่มคีย์ใหม่ใน `metadata` ของแถวเอกสาร Google**

## มติเจ้าของ (08/10/2569)

| เรื่อง | มติ |
|---|---|
| ผูกอะไรได้ | เฉพาะ **Google Doc / Google Sheet ที่คนผูกเปิดได้อยู่แล้ว** บน Drive |
| คนผูกได้สิทธิ์เพิ่มไหม | **ไม่ได้** — ระบบไม่ให้สิทธิ์อะไรเพิ่มแก่คนผูก |
| คนที่เห็นระเบียน | **ยังได้สิทธิ์เปิดเอกสารที่ผูกไว้ต่อไป** — แม้คนผูกจะหลุดสิทธิ์หรือลาออกไปแล้ว |

โหมด "สร้าง Doc/Sheet ใหม่" ไม่เปลี่ยนกติกา: ไฟล์เป็นของระบบ ใครแก้ระเบียนได้ก็แก้เอกสารได้

## ช่องเดิม

- **ผูก id อะไรก็ได้ แล้วได้ writer** — เดิมแกะ id จากลิงก์ → อ่าน metadata ด้วย service account → `grantWriter` ให้คนกด ⇒ ใครแนบไฟล์เข้าระเบียนของตัวเองได้ วางลิงก์ของไฟล์ไหนก็ได้ที่ service account มองเห็น (เอกสารของดีลอื่น · ไฟล์แนบ · **แม้แต่โฟลเดอร์** ซึ่งสิทธิ์ไหลลงทุกไฟล์ข้างใน) แล้วได้สิทธิ์ **แก้** ทันที · service account เห็นทั้ง Shared Drive ⇒ "ระบบอ่านได้" ไม่ใช่หลักฐานว่าคนกดเปิดได้
- **คนดูถูกยก/ลดสิทธิ์** — ตอนเปิดรายการไฟล์แนบ `grantFileRole` เขียนทับ role เดิมได้ทั้งสองทาง ⇒ คนอ่านได้อย่างเดียวผูกแล้วเปิดรายการหนึ่งครั้งได้ writer · คนที่เจ้าของเอกสารให้ writer ไว้เองถูกลดเป็น reader เพียงเพราะเปิดหน้า
- **ลบแถว = ลบ permission ที่ระบบไม่ได้สร้าง** — ทุกคนที่เปิดรายการถูกจดลง `accessGranted` และตอนลบแถวตัวถอนลบ permission ของทุกชื่อทิ้งทั้งอัน ⇒ ผูกเอกสารเข้าระเบียนร่วมแล้วลบแถว เพื่อตัดสิทธิ์เพื่อนร่วมงานได้
- **สมุดสิทธิ์แก้จาก client ได้** — `accessGranted` / `accessRoles` ไม่ถูกตัดจาก metadata ที่ client ส่ง ⇒ ส่ง `accessGranted: []` ให้ระบบลืมว่าเคยให้ใคร (ตัวถอนหาไม่เจออีก)
- **โหมดสร้าง ให้สิทธิ์แล้วไม่จด** — `grantWriter` กลืน error และไม่จดอะไร ⇒ ลบแถวก่อนมีใครเปิดรายการ = สิทธิ์ค้างบน Drive ที่ตัวถอนหาไม่เจอ

## โหมดผูก: ลำดับด่าน

[`buildGoogleAttachment`](../webapp/src/lib/master/googleDocs.js) โหมด `link` — เรียกจาก `POST /api/attachments` หลังผ่านด่านสิทธิ์ของระเบียนแล้วเท่านั้น

| # | ด่าน | ไม่ผ่าน |
|---|---|---|
| 1 | แกะ id จากลิงก์ (`parseDriveId`) | 400 `ลิงก์ Google Drive ไม่ถูกต้อง` |
| 2 | คนผูกต้องมีอีเมล Google (`workspaceEmail` — บัญชีล็อกอินด้วยเบอร์ได้ `null`) · ตรวจ **ก่อนแตะ Drive** | 403 `บัญชีนี้ไม่มีอีเมล Google ให้ตรวจสิทธิ์ จึงผูกลิงก์เอกสารไม่ได้ — ใช้ปุ่มสร้าง Doc หรือ Sheet แทน` |
| 3 | **พิสูจน์สิทธิ์ก่อนอ่านอะไรของไฟล์** — `fileAccessRole(fileId, อีเมล)` | Drive ล่ม/โควตา/อ่านไม่ครบ: 502 `ตรวจสิทธิ์ของคุณบนเอกสารนี้ไม่สำเร็จ จึงยังผูกไม่ได้ — ลองใหม่อีกครั้ง` (ตรวจไม่ได้ = ไม่ผูก) |
| 4 | ต้องได้ `writer` หรือ `reader` | **403 ข้อความเดียว** (ดูข้างล่าง) |
| 5 | อ่าน metadata (`getFileMeta` · ช่อง `id, name, mimeType, webViewLink, trashed`) | Drive ตอบ 404/403: 403 ข้อความเดียวกับข้อ 4 · เหตุอื่น: 500 `ดำเนินการกับ Google Drive ไม่สำเร็จ` |
| 6 | ไม่อยู่ในถังขยะ | 400 `เอกสารนี้อยู่ในถังขยะของ Drive จึงผูกไม่ได้ — กู้คืนเอกสารก่อนแล้วผูกใหม่` |
| 7 | ชนิดต้องเป็น Doc หรือ Sheet (`kindFromMime` — รายชื่อที่อนุญาต · โฟลเดอร์ · PDF/รูป · Slides/Forms ตกหมด) | 400 `ผูกได้เฉพาะ Google Doc หรือ Google Sheet — ไฟล์ชนิดอื่นให้อัปโหลดเป็นไฟล์แนบแทน` |
| 8 | สำเร็จ: **ไม่ grant อะไรเลย** · จด `metadata.linkRole` (role ที่พิสูจน์ได้) + `metadata.linkedBy` (อีเมลคนผูก ตัวพิมพ์เล็ก ตัดช่องว่าง) | — |

**403 ข้อความเดียว — ไม่เป็นช่องถาม (no oracle)**: `ผูกได้เฉพาะเอกสารที่มีอยู่และคุณเปิดได้อยู่แล้ว — ตรวจลิงก์ หรือขอสิทธิ์จากเจ้าของเอกสารก่อน` (`LINK_NO_ACCESS`)

- คนที่พิสูจน์สิทธิ์ไม่ได้ได้คำตอบนี้เหมือนกันทุก id — เอกสารที่มีอยู่แต่เปิดไม่ได้ · โฟลเดอร์ · PDF · ไฟล์ในถังขยะ · id ที่ไม่มีจริง — และ `getFileMeta` **ไม่ถูกเรียกเลย** สำหรับคนกลุ่มนี้ · ข้อความข้อ 6–7 (ที่บอกรายละเอียดของไฟล์) ถึงได้เฉพาะคนที่พิสูจน์แล้วว่าเปิดได้
- Drive ตอบ 404 หรือ 403 ตอนถามสิทธิ์ = นับเป็น "ไม่มีสิทธิ์" (คำตอบเดียวกัน) · **ยกเว้น 403 เรื่องโควตา** (`errors[].reason` มีคำว่า limit/quota) ซึ่งตกทาง 502 — ไม่งั้นคนที่มีสิทธิ์จริงโดนบอกว่าไม่มีเพราะ Drive ยุ่ง
- ห้ามแตกข้อความนี้ตามสาเหตุ — ข้อความที่ต่างกันคือช่องถามว่าไฟล์ไหนมีอยู่จริง

## `fileAccessRole` ([`lib/drive.js`](../webapp/src/lib/drive.js))

"คนนี้เปิดไฟล์นี้ได้อยู่แล้วระดับไหน" — คืน `'writer'` · `'reader'` · `null` จาก `permissions.list` ของ Drive

| เรื่อง | กติกา |
|---|---|
| permission ที่นับ | `user` ที่อีเมลตรงกัน (ไม่สนตัวพิมพ์) · `anyone` (ใครมีลิงก์ก็เปิดได้) · `domain` ที่ตรงกับโดเมนของอีเมล |
| ที่ไม่นับ | **`group`** (ระบบไม่รู้ว่าใครอยู่กลุ่มไหน ⇒ ปฏิเสธเกิน ไม่ใช่ปล่อยเกิน) · ชนิดอื่นนอกตาราง · permission ที่ `deleted` |
| แปลง role | `owner` · `organizer` · `fileOrganizer` · `writer` → **writer** · `commenter` · `reader` → **reader** · เอาชั้นสูงสุด รวม role ใน `permissionDetails` (ชั้นที่สืบทอดบน Shared Drive) |
| หลายหน้า | อ่านทุกหน้า (`pageSize: 100`) · เกิน 50 หน้า (`ACCESS_MAX_PAGES`) = **โยน error** ไม่คืนผลครึ่งเดียว |
| Drive ตอบ error | โยนต่อ ไม่คืน `null` — `null` แปลว่า "ตรวจแล้วไม่มี" ซึ่งเส้นเปิดรายการเอาไปสร้าง permission ใหม่ |
| ไม่มี fileId / อีเมล | `null` โดยไม่ยิง Drive |

## คีย์ metadata ที่เป็นของเซิร์ฟเวอร์

`DRIVE_OWNED_METADATA_KEYS` = `kind` · `googleFileId` · **`accessGranted`** · **`accessRoles`** · **`linkRole`** · **`linkedBy`** (สี่ตัวหลังเพิ่มรอบนี้)

- `stripDriveMetadata` ตัดทุกคีย์ในลิสต์ออกจาก metadata ที่ client ส่ง — ถูกเรียกที่ `POST /api/attachments` และ `PATCH /api/attachments/[id]` · PATCH merge ทับของเดิมบนแถว (`{ ...att.metadata, ...requested }`) ⇒ ค่าเดิมของเซิร์ฟเวอร์อยู่ครบ
- ตัวเขียนของเซิร์ฟเวอร์ (`buildGoogleAttachment` · `ensureGoogleDocAccess` · `revokeGoogleDocAccess`) เขียนตรงลงแถว ไม่ผ่านตัวตัด
- **เพิ่มคีย์ที่เซิร์ฟเวอร์ผลิตเมื่อไร ต้องเพิ่มในลิสต์นี้** — เทสต์ ratchet ใน `googleDocLink.test.mjs` ตกเมื่อ `buildGoogleAttachment` ผลิตคีย์ที่ไม่อยู่ในลิสต์

| คีย์ | ความหมาย |
|---|---|
| `accessGranted` · `accessRoles` | สมุดสิทธิ์: อีเมลที่ระบบสั่งให้สิทธิ์ผ่านแถวนี้ และ role ที่ให้ไป — ตัวถอนหาไฟล์จากตรงนี้ทางเดียว · บนแถวที่มี `linkRole` ชื่อในสมุด = permission ที่ **ระบบเป็นคนสร้าง** เท่านั้น |
| `linkRole` | เพดานของแถวที่ผูกมา · มีคีย์นี้ = "แถวที่ผูก" · ค่าที่ไม่ใช่ `'writer'` นับเป็น `reader` |
| `linkedBy` | คนผูก — คนเดียวที่แถวนั้นไม่มีวันสร้าง permission ให้ |

## ให้สิทธิ์ตอนเปิดรายการ ([`ensureGoogleDocAccess`](../webapp/src/lib/master/googleDocAccess.js))

`GET /api/attachments` เรียกตัวนี้ด้วย role ที่ระบบอยากให้ (`writer` เมื่อแก้ไฟล์แนบของระเบียนได้ · นอกนั้น `reader`) · **แถวที่มี `linkRole`** เดินตามนี้:

0. **คนดูคือคนผูกของแถวนั้นเอง** (`linkedBy` เทียบไม่สนตัวพิมพ์) ⇒ ข้ามทั้งแถวก่อนถาม Drive — ไม่ให้ ไม่ลด ไม่จด แม้สิทธิ์ของเขาบนไฟล์ถูกถอนไปแล้ว (ไม่งั้นถอนกี่รอบแถวของตัวเองก็คืนให้)
1. คนดูคนอื่นได้ **ไม่เกิน `linkRole`** (`roleForViewer`) — แถวที่คนผูกอ่านได้อย่างเดียวไม่มีวันพา writer ไปให้ใคร
2. ระบบยังไม่เคยจดชื่อคนนี้ในแถว ⇒ ถาม `fileAccessRole` ก่อน: **มีสิทธิ์อยู่แล้วไม่ว่าระดับไหน = ไม่แตะและไม่จด**
3. ไม่มีสิทธิ์เลยเท่านั้น จึงสร้าง permission แล้วจด ⇒ ชื่อในสมุดของแถวแบบนี้แปลว่า "ระบบเป็นคนสร้าง" จริง ๆ · รอบถัดไป role ของคนนั้นเดินตามสิทธิ์ในระบบได้ (ลดเป็น reader เมื่อหลุดขอบเขต) โดยไม่เกินเพดาน
4. ถามไม่สำเร็จ = ข้ามคนนี้ (log `[googleDocAccess] อ่านสิทธิ์เดิมของคนดูไม่สำเร็จ — ข้ามการให้สิทธิ์รอบนี้`) — รายการไฟล์แนบต้องขึ้นตามปกติ

**แถวเก่าที่ผูกไว้ก่อนรอบนี้ไม่มี `linkRole` ⇒ เดินแบบเดิมทุกประการ** (ไม่มี backfill) · แถวที่มี `linkRole` แต่ไม่มี `linkedBy` = ไม่รู้ว่าใครผูก เดินแบบคนดูทั่วไป · แถวที่ระบบสร้างเอกสารเองก็เดินแบบเดิม (ให้ตาม role ในระบบ จดทุกคนที่ให้)

## ถอนสิทธิ์ตอนลบแถว — กติกาแถวพี่น้อง

`revokeAttachmentGrants` (ถูกเรียกจากตัวปล่อยไฟล์ของแถวไฟล์แนบ): permission บน Drive มี **อันเดียวต่อคนต่อไฟล์** ไม่ใช่อันละแถว และเอกสารใบเดียวผูกจากหลายระเบียนได้ ⇒ **ไม่ถอนอีเมลที่แถวอื่นของไฟล์เดียวกันยังจดอยู่**

- อ่านแถวพี่น้องครั้งเดียว (`attachments` ที่ `metadata.googleFileId` ตรงกัน · เพดาน 200 แถว)
- อ่านไม่ได้ · ได้เต็มเพดาน · `googleFileId` หลุดรูป id ของ Drive ⇒ **ไม่ถอนใครเลย** + log `[googleDocAccess] ⚠️ ตรวจไม่ได้ว่าแถวอื่นยังใช้สิทธิ์ของไฟล์นี้อยู่ไหม — ไม่ถอนสิทธิ์ (ต้องตามถอนด้วยมือ)`
- ผู้เรียกที่ส่ง `deps.supabase` เองต้องส่ง client ระดับ service role (ต้องเห็นแถวของไฟล์นี้ครบ)
- ปุ่มโล่ในหน้าผู้ใช้ (`revokeGoogleDocAccess`) **ไม่ผ่านกติกานี้โดยเจตนา** — ทางนั้นถอนคนคนเดียวจากทุกแถวที่จดชื่อเขา

## โหมดสร้าง: จดเฉพาะเมื่อให้สำเร็จ

`grantFileRole(file.id, อีเมล, 'writer')` ใน try/catch — สำเร็จจึงจด `accessGranted` + `accessRoles` ลงแถวทันที · ล้ม = ไม่จด (log `[googleDocs] ให้สิทธิ์คนสร้างเอกสารไม่สำเร็จ`) ⇒ รอบเปิดรายการถัดไป `ensureGoogleDocAccess` ให้ซ้ำเอง · คนที่ไม่มีอีเมล Google ยังสร้างได้ แค่ไม่มีการให้สิทธิ์

## สิ่งที่ลองก่อนขึ้นระบบไม่ได้

เทสต์ของส่วนนี้ (`lib/master/googleDocLink.test.mjs` 46 เทสต์ + `googleDocAccess.test.mjs`) ใช้ Drive ตัวปลอมทั้งหมด — สองเรื่องนี้รู้ได้จาก production เท่านั้น:

- **`permissions.list` ของ service account** บนไฟล์ที่อยู่นอก Shared Drive (service account ถูกแชร์แค่ reader หรือมองไม่เห็นเลย) จะตอบสำเร็จไหม — Drive ตอบ 403 ที่ไม่ใช่โควตา = ผู้ใช้ได้ 403 "ตรวจลิงก์ หรือขอสิทธิ์" ทั้งที่ตัวเองเปิดไฟล์ได้จริง
- **role ที่สืบทอดจากการเป็นสมาชิก Shared Drive** โผล่ใน `permissions.list` ของไฟล์จริงไหม (โค้ดอ่าน `permissionDetails` ไว้แล้ว แต่ไม่เคยเห็นคำตอบจริง)

ทั้งสองกรณีระบบ **ปิดไว้ก่อน** (ผูกไม่ได้ ไม่ใช่ผูกเกิน) และไม่มีสวิตช์ผ่อน — เฝ้า log บรรทัด **`[googleDocs] อ่านสิทธิ์ของคนผูกบนไฟล์ไม่สำเร็จ`** หลัง deploy: เขียนทุกครั้งที่ `fileAccessRole` โยน error ในโหมดผูก (ทั้งทาง 403 และ 502) ถ้าขึ้นถี่กับคนที่เปิดเอกสารได้จริง = ต้องแก้โค้ด

## ข้อจำกัดที่รู้แล้ว

- **สิทธิ์ผ่าน Google Group ไม่นับ** — คนที่เปิดเอกสารได้เพราะอยู่ในกลุ่มอย่างเดียวจะผูกไม่ได้ ต้องขอแชร์รายคน
- **ต้นทุนตอนเปิดรายการ** — คนดูที่มี permission ของตัวเองอยู่แล้วบนเอกสารที่ผูกมา ไม่ถูกจด ⇒ ถูกถาม `permissions.list` หนึ่งครั้งต่อแถวที่ผูก ทุกครั้งที่โหลดรายการ · ไม่มี cache (คนผูกเองไม่เสียต้นทุนนี้ — ถูกข้ามก่อนถาม Drive)
- **แถวผูกรุ่นเก่า** (ไม่มี `linkRole`) ยังยก/ลด permission เดิมและจดทุกคนที่เปิดรายการได้เหมือนก่อน
- **"คนอื่นผูกเอกสารใบเดียวกัน"** — ถ้า B ผูกเอกสารใบเดียวกันเข้าระเบียนที่ A เห็น A เป็นคนดูทั่วไปของแถวของ B และได้สิทธิ์ไม่เกิน `linkRole` ของ B แม้สิทธิ์ของ A เองถูกถอนไปแล้ว · เป็นผลตรงของมติ "คนที่เห็นระเบียนยังได้สิทธิ์" — ⚠️ **ยังไม่ได้ถามเจ้าของว่ารับได้ไหม** (ปิดช่องนี้ = สิทธิ์ของคนดูต้องขึ้นกับคนผูก)
- **ลบทั้งระเบียน (`purgeAttachments`)** ปล่อยของก่อนลบแถว ⇒ สองแถวของระเบียนเดียวกันที่ผูกไฟล์ใบเดียว ต่างคนต่างเห็นอีกแถวจดอยู่แล้วไม่ถอน · ตัวปิดช่องนี้ (`revokeTwinDocGrants`) อยู่ใน PR `claude/upload-receipts` ไม่ใช่ PR นี้ · คอมเมนต์ในโค้ดจดว่าวัดจริง 08/10/2569 ไม่มีไฟล์ไหนผูกเกินหนึ่งแถว
- `GET /api/attachments` ส่ง `metadata` ของแถวที่คนดูเปิดได้กลับไปทั้งก้อน ⇒ รวม `linkedBy` (อีเมลคนผูก) เหมือนที่ `accessGranted` ออกไปอยู่ก่อนแล้ว
- id ที่ไม่มีจริงกับไฟล์ที่มีแต่เปิดไม่ได้ ได้สถานะและข้อความเดียวกัน แต่เวลาตอบอาจต่างกันเล็กน้อย

## เช็กลิสต์หลังขึ้น production

1. ผูก Google Doc ที่ตัวเองเปิดได้เข้าระเบียนที่แก้ได้ → ต้องผูกสำเร็จ และสิทธิ์ของตัวเองบน Drive ไม่เปลี่ยน
2. ลองผูก **ลิงก์โฟลเดอร์** และ **เอกสารที่ตัวเองเปิดไม่ได้** → ต้องได้ 403 ข้อความเดียวกันทั้งสองครั้ง
3. สร้าง Doc ใหม่จากแผงไฟล์แนบ (โมดัล "สร้าง Doc ใหม่") → ต้องสร้างได้และเปิดแก้ได้ทันที
4. ลบแถวที่ผูกไว้ในข้อ 1 → เปิด Drive ยืนยันว่า **permission ของตัวเองบนเอกสารยังอยู่**
5. เปิด Vercel → Logs หา `[googleDocs] อ่านสิทธิ์ของคนผูกบนไฟล์ไม่สำเร็จ` — **ข้อ 1 ต้องไม่มี** · ข้อ 2 มีหรือไม่มีก็ได้ (ขึ้นเฉพาะเมื่อ Drive ตอบ error ให้ service account · ถ้า Drive ตอบรายชื่อสิทธิ์มาได้แต่ไม่มีชื่อเรา จะได้ 403 โดยไม่มีบรรทัดนี้)
