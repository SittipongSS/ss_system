## ทำไม

ใบสั่งขายสายบริการอนุมัติแล้ว **ไม่มีใครรู้ว่าของไปตั้งที่ไหน** — TS ต้องเปิดใบไล่จับคู่บรรทัดกับโซนเอง (วิซาร์ด "ผูกโซน")
ทั้งที่ฝ่ายขายเป็นคนเดียวที่รู้ว่าขายแพ็คเกจไหน ลงไซต์ไหน กี่แพ็คต่อรอบ กี่รอบ ช่วงไหน · บรรทัด "พิมพ์เอง" ไม่มี `fgCode`
⇒ ระบบตอบไม่ได้ว่าเป็นแพ็คเกจบริการหรือค่าขนส่ง · วิซาร์ดของ TS ไม่เคยถูกใช้จริง (term บน prod = 0)

**ของใหม่:** ฝ่ายขายตั้งที่ตารางรายการของใบสั่งขาย → ผู้อนุมัติเห็นครบก่อนกด → อนุมัติ = เปิดรอบขาย (term) ให้ TS
ในทรานแซกชันเดียวกัน · TS เริ่มที่ "รอตั้งรอบ" ตรง ๆ · ใบที่อนุมัติไปแล้ว (60 ใบเข้าเกณฑ์ตอนรัน 0392 · ขึ้นจริง 49 ใบตาม D25 — อีก 11 ใบเป็นงานออกแบบล้วน
FG หมวด 03-xxx ทั้งใบ ไม่มีอะไรให้ตั้ง) ฝ่ายขายตั้งย้อนหลังแล้วผู้จัดการฝ่ายขายตรวจ

**ด่านเงินของการยื่นแบบข้ามบนใบที่ยังไม่ตอบ ‘งานบริการ?’** (`serviceSetupSkipMoneyIssues` · ตรวจทานรอบสุดท้าย 08/10) — ด่านงวดของ `serviceSetupIssues`
ทำงานเฉพาะใบที่มีรายการแพ็คเกจแล้ว (ตอบ ‘ใช่’ หรือ FG หมวด 02-001) · ใบที่ทุกรายการพิมพ์เองยังไม่ตอบจึงไม่มีข้อเงินเลย และการยื่นปกติก็ยื่นไม่ได้อยู่แล้ว
(ยังไม่ตอบ) — แต่การยื่นแบบข้าม **เลื่อน** ข้อ "ยังไม่ตอบ" ออกไป ⇒ ถ้าไม่ตรวจเพิ่ม กติกา "งวดชำระ/วันวางบิล/กำหนดชำระ ข้ามไม่ได้" จะจริงเฉพาะใบที่ตอบ ‘ใช่’ ไปแล้ว
และผู้ยื่นที่ติดข้อเงินแค่ล้างคำตอบก็ข้ามได้ ⇒ **ใบที่จะข้ามถูกตรวจสามข้อนี้เหมือนมีแพ็คเกจ** เมื่อยังไม่มีรายการแพ็คเกจและยังมีรายการที่ยังไม่ตอบ
(ยอดศูนย์ = ไม่ต้องมีงวด · ข้อช่วงครอบไม่ถูกเติม — เลื่อนได้อยู่แล้ว) · ข้อชุดนี้ **ไม่ใช่ข้อของการยื่นปกติ** (ตอบ ‘ไม่ใช่’ ครบทุกรายการ = ไม่ต้องมีงวด)
จึงไม่อยู่ใน `issues` ของใบร่าง: อยู่ที่ `skip.extraIssues` ของ GET (นับรวมใน `skip.blockingCount` · แผงแดงวาดเป็นแถวต่อท้ายเมื่อกดปุ่มข้าม · route ส่งรวมไปกับ 400)
และเป็นข้อที่หยุดการอนุมัติของใบรออนุมัติที่ยังข้ามอยู่ (`serviceSetupApprovalGate` — งวดถูกลบ/กำหนดชำระถูกล้างระหว่างรออนุมัติ)

**ใบที่ข้ามไม่ได้ทั้งใบ** (ต้องตั้งให้ครบแล้วกด "ยื่นอนุมัติ" ตามปกติ)

- **ใบที่กู้คืนจากการยกเลิก** แล้วยังมีรอบขายของการอนุมัติรอบก่อนค้างอยู่ — ข้ามแล้วรอบขายเก่าจะกลับมามีผลบนใบที่ป้ายบอกว่า "ยังไม่ตั้ง" ⇒ RPC ตอบ
  `service_setup_defer_terms_exist` · จอมองไม่เห็นกรณีนี้ล่วงหน้า (รู้หลังกดยืนยัน — โมดัลปิด เหตุขึ้นที่แถบ error ของหน้า) · เกิดได้เฉพาะหลัง admin กู้ใบ
- **ใบ Rev. ของใบที่ TS ยังเดินรอบบริการอยู่** — การอนุมัติแบบข้ามไม่ย้ายรอบบริการมาใบ Rev. ⇒ TS จะเห็น "Rev. ไม่มีไซต์นี้ — ปิดรอบ หรือนัดถอนเครื่อง" ซึ่งไม่จริง
  ⇒ ปุ่มยังโชว์ กดแล้วบอกเหตุ (`service_setup_defer_plans_running` ที่ฐาน · `view.skip.blockedReason` ที่จอ) · แผงแดงไม่ติดป้าย "ข้ามได้" สักแถว
  · ใบ Rev. ที่ใบเดิมไม่มีรอบบริการเดินอยู่ข้ามได้ตามปกติ
- **ใบ Rev. ของใบที่ TS ตั้งมาตรฐาน มล./เดือนบนรอบขายไว้แล้ว** (ตรวจทานรอบสุดท้าย 08/10) — ตัวเปิดรอบขายยกค่ามาตรฐานจากรอบขายของใบเดิม **ทอดเดียว**
  (`revisedFromId` · 0392 §7) · ใบที่อนุมัติแบบข้ามไม่มีรอบขาย ⇒ ถ้าใบนั้นถูกออก Rev. ต่ออีกทอดก่อนตั้งงานบริการ รอบขายของใบถัดไปหาค่าไม่เจอ = ค่าที่ TS ตั้ง
  **หายเงียบ** (ไม่มี error ไม่มี audit — พิสูจน์บน PGlite ก่อนแก้) ⇒ RPC ตอบ `service_setup_defer_ml_set` · D1 มีเงื่อนไขเดียวกันเป็นตาข่าย ·
  จอ: ปุ่มยังโชว์ กดแล้วบอกเหตุ ไม่มีป้าย "ข้ามได้" สักแถว (`loadPredecessor` อ่าน `standardMlTermCount` จากรอบขายของใบเดิม) · เหตุเดียวกับตัวกัน `ml_set`
  ของปุ่ม "แก้งานบริการ" (0396) · ค่ามาตรฐานตั้งได้เฉพาะบนรอบขายของใบที่ยังมีผล (`/api/service/terms/[id]`) ⇒ หลังใบเดิมถูกย้อนการอนุมัติ ค่านี้นิ่ง —
  ตรวจตอนยื่นแล้วไม่มีช่องให้หลุดทีหลัง · ตั้งครบแล้วยื่นตามปกติ = ค่ามาตรฐานถูกยกมาใบ Rev. ตามเดิม

**ข้อจำกัดที่รู้อยู่: ด่าน "ใบเดิมยังเดินรอบ" ตรวจ ณ ตอนยื่น/อนุมัติ และย้อนไปทอดเดียว** (ตรวจทานรอบสุดท้าย 08/10 · ฮาร์เนสเคส V-10/V-11)

- TS เปิดรอบของใบเดิมกลับได้ **หลัง** ใบ Rev. ถูกอนุมัติแบบข้าม (`PATCH /api/service/plans/[id]` ไม่ดูสถานะของใบ) ⇒ รอบเดินอยู่บนใบที่ถูกแทนแล้ว ขณะที่ใบ Rev.
  อนุมัติแล้วแต่ยังไม่มีรอบขาย · เดิมแถบรอบกำพร้าของหน้างานเข้าใหม่จะนับเป็น "Rev. ไม่มีไซต์นี้ — ปิดรอบ หรือนัดถอนเครื่อง" (ไม่จริง และชวน TS ปิดรอบ/ถอนเครื่อง)
  ⇒ **แก้ที่ฝั่งอ่าน**: `orphanPlanRows` (`lib/service/intakePlanFacts.js`) มีกลุ่มใหม่ `unset` สำหรับใบปลายโซ่ที่ `serviceSetupDeferred` ตอบขั้น 'approved'
  — หัวข้อ "รอบที่ยังผูกใบเดิม n รอบ — ใบ Rev. ล่าสุดยังไม่ตั้งงานบริการ (ฝ่ายขายข้ามตอนยื่น) · ยังไม่ต้องปิดรอบหรือถอนเครื่อง …" (`SERVICE_DEFERRED_TEXT.tsOrphanTitle`)
  · ใบปลายโซ่ที่ยังไม่ประทับแต่ไม่มีตราการข้าม (ใบเดิม) = `dropped` เหมือนเดิมทุกตัวอักษร
- **ทอดเดียว**: ผู้จัดการอนุมัติงานบริการของใบ Rev. นั้น = ตัวเปิดรอบขายย้ายรอบของใบก่อนหน้ามาให้เอง (เคส V-10)
- **สองทอด** (ใบ Rev. ที่ข้ามไว้ถูกออก Rev. ต่ออีกทอดก่อนตั้งงานบริการ): ด่านของฐานดูแค่ `revisedFromId` ⇒ ใบทอดที่สอง **ข้ามได้** แม้รอบของใบต้นโซ่เดินอยู่
  และตัวเปิดรอบขายไม่ย้ายรอบข้ามสองทอด — หลังประทับ แถบรอบกำพร้ากลับเป็น `stale` ("ย้ายรอบไปใบนั้นที่หน้าไซต์") หรือ `dropped` ตามจริง ให้ TS ลงมือเอง (เคส V-11)
  · ไม่ได้ทำให้ด่านเดินทั้งโซ่ในงานนี้ (ผลลัพธ์สุดท้ายเท่ากันเพราะตัวย้ายรอบของ 0392 เป็นทอดเดียวอยู่แล้ว — ถ้าจะปิดต้องแก้ตัวย้ายรอบ ซึ่งแตะการเปิดรอบขายของทุกใบ)
- ค่ามาตรฐาน มล./เดือนไม่มีช่องโหว่แบบนี้ (ย่อหน้าก่อน: ค่านิ่งหลังใบเดิมถูกย้อนการอนุมัติ)

**API**

- `PATCH /api/sales-planning/sales-orders/[id]` `{ action: 'submit', deferServiceSetup: true, expectedUpdatedAt }` — `true` ตัวอักษรเท่านั้น · server คิดใหม่จากบริบทสด
  (`serviceSetupSkipState`) ไม่เชื่อจอ → ข้ามได้ = `submitOrderDeferringServiceSetup` (RPC ตัวห่อ · ตัวตนผู้ลงนามเท่าการยื่นปกติ) · ติดข้อที่ข้ามไม่ได้ = 400
  `{ error: เหตุ, issues: ทุกข้อ + skip.extraIssues, skip }` (จอวาดแผงแดงและบรรทัดท้ายแผงจากคำตอบเดียวกัน) · ครบแล้ว = 409 `service_setup_defer_nothing`
  (ไม่มี `issues`) · ใบขยับ = 409 `workflow_stale` · ไม่ส่งธง = ยื่นปกติทุกตัวอักษร
- `GET …/service-setup` เพิ่ม `skip` (`visible` · `canSkip` · `blockedReason` · `lead` · ตัวนับ · `extraIssues` · `prompt`) และ `deferred` (`at` · `byName` · `stage` · `active` · `missing` · `blocking`)
  · `issues` ของใบรออนุมัติที่ยังข้ามอยู่ = เฉพาะข้อที่หยุดการอนุมัติ (ข้อที่ถูกเลื่อนไปอยู่ที่ `deferred.missing`)
- ทะเบียน SO: แถวพก `serviceDeferredTag` (ใบรออนุมัติที่ข้าม) · `serviceReview.label` = "งานบริการ (ข้ามตอนยื่น)" · เลน/ชิป/ป้ายเมนูไม่มีคิวรีใหม่
- `GET /api/service/intake` select เพิ่มสองช่อง · `orphans` มีกลุ่ม `unset` (ข้อจำกัดข้างบน) · reject / withdraw / restore / revoke / revise / cancel **ไม่มีโค้ดใหม่** (trigger เป็นคนล้าง)
- ป้ายโซน/คำเตือนปิดโซน/ชิปด่านนัด (`lib/service/zoneSalesRepo.js`): select ของใบพก `"serviceSetupDeferredAt"` ด้วย — ใบที่เคยเปิดแก้ (0396) แล้วถูกยกเลิก → กู้คืน →
  ยื่นแบบข้าม ต้องเป็นกลุ่ม "ตั้งย้อนหลัง" เหมือนที่หน้าใบ/ทะเบียน/แท็บ TS พูดว่า "ข้ามตอนยื่น" (เหตุการณ์ที่เกิดทีหลังชนะ · ไม่พกช่องนี้ = เล่าเป็น "แก้หลังอนุมัติ")
  ⚠️ บนฐานที่ยังไม่มี 0404 `check:columns` จึงแดง **สามจุด**: สองช่องของหน้างานเข้าใหม่ + ช่องนี้ (ฐานจริงมีครบแล้วตั้งแต่ 08/10 — เขียว)

**จอ** (`components/salesPlanning/serviceSetup/*` · หน้าใบ `[id]/page.js` · ทะเบียน) — จอไม่ตัดสินเองว่าข้ามได้ไหม: ถาม `view.skip` / `view.deferred` ของ GET
· คำทุกคำมาจาก `SERVICE_DEFER_TEXT` (ปุ่ม · ท้ายแผง · โมดัล · ทัก) และ `SERVICE_DEFERRED_TEXT` (ป้ายของใบที่ข้าม) ใน `serviceSetup.js`

- **แผงแดง** (`SubmitGateNotice`): หน้าส่ง `skip` เฉพาะแผงของการยื่นอนุมัติที่ server ตอบ ⇒ ท้ายแผงพื้นกลาง (ไม่แดง) = บรรทัด `skip.lead` ที่ server เลือก + ปุ่ม
  "ยื่นโดยยังไม่ตั้งงานบริการ" (ปุ่มรอง · **กดได้เสมอ** — ติดด่าน = โชว์แล้วบอกเหตุตอนกด) · แถวที่เลื่อนได้ติดป้าย "ข้ามได้" (`submitGateGroups` รับตัวถาม `deferrable` ·
  `skipTagsShown` — ใบที่ข้ามไม่ได้ทั้งใบไม่มีป้าย · ข้อของบัญชีไม่มีป้าย) · จอกว้างกว่า 680px ท้ายแผงแถวเดียว · จอแคบข้อความแล้วปุ่มเต็มแถว (สูงขนาดนิ้ว) และแถวที่ติดป้ายให้ข้อความเต็มแถว
  · แผงของเส้นตั้งย้อนหลัง ("ยื่นตรวจไม่ได้") และด่าน "ยังไม่บันทึก" ไม่มีท้ายแผง
  · ท้ายแผงวาดจาก **ก้อน `skip` ของคำตอบเดียวกับที่ให้ข้อ** (เก็บไว้กับภาพของแผง — GET สด หรือ 400 ของ route) ไม่ใช่ก้อนงานบริการสดของหน้า: แผงคือภาพ ณ ตอนกด
    (บันทึกงานบริการแล้วแผงคงเดิม) ⇒ หัวแผง · แถว · ป้าย · จำนวนบนบรรทัดท้ายแผงเล่าเรื่องเดียวกันเสมอ · กดปุ่มข้ามเมื่อไร แผงทั้งก้อนตามก้อนสด
  · ปุ่มใช้ `aria-disabled` + ไม่รับการกดซ้ำ ระหว่างหน้ายิงคำสั่ง — **ไม่ใช่ `disabled` ของเบราว์เซอร์** (ปุ่มที่ถือโฟกัสถูก disabled = โฟกัสตกไป `<body>` ·
    โมดัลที่เปิดตามมาคืนโฟกัสผิดที่) ⇒ คีย์บอร์ด/โปรแกรมอ่านจอ: Enter → โมดัล → Esc → โฟกัสกลับมาที่ปุ่ม
- **กดปุ่ม** (`pressSkipSubmit` ของหน้าใบ): ฟอร์มเอกสารของใบมีของที่ยังไม่บันทึก (โหมด "แก้ไขข้อมูล" · ไฟล์ยืนยันคำสั่งซื้อที่เลือกค้าง · ร่างวันของงวด) =
  **ไม่ยิง ทักเหตุ** (ปุ่ม "ยื่นอนุมัติ" ปกติหายไประหว่างแก้ แต่แผงแดงกับปุ่มนี้ยังอยู่ — ยื่นแล้วของที่พิมพ์ค้างหายเงียบและใบล็อก) → ยังไม่บันทึก = ข้อเดียว "ยังไม่บันทึก" → โหลดก้อน GET สด

## เส้นตั้งย้อนหลัง (ใบที่อนุมัติก่อนมีการตั้งงานบริการ)

> ใบที่เข้าเส้นนี้มีสามที่มา — ป้ายต่างกัน เส้นเดียวกันทุกก้าว: **ใบเดิม** (อนุมัติก่อนมีการตั้งงานบริการ · ตารางข้างล่างเล่าด้วยคำของใบนี้) ·

| จังหวะ | ใคร | เกิดอะไร |
|---|---|---|
| ใบเข้าข่าย | — | `serviceBackfillNeeded` จริง (D25) ⇒ หน้าใบขึ้นแบนเนอร์ + การ์ด "งานบริการ (ใบเดิม)" · ทะเบียนนับในชิป "ยังไม่ตั้งงานบริการ" · เจ้าของดีลเห็นใน "รอฉันลงมือ" · TS เห็นในแท็บ "รอฝ่ายขายตั้งงานบริการ (ใบเดิม)" |

### ทะเบียนใบสั่งขาย (`/sa/sales-orders`)

- **คิวรออนุมัติ** (เปลือกงานขาย) รวมแถวที่ `_awaitingMyServiceReview` — บรรทัดหลัก "งานบริการ (ใบเดิม) · SO-…" · บรรทัดรอง
  "ลูกค้า · แต่ละครั้ง z โซนใน s ไซต์ · จำนวนรอบบริการ r เดือน · ไม่นับ Actual · ยื่นโดย ชื่อ dd/mm/yyyy" (ตัวเลขจาก `serviceReview` ของ server · คำตามมติ 29/09 ·
  **หน่วยเดือนและลำดับ โซน → จำนวนรอบบริการ ตามมติ 08/10** — เดิม "… จำนวนรอบบริการ r รอบ · แต่ละครั้ง …") · ปุ่ม "เปิดใบเพื่ออนุมัติ"
  · เปลือกบัญชีไม่มีแถวชนิดนี้ · ไม่ชนกับแถวใบรออนุมัติ (อันนั้น `pending_approval` · อันนี้ `approved`)
- **ชิป "ยังไม่ตั้งงานบริการ n"** — ปุ่มสลับ (`aria-pressed`) ติดท้าย Segmented มุมมองสาย · n = แถว `_serviceSetupPending` ของ **ทุกแถว** (ไม่ใช่หลังกรอง) ·
  ขึ้นเมื่อ n > 0 หรือกำลังเปิด · จำค่าด้วย `useStickyState` · อยู่ใน resetKey ของการแบ่งหน้า · ปุ่มตัวกรองล้างให้ · **ไม่นับ** ในป้ายของปุ่มตัวกรอง
- "รอฉันลงมือ" อ่าน `_waitingOnMe` ตัวเดิม — route ใส่เลนเจ้าของดีล (`serviceBackfillNeeded`) + เลนผู้จัดการให้แล้ว · ป้ายเมนู `salesOrders` นับชุดเดียวกัน (ใบไม่ซ้ำ)
