# Decision 0014 — เอกสารไทม์ไลน์โครงการ (FM-PD-05) เป็นเอกสารควบคุม

วันที่: 4 สิงหาคม 2026
สถานะ: เสร็จสมบูรณ์ — merged 4 สิงหาคม 2026 (PR #927) · Migration 0198 (เดิมเลข 0193 · ชนกับ `0193_workflow_template_line` ที่เข้า main ก่อน จึงเลื่อนเลข เนื้อหา SQL ไม่เปลี่ยน) รันบนฐานจริงแล้ว

## บริบท

หลัง Phase 6A/0162 ระบบมีเอกสารควบคุมสามชนิด (`quotation`, `salesOrder`, `exciseTaxNotice`) ที่แก้รหัสแบบฟอร์ม Revision วันที่มีผล Accent และรูปแบบเลขที่ได้จาก `ตั้งค่า > มาตรฐานเอกสาร` เอกสารไทม์ไลน์โครงการ (FM-PD-05) เป็นเอกสารพิมพ์ชนิดเดียวที่ยังอยู่นอกระบบ: `ganttPrint.js` อ่านรหัสแบบฟอร์มจากค่าคงที่ `DOCUMENT_FORMS.projectTimeline` ใน `documentBrand.js` หัวใบไม่มี Rev/วันที่มีผล และไม่มีเลขที่เอกสารของตัวเอง — หัวใบแสดงรหัสโครงการ `PJ-YYMMXXXX-R` แทน

## การตัดสินใจ

- เพิ่ม document key `projectTimeline` เป็นเอกสารควบคุมชนิดที่สี่ เผยแพร่ Version 1 จากค่าที่ใช้จริง: `FM-PD-05` Rev `00` วันที่มีผล 08/05/2568 (เท่ากับ FM-SA-01/FM-SA-03) แก้ต่อได้ผ่านร่าง → เผยแพร่ เหมือนอีกสามใบ
- หัวใบพิมพ์บรรทัดควบคุมเต็ม `FM-PD-05: Rev. No.00. 08/05/2568` แทนการพิมพ์เฉพาะรหัสแบบฟอร์ม
- Accent ของเอกสารนี้ต้องต่างจากอีกสามใบ → `navy` (#1f3551) และเพิ่ม `navy` กลับเข้า `DOCUMENT_ACCENT_KEYS` เพราะตอนนี้มีเอกสารใช้จริงแล้ว (มติ 2026-07-25 ให้เปิดเฉพาะสีที่มีเอกสารใช้)
- Accent ผูกกับ "กรอบเอกสาร" เท่านั้น (รหัสฟอร์ม ชื่อเอกสาร เส้นคั่น หมุด milestone) **ไม่แตะ** `STATUS_FILL` ซึ่งเป็นสีตามสถานะงานที่ต้องตรงกับบนจอ (`ProjectDocumentView`)
- เอกสารไทม์ไลน์ออกเลขที่ของตัวเองจริง `PT-YYMMXXXX-R` มีตัวนับรายเดือนแยก (`project_timeline_number_counters`) unique index และ snapshot มาตรฐาน ณ วันออกเลข — เก็บบนแถวโครงการ (`projects."timelineDocBase"`, `"timelineDocNumber"`, `"timelineStandardVersionId"`, `"timelineStandardSnapshot"`)
- ออกเลขด้วย trigger `BEFORE INSERT` บน `projects` ไม่ใช่ฝั่งแอป และ backfill โครงการเดิมแบบกำหนดผลได้ (เรียงตาม `createdAt` ในเดือนนั้น)
- เลขที่เอกสารกับรหัสโครงการอยู่บนหัวใบทั้งคู่ คนละบรรทัด (`PT-…-R` เป็นเลขที่เอกสาร, `รหัสโครงการ PJ-…-R`)
- ไทม์ไลน์ของดีลที่ยังไม่มีโครงการจริงไม่มีเลขที่เอกสาร — พิมพ์รหัสดีลเหมือนเดิม
- พิมพ์ซ้ำอ่าน `timelineStandardSnapshot` ก่อนมาตรฐานที่เผยแพร่อยู่ปัจจุบัน (แพทเทิร์นเดียวกับ `taxNoticeStandardSnapshot` — mig 0162)

## เหตุผล

- FM-PD-05 เป็นแบบฟอร์มควบคุมตามระบบคุณภาพเหมือน FM-SA-01/03 การให้แก้ Rev/วันที่มีผลได้เฉพาะสามใบทำให้เอกสารชุดนี้หลุดการควบคุมโดยไม่มีเหตุผลทางธุรกิจ
- ออกเลขที่ trigger เพราะโครงการถูกสร้างจากสามทาง (`/api/sa/projects`, ดีล → โครงการ, PO สหมิตร → โครงการ) การออกเลขต้องเหมือนกันทุกทางและอยู่ในทรานแซกชันเดียวกับ INSERT — ฝั่งแอปต้องแก้สามที่และหลุดได้เมื่อมีทางที่สี่
- เก็บทั้งเลขฐานและเลขที่ตอนออก เพราะ Rev ของไทม์ไลน์เดินบนแถวโครงการเดิม (`currentRev` — mig 0040) ไม่แตกแถวใหม่เหมือนใบเสนอราคา ตอนพิมพ์จึงต้องต่อเลข Rev ปัจจุบันด้วย **ตัวคั่นของใบตัวเอง** ที่อ่านย้อนจากเลขที่ตอนออก ไม่ใช่ตัวคั่นของรูปแบบปัจจุบันที่อาจถูกแก้ไปแล้ว
- Backfill แบบกำหนดผลได้ให้โครงการเดิมมีเลขที่เอกสารครบ ไม่ต้องแยกเส้นทางพิมพ์ระหว่างของเก่ากับของใหม่

## ผลตามมา

- `documentBrand.DOCUMENT_FORMS.projectTimeline` ยังอยู่ในฐานะ "ค่าสำรองที่เดียว" และได้ `revision`/`effectiveDate` เพิ่มเข้ามา — โหลดมาตรฐานไม่ได้ต้องยังพิมพ์ได้
- หัวใบไทม์ไลน์มีสองรหัส (เลขที่เอกสาร + รหัสโครงการ) ผู้ใช้ที่คุ้นกับรหัสโครงการอย่างเดียวจะเห็นบรรทัดเพิ่ม
- โครงการทุกใบกินเลข `PT` ตั้งแต่ตอนสร้าง แม้ไม่เคยพิมพ์ไทม์ไลน์ — เหมือนใบยื่นภาษีที่ได้เลข `ET` ตั้งแต่สร้าง (mig 0162)
- `projects."docNumber"` (ช่องข้อความอิสระจาก mig 0008 ที่ทุกทางสร้างเป็น `''`) ยังอยู่ ไม่ถูกนำมาใช้เป็นเลขที่ควบคุม
- หน้าเต็มจอของพรีวิว (`quotation-preview`) ยังรองรับเฉพาะ QT/SO — ไทม์ไลน์และใบภาษีดูจากพรีวิวในหน้าตั้งค่า

## ทางเลือกที่ไม่เลือก

- ให้ `numberingPattern` ของไทม์ไลน์ไปคุมรหัสโครงการ `PJ-YYMMXXXX` ที่มีอยู่แล้ว: รหัสนั้นเป็นรหัส "ตัวโครงการ" ใช้ทั้งระบบ ไม่ใช่เลขที่เอกสาร การให้หน้าตั้งค่าเอกสารเปลี่ยนรหัสโครงการคือ blast radius ที่ไม่มีใครคาด
- ปล่อยช่องรูปแบบเลขที่ว่างไว้/ใส่ค่าหลอก: ขัดกับหลัก "ไม่มีปุ่มที่กดแล้วไม่เกิดอะไร" ที่ใช้ตัดสินเรื่อง Accent มาแล้ว
- ออกเลขตอนพิมพ์ครั้งแรก: เขียนฐานข้อมูลจากปุ่มพิมพ์ และเลขจะกระโดดตามลำดับการพิมพ์ ไม่ใช่ลำดับการสร้างงาน
- ผูก Accent เข้ากับสีบาร์ "กำลังทำ": สีบาร์เป็นสีตามสถานะที่ต้องตรงกับบนจอ เปลี่ยนแล้วเอกสารกับหน้าจอเดินหนีกัน
