# Decision 0015 — ผู้ใช้หนึ่งคนสังกัดได้หลายทีม

วันที่: 11 สิงหาคม 2026
สถานะ: ยืนยันและนำไปใช้

## บริบท

โครงสร้างเดิมผูกผู้ใช้หนึ่งคนกับทีมเดียว (`app_metadata.team` เป็นสตริงเดี่ยว) ทั้งที่งานจริงมีคนที่ดูแลสองสายพร้อมกัน — คำสั่งของผู้ใช้ 11 สิงหาคม 2026: "ฝ่ายขาย Account Executive อยู่ ODM กับ Service"

ทางออกที่มีอยู่ก่อนหน้านี้มีแค่สองทาง และผิดทั้งคู่: เปิดบัญชีซ้ำให้คนคนเดียว (ยอด KPI แตกเป็นสองคน งานของฉันไม่รวมกัน) หรือเลือกทีมเดียวแล้วตัดการมองเห็นของอีกทีมทิ้ง

ฝั่งเรคคอร์ดแก้ปัญหาเดียวกันนี้ไปแล้วตั้งแต่ migration 0037 (`customers.teams[]` — ลูกค้าหนึ่งรายมีหลายทีมดูแล) เอกสารฉบับนี้ยกรูปแบบเดียวกันมาใช้กับฝั่งผู้ใช้

## การตัดสินใจ

แยกสองความหมายที่เดิมทับกันอยู่ในช่องเดียวออกจากกัน:

- `app_metadata.teams` = **ขอบเขต** — ทุกทีมที่ผู้ใช้สังกัด ใช้ตอบว่าเห็นและแก้แถวของทีมไหนได้บ้าง
- `app_metadata.team` = **ทีมหลัก (attribution)** — ทีมเดียวเสมอ ใช้ตอน stamp เจ้าของงานที่สร้างใหม่ (ดีล ลูกค้า โครงการ ใบยื่น เป้า) ยอดและ KPI จึงยังนับเข้าทีมเดียว ไม่มีการนับซ้ำสองทีม

กติกาที่ตามมา:

- ทุกด่านที่ถามว่า "ทีมเดียวกันไหม" ใช้ **การตัดกันของชุดทีม** (`hasTeam` / `inScope`) ไม่ใช่ `===` — รวมถึงมอบหมายงาน ดึงงาน อนุมัติ master data ด่านโมดูลสหมิตร (KA) และด่านธุรกิจบริการ (SV)
- ทุกตัวกรองลิสต์ที่เคยเป็น `.eq('team', user.team)` เป็น `.in('team', ทีมทั้งหมด)` — ผ่านตัวกลาง `lib/teamScope.js` ที่เดียว
- แถวไร้ทีม (`team is null`) ยังเป็นของกลางเหมือนเดิมทุกประการ กติกานี้ไม่ถูกแตะ
- ทีมหลักต้องเป็นหนึ่งในทีมที่สังกัดเสมอ — บังคับที่ `resolveTeamAssignment` ตัวเดียว ซึ่งทั้ง API สร้าง/แก้ผู้ใช้ และฟอร์มหน้าตั้งค่าเรียกใช้ร่วมกัน
- ตำแหน่งที่ไม่ผูกทีม (viewer/legal/staff) ต้องถูกล้าง **ทั้งสองช่อง** ตอนเปลี่ยน role ไม่งั้นขอบเขตทีมเดิมค้างเงียบ ๆ

## กับดักที่เจอจริงตอนตรวจซ้ำ (ห้ามพลาดซ้ำ)

ด่านที่ "ถามเรื่องทีม" ไม่ได้อยู่แค่ใน `permissions.js` — มีอีกสองตระกูลที่พลาดง่าย
เพราะมันอ่าน `app_metadata.team` เองโดยไม่ผ่านตัวช่วยกลาง:

1. **endpoint ที่คืนรายชื่อคน** (`/api/pm/assignable-users`) ต้องส่ง `teams` ไปด้วย —
   ฝั่งจอเอารายชื่อนี้ไปตัดสิน "ทีมเดียวกันไหม" ถ้าได้แต่ทีมหลัก คนที่อยู่หลายทีมจะหาย
   จาก dropdown ทั้งที่ server อนุญาต = จอกับ API ไม่ตรงกัน
2. **ตัวตรวจตอนเขียน** (`validateDealOwner`, `validateLeadAssignee`, ตัวประกอบ
   `assignee` ก่อนเรียก `canAssignTask`) — พวกนี้โหลด user จาก Supabase เองแล้วเทียบ
   `app_metadata.team` ตรง ๆ · เทียบทีมหลักต่อทีมหลักจะปฏิเสธคู่ที่ทำงานทีมเดียวกันจริง
   ซึ่งเป็นเคสหลักของฟีเจอร์นี้พอดี

กติกา: ทุกที่ที่อ่าน `app_metadata` เองต้องผ่าน `userTeams()` เสมอ และด่านเปรียบเทียบ
ต้องเป็น "ตัดกันของชุดทีม" ไม่ใช่ `===`

## ความเข้ากันได้กับข้อมูลเดิม

- **ไม่ต้องรัน migration และไม่ต้อง backfill** — `userTeams()` ถอยไปอ่าน `[team]` เองเมื่อบัญชียังไม่มี `teams` บัญชีเดิมทั้งหมดจึงทำงานเหมือนเดิมทุกประการ
- `teams` ถูกเขียนลง app_metadata ครั้งแรกตอนมีคนกดบันทึกผู้ใช้รายนั้น
- แถวข้อมูลเดิมไม่ถูกแตะเลย — คอลัมน์ `team` ของทุกตารางยังเป็นทีมเดียวเหมือนเดิม การเปลี่ยนแปลงอยู่ที่ฝั่ง "คนคนนี้เห็นแถวไหนได้" เท่านั้น
- ผู้ใช้ที่มีทีมเดียว (ส่วนใหญ่ของระบบ) ได้พฤติกรรมเดิมทุกจุด

## ตัวกรอง "แสดงทีมไหนบ้าง" (เพิ่ม 2026-08-11 รอบสอง)

พอคนหนึ่งคนอยู่หลายทีม ปุ่มขอบเขต "ทีม" กว้างขึ้นเงียบ ๆ — กดแล้วได้สองทีมปนกัน
แยกดูทีละทีมไม่ได้ · แก้ด้วยชิปติ๊กหลายอันข้างปุ่มขอบเขต (`ui/MyTeamsFilter` +
`useMyTeamsFilter`) บนหน้าที่มีขอบเขต "ทีม": คิวลีด · ไปป์ไลน์ดีล · ปฏิทินนัด · คิวคำร้อง

- โผล่เฉพาะคนที่อยู่ตั้งแต่ 2 ทีม — คนทีมเดียวไม่เห็นอะไรเพิ่มและพฤติกรรมเดิมไม่ขยับ
- ตั้งต้นเลือกครบทุกทีม (ตัวกรองมีไว้ *แคบลง* ไม่ใช่บังคับเลือกก่อนใช้งาน)
- เหลืออย่างน้อยหนึ่งทีมเสมอ — ตัวสุดท้ายขึ้นเป็นปุ่มกดไม่ลง ไม่ปล่อยให้ลิสต์ว่าง
  แล้วอ่านเหมือน "ไม่มีข้อมูล"
- ⚠️ กรองฝั่งจอเท่านั้น และแคบกว่าขอบเขตที่ API ให้มาแล้วเสมอ — **ไม่ใช่ด่านสิทธิ์**
- หน้าคิวคำร้องกรองที่ชุดข้อมูลชุดเดียวก่อนแตกแท็บ เพื่อให้ตัวเลขบนแท็บกับตารางตรงกัน

## เลือกทีมตอนสร้างงาน (เพิ่ม 2026-08-11 รอบสาม)

ของใหม่เคยถูกบันทึกเข้า **ทีมหลักเสมอ** ⇒ ดีลที่ AE เปิดให้งานฝั่ง Services ไปโผล่ใน
ยอด ODM ทั้งใบ ตัวเลขทีมกับงานจริงจึงเล่าคนละเรื่อง · เปิดให้เลือกทีมตอนสร้างแทน

- ตัวกลางเดียว `attributionTeam(who, requested)` — **เลือกได้เฉพาะทีมที่ `who` สังกัด**
  ค่าที่ไม่ใช่/ไม่ส่งมา = ทีมหลัก · ไม่มี route ไหนเขียน `body.team` ลงแถวตรง ๆ ได้
  (เทสต์ `teamScope.test.mjs` อ่าน source ห้ามไว้)
- `who` = **คนที่จะเป็นเจ้าของงาน ไม่ใช่คนกด** — ดีลตามเจ้าของ (AE ที่ถูกเลือก)
  ไม่ใช่ AC ที่กดสร้าง · ตัวเลือกบนฟอร์มจึงเป็นทีมของเจ้าของ
- ช่องโผล่เฉพาะตอนมีคำตอบให้เลือกจริง (เจ้าของ/คนเปิดอยู่ตั้งแต่ 2 ทีม) — คนทีมเดียว
  ไม่เห็นช่องนี้เลยและพฤติกรรมเดิมไม่ขยับ
- ลงที่: **ดีล** (ยอด/เป้า) · **ลูกค้า** (ทีมดูแล — เดิม superuser เท่านั้นที่เลือกได้) ·
  **คำร้อง** (เข้าคิวทีมไหน) · **ทะเบียนสรรพสามิต** (คิวภาษีทีมไหน)
- งานที่มี "พ่อแม่" ไม่ถาม — โครงการจากดีล / ทะเบียนจากโครงการ / งานสหมิตร สืบทีม
  จากต้นทางเสมอ ถามซ้ำ = เปิดช่องให้ลูกหลุดไปคนละทีมกับพ่อแม่
- ⚠️ ค่าตั้งต้นและค่าที่ถอยกลับต้องเป็น **ทีมหลัก** ทั้งฝั่งจอและ server — ถ้าฝั่งจอ
  ถอยไป `teams[0]` ชิปจะชี้ทีมหนึ่งแต่งานไปลงอีกทีมเงียบ ๆ (มีเทสต์ตรึงไว้)

**ยังไร้ทีมได้อยู่**: เจ้าของที่ไม่มีทีม (admin/AE Sup เปิดดีลเอง) ยังได้แถวไร้ทีม
เหมือนเดิม — ถัง "ไม่ระบุทีม" ในแดชบอร์ดจึงยังต้องโชว์ (ดู `dashboardReconcile.test.mjs`)

## ผลตามมา

- AE ที่ดูแล ODM + Services ใช้บัญชีเดียว เห็นคิวลีด ดีล โครงการ คำร้อง และงานของทั้งสองทีม
- ยอดขาย/เป้า/KPI ยังอ่านออกเหมือนเดิม เพราะงานหนึ่งชิ้นยังเข้าทีมเดียวเสมอ (ไม่นับซ้ำ) — เปลี่ยนแค่ว่า *ทีมไหน* เลือกได้แล้ว
- หน้าตั้งค่าผู้ใช้: ช่องทีมเป็นแผ่นเลือกติ๊กได้หลายทีม (ไม่ใช่ดรอปดาวน์) และถามทีมหลักเฉพาะตอนเลือกตั้งแต่สองทีมขึ้นไป ตามกติกาคอนโทรลใน `docs/form-design-rules.md` §3
- เลือกทีมของงานรายชิ้นได้แล้ว (ดูหัวข้อ "เลือกทีมตอนสร้างงาน") — ทำโดย**เพิ่มช่องที่ฟอร์ม** ไม่ได้เปลี่ยนความหมายของ `team` ในบัญชีผู้ใช้ · ที่ยังไม่มีคือ "สลับทีมที่ทำงาน" (switcher) ซึ่งตกไปเพราะลืมสลับแล้วยอดเข้าผิดทีมเงียบ ๆ
