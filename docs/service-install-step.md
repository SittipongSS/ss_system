## 1. ของที่มีอยู่แล้ว และใช้ต่อได้

| ของเดิม | ใช้ทำอะไรในงวดนี้ |
|---|---|
| `service_visits.kind = 'install'` | นัดติดตั้งเป็นนัดชนิดนี้ |
| สถานะนัด `draft → scheduled → in_progress → done` | ร่าง = TS ยืนยันวันแล้ว · รอ SA คอนเฟิร์มลูกค้า · ช่างยังไม่เห็น |

- ยังไม่มีที่เก็บคำขอติดตั้งราย SO × ไซต์

- นัดยังไม่รู้ว่าครอบโซนไหนบ้าง (นัดตามรอบครอบทั้งไซต์)
- ยังไม่มีที่เก็บเครื่องที่ TS วางไว้ล่วงหน้า
- ยังไม่มีร่องรอยของการยืนยันวันโดย TS และการคอนเฟิร์มลูกค้าโดย SA

## 2. ข้อมูล (mig 0425_service_install_step.sql ไฟล์เดียว)

หลักคือ **เก็บเฉพาะการตัดสินใจของคน ส่วนสถานะคำนวณสดทั้งหมด** ตามหลักข้อ 7 ของ SO-centric

### 2.1 ธง "ก่อนติดตั้ง" บนงวด
- เพิ่ม `sales_order_installments."beforeInstall" boolean NOT NULL DEFAULT false`
- เพิ่ม trigger กันแก้ธงของงวดที่บัญชีรับรองแล้ว
- ~~CREATE OR REPLACE `_so_installments_write_plan` จาก 0377~~ — **ตกไป** (ดูกล่องแดงหัวเอกสาร)
- Rev. ย้ายงวดด้วย UPDATE `salesOrderId` (0376) ธงจึงติดไปเอง แต่ต้องมีเทสต์ยืนยัน

### 2.2 คำขอติดตั้ง ราย SO × ไซต์
ตาราง `service_install_requests`
- คอลัมน์: `id`, `salesOrderId`, `siteId`, `mode` ('install' | 'none')
- unique (`salesOrderId`, `siteId`)
- `mode='none'` คือ SA เลือก "Service" (ไม่ต้องติดตั้ง) ซึ่งไม่เข้าคิว TS
- วันที่ลูกค้าต้องการ: `requestedDate`, `requestedStartTime`, `requestedEndTime`
- `contactName`, `contactPhone`, `note`
- ร่องรอยคนขอ: `requestedById`, `requestedByName`, `requestedAt`
  - ⭐ `requestedAt` ขยับทุกครั้งที่ SA ขอใหม่ ตัวตัดสินใช้เวลานี้เทียบกับเวลาที่ TS ยืนยัน
- `changeReason` คือเหตุที่ลูกค้าขอเปลี่ยนวัน (บังคับเมื่อขอใหม่หลัง TS ยืนยันแล้ว)

ตาราง `service_install_request_zones` (`requestId`, `zoneId`) เก็บโซนที่ SA ขอ
- server ตรวจว่าทุกโซนอยู่ในรอบขายของใบนี้ที่ไซต์นี้จริง

### 2.3 นัดติดตั้ง
เพิ่มคอลัมน์บน `service_visits`
- `installRequestId` ชี้คำขอติดตั้ง (FK แบบ SET NULL)
  - ไม่ใช้ `requestId` เดิม เพราะคอลัมน์นั้นชี้ dept_requests ของงานประเมิน
- ร่องรอย TS ยืนยันวัน: `tsConfirmedAt`, `tsConfirmedById`, `tsConfirmedByName`
- `dateChangeReason` คือเหตุที่ TS ปรับวัน (CHECK บังคับเมื่อวันไม่ตรงกับที่ขอ ซึ่งตรวจที่ server)
- ร่องรอย SA คอนเฟิร์มลูกค้า: `customerConfirmedAt`, `customerConfirmedById`, `customerConfirmedByName`

ตารางใหม่อีกสองตัว
- `service_visit_zones` (`visitId`, `zoneId`) บอกว่านัดนี้ครอบโซนไหน เพราะ TS แยกโซนเป็นหลายนัดได้
- `service_visit_planned_assets` (`visitId`, `zoneId`, `assetId`) เก็บเครื่องที่ TS วางจากคลังไว้
  - server กันไม่ให้เครื่องเดียวกันถูกวางในนัดติดตั้งที่ยังเปิดอยู่สองใบ

### 2.4 สถานะ (คำนวณสด ไม่เก็บ)
อยู่ใน `lib/service/installQueue.js` เป็นไฟล์ pure และคิดรายโซน

| สถานะ | เงื่อนไข | เจ้าของเรื่อง |
|---|---|---|
| รอฝ่ายขายเลือก | ใบอนุมัติแล้ว ตั้งงานบริการแล้ว แต่ไซต์ยังไม่มีแถวคำขอ | SA |
| ขอคิวแล้ว · รอมัดจำ | โซนยังไม่มีนัดติดตั้งที่เปิดอยู่ และงวด "ก่อนติดตั้ง" ยังรับรองไม่ครบ | SA → FN |
| รอ TS ยืนยันวัน | มัดจำครบแล้ว (หรือใบไม่มีงวดก่อนติดตั้ง) แต่ยังไม่มีนัด หรือ `requestedAt` ใหม่กว่า `tsConfirmedAt` (ลูกค้าขอเปลี่ยนวัน) | TS |
| รอ SA คอนเฟิร์มลูกค้า | มีนัดร่างที่ TS ยืนยันแล้ว และ `customerConfirmedAt` ว่าง | SA |
| นัดยืนยันแล้ว | นัดเป็น scheduled หรือ in_progress | ช่าง |
| ติดตั้งแล้ว | นัดปิดแล้ว และโซนมีเครื่องที่ผล = done | — |

โซนที่ผลเป็น "ติดไม่ได้" ทั้งโซน จะกลับไปที่ "รอ TS ยืนยันวัน"

## 3. ด่าน (ขยาย `visitGate.js` ตัวเดิม ไม่สร้างตัวตัดสินที่สอง)

นัดชนิด `install` ใช้กติกาเฉพาะดังนี้ ส่วนชนิดอื่นไม่เปลี่ยนแม้แต่ไบต์เดียว (ต้องมีเทสต์ล็อกไว้)

| ข้อ | นัดติดตั้ง | เจ้าของ |
|---|---|---|
| ① สัญญา | **ไม่ตรวจ** — สัญญาทำหลังติดตั้ง (มติ 09/11 รอบสอง) · ข้อนี้ขึ้นว่า "ทำสัญญาหลังติดตั้ง" ไม่ใช่ผ่านเงียบ | — |
| ② เงิน | งวดที่ติดธง "ก่อนติดตั้ง" ต้องรับรองครบทุกงวด · ใบที่ไม่มีงวดติดธง = ผ่าน และบอกในรายละเอียดว่า "ใบนี้ไม่มีงวดก่อนติดตั้ง" · ไม่ใช้ paidThrough | SA → FN |
| ③ มีช่าง | เหมือนเดิม | TS |
| ④ ช่วงเวลาที่ไซต์ให้เข้า | เหมือนเดิม | TS |
| ⑤ **ลูกค้ายืนยันนัด** (ข้อใหม่ เฉพาะนัดติดตั้ง) | `customerConfirmedAt` มีค่า | SA |

- ด่านคิดเฉพาะโซนใน `service_visit_zones` ของนัดนั้น
- "มัดจำครบ" ที่คิวและการ์ดใช้คือข้อ ② ของตัวตัดสินนี้ ห้ามเขียนเงื่อนไขซ้ำที่จอ
- ตอน SA กด "ลูกค้ายืนยันแล้ว" server จะประทับร่องรอยแล้วเลื่อนร่างเป็น scheduled ในคำสั่งเดียว ถ้าด่านผ่าน
  - ถ้ามีข้อติดในจังหวะนั้น (เช่นบัญชีถอนคำรับรอง) นัดจะคงเป็นร่าง พร้อมเหตุและเจ้าของเรื่อง

## 6. ค่าตั้งต้นที่ใส่ในแผน (ยังไม่ได้ถาม · บอกได้ถ้าไม่ตรง)

1. (ตัดสินแล้ว 09/11) **ติดตั้งเป็นรายไซต์ · สัญญาเป็นราย SO และทำหลังทุกไซต์ที่เลือก "ติดตั้ง" เสร็จครบ** · การ์ดบน SO ชี้ "ทำสัญญา" เมื่อครบ พร้อมจำนวนเครื่องและจุดจริงรวมทุกไซต์ · ไม่ล็อกการทำสัญญา และยังไม่เติมค่าลงสัญญาเอง
   - "ครบ" = ทุกไซต์ที่เลือกติดตั้งมีทุกโซนเป็น "ติดตั้งแล้ว" · ไซต์ที่เลือก Service ไม่นับ · ไซต์ที่ฝ่ายขายยังไม่เลือก = ยังไม่ครบ
   - ผลตามมา: ไซต์ที่ติดก่อนยังเริ่มรอบไม่ได้จนกว่าจะมีสัญญา (ด่าน ① ของนัดตามรอบเดิม)
2. **นัดร่างที่รอ SA คอนเฟิร์ม กันคิวช่างไว้** โดยตัวเลือกช่างนับเป็น "จองไว้" กัน TS วางช่างคนเดิมซ้ำวันเดียวกัน
3. เมื่อ SA กด "ลูกค้ายืนยันแล้ว" นัดขึ้นตารางช่างเองทันที TS ไม่ต้องกดปล่อยซ้ำ
4. ทั้งเส้นอยู่หลังสวิตช์จนกว่า PR-5 จะขึ้น
5. ไซต์ที่มีเครื่องอยู่แล้ว (ต่อสัญญา) ให้ SA เลือก "Service" ได้ ระบบไม่เดาเอง
6. (PR-3b) แถว "รอฝ่ายขายเลือก" ในแท็บรอติดตั้ง = ไซต์ของใบที่อนุมัติแล้ว ยังไม่ถูกแทนด้วย Rev. ใหม่ และเปิดรอบบริการ (`serviceTermsOpenedAt`) ไม่เกิน **60 วัน** (`INSTALL_UNDECIDED_WINDOW_DAYS`) ที่ฝ่ายขายยังไม่ตอบ — ใบเก่ากว่านั้นถือว่าเดินทางเดิมไปแล้ว ไม่ขึ้นในแท็บ

✅ ข้อ 2 ทำใน PR-4b — นับเป็น "จองไว้" แยกจากภาระบนตาราง (ไม่บวกจุด/แพ็ค เพราะยังไม่แน่ว่าไปวันนั้น) แต่คนนั้นไม่อยู่กลุ่ม "ว่างทั้งวัน" แล้ว · ตารางปฏิทินยังไม่โชว์ร่าง (คงเดิม)
7. (PR-4a) ฝ่ายขายรับคำตอบของลูกค้าได้เฉพาะนัด **ร่าง** — ขึ้นตารางช่างแล้วลูกค้าขอเปลี่ยน = TS เลื่อนนัดพร้อมเหตุที่หน้าจัดคิว (ทางเดิม)
8. (PR-4a) คอนเฟิร์มแล้วแต่ด่านข้ออื่นติด (เช่นบัญชีถอนคำรับรอง) = นัดคงร่าง ฝ่ายขายกดซ้ำไม่ได้ · TS ปล่อยขึ้นตารางเองที่หน้าจัดคิวเมื่อแก้แล้ว
9. (PR-4a) ลูกค้าขอเปลี่ยนวัน ⇒ TS ยืนยันวันใหม่บนนัดเดิม (ไม่ยกเลิกแล้วสร้างใหม่) — โซนและเครื่องที่วางไว้คงเดิม
