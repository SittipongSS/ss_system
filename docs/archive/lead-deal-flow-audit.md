# ผลตรวจสาย LD → DL → PJ → QT — รอยรั่วที่ล้มเหลวเงียบ

> สถานะ: **แก้แล้วทั้งหมด · merged 2026-08-04** (PR #927, commit `9ad04abb`, migration 0199)
> ที่มา: เดินสายลีด → ดีล → โครงการ → ใบเสนอราคา ทีละขั้นเพื่อดูว่าข้อมูลไหลครบไหม
> จุดร่วมของทั้งห้าเรื่อง: **ไม่มี error บนหน้าจอ** ผู้ใช้เห็นว่างานสำเร็จทุกครั้ง แต่ข้อมูลหายหรือเพี้ยนอยู่ข้างหลัง

## 0. ทำไมต้องมีเอกสารนี้

ทั้งห้าเรื่องเป็นบั๊กประเภทเดียวกัน: **เขียนไม่ลงแล้วไม่มีใครรู้** ไม่ใช่เพราะโค้ดผิดตรรกะ แต่เพราะ
ปลายทางที่เขียนกับสิ่งที่ schema ยอมรับไม่ตรงกัน แล้วผลลัพธ์ของการเขียนไม่ถูกอ่าน จึงไม่มีสัญญาณอะไร
เตือนเลย — บั๊กแบบนี้ค้างได้เป็นเดือนและถูกจับได้ก็ต่อเมื่อมีคนไล่ดูข้อมูลจริงทีละแถว

เอกสารนี้บันทึกไว้เพื่อสองเรื่อง: ให้ตามได้ว่าประวัติที่หายไปหายช่วงไหน และกันไม่ให้แพตเทิร์นเดิม
กลับมาอีกในเส้นทางอื่น

## 1. ห้าจุดที่เจอ

### 1.1 `lead_events.kind = 'create_deal'` ชน CHECK ทุกครั้ง

CHECK ของ `lead_events.kind` (mig 0091) มีชุดค่า `create/screen/assign/contact/meeting/qualify/disqualify/bounce/update`
ซึ่ง **ไม่มี `create_deal`** แต่ `POST /api/sales-planning/deals` เขียนค่านี้ทุกครั้งที่เปิดดีลจากลีด
insert จึงชน constraint ทุกครั้ง และเพราะเป็น fire-and-forget ที่ไม่อ่าน error กลับมา จึงเงียบสนิท

ผลจริง: เปิดดีลจากลีดแล้ว **ไม่มีเหตุการณ์ "สร้างดีล" ในประวัติของลีดเลย** และลีดใบเดียวที่แตกดีล
ใบที่ 2, 3 … ไม่ทิ้งร่องรอยอะไรไว้เลย (ใบแรกยังพอเดาได้จากสถานะที่เปลี่ยนเป็น qualified)

- แก้: mig 0199 เปิด `create_deal` เข้าชุด + route อ่าน error แล้ว `console.error` แทนการกลืน
- ยังไม่ทำให้ทั้ง request ล้ม: ดีลถูกสร้างและลีดถูกปิดไปแล้วก่อนถึงบรรทัดนี้ ตอบ 500 จะทำให้หน้าเว็บ
  เข้าใจผิดว่าเปิดดีลไม่สำเร็จทั้งที่สำเร็จ
- **ไม่ backfill** — เหตุการณ์ที่หายไปไม่มีเวลา/ผู้ทำที่เชื่อถือได้เหลืออยู่ การเดาเวลาย้อนหลังลงตาราง
  audit/KPI คือการสร้างหลักฐานปลอม · ประวัติเริ่มนับครบตั้งแต่วันที่รัน 0199

### 1.2 `POST /deals/[id]/timeline` ดึงสถานะดีลถอย

route สะกดลิสต์สถานะเองว่า `['lead','qualified','quotation']` แล้วดันเป็น `timeline_proposed`
ผลคือดีลที่ออกใบเสนอราคาไปแล้ว แต่โครงการถูกลบ (FK SET NULL — mig 0064) แล้วกลับมาทำไทม์ไลน์ใหม่
จะถูก **ดึงถอย** กลับมาขั้นเสนอไทม์ไลน์ทั้งที่ใบเสนอราคายังอยู่ — ผิดมติ B4 (2026-07-28 ห้ามถอยขั้น)

กติกาห้ามถอยถูกตรึงไว้ที่ระดับฟังก์ชัน (`advanceStage` + `dealStageOrder.test.mjs`) อยู่แล้ว
แต่ route นี้เลี่ยงฟังก์ชันไปเขียนเอง — แก้เป็นเรียก `advanceStage` ที่เดียวเหมือน `create-project`/`link-project`

### 1.3 `createQuotationDraft` ดันขั้นโดยไม่เขียนประวัติ

ดัน stage → `quotation` แต่ไม่เขียน `sales_deal_stage_history` ⇒ ขั้น "เสนอราคา" หายจากเส้นเรื่องของดีล
และ `daysInStage` นับยาวเกินจริงเพราะยังอ้างอิงเวลาที่เข้าขั้นก่อนหน้า

### 1.4 โฟลเดอร์ไฟล์แนบของลีดชื่อเป็น id ดิบ

`SALES_THREAD_FOLDER.lead` ตั้ง `labelKeys: ['name','companyName','title']` ซึ่ง **ไม่มีสักคอลัมน์**
ใน `sales_leads` (mig 0091 ใช้ `contactName`/`company`) ⇒ `docLabel` หาไม่เจอแล้วตกไปใช้ `String(row.id)`
⇒ โฟลเดอร์ของลีดทุกใบชื่อ `LEAD-xxxxxxxx` เปิด Drive มาแล้วไม่รู้ว่าของใคร ทั้งที่สกรีนช็อตแชท/นามบัตร
คือหลักฐานต้นทางของลีด — แก้ labelKeys เป็นคอลัมน์ที่มีจริง

### 1.5 PATCH โครงการเขียนทับ `metadata` ทั้งก้อน

รับ `metadata` จาก client แล้ว replace ทั้งก้อน ⇒ กุญแจที่ route อื่นเขียนไว้หลุดหายเงียบ ๆ:
`dealOrder` (PUT `/deal-order`), `salesDealId`/`salesDealTitle`/`source` (create-project)

ฟอร์มฝั่งหน้าเว็บ spread ของเดิมมาให้ก็จริง แต่นั่นคือ snapshot ตอนเปิดฟอร์ม — จัดลำดับดีลระหว่าง
ฟอร์มเปิดค้างแล้วกดบันทึก = ลำดับที่เพิ่งจัดถูกย้อนกลับ · แก้เป็น merge ทับของเดิมเสมอ (กติกาเดียวกับ PATCH ดีล)
และไม่รับค่าที่ไม่ใช่ object เพราะไม่มีเส้นทางที่ตั้งใจล้าง metadata ทั้งก้อน

### 1.6 ของแถม — dropdown มอบหมายลีดว่างสำหรับทุก role ที่ไม่ใช่แอดมิน

หน้ารายละเอียดลีดยิง `/api/users` ซึ่งเปิดให้แอดมินเท่านั้น ⇒ `senior_ae`/`ac`/`ae_supervisor`
ได้ dropdown ว่าง มอบหมายลีดไม่ได้เลย — เปลี่ยนไปใช้ `usePeopleDirectory` ชุดเดียวกับหน้ารายการ

## 3. บทเรียนที่ควรใช้ต่อ

1. **การเขียน audit/event ที่ไม่อ่าน error = ไม่มีการเขียน** ถ้าเลือกไม่ให้ทั้ง request ล้ม อย่างน้อยต้อง log
2. **CHECK constraint กับค่าที่โค้ดเขียน ต้องมีเทสต์จับคู่กัน** ไม่งั้นทั้งสองฝั่งเดินหนีกันได้โดยไม่มีใครรู้
3. **กติกาข้ามขั้น/ห้ามถอย ต้องมีฟังก์ชันเดียว** และเทสต์ต้องสแกนว่าไม่มีใครเลี่ยงฟังก์ชันนั้น
4. **`metadata` jsonb ที่หลาย route เขียน ต้อง merge เสมอ** การ replace ทั้งก้อนคือการลบงานของ route อื่น
5. **ค่าคงที่ที่อ้างชื่อคอลัมน์ ต้องมีเทสต์ยันกับ schema จริง** — พิมพ์ผิดแล้ว fallback ทำงานเงียบเป็นเดือน
