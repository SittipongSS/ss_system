# ต้นแบบเส้นงานที่มี SO เป็นศูนย์กลาง (SO-centric workflow model)

**สถานะ:** มติเคาะแล้ว (2026-08-30) — ใช้เป็นแม่แบบเวลาเปิดเส้นงานใหม่
**ที่มา:** ออกแบบครั้งแรกกับเส้นบริการหมวด 02-001 → [service-contract-phase-plan.md](service-contract-phase-plan.md)
(ม็อกรายจอ + ม็อกเดินเรื่องกดได้อยู่ในไฟล์ชุดเดียวกัน) — เส้นนั้นคือ reference implementation ของโมเดลนี้

> **มติผู้ใช้:** *"อยากเอา SO มาเป็นศูนย์กลางการทำงานของทุก ๆ ฝ่ายที่เกี่ยวข้อง
> ทำงานในโมดูลตัวเอง เพื่อที่จะได้มองในทางเดียวกัน"* — เก็บโมเดลนี้เป็นต้นแบบเพื่อขยายไปเส้นอื่น

---

## หลัก 8 ข้อ

1. **ใบเดียวเป็นศูนย์กลาง** — หน้า SO รายใบคือที่ที่ทุกฝ่ายมาบรรจบ · แต่ละฝ่ายเข้าจาก**คิวในโมดูลของตัวเอง**
   (SA ทะเบียน SO · FN /finance · TS /service/intake …) · **ห้าม**สร้างหน้าศูนย์รวมใหม่ และ**ห้าม**ยุบเมนูฝ่ายเข้าหากัน
   (ต่อยอด module-ownership: เมนูฝ่าย = คิวงาน · หน้า entity = ของกลาง)

2. **เกณฑ์เข้าเส้นตัดสินระดับใบ ด้วยฟังก์ชันตัวตัดสินเดียว** — เช่น เส้นบริการ:
   สายดีล = SERVICE **และ** มีบรรทัดหมวด `02-001` ≥ 1 → ทั้งใบเข้าเส้น ไม่แยกชนิดรายบรรทัด
   · ตัวตัดสินอยู่ lib กลาง ใช้ร่วม ฟอร์ม/คิว/ทะเบียน — ห้ามเขียนเงื่อนไขซ้ำรายจอ
   · อ่านจาก snapshot บนใบ (fgCode) ไม่อ่าน master สด — ใบที่ตรึงแล้วต้องนิ่ง

3. **ทะเบียนกลางมี toggle สาย** — segmented ทุกสาย/SCENT/PRODUCT/SERVICE บนทะเบียนใบสั่งขาย
   เลือกสายแล้ว**คอลัมน์เปลี่ยนเป็นของสายนั้น** (เส้นบริการ: สัญญา · จ่ายถึง · รอบ n/N) — ไม่งอกทะเบียนแยกต่อสาย

4. **การ์ดสรุปงานข้ามโมดูลบนหน้าใบ** — "งาน X ของใบนี้" สรุปความคืบของฝั่งปฏิบัติการ
   (จัดสรร/รอบ/นัดผ่าน-ติดด่าน/จ่ายถึง) + ปุ่มกระโดดไปโมดูลปลายทาง · ตัวเลข**คำนวณสด**จากทะเบียนจริง

5. **เอกสารผูกพันเป็นด่าน และมีทางเข้าสำรอง** — สัญญาเจนจากแม่แบบ *หรือ* "เอกสารภายนอก"
   (PO ลูกค้า/อีเมล/ฉบับกระดาษ) + ผู้อนุมัติที่กำหนดชัด (AE Sup) → นับเป็นเอกสารมีผลด้วยตัวตัดสินเดียวกัน
   — ทางสำรองนี้คือสิ่งที่ทำให้เส้นเปิดใช้ได้โดยไม่รอต้นฉบับ และไล่เก็บของเก่าได้

6. **เงินนำงาน (จ่ายก่อนบริการ)** — งวดผูก**ช่วงวันที่ที่ครอบ** (`coversFrom/To`) ไม่ผูกเลขชิ้นงาน
   → ได้ค่าเดียว **paidThrough** = ครอบถึงวันไหนจากงวดที่*รับรองแล้ว* · สองลายเซ็นเสมอ:
   ผู้ขายแจ้ง → การเงินรับรอง · **"แจ้งแล้ว" ไม่ปลดด่าน**

7. **ด่านก่อนงานขึ้นตาราง** — ตัวตัดสินเดียว (แบบ `visitGate`) ใช้ทั้งปุ่มบนจอและ server
   · **คำนวณสดเสมอ ไม่เก็บผลตรวจลงฐาน** เก็บแค่ร่องรอยการตัดสินใจของคน
   · ตัดสินราย (งาน × ส่วนที่เอกสารครอบ) — จ่ายบางใบ เปิดเฉพาะส่วนใต้ใบนั้น
   · งานติดด่าน = เห็นแต่เทา วางคิวไม่ได้ พร้อมเหตุ + เจ้าของเรื่อง
   · หัวหน้า override ได้ เหตุผลบังคับ ลงบันทึกถาวร ขึ้นบนเอกสารงาน
   · งานชนิด "ปิดเรื่อง/ถอน/สำรวจ" ไม่เข้าด่านเงิน (ไม่งั้นติดตลอดกาลโดยนิยาม)

8. **วงจรต่ออายุปิดเป็นวง** — เขตเวลาเตือน (90 วันก่อนหมด) **คำนวณสดจากวันจบจริง** ไม่เก็บสถานะ
   · followup รายหน่วยงานจริง (ไซต์ ไม่ใช่สัญญา — เพราะจบไม่พร้อมกัน) เปิดค้างได้ใบเดียว
   · จบด้วยการวนกลับต้นเส้น: ดีลใหม่ → ใบใหม่ → **ชี้ของเดิม** (term ใหม่ชี้โซนเดิม) ให้ประวัติต่อเนื่อง

## เช็กลิสต์ตอนขยายไปเส้นใหม่

ตอบ 7 คำถามนี้ให้ครบก่อนเขียนโค้ด (เทียบกับคำตอบของเส้นบริการในวงเล็บ):

1. เกณฑ์ใบเข้าเส้น? (สายดีล + หมวดสินค้า ≥1 บรรทัด)
2. หน่วย "พื้นที่/ของ" ที่งานเกาะ? (ไซต์ → โซน → term)
3. หน่วย "เวลา/รอบ" ของงาน? (รอบต่อไซต์ → gen นัด)
4. งวดครอบอะไร? (ช่วงวันที่บริการ → paidThrough)
5. เอกสารผูกพัน + ใครอนุมัติทางสำรอง? (สัญญา/external + AE Sup)
6. ด่านมีกี่ข้อ ใครเป็นเจ้าของแต่ละข้อ ชนิดงานไหนยกเว้น? (4 ข้อ · SA/FN/TS · ถอน-สำรวจยกเว้นด่านเงิน)
7. วงจรต่ออายุ/ปิดจบเป็นยังไง? (90 วัน + followup + ดีล RE-ORDER ชี้ของเดิม)

## กับดักที่ต้นแบบนี้กันไว้แล้ว — อย่าเอากลับมา

- สถานะที่คำนวณได้ ห้ามเก็บลงฐาน (serviceStatus / ผลด่าน / ใกล้หมดสัญญา)
- ตัวตัดสินซ้ำสองที่ = วันหนึ่งพูดคนละเรื่อง (ปุ่มบนจอ vs server · เงื่อนไขเส้น vs คิว)
- ผูกงวดกับ "เลขรอบ" แทนช่วงวันที่ — รอบเลื่อน/งดแล้วเพี้ยนทันที
- บล็อกแข็งวันแรกกับของเก่าที่วิ่งอยู่ — ต้องมีรอบเปลี่ยนผ่าน (เอกสาร external + override)
- หน้า "ศูนย์รวม" แยกต่างหาก — ของจริงคือหน้า entity เดิม + การ์ด/คอลัมน์เพิ่ม
