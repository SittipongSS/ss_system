### เฟส 1 — ซ่อมสามช่องของขั้นตอน (บั๊กที่ผู้ใช้เจออยู่) — **เสร็จแล้ว 12 ส.ค. 2026**

ทำจริงตามนี้ · เทสต์ล็อกที่ `lib/pm/stepDateSync.test.mjs` (8 เคส) · `npm test` 2801 เคสผ่าน ·
`check:migrations` · `audit:ui` · `eslint` ผ่านทั้งหมด

- **B1** ช่องจำนวนวันในตารางผูก `key={\`dur-${t.id}-${t.durationDays ?? 1}\`}` + Enter เพื่อ commit
  (ท่าเดียวกับมุมมองเอกสาร) — ค่าที่คำนวณจากการแก้วันเริ่ม/วันจบเข้า DOM แล้ว

  ทิ้งคีย์ `finishDate` ที่ว่างก่อนลง drafts — ไม่มี `null` ไหลไปถึง PATCH
- **B3/B4** ฝั่ง server เข้าเงื่อนไขด้วย `'finishDate' in updates` แล้วถอดออกจาก `updates` ทุกกรณี ·

### เฟส 2 — สูตรวันเหลือชุดเดียว — **เสร็จแล้ว 12 ส.ค. 2026**

เดิมมีสามก๊อบปี้: `stepSchedule.js` (ฟอร์ม) · `withOptimisticSchedule` (ตาราง) · บล็อกใน route (server)
คอมเมนต์ใน route เขียนเจตนาไว้แล้วว่า *"ให้ server เป็นเจ้าของการคำนวณวันทำการเพียงเจ้าเดียว"*

ทำจริง:

- `lib/pm/stepSchedule.js` ได้แกนกลาง `resolveStepDates()` เป็น **ที่เดียวที่รู้กติกาสามช่อง**
  พร้อม `snapToBusinessDay()` · `syncStepForm()` (ฟอร์ม) และ `syncStepPatch()` (ตาราง/มุมมองเอกสาร)
  เป็นเปลือกสองใบบนแกนเดียวกัน — ต่างกันแค่รูปข้อมูล (ทั้งฟอร์ม vs เฉพาะคีย์ที่ส่งไปกับแพตช์)
- `withOptimisticSchedule` ในตารางถูกลบทิ้ง · ตารางไม่ import ตัวนับวันทำการอีกแล้ว (เหลือแค่ `setHolidays`)
- server เรียก `durationFromDates()` ตัวเดียวกับฝั่ง client แทนการสะกดสูตรเอง
  (server ยังเป็นเจ้าของ "ความจริง" เหมือนเดิม — เปลี่ยนแค่ว่าสูตรมาจากโมดูลเดียวกัน)
- ผลพลอยได้: วันเริ่มถูก snap เป็นวันทำการ **ทุกทาง** แล้ว เดิมตารางเลื่อนให้แต่ฟอร์มไม่เลื่อน
  ⇒ กรอกวันเสาร์ในโมดัลเคยเห็นวันเสาร์ค้างจนกดบันทึกแล้วเด้งเป็นวันจันทร์
- พฤติกรรมการลากบาร์ในมุมมองเอกสารทั้ง 3 ท่า (ย้าย · ยืดขวา · ยืดซ้าย) เท่าเดิมทุกท่า

**เทสต์**: `stepDateSync.test.mjs` เพิ่ม 6 เคส (รวม 14) — ครอบ `syncStepPatch` ทุกท่า + ratchet
ห้ามตารางนับวันทำการเองอีก และห้าม `withOptimisticSchedule` กลับมา · `npm test` 2807 เคสผ่าน
