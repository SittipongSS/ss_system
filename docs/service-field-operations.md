## 2A. ⭐ `service_assets` ต้องมี `kind` — ไม่ใช่ทุกตัวเป็นเครื่องกระจายกลิ่น

```
service_assets.kind  →  diffuser | reed | soap | alcohol | …
```

**ประกาศชนิดในโค้ด ไม่ใช่ `CHECK` ใน DB** — แพตเทิร์นเดียวกับ `requestTypes.js` / `updateTypes.js` / `attachmentTypes.js` ที่ระบบใช้อยู่แล้ว (เพิ่มชนิดใหม่ = แก้ไฟล์เดียว ไม่ต้องออก migration ทุกครั้ง)

### 2A.1 หน่วยของแถว — แล้วแต่ชนิด (มติผู้ใช้ 2026-08-02)

| ชนิด | 1 แถว = อะไร | เหตุผล |
|---|---|---|
| `diffuser` | **1 เครื่อง** | มี serial · มีค่าตั้งรายตัว (เครื่องที่ 2 Grade 5 · เครื่องที่ 5–8 Grade 3) · เปลี่ยนเครื่องรายตัวได้ |
| `reed` · `soap` · `alcohol` | **1 แถว + จำนวนจุด** | ไม่มี serial รายจุด · ค่าตั้งเหมือนกันทั้งชุด · 242 แถวคือขยะ |

⚠️ **ผลตามมา**: `service_assets.serial` unique index ปัจจุบันบังคับ "เครื่องเดียวโผล่สองไซต์ไม่ได้" (`0187:104`) — ยังใช้ได้ เพราะชนิดที่ไม่มี serial จะปล่อยว่าง และ index เป็น partial `WHERE serial IS NOT NULL`

### 2A.2 ค่าตั้งเฉพาะชนิด

| ชนิด | ค่าตั้ง |
|---|---|
| `diffuser` | `workSec`/`pauseSec` · `schedule[]` · `grade` · ขนาดขวด |
| `reed` | ขนาดขวด · จำนวนก้าน · รอบเปลี่ยนก้าน |
| `soap` / `alcohol` | ขนาดถัง · ชนิดน้ำยา (สบู่โฟม / เจล / แอลกอฮอล์) |

**คอลัมน์ร่วม** (kind · label · floor · spot · model · colour · serial · qty · productId · installedAt · removedAt · status) เป็นคอลัมน์จริง
**ค่าตั้งเฉพาะชนิดอยู่ใน `settings jsonb` แล้วตรวจที่ API ตาม `kind`** — แพตเทิร์นเดียวกับที่ `dept_requests` บังคับ `title`/`dealId` ที่ API ไม่ใช่ `CHECK` เพราะกฎขึ้นกับชนิด เขียนเป็น CHECK แล้วอ่านไม่รู้เรื่อง

### 2A.3 ⭐ ภาระงาน = จุด × น้ำหนักตามชนิด ไม่ใช่จำนวนจุดดิบ

- 242 จุดสบู่ = 900 คน-นาที ⇒ **~3.7 นาที/จุด**
- เครื่องกระจายกลิ่นใช้เวลาต่อจุดมากกว่ามาก (เปิดฝา · เติม · ตั้งค่า · ถ่ายรูปหน้าจอ)

⇒ เอา "จำนวนจุด" ดิบมาเป็นภาระ **AWC จะกินเพดานทั้งสัปดาห์** ทั้งที่จริงคือหนึ่งวันของสามคน

**⭐ ทางออกที่ไม่ต้องเดาเลข**: พอ F-3 เก็บ `actualStartTime`/`actualEndTime` เป็น stamp จริงแล้ว
**ให้ระบบเรียนน้ำหนักจากของจริง** — นาทีเฉลี่ยต่อจุดแยกตามชนิด แทนที่จะตั้งค่าคงที่ไว้แล้วไม่มีใครกล้าแก้

⇒ นี่คือเหตุผล**ข้อที่สอง**ว่าทำไม stamp เวลาต้องมาก่อน: ไม่ใช่แค่ตอบ "ช่างถึงยัง" แต่เป็นข้อมูลที่ทำให้ตารางจัดคิวคิดเลขถูกในเดือนที่สาม

### 4.1 เปลี่ยนเครื่อง

> *"ทางทีมพบว่า เครื่องบริเวณทางเข้าชั้น 3 ชำรุด ทางทีมได้นำเครื่องมาเปลี่ยน สามารถทำงานปกติแล้วครับ"*

⇒ ต้องเป็น **asset ตัวเก่า `removedAt` + ตัวใหม่ `installedAt`** ไม่ใช่ข้อความในช่องหมายเหตุ
ไม่งั้น **ทะเบียนเครื่องเพี้ยนตั้งแต่เดือนแรก**

**นัดถอนเครื่อง (`remove`) ใช้หลักเดียวกัน + ช่างแจ้งเครื่องชำรุด — 2026-09-11 · ไม่มี migration** · ของเดิมปิดนัดถอนแล้ว
ทะเบียนไม่ขยับเลย (เครื่องที่ถือออกจากร้านไปแล้วยัง "ใช้งานอยู่" ที่ไซต์ลูกค้า)
- ติ๊ก **"ถอนแล้ว"** = ตอนปิดงาน ระบบสั่งคำสั่ง `return` ("ถอดออกจากไซต์") ให้เอง — ได้แถวประวัติ
  (วันที่เข้าจริง · เหตุผลจากโน้ตของนัด · ชื่อช่าง) แล้วเครื่องกลับเป็น **"ว่าง"** (`in_stock` · ไม่มีไซต์)
  ⚠️ **ไม่ใช่ `removed`** — ตั้งแต่ mig 0332 คำนั้นแปลว่าปลดระวาง (สมมติฐานตามม็อกทะเบียนเครื่อง
  จอ "ถอนกลับคลัง" · ยังไม่มีมติเขียนไว้)
- นัดถอนมีแค่ "ถอนแล้ว / ถอนไม่ได้" — ไม่มี "เปลี่ยนเครื่อง"
- ผลของเครื่องที่ **ไม่ได้ติดตั้งอยู่ที่ไซต์นี้แล้ว** (ถอนออก · ถูกเปลี่ยน · ส่งซ่อม) แช่แข็ง: แก้/ลบจาก
  แผ่นปิดงานไม่ได้ · ถอนผิด ให้ผู้จัดคิวสั่ง "ติดตั้งเข้าไซต์" ที่หน้าเครื่อง (นัดเดิมจะไม่ถอนทับอีก)
- นัดถอนที่ถอนเครื่องออกไปแล้ว ปิดเป็น "เข้าแล้ว/ทำไม่ครบ" ตลอดไป (เปลี่ยนเป็นเข้าไม่ได้/ยกเลิกไม่ได้) ·
  รับเครื่องที่ติดตั้ง **หลังวันที่ของนัด** ไม่ได้ · ช่างเลื่อนวันที่เข้าจริงของนัดถอนที่ปิดแล้วไม่ได้
- **ช่างแจ้ง "เครื่องชำรุด" ได้จากแผ่นปิดงาน** (ข้อ H) — สวิตช์รายเครื่อง + อาการ ⇒ คำสั่ง
  "แจ้งเปลี่ยนสภาพ" ลงทะเบียนพร้อมแถวประวัติ (ชื่อช่าง · อาการ) · ด่านสิทธิ์เป็นของ **นัด** (เฉพาะเครื่อง
  ที่ติดตั้งอยู่ที่ไซต์ของนัดที่ตัวเองถูกมอบหมาย) ไม่ได้เปิดเส้นคำสั่งย้ายให้ role ช่าง · แจ้งได้ทางเดียว
  ปกติ → ชำรุด (ซ่อมแล้วผู้จัดคิวแก้กลับที่หน้าเครื่อง) · ใบส่งงานขึ้นป้าย "เครื่องชำรุด" · ช่องสภาพเครื่อง
  ถูกล็อกในฟอร์มแก้ข้อมูลเครื่องแล้ว
- 🪤 **ยังค้าง:** เส้น "เปลี่ยนเครื่อง" ข้างบนยังเขียน `status: 'removed'` ตรง ๆ ไม่มีแถวประวัติ และกลืน
  error ของ update เงียบ (เช่นวันถอดก่อนวันติดตั้ง ⇒ ผลบอกเปลี่ยนแล้วแต่ทะเบียนยังใช้งาน) · เครื่องที่
  ถอนไม่ได้ในนัดถอนไม่มีงานตามต่อ · รอบ/นัดเติมที่ขึ้นตารางไว้แล้วของไซต์ที่ไม่ต่อสัญญายังค้างอยู่ ·
  เครื่องสถานะ "ซ่อม" ที่ยังชี้ไซต์ลูกค้า นัดถอนไม่เห็น

### 4.2 ทำไม่ครบ

> *"เนื่องจากในส่วนของ Reed diffuser ยังอยู่ในขั้นตอนปรับสูตร ทางทีมจึงยังไม่ได้ Service ครับ"*

เครื่อง 4 ตัวทำแล้ว · Reed 6 ขวดยังไม่ได้ทำ ⇒ **ปิด `done` ก็โกหก ปิด `unable` ก็โกหก**

### ⇒ มติ: ปิดงาน **รายเครื่อง** สถานะใบสรุปจากลูก

```
สถานะนัด:  scheduled ─[เริ่มงาน]─▶ in_progress ─[ปิดงาน]─▶ done
                                        │                 ├─▶ partial  (ทำไม่ครบ)
                                        └─────────────────┴─▶ unable   (ไปแล้วทำไม่ได้ · บังคับเหตุผล)
```

**เพิ่ม 3 ค่าเท่านั้น** — `in_progress` · `partial` · `unable`
❌ ไม่เอา "ออกเดินทาง / ถึงไซต์" — ต้องกดตอนขับรถ ไม่ปลอดภัยและลืมแน่

## 5. เวลาต้องเป็น stamp ไม่ใช่ช่องกรอก

⭐ **`actualStartTime` / `actualEndTime` มีอยู่ในตารางแล้ว** (`0188:68`) แต่วันนี้ช่างกรอกทีเดียวตอนปิดงาน = **เลขที่พิมพ์ย้อนหลัง ไม่ใช่เวลาจริง**

⇒ ปุ่ม "เริ่มงาน" ไม่ได้เพิ่มข้อมูลใหม่ มัน**ทำให้ช่องที่มีอยู่แล้วเชื่อถือได้**

### 🪤 กับดัก 3 อัน

1. **ต้อง stamp ที่ server ด้วย `now()`** — ใช้เวลาเครื่องช่าง เปลี่ยนเวลาในมือถือแล้วเพี้ยนโดยไม่มีอะไรจับได้
2. **แก้ย้อนหลังได้ แต่ต้องเห็นว่าแก้** — ใช้โทเคน `--origin-edited` ที่ระบบมีอยู่แล้วสำหรับ "แก้ไขโดยผู้ใช้"
3. **ลืมกดปิดงานจะเกิดแน่** — งานค้าง `in_progress` ข้ามเที่ยงคืนต้องเด้งขึ้นหัวจอเช้าวันถัดไป (กลุ่ม "ค้างอยู่" เดิมกรอง `status !== 'done'` อยู่แล้ว จะครอบให้เอง **ถ้าไม่เผลอไปเขียนกฎใหม่**)

## 6. หัวหน้ามอนิเตอร์จากไหน — สองชั้น

| ชั้น | ที่ไหน | ตอบอะไร |
|---|---|---|
| **ดัน** (แทนการแท็ก) | แจ้งเตือน + เธรดของไซต์ | "ต้าเพิ่งส่งงาน Outlet 93 — มีเครื่องชำรุด 1 ตัว" |
| **ดึง** (เปิดดูเอง) | **ภาพรวม `/service`** — แถบ **"ส่งงานล่าสุด"** | "วันนี้ส่งมาแล้วกี่ใบ ใบไหนต้องดู" |

⚠️ **ดันเฉพาะใบที่ผิดปกติ** — ถ้าดันทุกใบ = LINE เวอร์ชันในระบบ หัวหน้าจะปิดแจ้งเตือนภายในสัปดาห์เดียว
ป้าย "ต้องดู" = เปลี่ยนเครื่อง · ทำไม่ครบ · ไม่มีลายเซ็น · ค่าตั้งเปลี่ยน

🔴 **แจ้งเตือน Google Chat ถูกถอดออกทั้งระบบแล้ว** (mig 0236 · 2026-08-12) ⇒ ชั้น "ดัน" ทำงานในระบบเท่านั้น (กระดิ่ง + ป้ายตัวเลข)

คอลัมน์ชั้น" ซึ่งได้ **ไซต์เปล่าค้างในทะเบียนทั้งกอง · โซน 0 · เครื่อง 0** ไม่ใช่ล้มทั้งยวงให้รู้ตัว

### สองอย่างที่ทำให้ใช้จริงได้

1. **จับคอลัมน์ด้วยชื่อหัวตาราง ไม่ใช่ตำแหน่ง** — ชีตถูกแทรก/ย้ายคอลัมน์มานับครั้งไม่ถ้วน · หัวที่ระบบไม่รู้จักขึ้นบนจอ ไม่เงียบ

⚠️ **ไม่มีทรานแซกชันครอบทั้งงาน** (PostgREST ทำให้ไม่ได้) — ออกแบบให้ล้มกลางทางแล้วรันซ้ำได้แทน

⚠️ **สิทธิ์แคบกว่าการแก้รายใบ**: `canImportServiceData` = **ผู้ดูแลระบบเท่านั้น** (มติ 2026-08-30 ·
ยามอยู่ที่ `importAccess.test.mjs`) — ช่างและหัวหน้าฝ่าย TS ที่แก้ไซต์รายใบได้ ยังนำเข้าไม่ได้
เพราะเขียนทีเดียวหลายร้อยแถวและระบบไม่มีถังขยะ

**มติ 08/09/2026: คงไว้ที่แอดมิน** — ข้อความบนจอและ API ทั้งสี่จุดเคยเขียนว่า "หัวหน้าฝ่าย
บริการขึ้นไป" ซึ่ง **กว้างกว่าด่านจริง** ⇒ หัวหน้า TS ที่เปิด URL ตรงจะอ่านว่าตัวเองมีสิทธิ์
แล้วโดนปฏิเสธ — อาการที่คนจะรายงานว่า "ระบบพัง" ไม่ใช่ "ไม่มีสิทธิ์" · แก้ข้อความให้ตรงโค้ดแล้ว
พร้อมบอกทางที่เหลือจริง (เพิ่มไซต์ทีละใบที่ทะเบียน — ปุ่ม **"เพิ่มไซต์ย้อนหลัง"** §10C · มีตั้งแต่ 2026-09-11)

🔴 **ถ้าวันหนึ่งจะเปิดสิทธิ์จริง ต้องตอบเรื่องการเก็บกวาดก่อน** — หัวหน้า TS ลบไซต์เปล่าได้
แต่ไซต์ที่มีโซน/เครื่อง/นัดได้ 409 และ force เป็นของแอดมิน ⇒ ไม่มีทางถอนรอบนำเข้าเป็นก้อน
· audit ของการนำเข้าเก็บแค่จำนวน **ไม่เก็บ id ที่สร้าง** ⇒ ต้องเปิดพร้อม "ถอนรอบนำเข้านี้"

## 10B. ที่มาของไซต์ — ที่อยู่ลูกค้า และโครงการ (มติ 2026-08-29)

### ที่อยู่: ก๊อปมาตั้งต้น ไม่ผูกให้เปลี่ยนตามกัน

`customers.addresses[]` ตอบ *"ออกบิลที่ไหน · ส่งของที่ไหน"* · `service_sites` ตอบ
*"เครื่องตั้งอยู่ไหน · ช่างเข้าได้เมื่อไหร่"* — คนละคำถาม **ห้ามยุบเป็นตารางเดียว**
(ตัวเลขจริง: ลูกค้า 508 ราย มีหลายที่อยู่แค่ 19 ราย 3.7% · ชีตทีมมี 380 จุดติดตั้ง
จาก 148 ลูกค้า ⇒ ยุบรวมแล้วดรอปดาวน์ "ออกบิลที่ไหน" จะเต็มไปด้วยล็อบบี้กับห้องน้ำ)

| | |
|---|---|
| ก๊อปได้ 4 ช่อง | `address` · `mapUrl` · `contactName` · `contactPhone` — นอกนั้นไม่ตรงกันเลย |
| ก๊อปเมื่อไหร่ | **ตอนคนกดไทล์เท่านั้น** ทั้งโหมดสร้างและโหมดแก้ |
| ทะเบียนว่าง | **ไม่แตะของเดิม** — ไซต์ใบแรกบน production มี `mapUrl` แต่ไม่มี `address` ดึงใหม่แล้วหมุดต้องไม่หาย |
| ที่มา | `service_sites."customerAddressId"` (mig 0313) nullable ไม่มี FK — ที่อยู่เป็นแถวใน jsonb |
| ทะเบียนขยับทีหลัง | **ไม่อัปเดตให้เอง** · ฟอร์มบอกว่าช่องไหนต่าง แล้วมีปุ่ม "ดึงค่าจากทะเบียนมาทับ" ให้คนกด |
| ย้ายไซต์ข้ามลูกค้า | ล้าง `customerAddressId` ทั้งฝั่งจอและฝั่ง API — id ชี้เข้า `addresses[]` ของคนเดิม |

⚠️ **ไม่มี sync ย้อนกลับ** — ที่อยู่ทางภาษีกับที่อยู่หน้างานเป็นคนละความจริง
ห้างแก้ที่อยู่จดทะเบียนไม่ได้แปลว่าเครื่องย้ายชั้น (โรคเดียวกับกระจกชื่อลูกค้าบนเอกสาร)

⚠️ **ฟอร์มไซต์เลือกที่อยู่ได้อย่างเดียว เพิ่มไม่ได้** — ไม่งั้นที่อยู่หน้างานไหลกลับ
เข้าไปอยู่ในตัวเลือกของใบกำกับภาษี

### ที่อยู่หน้างานแยกช่องแบบทะเบียนลูกค้า (มติผู้ใช้ 2026-09-24 · mig 0384)

> *"การพิมพ์ไซต์อื่น อยากให้ฟอร์มเหมือนที่อยู่ของฐานข้อมูล"*

ของจริง 158/169 ไซต์ไม่ได้ตั้งจากทะเบียนลูกค้า (ไทล์ "ที่อยู่อื่น") และเดิมเป็นช่องข้อความก้อนเดียว
⇒ คีย์ไปปนไทย/อังกฤษ ("กรุงเทพมหานคร … Bangkok 10270") · ตอนนี้ฟอร์มไซต์ใช้ **ช่องที่อยู่ตัวเดียวกับทะเบียนลูกค้า**
(`components/master/ThaiAddressFields` — `AddressesEditor` ก็ใช้ตัวนี้ ไม่ใช่ก๊อปหน้าตา)

| | |
|---|---|
| ช่อง | บ้านเลขที่/อาคาร/ถนน (`line1`) · จังหวัด → อำเภอ/เขต → ตำบล/แขวง · ไปรษณีย์เติมจากตำบล · "พิมพ์ข้อความเอง" (`addressOverride`) |
| จังหวัด | **ช่องเดียวกับจังหวัดในรหัสไซต์** (mig 0315) — ย้ายเข้าการ์ดที่อยู่ ไม่มีสองช่องที่ขัดกันได้ · เลือกได้เสมอแม้ที่อยู่ยังเป็นข้อความก้อนเดียว |
| `address` | **ยังเป็นข้อความที่ทุกจออ่าน** · server ประกอบเองทุกครั้ง (`siteAddressText`) ไม่เชื่อข้อความที่ฟอร์มส่งมา |
| ต่างจากที่อยู่ลูกค้าหนึ่งข้อ | **จังหวัดอย่างเดียวไม่ใช่ที่อยู่** — ไซต์มีจังหวัดทุกใบ ถ้านับแบบลูกค้า ไซต์ใหม่ที่ไม่กรอกอะไรจะได้ที่อยู่ "กรุงเทพมหานคร" แล้วผ่านด่าน |
| ไซต์ใหม่ | เลือกอำเภอ/ตำบลแล้วต้องมีบ้านเลขที่ด้วย (`siteCreateMissing`) · พิมพ์ข้อความเองไม่ต้อง |
| ไซต์ยุคก่อน | ข้อความเดิมอยู่ครบ ไม่มี backfill · ฟอร์มเสนอ "แยกที่อยู่อัตโนมัติ" (แยกไม่ออก = ข้อความย้ายไปช่องบ้านเลขที่ ไม่แตะจังหวัด) |
| ไทล์ทะเบียน | ก๊อป **ทั้งชุดฟิลด์ย่อย** · แถวข้อความก้อนเดียว = ล้างฟิลด์ย่อยเดิม · โหมดแก้ที่ทะเบียนคนละจังหวัดกับรหัส = ก๊อปเป็นข้อความก้อนเดียว |
| "ที่อยู่อื่น" หลังกดไทล์ | โหมดสร้าง: ถอดเฉพาะค่าที่ไทล์เติมให้ (`siteAddressUncarry`) — ช่องที่คนแก้ต่อแล้วไม่แตะ · โหมดแก้ไม่ถอด |
| ลำดับบนจอ | ลูกค้า → ไทล์ → **การ์ดที่อยู่ (ติดใต้ไทล์)** → ชื่อไซต์ · เขตวิ่งงาน → รหัสที่จะออก → เวลาเข้า |

🔴 **mig 0384 ต้องรันก่อน deploy** — ตัวออกรหัสทิ้งคอลัมน์ที่ไม่มีเงียบ ๆ ⇒ ด่าน `siteAddressColumnsError`
(sitesRepo) ถามคอลัมน์ก่อนเขียนทั้งสามเส้น (POST · PATCH · legacy-sites) · ยังไม่รัน = 503 ข้อความไทย

### โครงการ: ระบบประทับเอง ไม่มีช่องกรอก และไม่บังคับ

`service_sites."projectId"` (mig 0299) เคยมีคอลัมน์แต่**ไม่มีใครเขียน ไม่มีใครอ่าน**
ตั้งแต่วันแรก · รอบนี้ให้ **วิซาร์ดรับใบสั่งขาย** ประทับให้จากใบที่กำลังเปิดอยู่ —
จุดเดียวที่ระบบรู้คำตอบโดยไม่ต้องถามคน

🔴 **ห้ามบังคับ** ด้วยสี่เหตุผล: (1) โครงการปิดตัวเมื่อรอบเดินเองได้ ไซต์อยู่ตลอด
อายุสัญญา — มัดของถาวรไว้กับของชั่วคราว (2) ของเก่า 380 จุดติดตั้งไม่เคยมีโครงการ

สืบย้อนได้อยู่แล้ว: ไซต์ → โซน → term → บรรทัดขาย → SO → `projectId`

⚠️ ทั้งสองช่อง**ไม่มี FK** ⇒ ด่านตรวจอยู่ที่ `lib/service/siteReferences.js` เท่านั้น —
ที่อยู่ต้องเป็นแถวของลูกค้ารายนี้ · โครงการต้องมีจริงและเป็นของลูกค้ารายเดียวกัน

## 10C. เพิ่มไซต์ย้อนหลัง — ไซต์ · โซน · จุดติดตั้ง (มติผู้ใช้ 2026-09-11)

สถานะ: **รอตรวจ** · ม็อก `mockups/legacy-site` · mig **0354** (`service_zones.spots`)

**ทำไมต้องมี** — ของจริง ~380 จุดติดตั้ง / 148 ลูกค้าอยู่ในชีต แต่ทางที่มีใช้กับของเก่าไม่ได้สักทาง:
ตัวนำเข้าเป็นของแอดมินคนเดียว (§10A) และชีตไม่มีคอลัมน์จังหวัด/ชั้น · ไซต์ปกติเกิดที่ใบประเมิน
พื้นที่เท่านั้น (มติ 30/08) ⇒ ไซต์เก่าต้องเปิดใบประเมินปลอม · มติ 08/09 เขียนว่า "ทางที่เหลือคือ
เพิ่มไซต์ทีละใบที่ทะเบียน" แต่ไม่เคยมีปุ่ม

**ขอบเขตที่ผู้ใช้เคาะ** — *"เพิ่มแต่ ไซต์ โซน จุด — ยังไม่ต้องเชื่อมเครื่อง กับ SO สัญญา การจ่าย"*
⇒ API อ่านแค่ `site · zones · targetSiteId · preview` (ยามอยู่ที่ `legacySite.test.mjs`)

| มติ | สิ่งที่ทำ |
|---|---|
| ปุ่ม | หัวทะเบียนไซต์ ข้าง "นำเข้าข้อมูลเก่า" · สีกลาง ไอคอนนาฬิกาย้อนหลัง · ไม่มีสิทธิ์ = ไม่เห็นปุ่ม |
| A — จุดอยู่ที่ไหน | คอลัมน์ใหม่ `service_zones.spots jsonb` รูป `[{ id, label, note }]` เหมือน spots ของใบประเมิน ไม่มี `selected` · ไม่มีรหัส ไม่มี FK · id คงเดิมข้ามการแก้ (วันหนึ่งเครื่องจะชี้จุดด้วย id นี้) |
| B — ใครใช้ได้ | `canEditService` (แอดมิน · Planner · หัวหน้า/Audit/Senior TS) — ตรงกับสิทธิ์เพิ่มโซนที่มีอยู่ |
| C — ชื่อซ้ำ | ลูกค้าเดียวกันมีไซต์ชื่อเดียวกันแล้ว (รวมที่ปิดใช้งาน) = **บล็อก** + ปุ่ม "เปิดไซต์เดิม" / "เติมโซน/จุดต่อในไซต์นี้" · กุญแจ = `nameKey` ของตัวนำเข้า **แล้วตัดช่องว่างทิ้ง** ("สาขา สีลม" = "สาขาสีลม") |
| D — จุดของโซน vs จุดของใบประเมิน | แยกกัน ไม่ซิงก์รอบนี้ · ทะเบียนโซนของลูกค้าโชว์เลขทะเบียนโซนเฉพาะโซนที่ไม่มีผลประเมิน |

**สามขั้น** — ① ไซต์ (ช่องชุดเดียวกับฟอร์มไซต์ `ServiceSiteFields` + รหัสที่จะออก + ไซต์ที่ลูกค้ามีอยู่)
② โซนและจุด (รางโซนซ้าย · `ServiceZoneFields` + ตัวแก้จุด · "เพิ่มหลายจุด" จากตัวเลขในชีตได้ชื่อ "จุดที่ N")
③ ตรวจก่อนบันทึก (**พรีวิวจาก server** ด้วย `planLegacySiteRow`/`planLegacyZones` ตัวเดียวกับตอนบันทึก —
บทเรียน #1685) → หน้าผลพร้อมรหัสจริง

**ไม่มีทรานแซกชันครอบทั้งงาน** — ตรวจทุกด่านก่อนเขียนแถวแรก · เขียนไซต์ → โซนทีละแถว (จุดไปพร้อมโซน)
· โซนไหนล้มข้ามเฉพาะโซนนั้น แล้วหน้าผลบอกว่าเหลืออะไร → "ส่งส่วนที่เหลืออีกครั้ง" = โหมดเติมต่อ
(`targetSiteId`) ไม่สร้างไซต์ซ้อน · กดบันทึกแล้วเน็ตหลุด = ไม่ลองซ้ำเอง กดใหม่จะชนด่านชื่อซ้ำแล้วพาเข้าโหมดเติมต่อ

## 11. ยังไม่ตัดสิน

- **`Grade 3/5` แมปกับ work/pause ยังไง** — เดาจากข้อมูลว่าเป็น preset แต่ยังไม่มีใครยืนยันตาราง
- **เพดานภาระต่อคนต่อวันควรเป็นเท่าไหร่** — ของเดิมตั้ง 5 นัด/คน/วัน ซึ่งไม่มีที่มา · รอ F-3 เก็บเวลาจริงสัก 1–2 เดือนก่อนตั้งเลข
- **ชนิดอุปกรณ์มีอีกไหมนอกจาก 4 ชนิด** — `diffuser` / `reed` / `soap` / `alcohol` มาจากที่เจอในข้อมูลและที่ผู้ใช้ระบุ · เพิ่มทีหลังได้โดยไม่ต้อง migration
- **แพ็คของ reed/สบู่ คิดต่อจุดหรือต่อชุด** — 17 แถวที่ใช้ Reed อย่างเดียวช่องแพ็คว่างหมด จึงยังไม่มีตัวอย่างให้ดูสูตร
