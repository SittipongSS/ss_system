**สถานะ: บทวิเคราะห์ + มติ · ยังไม่เริ่มเขียนโค้ด**

- เขียน: 2026-08-02
- ต่อจาก: `docs/business-line-vs-project-seam.md` (#868), `docs/service-business-system-plan.md` (#872), `docs/service-field-operations.md` (#886) — merged ครบ
- คำถามตั้งต้น: *"เรามีการแบ่ง Product หรือ Service แล้ว ควรแบ่งในระดับไหน ดีลหรือโครงการ"* · *"TS จะมีอะไรส่งมามั้ยคล้ายระบบ tax หาก SO มาแล้ว ก็ส่งต่องานมา"*

## 0. สองคำตอบสั้น

1. **`line` อยู่ที่โครงการ · `type` อยู่ที่ดีล** — แม่แบบไทม์ไลน์คือคู่ `(project.line, deal.type)`
2. **ลูกศรที่ 3 ใช้แพตเทิร์นเดียวกับ tax เป๊ะ** — `lib/service/handoff.js` (บริสุทธิ์) + loader + โผล่หลายที่ด้วยตัวตัดสินเดียว

## 1. `line` ที่โครงการ · `type` ที่ดีล

| แกน | อยู่ที่ | ตัดสินอะไร |
|---|---|---|
| **`line`** `PRODUCT` \| `SERVICE` | **โครงการ** | *"งานนี้จบยังไง"* — ส่งของแล้วจบ vs **ตั้งรอบดูแลตลอดกาล** |
| **`type`** `SCENT` \| `NPD` \| `RE-ORDER` | **ดีล** (มีอยู่แล้ว) | *"ใบนี้เติมช่วงไหนของเส้นทาง"* |

**แม่แบบ = คู่ `(project.line, deal.type)`** — ไม่ใช่ข้ามชั้นแบบผิด แต่เป็น **บริบท × ส่วน**
โครงการบอกว่าเส้นทางนี้จบแบบไหน · ดีลบอกว่าใบนี้เติมช่วงไหน

⭐ **โค้ดพร้อมรับอยู่แล้ว** — `buildAppendedTasks(project, { dealType })` (`schedule.js:229`) รับ `project` เข้ามาอยู่แล้ว
วันนี้บรรทัด `:230` เอา `dealType` ไปทับ `project.type`:

```js
const segProject = { ...project, type: dealType, startDate: ... };
```

⇒ เปลี่ยนเป็น lookup `(project.line, dealType)` ได้เลย **โดยไม่ต้องรื้อ signature**

## 2. เคสที่ตัดสิน — ดีล SCENT ใบเดียวใช้ได้ทั้งสองสาย

> **ผู้ใช้ 2026-08-02:** *"ดีลที่เป็น SCENT ของลูกค้า 1 เจ้า อาจจะถูกใช้ได้ทั้งกับโครงการที่เป็น product และ service"*

**ระบบรองรับอยู่แล้ว — แต่ที่ระดับ "กลิ่น" ไม่ใช่ "ดีล"**

`0171:26-37` ทะเบียนกลิ่น:

```
scents.customerId  text NOT NULL   ← ผูกลูกค้า
scents.dealId      text            ← "ดีล SCENT ต้นทางที่สั่งออกแบบ" nullable
```

คอมเมนต์ในไฟล์เขียนไว้เอง: *"มติ 9: กลิ่นที่ออกแบบให้ลูกค้า A ใช้กับ B ไม่ได้ → **ผูกลูกค้าเสมอ** ไม่มีแนวคิด 'กลิ่นกลาง'"*

⇒ **กลิ่นผูกกับลูกค้า ไม่ได้ผูกกับดีลหรือโครงการ** · `dealId` เป็นแค่ที่มา

### เคสเดินยังไง

```
ดีล SCENT ── ผูกโครงการ A (PRODUCT) ──▶ แม่แบบ (PRODUCT, SCENT)
   └─ กลิ่นเข้าทะเบียน ผูก customerId
              ↓ ใช้ซ้ำ ไม่ต้องออกแบบใหม่
ดีล SERVICE ─ ผูกโครงการ B (SERVICE) ──▶ แม่แบบ (SERVICE, NPD)
```

**ดีล SCENT ไม่ต้องมี `line` ของตัวเองเลย** — มันสืบจากโครงการที่ผูกอยู่

*(`0089` ดรอป unique เพื่อให้ **N ดีล : 1 โครงการ** — ดีลใบเดียวยังผูกได้แค่โครงการเดียว ซึ่งไม่ขวางเคสนี้)*

## 3. 📌 บันทึกทางที่เดินผิด — กันคนเดินซ้ำ

รอบแรกของบทวิเคราะห์นี้ (ในบทสนทนา ยังไม่ได้ลง docs) **เสนอให้ `line` อยู่ที่ดีล** ด้วยหลักฐาน 5 ข้อ · สองข้ออ่านผิด:

| ข้อ | ที่เคยอ้าง | ที่ถูก |
|---|---|---|
| 2 | *"`projects.type` พิสูจน์แล้วว่าเก็บแกนชนิดที่โครงการแล้วตาย"* | 🔴 **สรุปสาเหตุผิด** — มันตายเพราะ `0008:17` เขียน `default 'NPD'` **แล้วไม่มีใครถูกบังคับให้เลือก** ไม่ใช่เพราะอยู่ผิดที่ · เป็นบทเรียนเรื่อง **default** ไม่ใช่เรื่อง **ตำแหน่ง** |
| 4 | *"SO ผูกดีลเสมอ แต่โครงการไม่เสมอ ⇒ line ต้องอยู่ที่ดีล"* | 🔴 **อ่อนกว่าที่คิด** — `0101:45` `deal_project_required` บล็อก accept ถ้าดีลไม่มีโครงการ · `0107:197` SO **คัดลอก `projectId` จากดีล**ตอนสร้าง ⇒ **ตอน SO เกิด โครงการมีแล้วเสมอ** |

ข้อ 1 (แม่แบบเลือกด้วย `dealType`) · ข้อ 3 (N ดีล : 1 โครงการ) · ข้อ 5 (`lead.serviceInterest` มีอยู่แล้ว) **ยังจริง** แต่ไม่พอจะย้าย `line` ไปที่ดีล

⇒ ข้อ 5 ยังใช้ได้ในรูปอื่น: `leads.serviceInterest` (`0091:17` CHECK `'diffuser'|'workshop'|'product'|'other'`) เป็น**ตัวเสนอค่าตั้งต้นของ `project.line`** ตอนแตกดีลแล้วตั้งโครงการ
🐞 วันนี้แปลงลีด→ดีล ฮาร์ดโค้ด `dealType:"SCENT"` ทิ้ง `serviceInterest` ทั้งก้อน (`leads/page.js:276` — เจอไว้ตั้งแต่ #868)

## 5. ลูกศรที่ 3 — คิวรับงานเข้าบริการ

### แพตเทิร์นที่ tax วางไว้แล้ว

```
ใบเสนอราคา Won ──[1]──▶ Sale Order ──[2]──▶ ใบยื่นชำระภาษี (LG)
                                    ──[3]──▶ สัญญา/ไซต์/รอบ (SA→TS)  ← ของใหม่
```

คอมเมนต์บนหัว `lib/sales/handoffQueue.js` อธิบายปัญหาไว้ตรงกับที่ TS เจอ:

> สองลูกศรนี้เป็น manual ล้วน: **ไม่มีสถานะ "ค้าง" ในตารางไหนเลย** ของที่ยังไม่ถูกกดจึงไม่ปรากฏในคิวใด ต้องมีคนจำเอง

| ไฟล์ | หน้าที่ |
|---|---|
| `lib/sales/handoffQueue.js` | **ตัวตัดสินกลาง** — บริสุทธิ์ ไม่แตะ DB มีเทสต์ |
| `lib/sales/handoffQueueData.js` | ตัวโหลด — รับ supabase client มา (ผู้ใช้ / service-role) |
| โผล่ 4 ที่ | แดชบอร์ดส่วนตัว · แถบเตือนหน้าใบเสนอราคา · การ์ดสรุปเช้าเข้า Chat · **ด่านปิดโครงการ** |

*"เพื่อไม่ให้ตัวเลขบนแต่ละหน้าเพี้ยนหากัน"* ⇒ ของบริการต้องทำแบบเดียวกันเป๊ะ — `lib/service/handoff.js` + `handoffData.js`

### สามคิว ไม่ใช่คิวเดียว

| คิว | เข้าคิวเมื่อ | ออกเมื่อ | ใครทำ |
|---|---|---|---|
| **3a งานใหม่รอทำสัญญา** | SO `approved` · `project.line = 'SERVICE'` · ยังไม่มีสัญญา | สร้างสัญญาแล้ว | SA |
| **3b สัญญาที่ยังไม่มีไซต์/รอบ** | มีสัญญาแต่ไม่มี `service_plans` | ตั้งรอบแล้ว | TS |
| **3c ไซต์ที่ครบรอบแต่ไม่มีนัด** | ถึงรอบแล้วยังไม่มี visit | สร้างนัดแล้ว | TS |

⭐ **คิว 3b กับ 3c คือที่ที่ "102 จุดที่จ่ายเงินแล้วแต่ไม่มีคิวบริการ" หลุดไป** (ตัวเลขจาก #872) — วันนี้ไม่มีคิวไหนจับมันได้ มันไม่ได้หายไปไหน มันแค่**ไม่เคยปรากฏ**

### สามธงบนหน้าของ TS — เพื่อวางแผน ไม่ใช่เพื่อไปตาม

| ธง | TS เอาไปทำอะไร |
|---|---|
| 💰 **ค้างจ่าย** | นัดไม่ได้ (ติดด่าน) ⇒ **อย่าเพิ่งจัดคนลงตาราง** |
| ⏰ **ใกล้หมดสัญญา X วัน** | ⇒ **อย่าเพิ่งสั่งน้ำหอมล็อตใหญ่** ไปเติม |
| 📄 **ยังไม่ได้สัญญาคืนจากลูกค้า** (64% จาก #886) | ⇒ ความเสี่ยงว่าจะไม่ต่อ ⇒ ระวังการลงทุนอุปกรณ์เพิ่ม |

**TS ไม่ได้เป็นคนตามเงิน แต่ต้องรู้เพื่อไม่เสียแรงเปล่า** — จุดต่างจากหน้าของ SA/FN

## 6. กฎที่ต้องลอกมาด้วย ไม่ใช่ลอกแค่รูป

1. 🔴 **เงื่อนไขคิวต้องตรงกับด่านเป๊ะ** — คอมเมนต์เตือนว่า *"เข้มกว่า DB = ซ่อนใบที่กดได้จริง · หลวมกว่า DB = ชวนให้กดแล้วเด้ง 409"*
   ⇒ คิว 3c ต้องใช้ **ตัวตัดสินตัวเดียวกับด่าน `draft → scheduled`** ที่ตกลงไว้ใน #872 ไม่ใช่เขียนเงื่อนไขใหม่
2. 🔴 **ต้องมีตัวกรอง "มีของให้ทำจริง"** — คอมเมนต์เตือนว่า *"ไม่งั้น SO ที่ขายของไม่ใช่สรรพสามิตจะค้างคิวตลอดกาล (**ไม่มีวันเคลียร์**)"*
   ⇒ ของบริการ = `project.line === 'SERVICE'` · **นี่คือเหตุผลที่ลูกศรที่ 3 ทำไม่ได้จนกว่า `line` จะลงโค้ด**
3. **`businessDaysWaiting()` ใช้ได้เลย** — นับวันทำการข้ามเสาร์อาทิตย์+วันหยุด และเตือนไว้ว่าต้องใช้เวลาไทย เพราะ *"server รันที่ UTC ถ้าตัดสตริงตรง ๆ งานที่กดตอนเย็นวันจันทร์จะถูกนับเป็นคนละวัน"*

## 7. ของแถมที่ได้ฟรี — ด่านปิดโครงการ

`lib/pm/projectCloseReadiness.js` ใช้ `handoffQueue` อยู่แล้วเพื่อกันไม่ให้ปิดโครงการทั้งที่มีเอกสารค้าง

พอมีลูกศรที่ 3 ⇒ **โครงการสายบริการปิดไม่ได้ถ้ายังไม่ตั้งรอบ** — ตรงกับที่ #868 ตัดสินไว้เป๊ะว่า *"ขั้นสุดท้ายของโครงการสายบริการคือ ส่งมอบไซต์ + ตั้งรอบ"*
เติมแค่รายการเดียวใน `summarizeProjectCloseReadiness()`

⚠️ ต้องมีตัวกรอง `line === 'SERVICE'` ด้วย ไม่งั้นโครงการสายสินค้าจะปิดไม่ได้ตลอดกาล (คอมเมนต์ในไฟล์เตือนเรื่องนี้ไว้แล้ว: *"ห้ามนับ SO นอกพิกัดเป็นงานค้าง ไม่งั้นคำเตือนจะขึ้นตลอดกาลและคนจะเลิกอ่าน"*)

### มติเพิ่ม 2026-08-02 — Express อยู่ต่อ · ใบเสนอราคาเก่าไม่เข้า

> **ผู้ใช้:** *"express ยังอยู่"* · *"ใบเสนอราคาเก่าไม่เข้า จะเริ่มใหม่"*

**ผลข้อ 1 — ตัดงานออกหนึ่งชิ้น**
`quotations` **ไม่ต้องมีช่องอ้างอิงภายนอก** · ใบเสนอราคาเริ่มนับหนึ่งในระบบนี้

**ผลข้อ 2 — 🔴 แต่ `legacyQuoteRef` ยังต้องมีอยู่ดี**
*"ใบเสนอราคาไม่เข้า"* **≠** *"สัญญาไม่เข้า"* — สัญญา 380 ใบยังต้อง import (ไม่งั้นระบบบริการไม่มีอะไรทำงานเลย)
และเลข `Q#250117-0001-B` คือสิ่งที่ปรากฏบน**กระดาษสัญญาที่ลูกค้าเซ็น** ⇒ ถ้าไม่เก็บ จะจับคู่สัญญาในระบบกับกระดาษไม่ได้

⇒ import **ทั้ง 380 ไม่ใช่แค่ 182 ที่ยังมีผล** เพราะ C-7 (win-back) ต้องใช้สัญญาที่หมดแล้ว 196 จุด

**ผลข้อ 3 — ⭐ ระบบนี้จะไม่มี entity "ใบขายเชื่อ / IV" เลย**

Express ถือใบขายเชื่อต่อไป ⇒
- `service_contract_installments` ต้องมี **`invoiceRef` (text)** ที่ FN กรอกกลับหลังไปออกที่ Express — ไม่ใช่ FK

  ซึ่งตรงกับข้อความ LINE ที่ทีมใช้อยู่ทุกวันนี้พอดี

**ผลข้อ 4 — ⭐ ยืนยันว่าการยืนยันเงินเข้า automate ไม่ได้**

ไม่มีทางที่ระบบนี้จะรู้เองว่าเงินเข้าแล้ว เพราะรายการเดินบัญชีอยู่ใน Express

## 11. ยังไม่ตรวจ / ยังไม่ตัดสิน

- ⚠️ **มี SO บน prod ที่ `projectId IS NULL` กี่ใบ** — `deal_project_required` มาทีหลัง (`0101`) และ `sales_orders.projectId` เป็น `ON DELETE SET NULL` ⇒ ของเก่าอาจไร้สาย · **ยังไม่ได้นับ** (worktree นี้ไม่มี credential prod)
  ⇒ ถ้ามีเยอะ ลูกศรที่ 3 ต้อง fallback ผ่าน `dealId → deal.projectId` แล้วถ้ายังไม่เจอให้ขึ้นคิว **"ตอบไม่ได้ว่าสายอะไร"** ไม่ใช่เงียบ
- **โครงการที่มีทั้งสองสายจะเกิดจริงไหม** — โมเดลนี้บังคับให้แยกโครงการ · ถ้าของจริงต้องการโครงการเดียวที่มีทั้งสองสาย ต้องกลับมาคิดใหม่
- `workshop` / `other` ใน `serviceInterest` แมปเป็น `line` อะไร
- **สัญญาที่หมดแล้ว 196 จุด import เข้ามาในสถานะอะไร** — ต้องเข้าเพื่อ win-back (C-7) แต่ไม่ควรไปโผล่ในคิวบริการ ⇒ น่าจะ import พร้อมสถานะที่คำนวณจากวันที่แล้วเลย ไม่ต้องมีสวิตช์แยก
- **เลข IV จาก Express จะกรอกกลับเข้ามาตอนไหน** — ตอนบัญชีปิดคำร้อง `billing_doc` หรือตอนยืนยันเงินเข้า · สองจุดนี้อาจไม่ใช่เวลาเดียวกัน
