# รหัสลูกค้า (AR) และรหัสสินค้า (FG) — สวิตช์ "ระบบใหม่" ในโมดัลเพิ่มข้อมูล

> สถานะ: **เสร็จสมบูรณ์** · ลงโค้ดแล้ว 2026-08-12 (mig 0230) · อ้างอิงถาวร

มติผู้ใช้ 2026-08-12 หลังดูม็อกทางเลือก (ลูกค้า 2 ทาง · สินค้า 3 ทาง) แล้วเคาะ **แบบ A
ทั้งคู่** — "แถบรหัสอยู่บนสุด เห็นก่อนเริ่มกรอกว่ากำลังจะได้รหัสอะไร"

อ่านคู่กับ [form-design-rules.md](form-design-rules.md) (วิธีคิดออกแบบฟอร์ม) และ
[webapp/AGENTS.md](../webapp/AGENTS.md) (ฟอร์มสร้าง/แก้ต้องเป็น component เดียว)

## 1. กติการหัส

| สวิตช์ | รหัสลูกค้า | รหัสสินค้า |
|---|---|---|
| **เปิด** (ค่าตั้งต้น) | `AR-AAAA` 4 หลัก เริ่ม **1001** · ระบบออกให้ | `FG-AAAA-BB-CCC-DDDDD` · ระบบประกอบให้ |
| **ปิด** | `AR-AAA` 3 หลัก · กรอกเอง | `FG-AAA-BB-CCC-DDDD` · กรอกเอง |

ท่อนของรหัสสินค้า:

| ท่อน | มาจากไหน |
|---|---|
| `AAAA` | **รหัสลูกค้าที่เลือก** — เติมศูนย์หน้าให้ครบ 4 หลัก (`AR-109` → `0109`) |
| `BB` | หมวดหลักของหมวดสินค้าที่เลือก |
| `CCC` | หมวดรอง |
| `DDDDD` | **เลขรันเริ่ม 10001 นับรวมทั้งระบบ** ไม่ใช่ต่อลูกค้า |

**ลูกค้าเก่าไม่ถูกเปลี่ยนรหัส** — `AR-109` ยังเป็น `AR-109` ทุกที่ (เอกสารที่ออกไปแล้ว
และระบบสหมิตรอ้างค่านี้ตรง ๆ ที่ `lib/sahamit/server.js`) การเติมศูนย์เกิดตอน **ประกอบ
รหัส FG** เท่านั้น ซึ่งเป็นการอ่านค่า ไม่ใช่การเขียนทับ ⇒ รหัส FG ยาวเท่ากันทุกใบไม่ว่า
เจ้าของจะเป็นลูกค้ารายเก่าหรือใหม่

## 2. ทำไมสวิตช์อยู่ในโมดัล ไม่ใช่หน้าตั้งค่ากลาง

ผู้ใช้เลือกเอง (2026-08-12) จากสามทาง: ในโมดัล · ตั้งค่ากลาง · ทั้งสองชั้น

**เหตุผล**: การบันทึกข้อมูลย้อนหลังไม่ได้จบในวันเดียว — ต่อให้ "ระบบใหม่" เปิดใช้แล้ว
ก็ยังต้องบันทึกลูกค้า/สินค้าที่มีรหัสเดิมอยู่แล้วเรื่อย ๆ ถ้าเป็นสวิตช์กลาง คนกรอกจะทำ
งานนั้นไม่ได้เลยจนกว่าจะมีคนไปปิดสวิตช์ให้ทั้งระบบ · เป็นแพตเทิร์นเดียวกับสวิตช์
**"ดีลเก่าจากระบบเดิม"** ในฟอร์มดีล (มติ 2026-08-08) — ธง = สวิตช์ในฟอร์ม

**ค่าตั้งต้นคือเปิดทุกครั้งที่กดเพิ่ม** เพราะการเพิ่มของใหม่คือกรณีปกติ · สวิตช์ไม่ถูก
จำข้ามครั้ง — กดปิดครั้งนี้ไม่ได้แปลว่าครั้งหน้าจะปิดด้วย

## 3. กลไกเลขรัน (mig 0230)

ใช้ `entity_number_counters` + RPC `next_entity_number(scope, month)` ของ mig 0096 ซ้ำ
(atomic อยู่แล้ว: `INSERT … ON CONFLICT DO UPDATE … RETURNING`) — **ไม่สร้างตารางที่สอง**
สองตารางที่ทำงานเดียวกันคือจุดที่วันหนึ่งจะมีคนเพิ่มเลขผิดตารางแล้วรหัสซ้ำเงียบ ๆ

ตารางนั้นมีคีย์ `(scope, month)` เพราะรหัสดีล/โครงการรันใหม่ทุกเดือน — AR/FG รันยาวตัวเดียว
ตลอดกาล จึงลงคีย์เดือนคงที่ `'-'` หนึ่งแถวต่อ scope

| จุด | ทำอะไร |
|---|---|
| `GET /api/master/customers/next-code` · `…/products/next-code` | **พรีวิวอย่างเดียว ไม่จองเลข** — ฟอร์มเอาไปโชว์บนแถบรหัส |
| `POST /api/master/customers` · `…/products` | **จองเลขจริง** ตอนจะ insert |

**ทำไมไม่จองตั้งแต่เปิดฟอร์ม**: เปิดฟอร์มแล้วปิดทิ้งเป็นเรื่องปกติ จองตั้งแต่ตอนนั้น =
เลขโหว่เป็นรูทุกครั้งที่มีคนเปลี่ยนใจ · ผลที่ตามมาซึ่งฟอร์มต้องเขียนกำกับ: เลขที่โชว์
อาจไม่ใช่เลขที่ได้จริงถ้ามีคนบันทึกก่อน ⇒ หลังบันทึกสำเร็จระบบขึ้น toast บอกรหัสที่ได้จริง
(ผู้ใช้ไม่ได้พิมพ์เอง จึงไม่มีทางรู้ถ้าไม่บอก)

**ค่าที่ client ส่งมาในโหมด auto ไม่ถูกใช้เลย** — ถือเป็นแค่สิ่งที่หน้าจอโชว์ตอนนั้น
ไม่ใช่คำสั่ง (สองคนเปิดฟอร์มพร้อมกันเห็นเลขเดียวกัน แต่ต้องได้คนละเลข) · ท่อน `AAAA`/
`BB-CCC` ของรหัส FG ก็ประกอบจากค่าที่ server อ่านเอง ไม่ใช่สตริงจาก client ไม่งั้นรหัส
บนใบจะเป็นของลูกค้าหนึ่งแต่ `customerId` ชี้อีกคน

## 4. รหัสที่ระบบออกให้ = แก้ไม่ได้

`AR-\d{4}` และ `FG-\d{4}-\d{2}-\d{3}-\d{5}` แยกจากรูปแบบเดิมได้ด้วย**จำนวนหลัก** จึงไม่
ต้องเก็บธงว่าใบไหนออกด้วยโหมดไหน (ธงที่เก็บซ้ำกับสิ่งที่อ่านได้จากค่าจริง คือธงที่วันหนึ่ง
จะไม่ตรงกับค่าจริง)

โมดัลแก้จึง**ล็อกช่องรหัส**เมื่อรหัสนั้นเข้ารูปแบบอัตโนมัติ และ API ตีกลับซ้ำที่ PATCH:
เลขถูกจองจากเคาน์เตอร์กลางไปแล้ว และรหัสไปอยู่บนใบเสนอราคา/ใบสั่งขาย/ทะเบียนสรรพสามิต
⇒ แก้ = ข้อมูลปลายน้ำอ้างรหัสที่ไม่มีอยู่แล้ว · ต้องการรหัสอื่น = สร้างรายการใหม่

รหัสที่กรอกเองแบบเดิมยังแก้ได้ตามเดิม (ไม่มีเลขจองผูกอยู่) แต่ตอนนี้ผ่านด่านรูปแบบก่อน

## 5. สิ่งที่เปลี่ยนในสองโมดัลพร้อมกัน

ตามกฎในเอกสารฟอร์ม ทำในคอมมิตเดียวกับสวิตช์:

| จุด | เดิม | ใหม่ |
|---|---|---|
| ลูกค้า · ประเภท | dropdown 2 ตัวเลือก | `OptionTiles` (ชุดตายตัว 2–4 ต้องกางให้เห็น) |
| ลูกค้า · ป้าย | "ข้อมูลบริษัท / เบอร์โทรบริษัท / เลขผู้เสียภาษี" แม้เลือกบุคคลธรรมดา | ป้ายเปลี่ยนตามประเภทลูกค้า |
| ลูกค้า · section 4 | section ทั้งอันเพื่อช่องเครดิตช่องเดียว | ยุบเข้า section 1 |
| สินค้า · หมวด | พิมพ์ฝังในรหัส แล้ว parse กลับมาฟ้องว่าผิด | `ProductCategorySelect` (แผงสองชั้น 105 หมวด ตัวเดียวกับฟอร์มดีล) |
| สินค้า · ลำดับ | รหัสบนสุด ลูกค้าอยู่ล่าง | **ลูกค้าบนสุด** (ตัวกำหนดทั้ง `AAAA` และชุดแบรนด์) |
| สินค้า · หน่วยปริมาตร | dropdown 6 ตัว | ชิป (≤6 = กางให้เห็น) · หน่วยขาย 8 ตัวยังเป็น dropdown |

**หมวดสินค้ามีตัวเลือกเฉพาะโหมดระบบใหม่** — โหมดกรอกเองหมวดฝังอยู่ในรหัสที่พิมพ์แล้ว
การมีตัวเลือกซ้ำอีกช่องคือการพูดเรื่องเดียวกันสองทาง (ฟอร์มอ่านหมวดจากรหัสให้เอง และ
ด่านตรวจตีกลับเมื่อหมวดที่เลือกไม่ตรงกับ `BB-CCC` ในรหัส)

## 6. เช็คลูกค้าซ้ำจากเลขประจำตัวผู้เสียภาษี

มติผู้ใช้ 2026-08-12 (ต่อจากสวิตช์): ด่านกันซ้ำเดิมดูแค่ **รหัส AR** ซึ่งเป็นเลขที่เรา
ออกเอง ⇒ บริษัทเดียวกันถูกเปิดซ้ำได้ตราบใดที่ได้รหัส AR ใหม่ (ยิ่งเปิดสวิตช์ระบบใหม่
ที่ออกรหัสให้อัตโนมัติ ยิ่งไม่มีอะไรกั้น) · เลขผู้เสียภาษีคือตัวชี้นิติบุคคลจริงตัวเดียวที่เรามี

**ซ้ำ = เลขผู้เสียภาษี + สาขา** ไม่ใช่เลขเดี่ยว ๆ — ตรงกับ `unique (taxId, branchCode)`
ของ mig 0039 และตรงกับความจริงว่าบริษัทเดียวมีสำนักงานใหญ่ (00000) กับสาขา (00012)
เป็นคนละสถานประกอบการ:

| กรณี | ผล |
|---|---|
| เลขตรง · สาขาเดียวกัน | **ตีกลับ** พร้อมบอกว่าไปชนกับ AR ไหน ชื่ออะไร |
| เลขตรง · คนละสาขา | **เตือนบนฟอร์ม ไม่บล็อก** — เผื่อที่จริงตั้งใจแก้รายเดิม |
| ไม่กรอกเลข | ไม่เช็ค (ช่องนี้ไม่บังคับ) |

**เตือนตั้งแต่กรอกครบ 13 หลัก ไม่ใช่ตอนกดบันทึก** — ฟอร์มถาม
`GET /api/master/customers/by-tax-id` (หน่วง 350ms) แล้วขึ้นข้อความใต้ช่องทันที · ด่านจริง
อยู่ที่ API ทั้ง POST และ PATCH (PATCH เช็คเมื่อ **เลขหรือสาขาขยับ** เท่านั้น — แก้ที่อยู่
ออกบิลจากสำนักงานใหญ่ไปสาขา = ย้ายไปชนกับลูกค้าอีกรายได้)

**ทำไมไม่ปล่อยให้ unique ของ DB ตีกลับอย่างเดียว**: ข้อความจาก unique บอกแค่ว่า "ซ้ำ"
คนกรอกหาไม่เจอว่าซ้ำกับใบไหน · ด่านนี้จึงไม่ได้แทน unique (ยังกัน race อยู่) แต่เพิ่ม
**ชื่อของรายที่ชน** ลงในข้อความ

**เทียบแบบถอดขีดเสมอ** — `0105560000069` กับ `0-1055-60000-06-9` คือเลขเดียวกัน
(ช่องกรอกส่งตัวเลขล้วนอยู่แล้ว แต่ค่ายุคเก่า/ค่านำเข้ามีขีดได้) และ POST/PATCH เขียนลง
ฐานข้อมูลเป็นตัวเลขล้วนเสมอ
