# รหัสลูกค้า (AR) และรหัสสินค้า (FG) — สวิตช์ "ระบบใหม่" ในโมดัลเพิ่มข้อมูล

> สถานะ: **เสร็จสมบูรณ์** · ลงโค้ดแล้ว 2026-08-12 (mig 0230) · อ้างอิงถาวร

มติผู้ใช้ 2026-08-12 หลังดูม็อกทางเลือก (ลูกค้า 2 ทาง · สินค้า 3 ทาง) แล้วเคาะ **แบบ A
ทั้งคู่** — "แถบรหัสอยู่บนสุด เห็นก่อนเริ่มกรอกว่ากำลังจะได้รหัสอะไร"

อ่านคู่กับ [form-design-rules.md](form-design-rules.md) (วิธีคิดออกแบบฟอร์ม) และ
[webapp/AGENTS.md](../webapp/AGENTS.md) (ฟอร์มสร้าง/แก้ต้องเป็น component เดียว)

## 1. กติการหัส

| สวิตช์ | รหัสลูกค้า | รหัสสินค้า |
|---|---|---|
| **เปิด** (ค่าตั้งต้น) | `AR-AAAA` 4 หลัก เริ่ม **1001** · ระบบออกให้ | `FG-AAAA-BB-CCC-DDDDD` · ระบบประกอบให้ · **หมวดหลัก 03/04 = `FG-AAAA-BB-CCC` ไม่มีเลขรัน** |
| **ปิด** | `AR-AAA` 3 หลัก · กรอกเอง | `FG-AAA-BB-CCC-DDDD` **หรือ** `FG-AAA-BB-CCC` · กรอกเอง |

ท่อนของรหัสสินค้า:

| ท่อน | มาจากไหน |
|---|---|
| `AAAA` | **รหัสลูกค้าที่เลือก** — เติมศูนย์หน้าให้ครบ 4 หลัก (`AR-109` → `0109`) |
| `BB` | หมวดหลักของหมวดสินค้าที่เลือก |
| `CCC` | หมวดรอง |
| `DDDDD` | **เลขรันเริ่ม 10001 นับรวมทั้งระบบ** ไม่ใช่ต่อลูกค้า · **หมวด 03/04 ไม่มีท่อนนี้** |

### หมวดที่ออกรหัสโดยไม่มีเลขรัน (มติผู้ใช้ 2026-08-13)

**หมวดหลัก `03` ค่าออกแบบ และ `04` รายได้อื่นๆ** ออกรหัสจบที่ `CCC` — `FG-0109-03-001`

สองหมวดนี้ไม่ใช่ตัวสินค้าแต่เป็นค่าบริการ/รายได้ (ค่าจดแจ้งเลขเครื่องสำอางค์ · ค่าบรรจุ ·
ดีไซน์ 80000 บาท) ซึ่งลูกค้าหนึ่งรายมีได้รายการเดียวต่อหมวดรอง เลขรันจึงไม่มีอะไรให้แยก

🔴 **ผลที่ตามมาซึ่งตั้งใจ** — รหัสถูกกำหนดครบตั้งแต่เลือกลูกค้า + หมวด ⇒ สร้างคู่เดิมซ้ำ
ไม่ได้ `unique index 0035` ตีกลับ · API ตอบข้อความที่บอกเหตุผลตรง ๆ ไม่ใช่แค่ "รหัสซ้ำ"
เพราะคนกรอกไม่ได้พิมพ์รหัสเองจึงไม่รู้ว่าไปชนอะไร · วันหนึ่งถ้าต้องการหลายรายการต่อคู่
ให้เอาหมวดนั้นออกจาก `FG_NO_RUN_MAIN_CATEGORIES` **ไม่ใช่ไปปิด unique**

**เส้นทางบันทึกต่างจากหมวดอื่น** — ไม่มีเลขให้จอง จึง**ไม่เรียก** `create_product_with_code`
แต่ประกอบรหัสในเราต์แล้ว `insert` ตรงเหมือนโหมดกรอกเอง (เรียกไปก็ได้เลขรันติดท้ายซึ่ง
ผิดรูปแบบที่ตกลงไว้) · ตัวตัดสินเส้นทางคือ `fgPrefix` มีค่าไหม ไม่ใช่ `codeMode`

### รูปแบบกรอกเองที่ไม่มี `DDDD` (มติผู้ใช้ 2026-08-13)

`FG-AAA-BB-CCC` กรอกเองได้แล้ว — **ของเดิมที่มีอยู่จริงในทะเบียน 7 แถวก่อนวันนี้** ด่านตรวจ
เดิมรับเฉพาะแบบมี `DDDD` ⇒ แถวพวกนั้นแก้ผ่านฟอร์มไม่ได้เลยเพราะติดด่านรูปแบบของตัวเอง

ยังแยกจากรหัสที่ระบบออกให้ได้ด้วยจำนวนหลักเหมือนเดิม: **กรอกเองท่อนลูกค้า 3 หลัก ·
ระบบออกให้ 4 หลัก** ⇒ `FG-1090-01-002` (4 หลัก) ยังพิมพ์เองไม่ได้

**สองโหมดแยกขาดจากกัน** (มติผู้ใช้ 2026-08-12 · กลับมติเดิมของวันเดียวกัน) — โหมดกรอกเอง
พิมพ์ได้เฉพาะรูปแบบเดิมเท่านั้น ทั้งรูปแบบและจำนวนหลัก · พิมพ์ `AR-1001` หรือ
`FG-0109-01-002-10001` เองไม่ได้อีกแล้ว แม้จะเป็นรหัสที่ระบบเคยออกให้

**ทำไม**: รหัสรูปแบบใหม่คือเลขที่เคาน์เตอร์กลางเป็นเจ้าของ ปล่อยให้พิมพ์เองได้เมื่อไร
คนพิมพ์จะไป "จับจอง" เลขที่เคาน์เตอร์ยังรันไปไม่ถึง — พิมพ์ `AR-1005` ตอนเคาน์เตอร์อยู่ที่
1001 แล้วพอเคาน์เตอร์รันมาถึง 1005 คนที่เปิดสวิตช์อยู่จะโดน unique ตีกลับว่า "รหัสนี้มีใน
ระบบแล้ว" ทั้งที่ไม่ได้ทำอะไรผิด และเลข 1005 ก็หายไปด้วย · mig 0230 ซิงก์เคาน์เตอร์กับ
ข้อมูลจริงแค่ตอนรัน migration ครั้งเดียว ไม่ได้ซิงก์ต่อเนื่อง ⇒ ต้องการรหัสรูปแบบใหม่ =
เปิดสวิตช์ให้ระบบออกให้เท่านั้น

**ลูกค้าเก่าไม่ถูกเปลี่ยนรหัส** — `AR-109` ยังเป็น `AR-109` ทุกที่ (เอกสารที่ออกไปแล้ว
และระบบสหมิตรอ้างค่านี้ตรง ๆ ที่ `lib/sahamit/server.js`) การเติมศูนย์เกิดตอน **ประกอบ
รหัส FG** เท่านั้น ซึ่งเป็นการอ่านค่า ไม่ใช่การเขียนทับ ⇒ รหัส FG ยาวเท่ากันทุกใบไม่ว่า
เจ้าของจะเป็นลูกค้ารายเก่าหรือใหม่

## 2. ทำไมสวิตช์อยู่ในโมดัล ไม่ใช่หน้าตั้งค่ากลาง

ผู้ใช้เลือกเอง (2026-08-12) จากสามทาง: ในโมดัล · ตั้งค่ากลาง · ทั้งสองชั้น

**เหตุผล**: การบันทึกข้อมูลย้อนหลังไม่ได้จบในวันเดียว — ต่อให้ "ระบบใหม่" เปิดใช้แล้ว
ก็ยังต้องบันทึกลูกค้า/สินค้าที่มีรหัสเดิมอยู่แล้วเรื่อย ๆ ถ้าเป็นสวิตช์กลาง คนกรอกจะทำ
งานนั้นไม่ได้เลยจนกว่าจะมีคนไปปิดสวิตช์ให้ทั้งระบบ · เป็นแพตเทิร์นเดียวกับสวิตช์
**"ดีลเก่าจากระบบเดิม"** ในฟอร์มดีล (มติ 2026-08-08) — ธง = สวิตช์ในฟอร์ม

**ค่าตั้งต้นคือปิดทุกครั้งที่กดเพิ่ม** (มติผู้ใช้ 2026-08-13 · กลับมติเดิม 2026-08-12
ที่ตั้งต้นเปิดเพราะถือว่า "เพิ่มของใหม่คือกรณีปกติ") — งานจริงยังเป็นการบันทึกของที่มีรหัส
อยู่แล้วเป็นส่วนใหญ่ และ**ความเสียหายของการลืมกดสวิตช์ไม่เท่ากันสองทาง**:

| ลืมกด | ผลที่ได้ |
|---|---|
| ตั้งต้นเปิด แล้วลืมปิด | ได้รหัสใหม่จากเคาน์เตอร์ทับรหัสจริงที่ตั้งใจจะบันทึก · **เอาคืนไม่ได้** เลขถูกจองแล้วและรหัสไปอยู่บนเอกสารปลายน้ำ |
| ตั้งต้นปิด แล้วลืมเปิด | ฟอร์มขอให้กรอกรหัส — กดสวิตช์เพิ่มหนึ่งครั้งแล้วไปต่อ |

สวิตช์ไม่ถูกจำข้ามครั้ง — กดเปิดครั้งนี้ไม่ได้แปลว่าครั้งหน้าจะเปิดด้วย

⚠️ **`DEFAULT_CODE_MODE` กับ `codeModeOf()` เป็นคนละค่าโดยตั้งใจ** — ตัวแรกคือ "ฟอร์มเปิดมา
เห็นอะไร" (ตอนนี้ = manual) ตัวหลังคือ "คำขอที่ไม่ส่ง `codeMode` มาเลย แปลว่าอะไร" ซึ่ง
**ยังเป็น auto เหมือนเดิม** เพราะเป็นสัญญาของ API ที่ผู้เรียกอื่นยึดอยู่ · มัดรวมกันเมื่อไร
การเปลี่ยนหน้าตาฟอร์มจะไปเปลี่ยนความหมายของ API พร้อมกันโดยไม่มีใครตั้งใจ (มีเทสต์คุมไว้)

## 3. กลไกเลขรัน (mig 0230)

ใช้ `entity_number_counters` + RPC `next_entity_number(scope, month)` ของ mig 0096 ซ้ำ
(atomic อยู่แล้ว: `INSERT … ON CONFLICT DO UPDATE … RETURNING`) — **ไม่สร้างตารางที่สอง**
สองตารางที่ทำงานเดียวกันคือจุดที่วันหนึ่งจะมีคนเพิ่มเลขผิดตารางแล้วรหัสซ้ำเงียบ ๆ

ตารางนั้นมีคีย์ `(scope, month)` เพราะรหัสดีล/โครงการรันใหม่ทุกเดือน — AR/FG รันยาวตัวเดียว
ตลอดกาล จึงลงคีย์เดือนคงที่ `'-'` หนึ่งแถวต่อ scope

| จุด | ทำอะไร |
|---|---|
| `GET /api/master/customers/next-code` · `…/products/next-code` | **พรีวิวอย่างเดียว ไม่จองเลข** — ฟอร์มเอาไปโชว์บนแถบรหัส |
| `POST /api/master/customers` · `…/products` | **จองเลขจริง** ตอนจะ insert |

**ทำไมไม่จองตั้งแต่เปิดฟอร์ม**: เปิดฟอร์มแล้วปิดทิ้งเป็นเรื่องปกติ จองตั้งแต่ตอนนั้น =
เลขโหว่เป็นรูทุกครั้งที่มีคนเปลี่ยนใจ · ผลที่ตามมาซึ่งฟอร์มต้องเขียนกำกับ: เลขที่โชว์
อาจไม่ใช่เลขที่ได้จริงถ้ามีคนบันทึกก่อน ⇒ หลังบันทึกสำเร็จระบบขึ้น toast บอกรหัสที่ได้จริง
(ผู้ใช้ไม่ได้พิมพ์เอง จึงไม่มีทางรู้ถ้าไม่บอก)

**จองเลขเป็นด่านสุดท้ายก่อน `insert` เสมอ** — ด่านตรวจทุกด่านของ POST อยู่**เหนือ**บรรทัด
ที่เรียก `nextMasterNumber` (มติผู้ใช้ 2026-08-12) เพราะเลขที่ RPC คืนมาถูก commit ทันที
ในตัวมันเอง เอาคืนไม่ได้ ⇒ ทุก `return` ที่อยู่ใต้จุดจองคือรหัสที่หายจากระบบถาวร

ก่อนแก้ ด่านที่กินเลขทิ้งคือความผิดพลาดตอนกรอกล้วน ๆ ซึ่งเจอบ่อยที่สุด: ลูกค้า —
ไม่มีที่อยู่สำหรับออกเอกสาร, เลขผู้เสียภาษี + สาขาซ้ำ · สินค้า — เลือกสูตรที่ไม่มีอยู่
⇒ กรอกผิดสามรอบ ลูกค้ารายแรกของระบบได้ `AR-1004`

โหมด auto ไม่ต้องเช็ครหัสซ้ำก่อน insert อีกแล้ว (ตอนตรวจยังไม่มีเลขให้เช็ค · unique index
0031/0035 เป็นตาข่ายท้ายสุดอยู่แล้ว) ส่วนสินค้าใช้วิธี "ลองประกอบรหัสด้วยเลขแรกของ scope"
เป็นด่านตรวจแทน — ได้ preconditions ครบชุดโดยไม่ต้องไล่เดาเงื่อนไขซ้ำกับ `composeFgCode`

**`insert` ล้มเองก็ไม่กินเลขแล้ว** (mig 0237) — โหมด auto ไม่ได้จองเลขแล้วค่อย insert อีกที
แต่เรียกฟังก์ชัน SQL ที่บวกเลขเคาน์เตอร์กับ insert อยู่ในคำสั่งเดียว ⇒ ล้มตรงไหนก็ตาม
(ชน unique จริง ๆ, คอนเนกชันหลุด, RAISE เอง) เลขที่บวกไปถูก rollback คืน แพตเทิร์นเดียวกับ
`create_sales_order_draft` (mig 0155)

| ฟังก์ชัน | รับ | ทำ |
|---|---|---|
| `create_customer_with_code(p_prefix, p_width, p_row)` | `'AR-'` · `4` · แถวเป็น jsonb | จองเลข scope `AR` → เติม `arCode` → insert |
| `create_product_with_code(p_prefix, p_width, p_row)` | `'FG-AAAA-BB-CCC-'` · `5` · แถวเป็น jsonb | จองเลข scope `FG` → เติม `fgCode` → insert |

**ฟังก์ชันไม่รู้จักรูปแบบรหัส** — รับท่อนหน้าเลขรันกับความกว้างมาจากแอป แล้วเติมเฉพาะ
ตัวเลขที่จองได้ · `masterCodes.js` ยังเป็นที่เดียวที่รู้ว่ารหัสหน้าตาอย่างไร (`fgCodePrefix()`
เป็นตัวเดียวกับที่ `composeFgCode()` ใช้ประกอบ จึงไม่มีทางประกอบคนละแบบ)

**แถวส่งเป็น jsonb แล้วเลือกคอลัมน์ตามคีย์ที่ส่งจริง** ไม่ใช่ populate ทั้งแถว เพราะ
คอลัมน์ที่ไม่ได้ส่งจะกลายเป็น `NULL` ทับ DEFAULT แล้วชน NOT NULL ทันที (`"updatedAt"`
not null default now() ซึ่งฝั่งแอปไม่เคยส่ง) · ฝั่งแอปจึง**ไม่ใส่คีย์รหัสเลย**ในโหมด auto
ให้ฟังก์ชันเป็นคนเติม — ใส่ `null` ไว้ก่อนไม่ได้ เพราะถ้าวันหนึ่งท่อนเติมรหัสหลุดไป จะได้
แถวที่ไม่มีรหัสแบบเงียบ ๆ แทนที่จะพังให้เห็น

**ค่าที่ client ส่งมาในโหมด auto ไม่ถูกใช้เลย** — ถือเป็นแค่สิ่งที่หน้าจอโชว์ตอนนั้น
ไม่ใช่คำสั่ง (สองคนเปิดฟอร์มพร้อมกันเห็นเลขเดียวกัน แต่ต้องได้คนละเลข) · ท่อน `AAAA`/
`BB-CCC` ของรหัส FG ก็ประกอบจากค่าที่ server อ่านเอง ไม่ใช่สตริงจาก client ไม่งั้นรหัส
บนใบจะเป็นของลูกค้าหนึ่งแต่ `customerId` ชี้อีกคน

## 4. รหัสที่ระบบออกให้ = แก้ได้เฉพาะแอดมิน (อัปเดต 2026-08-24)

`AR-\d{4}` และ `FG-\d{4}-\d{2}-\d{3}-\d{5}` แยกจากรูปแบบเดิมได้ด้วย**จำนวนหลัก** จึงไม่
ต้องเก็บธงว่าใบไหนออกด้วยโหมดไหน (ธงที่เก็บซ้ำกับสิ่งที่อ่านได้จากค่าจริง คือธงที่วันหนึ่ง
จะไม่ตรงกับค่าจริง)

โมดัลแก้จึง**ล็อกช่องรหัส**เมื่อรหัสนั้นเข้ารูปแบบอัตโนมัติ และ API ตีกลับซ้ำที่ PATCH:
เลขถูกจองจากเคาน์เตอร์กลางไปแล้ว และรหัสไปอยู่บนใบเสนอราคา/ใบสั่งขาย/ทะเบียนสรรพสามิต
⇒ แก้ = ข้อมูลปลายน้ำอ้างรหัสที่ไม่มีอยู่แล้ว · ต้องการรหัสอื่น = สร้างรายการใหม่

รหัสที่กรอกเองแบบเดิมยังแก้ได้ตามเดิม (ไม่มีเลขจองผูกอยู่) แต่ตอนนี้ผ่านด่านรูปแบบก่อน

## 6. เช็คลูกค้าซ้ำจากเลขประจำตัวผู้เสียภาษี

มติผู้ใช้ 2026-08-12 (ต่อจากสวิตช์): ด่านกันซ้ำเดิมดูแค่ **รหัส AR** ซึ่งเป็นเลขที่เรา
ออกเอง ⇒ บริษัทเดียวกันถูกเปิดซ้ำได้ตราบใดที่ได้รหัส AR ใหม่ (ยิ่งเปิดสวิตช์ระบบใหม่
ที่ออกรหัสให้อัตโนมัติ ยิ่งไม่มีอะไรกั้น) · เลขผู้เสียภาษีคือตัวชี้นิติบุคคลจริงตัวเดียวที่เรามี

**ซ้ำ = เลขผู้เสียภาษี + สาขา** ไม่ใช่เลขเดี่ยว ๆ — ตรงกับ `unique (taxId, branchCode)`
ของ mig 0039 และตรงกับความจริงว่าบริษัทเดียวมีสำนักงานใหญ่ (00000) กับสาขา (00012)
เป็นคนละสถานประกอบการ:

| กรณี | ผล |
|---|---|
| เลขตรง · สาขาเดียวกัน | **ตีกลับ** พร้อมบอกว่าไปชนกับ AR ไหน ชื่ออะไร |
| เลขตรง · คนละสาขา | **เตือนบนฟอร์ม ไม่บล็อก** — เผื่อที่จริงตั้งใจแก้รายเดิม |
| ไม่กรอกเลข | ไม่เช็ค (ช่องนี้ไม่บังคับ) |

**เตือนตั้งแต่กรอกครบ 13 หลัก ไม่ใช่ตอนกดบันทึก** — ฟอร์มถาม
`GET /api/master/customers/by-tax-id` (หน่วง 350ms) แล้วขึ้นข้อความใต้ช่องทันที · ด่านจริง
อยู่ที่ API ทั้ง POST และ PATCH (PATCH เช็คเมื่อ **เลขหรือสาขาขยับ** เท่านั้น — แก้ที่อยู่
ออกบิลจากสำนักงานใหญ่ไปสาขา = ย้ายไปชนกับลูกค้าอีกรายได้)

**ทำไมไม่ปล่อยให้ unique ของ DB ตีกลับอย่างเดียว**: ข้อความจาก unique บอกแค่ว่า "ซ้ำ"
คนกรอกหาไม่เจอว่าซ้ำกับใบไหน · ด่านนี้จึงไม่ได้แทน unique (ยังกัน race อยู่) แต่เพิ่ม
**ชื่อของรายที่ชน** ลงในข้อความ

**เทียบแบบถอดขีดเสมอ** — `0105560000069` กับ `0-1055-60000-06-9` คือเลขเดียวกัน
(ช่องกรอกส่งตัวเลขล้วนอยู่แล้ว แต่ค่ายุคเก่า/ค่านำเข้ามีขีดได้) และ POST/PATCH เขียนลง
ฐานข้อมูลเป็นตัวเลขล้วนเสมอ

## 7. เช็คสินค้าซ้ำ: ลูกค้า + ชื่อ + ขนาดบรรจุ

มติผู้ใช้ 2026-08-12 (คำถามของผู้ใช้: "สินค้าจะเช็คซ้ำยังไง ลูกค้า 1 หลายสินค้าได้")

**รหัส FG กันซ้ำไม่ได้อีกแล้ว** — พอเปิดสวิตช์ระบบใหม่ เลขรันออกใหม่ทุกครั้ง กดเพิ่ม
สินค้าตัวเดิมซ้ำสิบรอบก็ผ่านหมด ได้สิบรหัส (ช่องเดียวกับที่รหัส AR เคยเปิดไว้ฝั่งลูกค้า)

**ลูกค้ารายเดียวมีหลายสินค้าเป็นเรื่องปกติ** ตัวตนของสินค้าจึงไม่ใช่ "ลูกค้า" เดี่ยว ๆ
วัดจากแคตตาล็อกจริง 143 แถวก่อนตัดสิน:

| คีย์ที่ลอง | ชนกันจริง |
|---|---|
| ลูกค้า + ชื่ออังกฤษ | 22 กลุ่ม / 45 แถว |
| ลูกค้า + ชื่อ + **ขนาดบรรจุ** | **0** |
| ลูกค้า + สูตร + ขนาด | 0 — **ใช้ไม่ได้**: ยังไม่มีสินค้าผูกทะเบียนสูตรสักแถว (0/143) |

22 กลุ่มที่ชื่อซ้ำต่างกันที่ขนาด **ทั้งหมด** (เช่น "Glenn Eau De Parfum" 5ml กับ 30ml)
ซึ่งเป็นคนละ SKU ที่ถูกต้อง ⇒ **ขนาดเป็นส่วนหนึ่งของตัวตน ไม่ใช่รายละเอียดปลีกย่อย**
และคีย์นี้ไม่เตือนผิดเลยบนข้อมูลจริง — เตือนเมื่อไรคือซ้ำจริง

| สิ่งที่เจอ | ผล |
|---|---|
| ชื่อ + ขนาดตรง | **เตือน (ไม่บล็อก)** พร้อมรหัส FG ที่ชน |
| ชื่อตรง ขนาดต่าง | บอกเฉย ๆ ว่า "ชื่อนี้มีอยู่แล้วที่ขนาด 5 ml · 30 ml" — ไม่ใช่คำเตือน |
| ยังไม่กรอกขนาด | ยังไม่ฟันธงว่าซ้ำ แต่บอกได้ว่าชื่อนี้มีอยู่ |

**ทำไมเตือนไม่บล็อก** (ต่างจากลูกค้าที่บล็อก): มีเคสจริงที่ตั้งใจซ้ำ — เปลี่ยนบรรจุภัณฑ์
แล้วออกรหัสใหม่ · ออกรหัสใหม่แทนตัวที่เลิกใช้ · และมีด่านอนุมัติของหัวหน้าคั่นอยู่แล้ว
(ฝั่งลูกค้าบล็อกได้เพราะ DB มี unique รองรับอยู่จริง — ฝั่งสินค้าไม่มีคีย์แบบนั้น
และการสร้าง unique บนชื่อจะทำให้ข้อมูลเดิมที่ชอบธรรมกลายเป็นผิดกฎย้อนหลัง)

**ชื่อตรงภาษาใดภาษาหนึ่งก็นับ** (ฟอร์มบังคับแค่ 1 ภาษา) · ชื่อว่างไม่นับว่าตรง ไม่งั้น
สินค้าทุกตัวที่ยังไม่มีชื่ออังกฤษจะซ้ำกันหมด · ขนาดเทียบเป็นตัวเลข ('50' = '50.0')

**สูตรเป็นชั้นที่สองในอนาคต** — เมื่อ Product Spec ผูกสูตรเข้า FG แล้ว (ดู
`rm-price-registry-split.md`) ค่อยเพิ่มเข้าไปในคีย์ ตอนนี้เพิ่มไปก็ไม่มีวันเตือน

**ฟังก์ชันรับหลายแถวเสมอ** — สองที่ที่ gen ทีละชุด (ใบผลิตอัตโนมัติ · นัดบริการตามรอบ)
ต้องได้พฤติกรรมเดิมคือล้มใบไหนก็ล้มทั้งชุด ไม่ค้างครึ่งทาง · ทั้งลูปอยู่ในฟังก์ชันเดียว

**สามที่ของ `PJ` มีลูป retry 5 รอบ** ซึ่งเดิม**ออกรหัสใหม่ทุกรอบที่ชน** = กินเลขรอบละใบ

ของรอบที่ล้มถูกคืนไปแล้ว

## 9. ลบร่างที่ยังไม่เคยอนุมัติ = ได้เลขคืน (mig 0248)

มติผู้ใช้ 2026-08-13: *"ถ้าเลขเป็นเลขที่ร่างแล้วลบไป ยังใช้ได้อยู่ แต่ถ้าอนุมัติแล้วลบไป
จะใช้ไม่ได้"* — ใช้กับ **AR และ FG เท่านั้น** รหัสเอนทิตีชุดอื่นยังห้ามคืนทุกกรณี

| แถวที่ถูกลบ | เลขรัน |
|---|---|
| ไม่เคยผ่านอนุมัติ (`pending` / `rejected` ตั้งแต่เกิด) | **กลับเข้ากอง** ออกให้ใบถัดไป |
| เคยผ่านอนุมัติแม้ครั้งเดียว | **ตายถาวร** ตามกติกา 0241 เดิม |
| รหัสกรอกเอง (สวิตช์ปิด) | ไม่เกี่ยว — ไม่เคยกินเลขรันตั้งแต่แรก |

**ทำไมร่างคืนได้แต่ของอนุมัติแล้วคืนไม่ได้**: ลิสต์ทุกหน้าคืนเฉพาะแถว `approved`
(`GET /api/customers`, `/api/products`) ⇒ ร่างที่ยังไม่ผ่านอนุมัติไปโผล่บนใบเสนอราคา/
ใบสั่งขาย/ทะเบียนสรรพสามิตไม่ได้ตั้งแต่แรก เลขจึงยังไม่เคยออกไปไหนจริง ๆ

### ⚠️ `approvalStatus = 'pending'` ไม่ได้แปลว่า "ยังไม่เคยอนุมัติ"

นี่คือกับดักที่ทั้งใบนี้มีอยู่เพื่อกัน — ของที่อนุมัติแล้วถูกแก้ไขจะถูกดีดกลับเป็น
`pending` และ `approvedAt`/`approvedBy` **ถูกล้างทิ้ง** (`resetApprovalOnEdit`) ⇒ บนแถวไม่
เหลือร่องรอยว่าเคยอนุมัติ · ตัดสินจากสถานะปัจจุบันเมื่อไร เลขของลูกค้าที่รหัสอยู่บนเอกสาร
จริงแล้วจะถูกปล่อยคืนให้รายอื่น ซึ่งคือความเสียหายที่ 0241 ตั้งใจกันไว้ทั้งใบ

⇒ ตัวตัดสินคือคอลัมน์ **`firstApprovedAt`** ที่ตั้งครั้งเดียวตอนอนุมัติครั้งแรกแล้ว
**ล้างไม่ได้เปลี่ยนไม่ได้** (trigger `*_first_approved_stamp` เขียนทับค่าเดิมกลับทุกครั้ง)
· `isReusableCode()` ฝั่งแอปอ่านค่าเดียวกันนี้ เพื่อให้ข้อความยืนยันก่อนลบพูดตรงกับที่ DB
จะทำจริง

"ยังไม่อนุมัติ" นับแค่ `'pending'` กับ `'rejected'` — ค่าอื่นรวมทั้ง `NULL` ถือว่าอนุมัติแล้ว
(คอลัมน์นี้ `DEFAULT 'approved'` มาตั้งแต่ mig 0027 และลิสต์คืนแถว `approvalStatus is null`
มาด้วย ⇒ แถวไม่มีสถานะ = แถวที่คนอื่นหยิบไปใส่เอกสารได้แล้ว)

**แถวที่มีอยู่ก่อนใบนี้ถูกถือว่าเคยอนุมัติทั้งหมด** (backfill `COALESCE(approvedAt, createdAt)`)
เพราะพิสูจน์ไม่ได้ว่าแถว pending ตรงหน้าเคยอนุมัติมาก่อนหรือไม่ — ต้นทุนของการเดาถูกคือได้เลข
คืนหนึ่งเลข ต้นทุนของการเดาผิดคือรหัสบนเอกสารจริงถูกออกซ้ำ ⇒ กติกาใหม่มีผลกับแถวที่สร้าง
**หลังใบนี้**เท่านั้น

### กลไก: กองเลขคืน ไม่ใช่การถอยเคาน์เตอร์

`entity_number_reclaimed (scope, no)` เป็นตารางแยก · `entity_number_counters` ยังบวก
อย่างเดียวและ trigger กันถอย/กันลบ/กัน truncate ของ 0241 ยังทำงานครบทุกตัว

**ห้ามแก้กลับไปเป็น "ลบร่างแล้วถอยเคาน์เตอร์"** — เคาน์เตอร์ถอยหนึ่งครั้ง = ทุกเลขที่ออก
หลังจากนั้นถูกออกซ้ำหมด ไม่ใช่แค่เลขที่ตั้งใจคืน

| จุด | ทำอะไร |
|---|---|
| `AFTER DELETE` บน customers/products | ไม่เคยอนุมัติ + รหัสเป็นรูปแบบอัตโนมัติ → ยัดเลขเข้ากอง |
| `create_customer_with_code` / `create_product_with_code` | **หยิบจากกองก่อน** (ตัวน้อยสุด) ไม่มีค่อยรันเลขใหม่ |
| `peekMasterNumber()` | พรีวิวอ่านกองก่อนเคาน์เตอร์ ให้ตรงลำดับเดียวกัน |

**คืนเลขที่ trigger ไม่ใช่ที่ route** — การลบมีหลายทาง (API · สคริปต์ · SQL มือ) และ trigger
อยู่ในทรานแซกชันเดียวกับ `DELETE` ⇒ ลบไม่สำเร็จก็ไม่มีเลขคืน ไม่มีทางหลุดคู่กัน

**หยิบเลขจากกองด้วย `FOR UPDATE SKIP LOCKED`** — สองคนกดบันทึกพร้อมกันต้องได้คนละเลข
· และ**เช็คทุกครั้งว่าเลขนั้นยังว่างจริง** ก่อนใช้ (ถ้ามีใครใส่รหัสนั้นกลับเข้าไปทางอื่น
เลขในกองจะกลายเป็นเลขชน ⇒ ทิ้งใบนั้นแล้ววนหาตัวถัดไป) · ฝั่ง FG เช็คที่**ท่อนท้ายของรหัส
FG ทุกใบ** ไม่ใช่เฉพาะ prefix ของใบที่กำลังออก เพราะเลขรัน FG นับรวมทั้งระบบ

### ลบลูกค้าที่ยังมีสินค้าไม่ได้แล้ว

รหัสสินค้าฝังรหัสลูกค้าไว้ในตัวเอง (`FG-AAAA-…`) ⇒ ลบลูกค้าที่ยังมีสินค้าแล้วปล่อยเลข AR
คืน รหัสสินค้าเดิมจะชี้ไปหาลูกค้าคนละคนทันทีโดยไม่มีอะไรฟ้อง · ด่านลบลูกค้าเดิมเช็คแค่
โครงการ/ออเดอร์/การขึ้นทะเบียน — **ไม่เคยเช็ค `products`** (สินค้ากลายเป็นกำพร้าเงียบ ๆ
มาตลอด) ตอนนี้เพิ่มเข้าไปแล้วพร้อมรายชื่อรหัส FG ที่ขวางอยู่

### ข้อความยืนยันบอกชะตากรรมของเลขตั้งแต่ก่อนกดลบ

ผู้ใช้ไม่ได้เป็นคนตั้งรหัสเอง จึงไม่มีทางรู้ว่าเลขนั้นจะกลับมาหรือหายถาวรถ้าไม่เขียนไว้
· และหน้ารายละเอียดเด้งกลับไปที่ทะเบียนทันทีหลังลบสำเร็จ ⇒ ข้อความหลังลบไม่มีใครได้อ่าน
(API ยังตอบ `message` ที่บอกผลจริงไว้สำหรับผู้เรียกอื่น)

**ทำไมออกได้โดยไม่แก้ฟังก์ชัน SQL** — `create_entity_rows_with_code` ไม่รู้จักรูปแบบรหัส

**เลขรันอยู่ท้ายสุด** ออกได้ทันที เปลี่ยนแค่สามค่าที่ฝั่งแอปส่งไป (`insertRowWithComposedCode`
ใน `lib/entityCode.js`):

| ไซต์ | `ST-0121-01-BKK-` | `'-'` (นับยาวตลอดกาล แบบ AR/FG) | 4 |

**ไม่ออกรหัสใหม่และไม่แก้รหัสเดิม** · รหัสคือ *ตัวตน* ไม่ใช่ *สรุปสถานะปัจจุบัน* (กติกาเดียวกับ
`docNo` ของคำร้องที่ trigger ทำให้แก้ไม่ได้) ⇒ จอต้องบอกเรื่องนี้ตรงช่องที่แก้ได้ ไม่ใช่ปล่อยให้

⚠️ **สองอย่างที่กลายเป็นของบังคับ** เพราะเป็นท่อนหนึ่งของรหัส:

## 11. รอบตัดเลขรัน — ใบเสนอราคา/ใบสั่งขายตัดทุกปี (มติผู้ใช้ 2026-09-01 · mig 0328)

> *"ใบเสนอราคา ใบสั่งขาย รันไปเรื่อยๆ ตัดทุกปี"*

**เปลี่ยนรอบตัดอย่างเดียว รูปแบบเลขไม่เปลี่ยนสักตัวอักษร** — ยังเป็น `QT-YYMMXXXX-R` /
`SO-YYMMXXXX-R` ⇒ ก.ย. 2026 เดินต่อจากเลขสุดท้ายของปี `QT-26080241` → **`QT-26090242`**
(ไม่ย้อนกลับเป็น `QT-26090001`) · ปีใหม่เริ่ม `QT-27010001`

### รอบตัดของเลขทุกชุดในระบบ (สภาพหลัง 0328)

| เลข | ตัวนับ | คีย์ | รอบตัด |
|---|---|---|---|
| ใบเสนอราคา QT | `quote_number_counters` | `'26'` | **ทุกปี** |
| ใบสั่งขาย SO | `sales_order_number_counters` | `'26'` | **ทุกปี** |
| ใบแจ้งภาษี ET | `excise_tax_notice_number_counters` | `'26'` | **ทุกปี** (mig 0329) |
| ไทม์ไลน์ PT | `project_timeline_number_counters` | `'26'` | **ทุกปี** (mig 0330) |
| ดีล DL · โครงการ PJ | `entity_number_counters` | `(scope, '26')` | **ทุกปี · เลขรัน 5 หลัก** (mig 0330) |
| คำร้อง RQ | `entity_number_counters` | `(RQ, '26')` | ทุกปี |
| สัญญา CT · AR · FG · ไซต์ · โซน | `entity_number_counters` | `(scope, '-')` | ไม่ตัด |
| PB · SV · IS · PDR · CR | `entity_number_counters` | `(scope, 'YYMM')` | ทุกเดือน |

🔴 **`YYMM` ในเลข ≠ ตัวตัดรอบของเลขรัน** — กับดักเดียวกับที่ `requests/docNo.js` และ
`sales/contracts.js` เขียนเตือนไว้แล้ว · `YYMM` ที่คนเห็นมาจาก **รูปแบบเลขที่** ของมาตรฐาน
เอกสาร = เดือนที่ออกใบ · ส่วนตัวตัดรอบคือ **คีย์ `month` ของตารางตัวนับ** ⇒ ตารางตัวนับ
มีทั้งแถวยุคเดือน (`'2608'`) และแถวยุคปี (`'26'`) อยู่ด้วยกัน **ห้ามลบแถวยุคเดือน**
(trigger `doc_number_counter_guard` ของ 0242 กันไว้แล้ว — มันคือหลักฐานว่าเลขไหนออกไปแล้ว)

### จุดที่ตัดสินรอบตัดจริง (แก้ที่นี่เท่านั้น)

- **QT** — `quoteCounterYear()` ใน `lib/salesPlanning.js` (แอปส่งคีย์ถังนับเข้า RPC)
- **SO** — `v_year := to_char(v_now, 'YY')` ใน `create_sales_order_draft` (คิดในฝั่ง SQL
  เพราะใบสั่งขายเกิดจาก RPC ล้วน ไม่มีฝั่ง JS ประกอบเลข)
- `DOCUMENT_NUMBER_CYCLES` ใน `lib/documentStandards.js` **ไม่ใช่** ตัวตัดรอบ — มันคือ
  กติกาว่ารูปแบบเลขต้องมี token อะไร (รายเดือนต้องมี `{MM}` · รายปีไม่บังคับ)
  🪤 แก้ค่านั้นที่เดียวโดยไม่แก้สองข้อบน = ด่านตรวจหลวมกว่าของจริง

### สิ่งที่ต้องทำตอนสลับรอบ (ทำไปแล้วใน 0328 — คัดไปใช้ตอนสลับชุดถัดไป)

1. **seed แถวรอบใหม่ก่อนสลับฟังก์ชัน** ไม่งั้นเลขเริ่มที่ 1 แล้วทับเลขที่ออกไปแล้ว
2. **seed ต้องนับ "เลขที่ออกไปแล้ว" ไม่ใช่ "แถวที่ยังเหลือ"** — ใบที่ถูกลบทิ้งไม่เหลือแถว
   ให้นับ แต่เลขของมันออกไปแล้ว ⇒ `GREATEST(เลขรันสูงสุดในแถวจริง, lastNo สูงสุดของแถว
   ยุคเดิมในรอบเดียวกัน)` (ของจริงตอนทำ: ตัวนับเดือน `2609` = 1 ทั้งที่ไม่เหลือใบ `QT-2609…`)
3. **เพดานเปลี่ยนหน่วยตาม** — จาก 9,999 ใบ/เดือน เป็น 9,999 ใบ/**ปี** (ปี 2026 ออกไปแล้ว
   QT 241 · SO 143) · วันที่ใกล้เพดานให้ขยายความกว้างที่รูปแบบเลขในหน้าตั้งค่า
   ฟังก์ชันอ่านความกว้างจากรูปแบบจริง ไม่ได้ฮาร์ดโค้ด
4. **ไม่ backfill เลขเก่าแม้แต่ใบเดียว** — เลขที่ออกไปหาลูกค้าแล้วห้ามเปลี่ยนความหมายย้อนหลัง
5. **เช็ค CHECK ของตารางตัวนับก่อน** — `sales_order_number_counters.month` ถูกบังคับ 4 หลัก
   มาตั้งแต่ 0109 (ตัวเดียวในระบบที่มี) ⇒ ลืมปลด = สร้างใบสั่งขายไม่ได้ทั้งระบบ
   ส่วน `quote_number_counters` / `excise_tax_notice_number_counters` /
   `project_timeline_number_counters` เป็น `text PRIMARY KEY` เฉย ๆ ใส่คีย์ปีได้เลย

### รอบ ET (มติผู้ใช้ 2026-09-01 "ET เอาแบบ QT" · mig 0329)

ทำตามข้อ 1–5 ข้างบนทุกข้อ · จุดที่ต่างคือ **ตาราง `orders` ที่ถือ `taxNoticeNumber`
ไม่เหลือแถวเลย** แต่ตัวนับรายเดือนยังจำได้ว่าเคยออกเลขไปแล้ว (`2607`=1 · `2608`=3)
⇒ เป็นตัวอย่างชัดที่สุดของข้อ 2: ถ้า seed จากแถวจริงอย่างเดียวจะได้ 0 แล้วออกเลขซ้ำ

### รอบ DL/PJ/PT (มติผู้ใช้ 2026-09-01 "PT ขอทำพร้อม DL PJ" + เลือก 5 หลัก · mig 0330)

สามอย่างนี้ **เกิดคู่กัน** (ปิดดีล Won → โครงการ → ไทม์ไลน์ของโครงการ) ⇒ รอบตัดต้องตรงกัน

**DL/PJ ขยายเลขรัน 4 → 5 หลัก** เพราะเพดานเปลี่ยนหน่วยเป็น "ต่อปี" — ดีลออก ~415 ใบ/เดือน
≈ 5,000/ปี ⇒ 4 หลัก (9,999/ปี) เหลือหัวไม่ถึงเท่าตัว ชนเมื่อไร = **สร้างดีลไม่ได้ทั้งระบบ**
⚠️ ชุด 5 หลักไม่ชนกับชุด 4 หลักเดิมโดยโครงสร้าง (คนละความยาว = คนละสตริง) จึงไม่ backfill
🪤 แต่เรียงสตริงสลับกัน — ชุด 5 หลักมาก่อนชุด 4 หลักในการ sort ตามตัวอักษร

**PT ขยายเป็น 5 หลักด้วย** (มติผู้ใช้ 2026-09-01 รอบสอง · mig 0331) — ความกว้างของ PT
มาจาก `numberingPattern` ของ **มาตรฐานเอกสารที่เผยแพร่** ไม่ใช่ค่าคงที่ในโค้ด ⇒ mig 0331
จึงไม่ได้แก้ schema แต่ **เผยแพร่มาตรฐานเวอร์ชันใหม่** ผ่าน RPC ชุดเดียวกับที่หน้าตั้งค่าใช้
(`create_document_standard_draft` → แก้ร่าง → `publish_document_standard_draft_atomic`)

⚠️ **ห้าม UPDATE ทับแถวที่เผยแพร่อยู่** — trigger `document_standard_versions_guard` (0123)
บล็อกการแก้ payload ของแถวที่ไม่ใช่ร่าง และประวัติเวอร์ชันคือหลักฐานของระบบคุณภาพ
⚠️ **migration ไม่ตั้ง `revision` (Rev. No. บนหัวกระดาษ) ให้เอง** — เป็นเลขควบคุมเอกสาร
ของฝ่ายเอกสาร ถ้ารอบนี้ต้องนับเป็น Rev. ใหม่ ให้คนดูแลเอกสารกดแก้จากหน้าตั้งค่า

**ที่ไม่แตะ:** PB (ใบผลิต) · SV (นัดบริการ) · IS (แจ้งปัญหา) ยังรายเดือน — ไม่อยู่ในมติ
