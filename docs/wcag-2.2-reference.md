# WCAG 2.2 — เอกสารอ้างอิงเกณฑ์การออกแบบสากล

สรุปจากต้นฉบับ W3C: [WCAG 2.2 Recommendation](https://www.w3.org/TR/WCAG22/) (ประกาศเป็น W3C Recommendation 5 ตุลาคม 2023) และชุดเอกสาร [Understanding WCAG 2.2](https://www.w3.org/WAI/WCAG22/Understanding/)

เอกสารนี้เป็นของกลาง ใช้เป็นเกณฑ์ตรวจงานออกแบบ/หน้าจอทุกโมดูลของระบบ อ่านคู่กับ `docs/form-design-rules.md`

---

## 1. โครงสร้างมาตรฐาน

WCAG = Web Content Accessibility Guidelines ของ W3C/WAI โครงสร้างสามชั้น

```
4 Principles (หลักการ)  →  13 Guidelines (แนวทาง)  →  86 Success Criteria (เกณฑ์ความสำเร็จ)
```

**หลักการ 4 ข้อ (POUR)**

| # | หลักการ | ความหมาย |
|---|---------|----------|
| 1 | **Perceivable** (รับรู้ได้) | ข้อมูลและส่วนติดต่อผู้ใช้ต้องถูกนำเสนอในรูปแบบที่ผู้ใช้รับรู้ได้ |
| 2 | **Operable** (ใช้งานได้) | ส่วนควบคุมและการนำทางต้องสั่งงานได้ |
| 3 | **Understandable** (เข้าใจได้) | ทั้งข้อมูลและวิธีใช้งานต้องเข้าใจได้ |
| 4 | **Robust** (ทนทาน) | เนื้อหาต้องถูกตีความได้อย่างเชื่อถือได้โดยเทคโนโลยีสิ่งอำนวยความสะดวก (assistive technology) |

**แนวทาง 13 ข้อ**

1.1 Text Alternatives · 1.2 Time-based Media · 1.3 Adaptable · 1.4 Distinguishable ·
2.1 Keyboard Accessible · 2.2 Enough Time · 2.3 Seizures and Physical Reactions · 2.4 Navigable · 2.5 Input Modalities ·
3.1 Readable · 3.2 Predictable · 3.3 Input Assistance ·
4.1 Compatible

**เกณฑ์ความสำเร็จ (Success Criteria) จำนวน 86 ข้อ**

| ระดับ | จำนวน | สะสม |
|-------|-------|------|
| A | 31 | 31 |
| AA | 24 | 55 |
| AAA | 31 | 86 |

> **AA คือเป้าหมายจริงของงานเรา** — เป็นระดับที่กฎหมายและสัญญาจัดซื้อทั่วโลกอ้างถึง ส่วน AAA ไม่ถูกกำหนดให้ทำทั้งเว็บ (W3C ระบุเองว่าเนื้อหาบางประเภททำ AAA ไม่ได้)

## 2. ข้อกำหนดการอ้างความสอดคล้อง (Conformance Requirements) 5 ข้อ

ข้อนี้สำคัญกว่าที่คนทั่วไปคิด เพราะกำหนดว่า "ผ่าน" หมายถึงอะไร

1. **Conformance Level** — ต้องผ่าน *ทุก* success criteria ในระดับที่อ้าง ไม่มีการผ่าน 90%
2. **Full Pages** — วัดที่ *ทั้งหน้า* ไม่ใช่บางส่วนของหน้า ("full page" = ทรัพยากรที่ได้จาก URI เดียว รวมทุกอย่างที่เรนเดอร์ร่วมกัน) จะยกเว้นบางส่วนของหน้าไม่ได้
3. **Complete Processes** — ถ้าหน้าเป็นส่วนหนึ่งของกระบวนการ (เช่น สร้างดีล → QT → SO) **ทุกขั้นตอน**ต้องผ่านระดับเดียวกัน ขั้นใดขั้นหนึ่งตกคือทั้งกระบวนการตก
4. **Accessibility-Supported** — เทคนิคที่ใช้ต้องรองรับจริงโดย assistive technology ที่ผู้ใช้ใช้อยู่ (ใช้ ARIA ที่ screen reader ไม่รู้จัก = ไม่นับ)
5. **Non-Interference** — เนื้อหาที่ไม่ผ่านเกณฑ์ต้องไม่ไปขวางการใช้งานส่วนที่เหลือของหน้า (โดยเฉพาะ 1.4.2 เสียงอัตโนมัติ, 2.1.2 keyboard trap, 2.2.2 หยุดภาพเคลื่อนไหว, 2.3.1 แสงกะพริบ)

**นิยามที่ต้องจำ**

- **Programmatically determined** = ซอฟต์แวร์อ่านค่าออกได้จาก markup/accessibility API ไม่ใช่แค่ตาคนเห็น
- **Essential** = ถ้าเอาออกแล้ว *เปลี่ยนความหมายหรือความสามารถของเนื้อหาโดยพื้นฐาน* และไม่มีวิธีอื่นทำแทนได้ (คำนี้คือ "ประตูหนีภัย" ของหลายเกณฑ์ — ห้ามใช้มั่ว)
- **Mechanism** = วิธีที่ผู้ใช้ทำได้จริง จะเป็นของเว็บหรือของ user agent ก็ได้

## 3. เกณฑ์ทั้งหมด เรียงตามหลักการ

### หลักการ 1 — Perceivable

#### 1.1 Text Alternatives
| SC | ชื่อ | ระดับ | สาระ |
|----|------|-------|------|
| 1.1.1 | Non-text Content | A | เนื้อหาที่ไม่ใช่ข้อความทุกชิ้นต้องมี text alternative ที่ทำหน้าที่เทียบเท่า · ยกเว้น: ปุ่ม/ตัวควบคุม (ใช้ชื่อบอกหน้าที่), สื่อเวลา, แบบทดสอบ, ประสบการณ์ทางประสาทสัมผัส, CAPTCHA, ภาพตกแต่ง (ซ่อนจาก AT) |

#### 1.2 Time-based Media
| SC | ชื่อ | ระดับ | สาระ |
|----|------|-------|------|
| 1.2.1 | Audio-only and Video-only (Prerecorded) | A | เสียงล้วน/วิดีโอล้วนที่บันทึกไว้ ต้องมีทางเลือกเป็นข้อความ |
| 1.2.2 | Captions (Prerecorded) | A | คำบรรยายแทนเสียงสำหรับสื่อประสานเวลาที่บันทึกไว้ |
| 1.2.3 | Audio Description or Media Alternative (Prerecorded) | A | คำบรรยายเสียงหรือทางเลือกข้อความ |
| 1.2.4 | Captions (Live) | AA | คำบรรยายแทนเสียงสำหรับเนื้อหาสด |
| 1.2.5 | Audio Description (Prerecorded) | AA | คำบรรยายเสียงสำหรับวิดีโอที่บันทึกไว้ |
| 1.2.6 | Sign Language (Prerecorded) | AAA | ภาษามือ |
| 1.2.7 | Extended Audio Description | AAA | คำบรรยายเสียงแบบขยาย เมื่อช่องว่างเสียงไม่พอ |
| 1.2.8 | Media Alternative (Prerecorded) | AAA | ทางเลือกข้อความเต็มรูปแบบ |
| 1.2.9 | Audio-only (Live) | AAA | ทางเลือกสำหรับเสียงสด |

#### 1.3 Adaptable
| SC | ชื่อ | ระดับ | สาระ |
|----|------|-------|------|
| 1.3.1 | Info and Relationships | A | โครงสร้าง/ความสัมพันธ์ที่สื่อด้วยการจัดวางสายตา ต้องอ่านออกได้ด้วยโปรแกรม (heading, list, table header, label, fieldset, landmark) |
| 1.3.2 | Meaningful Sequence | A | ลำดับการอ่านที่มีความหมายต้องอ่านออกได้ด้วยโปรแกรม |
| 1.3.3 | Sensory Characteristics | A | คำสั่งใช้งานห้ามอ้างรูปทรง/สี/ขนาด/ตำแหน่ง/ทิศทาง/เสียงเพียงอย่างเดียว ("กดปุ่มกลม ๆ ด้านขวา" ตก) |
| 1.3.4 | Orientation | AA | ห้ามล็อกแนวจอ (แนวตั้ง/แนวนอน) เว้นแต่จำเป็น |
| 1.3.5 | Identify Input Purpose | AA | ช่องกรอกที่เก็บข้อมูลของผู้ใช้เองต้องระบุวัตถุประสงค์ด้วยโปรแกรม (`autocomplete="name"`, `"email"`, `"tel"` ฯลฯ ตามรายการ 53 ค่าของ HTML) |
| 1.3.6 | Identify Purpose | AAA | ระบุวัตถุประสงค์ของ component/ไอคอน/region ได้ด้วยโปรแกรม |

#### 1.4 Distinguishable
| SC | ชื่อ | ระดับ | สาระ |
|----|------|-------|------|
| 1.4.1 | Use of Color | A | ห้ามใช้ "สีอย่างเดียว" สื่อข้อมูล/บอกสถานะ/บอกการกระทำ |
| 1.4.2 | Audio Control | A | เสียงเล่นเองเกิน 3 วินาที ต้องมีปุ่มหยุด/คุมความดัง |
| 1.4.3 | Contrast (Minimum) | AA | ข้อความ 4.5:1 · ข้อความใหญ่ 3:1 |
| 1.4.4 | Resize Text | AA | ขยายข้อความได้ถึง 200% โดยไม่เสียเนื้อหา/ฟังก์ชัน |
| 1.4.5 | Images of Text | AA | ใช้ข้อความจริงแทนภาพข้อความ |
| 1.4.6 | Contrast (Enhanced) | AAA | 7:1 · ข้อความใหญ่ 4.5:1 |
| 1.4.7 | Low or No Background Audio | AAA | เสียงพื้นหลังต่ำกว่าเสียงพูด ≥ 20 dB |
| 1.4.8 | Visual Presentation | AAA | ผู้ใช้เลือกสี/ความกว้างบรรทัด (≤80 ตัวอักษร)/ระยะบรรทัด (≥1.5)/ไม่จัดชิดขอบสองข้างได้ |
| 1.4.9 | Images of Text (No Exception) | AAA | ภาพข้อความใช้ได้เฉพาะตกแต่งหรือจำเป็นจริง |
| 1.4.10 | Reflow | AA | ไหลลงคอลัมน์เดียวได้ที่ 320 CSS px โดยไม่ต้องเลื่อนสองแกน |
| 1.4.11 | Non-text Contrast | AA | ตัวควบคุม/กราฟิกที่จำเป็นต่อความเข้าใจ ≥ 3:1 |
| 1.4.12 | Text Spacing | AA | ผู้ใช้ปรับระยะข้อความ 4 ค่าได้โดยไม่เสียเนื้อหา |
| 1.4.13 | Content on Hover or Focus | AA | ป๊อปอัปจาก hover/focus ต้อง **ปิดได้ (dismissible) · เอาเมาส์ไปวางบนมันได้ (hoverable) · อยู่จนกว่าจะเลิกสนใจ (persistent)** |

### หลักการ 2 — Operable

#### 2.1 Keyboard Accessible
| SC | ชื่อ | ระดับ | สาระ |
|----|------|-------|------|
| 2.1.1 | Keyboard | A | ทุกฟังก์ชันสั่งงานด้วยคีย์บอร์ดได้ ไม่บังคับจังหวะการกด |
| 2.1.2 | No Keyboard Trap | A | ย้ายโฟกัสออกจากทุก component ได้ด้วยคีย์บอร์ด ถ้าออกด้วยวิธีพิเศษต้องบอกวิธี |

#### 2.2 Enough Time
| SC | ชื่อ | ระดับ | สาระ |
|----|------|-------|------|
| 2.2.1 | Timing Adjustable | A | ปิด/ปรับ/ขยายเวลาได้ (ขยายได้ ≥10 เท่า หรือเตือนก่อนหมดพร้อมต่อเวลาอย่างน้อย 20 วินาที) |
| 2.2.2 | Pause, Stop, Hide | A | สิ่งที่เคลื่อน/กะพริบ/เลื่อน/อัปเดตเองเกิน 5 วินาที ต้องหยุด/ซ่อนได้ |
| 2.2.3 | No Timing | AAA | ไม่มีการจับเวลาเลย |
| 2.2.4 | Interruptions | AAA | เลื่อน/ปิดการขัดจังหวะได้ ยกเว้นภาวะฉุกเฉิน |
| 2.2.5 | Re-authenticating | AAA | ล็อกอินใหม่แล้วทำงานต่อได้โดยข้อมูลไม่หาย |
| 2.2.6 | Timeouts | AAA | เตือนระยะเวลาที่ข้อมูลจะหาย (เว้นแต่เก็บไว้เกิน 20 ชั่วโมง) |

#### 2.3 Seizures

|----|------|-------|------|

| 2.3.2 | Three Flashes | AAA | ห้ามกะพริบเกิน 3 ครั้ง/วินาที โดยไม่มีข้อยกเว้น |
| 2.3.3 | Animation from Interactions | AAA | ปิดแอนิเมชันที่เกิดจากการกระทำผู้ใช้ได้ (`prefers-reduced-motion`) |

#### 2.4 Navigable
| SC | ชื่อ | ระดับ | สาระ |
|----|------|-------|------|

| 2.4.3 | Focus Order | A | ลำดับโฟกัสรักษาความหมายและใช้งานได้ |

| 2.4.5 | Multiple Ways | AA | มีมากกว่าหนึ่งวิธีในการหาหน้า (เมนู + ค้นหา + sitemap) ยกเว้นหน้าที่เป็นขั้นในกระบวนการ |
| 2.4.6 | Headings and Labels | AA | หัวเรื่องและป้ายกำกับต้องบอกหัวข้อ/จุดประสงค์ |
| 2.4.7 | Focus Visible | AA | เห็นตัวชี้โฟกัสคีย์บอร์ดได้ (ยังคงเป็นระดับ AA ใน 2.2) |
| 2.4.8 | Location | AAA | บอกตำแหน่งผู้ใช้ในชุดหน้า (breadcrumb) |
| 2.4.9 | Link Purpose (Link Only) | AAA | รู้จุดหมายจากข้อความลิงก์อย่างเดียว |
| 2.4.10 | Section Headings | AAA | ใช้หัวเรื่องแบ่งเนื้อหา |
| 2.4.11 | **Focus Not Obscured (Minimum)** | AA | 🆕 สิ่งที่ได้โฟกัสต้องไม่ถูกเนื้อหาของเราบังจนมิด |
| 2.4.12 | **Focus Not Obscured (Enhanced)** | AAA | 🆕 ต้องไม่ถูกบังแม้แต่บางส่วน |
| 2.4.13 | **Focus Appearance** | AAA | 🆕 ขนาด/คอนทราสต์ของตัวชี้โฟกัส |

## 4. เกณฑ์ที่ต้องรู้ลึก (ตัวที่กระทบงานเราจริง)

### 4.1 คอนทราสต์ข้อความ — 1.4.3 (AA) / 1.4.6 (AAA)

**ข้อกำหนด**
- ข้อความปกติ: **≥ 4.5:1**
- ข้อความใหญ่: **≥ 3:1**
- AAA: 7:1 และ 4.5:1 ตามลำดับ

**นิยาม "ข้อความใหญ่"** = ตั้งแต่ 18pt ขึ้นไป หรือ 14pt ตัวหนา
1pt = 1.333px → **≈ 24px ปกติ / ≈ 18.5px ตัวหนา**
(สำหรับฟอนต์ CJK ใช้ขนาดที่ให้ผลเทียบเท่า — ฟอนต์ไทยที่มีสระบน-ล่างควรคิดเผื่อเช่นกัน)

**สูตร**

```
contrast ratio = (L1 + 0.05) / (L2 + 0.05)      L1 = ตัวสว่างกว่า, L2 = ตัวเข้มกว่า
                                                 ค่าอยู่ระหว่าง 1:1 ถึง 21:1

relative luminance L = 0.2126·R + 0.7152·G + 0.0722·B

โดยแต่ละช่อง C ∈ {R,G,B} ที่ normalize เป็น 0..1 แล้ว:
    ถ้า C ≤ 0.04045   →  C / 12.92
    ถ้า C >  0.04045   →  ((C + 0.055) / 1.055) ^ 2.4
```

**ห้ามปัดเศษ** — W3C ระบุชัด 4.499:1 ถือว่าไม่ผ่าน

**ข้อยกเว้น**
- ข้อความในตัวควบคุมที่ถูกปิดใช้งาน (disabled)
- ข้อความตกแต่งล้วน / มองไม่เห็น
- ข้อความที่เป็นส่วนหนึ่งของภาพซึ่งมีเนื้อหาอื่นสำคัญกว่า
- โลโก้/ชื่อแบรนด์

**ที่มาของเลข 4.5** — ชดเชยความไวคอนทราสต์ที่หายไปของสายตาระดับ 20/40 : `3 × 1.5 = 4.5`

**หมายเหตุฟอนต์** — W3C เตือนเองว่าฟอนต์เส้นบางมาก อ่านยากกว่าแม้ผ่านคอนทราสต์ ควรเลือกน้ำหนักเส้นหนาขึ้นเมื่อคอนทราสต์เฉียดเกณฑ์

### 4.2 คอนทราสต์ของสิ่งที่ไม่ใช่ข้อความ — 1.4.11 (AA)

**≥ 3:1 เทียบกับสีที่อยู่ติดกัน** สำหรับ

1. **ส่วนที่จำเป็นต่อการระบุตัวควบคุมและสถานะของมัน** — เส้นขอบ input, checkbox, ปุ่ม, ตัว toggle, ตัวชี้โฟกัส
2. **กราฟิกที่จำเป็นต่อความเข้าใจเนื้อหา** — เส้นในกราฟ, ไอคอนสื่อความหมาย, ส่วนของแผนภาพ

**กฎ "สีที่อยู่ติดกัน"** — เทียบกับสีที่อยู่ *นอก* component เช่น input พื้นขาว ขอบเทา บนพื้นหลังขาว → เทียบขอบเทากับขาว

**ข้อยกเว้น** — ตัวควบคุมที่ปิดใช้งาน · ค่าเริ่มต้นของเบราว์เซอร์ที่เราไม่ได้แก้ · โลโก้ · กราฟิกที่การนำเสนอนั้นจำเป็น (ธงชาติ, heatmap, ภาพหน้าจอ) · **กราฟิกที่มีข้อความกำกับค่าเดียวกันอยู่แล้ว**

**ตัวอย่างชัด ๆ**

| กรณี | ผล | เหตุ |
|------|-----|------|
| ขอบ input `#767676` บนพื้นขาว | ผ่าน | ~8:1 |
| ขอบ input `#AAA` บนพื้นขาว และไม่มีตัวบ่งชี้อื่น | **ตก** | ~2.3:1 |
| checkbox ขอบ `#9D9D9D` บนขาว ไม่มีป้าย | **ตก** | ~2.7:1 |
| checkbox ขอบจาง แต่มีข้อความ "ยอมรับ" กำกับ | ผ่าน | ป้ายข้อความระบุตัวมันแล้ว |
| ปุ่ม disabled เทาอ่อนบนเทา | ผ่าน | ยกเว้น |
| กราฟเส้น 4 เส้นสีใกล้กัน แยกไม่ออก | **ตก** | เส้นแต่ละเส้นคือ graphical object |
| พายชาร์ตชิ้นสีเหมือนกัน ไม่มีเส้นคั่น | **ตก** | แยกชิ้นไม่ออก |
| ลิงก์ที่บอกด้วยขีดเส้นใต้สี `#B1262B` บนพื้นเกือบดำ | **ตก** | ตัวบ่งชี้เดียวคอนทราสต์ไม่ถึง |

ห้ามปัดเศษเช่นกัน — 2.999:1 ไม่ผ่าน

### 4.3 ขนาดเป้ากด — 2.5.8 (AA, 24px) / 2.5.5 (AAA, 44px)

**กฎหลัก** — ต้องวาดสี่เหลี่ยมจัตุรัสทึบ **24×24 CSS px** ที่ขนานแกนจอ ลงในพื้นที่เป้าได้ทั้งอัน

**ข้อยกเว้น 5 ข้อ**

1. **Spacing (ระยะห่าง)** — วิธีวัด: วาดวงกลม **เส้นผ่านศูนย์กลาง 24 CSS px** ทับกึ่งกลางกล่องครอบของเป้าที่เล็กเกิน ถ้าวงกลมนี้ *ไม่ทับ* เป้าอื่นและไม่ทับวงกลมของเป้าเล็กตัวอื่น → ผ่าน
   ตัวอย่าง: ปุ่มไอคอน 20×20 เรียงกัน เว้นห่าง 4px → ผ่าน · เว้น 0px → ตก
2. **Equivalent (มีตัวแทน)** — มีตัวควบคุมอื่นในหน้าเดียวกันที่ทำงานเหมือนกันและขนาดผ่าน
3. **Inline (อยู่ในบรรทัดข้อความ)** — ลิงก์ในย่อหน้า ที่ขนาดถูกจำกัดด้วย line-height ของข้อความรอบข้าง
4. **User agent control** — ตัวควบคุมค่าเริ่มต้นของเบราว์เซอร์ที่เราไม่ได้แต่ง (ถ้าแต่งเองแล้วต้องคุมระยะห่าง)
5. **Essential** — ขนาด/ตำแหน่งจำเป็นต่อความหมาย เช่น หมุดบนแผนที่ตามพิกัดจริง

**กับดักที่เจอบ่อย** — แถวเมนู/แถวตารางสูง 18px ซ้อนกันสองแถวห่าง 1px → **ตก** เพราะวงกลมของแถวบนกินเข้าเป้าแถวล่าง

### 4.4 Reflow — 1.4.10 (AA)

**ข้อกำหนด** — แสดงเนื้อหาโดยไม่เสียข้อมูล/ฟังก์ชัน และ **ไม่ต้องเลื่อนสองแกน** ที่

- เนื้อหาเลื่อนแนวตั้ง: กว้างเทียบเท่า **320 CSS px**
- เนื้อหาเลื่อนแนวนอน: สูงเทียบเท่า **256 CSS px**

**ที่มาของเลข** — ซูม 400% บนจอ 1280×1024 → 1280÷4 = 320 · 1024÷4 = 256

**ข้อยกเว้น** — เนื้อหาที่ *จำเป็น* ต้องเป็นสองมิติ: **ตารางข้อมูล**, แผนที่, แผนภาพ, วิดีโอ, แถบเครื่องมือที่ต้องเห็นพร้อมพื้นที่ทำงาน

**สำคัญกับระบบเรา** — ตารางข้อมูลได้รับการยกเว้น และ **เอาตารางใส่ container ที่เลื่อนแนวนอนได้เองนั้นถูกต้องตามเกณฑ์** แต่ข้อยกเว้นครอบเฉพาะตัวตาราง — หัวเรื่อง ตัวกรอง ปุ่ม แถบแบ่งหน้า ที่อยู่รอบ ๆ ยังต้องไหลลงได้ที่ 320px และหน้าต้องไม่มีสกรอลล์แนวนอนระดับ page

"ไม่เสียข้อมูล/ฟังก์ชัน" — การยุบหลายคอลัมน์เป็นแนวตั้ง ซ่อนเมนูใต้ hamburger ย้าย sidebar ลงล่าง **ไม่ถือว่าเสีย** เพราะยังเข้าถึงได้

### 4.5 Text Spacing — 1.4.12 (AA)

ผู้ใช้ต้องตั้งค่า 4 ค่านี้พร้อมกันได้โดยเนื้อหาไม่ขาดหาย ไม่ทับกัน ไม่ถูกตัดด้วย ellipsis

| ค่า | ขั้นต่ำที่ต้องรองรับ |
|-----|---------------------|
| line-height | ≥ 1.5 × font-size |
| ระยะหลังย่อหน้า | ≥ 2 × font-size |
| letter-spacing | ≥ 0.12 × font-size |
| word-spacing | ≥ 0.16 × font-size |

**CSS ที่ใช้ทดสอบ** (แปะทับแล้วต้องไม่พัง)

```css
* {
  line-height: 1.5 !important;
  letter-spacing: 0.12em !important;
  word-spacing: 0.16em !important;
}
p { margin-bottom: 2em !important; }
```

> ข้อนี้กับเรื่องสระไทยของเราเกี่ยวกันโดยตรง — กล่องที่กำหนดความสูงตายตัวและ `overflow: hidden` จะตกข้อนี้ทันทีเมื่อ line-height ถูกดันเป็น 1.5 ดู `thai-clip-vs-optical-center` ประกอบ

### 4.6 โฟกัส — 2.4.7 (AA) · 2.4.11 (AA) · 2.4.13 (AAA) · 1.4.11 (AA)

สี่เกณฑ์นี้ต้องอ่านรวมกัน

- **2.4.7 Focus Visible (AA)** — ต้องมีโหมดการทำงานที่เห็นตัวชี้โฟกัส · `outline: none` โดยไม่ใส่อะไรแทน = **ตก** · เทคนิคที่แนะนำคือ `:focus-visible`
- **1.4.11 (AA)** — ตัวชี้โฟกัสต้องคอนทราสต์ ≥ 3:1 กับสีข้างเคียง
  - ตัวชี้ *นอก* component → เทียบกับพื้นหลังของหน้า
  - ตัวชี้ *ใน* component → เทียบกับสีพื้นของ component
- **2.4.11 Focus Not Obscured (Minimum) (AA)** — เมื่อ component ได้โฟกัส ต้องไม่ถูกเนื้อหาที่เราสร้างบัง **จนมิด**
  - ตัวการที่พบบ่อย: sticky header/footer, แบนเนอร์คุกกี้, วิดเจ็ตแชตลอย
  - ผ่าน: sticky footer + `scroll-padding-bottom` ที่กันไม่ให้บังมิด · โมดัลที่รับโฟกัสไปเอง
  - ตก: sticky footer บังปุ่มที่โฟกัสอยู่ทั้งอัน · แชตลอยที่ปิดไม่ได้บังลิงก์ที่โฟกัส
  - ยกเว้น: เนื้อหาที่ผู้ใช้ย้ายเองได้ — ตรวจเฉพาะตำแหน่งเริ่มต้น
- **2.4.12 (AAA)** — ห้ามบังแม้แต่บางส่วน
- **2.4.13 Focus Appearance (AAA)** — ตัวชี้ต้อง (ก) มีพื้นที่ ≥ พื้นที่ของกรอบหนา 2 CSS px รอบ component (สี่เหลี่ยม w×h → `4h + 4w`) และ (ข) คอนทราสต์ ≥ 3:1 **ระหว่างพิกเซลเดียวกันในสถานะโฟกัสกับไม่โฟกัส**

**CSS ที่ผ่าน**

```css
:focus-visible {
  outline: 2px solid <สีคอนทราสต์สูง>;
  outline-offset: 2px;
}

/* ถ้าวาดเข้าด้านใน ต้องหนากว่า 2px เพื่อชดเชยพื้นที่ */
.button:focus-visible {
  outline: 3px solid <สี>;
  outline-offset: -3px;
}
```

### 4.7 Status Messages — 4.1.3 (AA)

**นิยาม** — ข้อความที่บอก (ก) ผลสำเร็จของการกระทำ (ข) สถานะรอ (ค) ความคืบหน้า (ง) การมีอยู่ของข้อผิดพลาด **และไม่ทำให้เกิดการเปลี่ยนบริบท**

**นับ** — "พบ 5 รายการ" · "บันทึกแล้ว" · "มี 3 ข้อผิดพลาด" · แถบความคืบหน้าอัปโหลด · ตัวเลขในกระดิ่ง

**ไม่นับ** — โมดัลที่ดึงโฟกัสไป (นั่นคือเปลี่ยนบริบท) · เมนู/accordion ที่กางออก · ช่องฟอร์มใหม่ที่โผล่ตามเงื่อนไข

**วิธีทำ**

| สถานการณ์ | ARIA |
|-----------|------|
| ผลสำเร็จ / สถานะแอป | `role="status"` (= `aria-live="polite"` + `aria-atomic="true"`) |
| ข้อผิดพลาด/คำเตือนที่ต้องรู้ทันที | `role="alert"` หรือ `aria-live="assertive"` |
| รายการที่ต่อท้ายเรื่อย ๆ | `role="log"` |
| ความคืบหน้า | `role="progressbar"` + live region |

**กับดักใหญ่สุด** — ต้องมี container ที่มี role อยู่ใน DOM **ตั้งแต่โหลดหน้า** แล้วค่อยเปลี่ยนข้อความข้างใน ถ้าฉีดทั้ง element ที่มี `aria-live` เข้าไปทีหลัง screen reader มักไม่ประกาศ

```html
<!-- ถูก -->
<div role="status" id="toast"></div>
<script>document.getElementById('toast').textContent = 'บันทึกแล้ว'</script>
```

`aria-atomic="true"` ใช้เมื่อข้อความเปลี่ยนบางส่วน แต่ต้องการให้อ่านทั้งประโยค (เช่น "0 รายการ" → "3 รายการ")

### 4.8 Info and Relationships — 1.3.1 (A)

เกณฑ์ที่ถูกละเมิดบ่อยที่สุดในโลก สาระคือ **อะไรที่ตาเห็นเป็นโครงสร้าง โค้ดต้องบอกด้วย**

| โครงสร้าง | ต้องใช้ |
|-----------|---------|
| หัวเรื่อง | `<h1>`–`<h6>` ไล่ระดับจริง ไม่ใช่ `<div class="big-bold">` |
| รายการ | `<ul> <ol> <dl>` |
| ตารางง่าย | `<th>` + `scope="col"/"row"` + `<caption>` |
| ตารางซับซ้อน | `headers` / `id` จับคู่เซลล์กับหัว |
| ป้ายฟอร์ม | `<label for>` หรือ `aria-labelledby` |
| กลุ่มช่อง (radio, ที่อยู่) | `<fieldset>` + `<legend>` |
| คำอธิบาย/ข้อความ error ของช่อง | `aria-describedby` |
| ภูมิภาคของหน้า | `<nav> <main> <header> <footer> <aside>` |
| เน้นข้อความ | `<strong> <em>` ไม่ใช่ CSS ล้วน |
| ช่องบังคับกรอก | `required` / `aria-required` **คู่กับ** เครื่องหมายที่ตาเห็น |

**ความล้มเหลวที่มีชื่อเรียก (Failure techniques)** — F2 (จัดรูปด้วยสไตล์ล้วน) · F33/F34 (ใช้ช่องว่างทำคอลัมน์/ตาราง) · F42 (ทำลิงก์ปลอมด้วย `onclick` บน `<div>`) · F43 (ใช้ markup โครงสร้างผิดความหมาย) · F46 (`<th>` ในตารางจัดหน้า) · F91 (ตารางไม่มีหัวจริง) · F92 (`role="presentation"` ทับเนื้อหาที่มีความหมาย) · **F111 (มีป้ายที่ตาเห็นแต่ control ไม่มี accessible name)**

### 4.9 Landmarks (ARIA APG)

| role | HTML |
|------|------|
| banner | `<header>` ระดับ body |
| main | `<main>` — **หนึ่งหน้าหนึ่งอัน** |
| navigation | `<nav>` |
| complementary | `<aside>` |
| contentinfo | `<footer>` ระดับ body |
| search | `<search>` |
| form | `<form>` ที่มีป้ายกำกับ |
| region | `<section>` ที่มีป้ายกำกับ |

หลัก: เนื้อหาที่รับรู้ได้ทุกชิ้นควรอยู่ใน landmark สักอัน · ถ้ามี landmark ชนิดเดียวกันหลายอันต้องตั้งชื่อแยกด้วย `aria-label`/`aria-labelledby` · อย่าใส่คำว่าชนิดซ้ำในชื่อ ("เมนูหลัก" ไม่ใช่ "navigation เมนูหลัก")

### 4.10 โมดัล (ARIA APG Dialog Pattern)

- `role="dialog"` + `aria-modal="true"` + `aria-labelledby` (ชี้ไปที่หัวข้อที่มองเห็น) และ `aria-describedby` ถ้าจำเป็น
- **เปิด** → ย้ายโฟกัสเข้าโมดัล (ตัวแรกที่ tab ได้ · ถ้าเนื้อหายาวให้โฟกัสหัวข้อที่ `tabindex="-1"` · ถ้าเป็นการกระทำอันตรายให้โฟกัสตัวเลือกที่เสียหายน้อยสุด)
- **Tab / Shift+Tab วนอยู่ในโมดัล** ออกไปข้างนอกไม่ได้
- **Esc ปิด**
- **ปิด** → คืนโฟกัสกลับไปที่ปุ่มที่เปิดมัน

> เกี่ยวกับกติกาเราเรื่อง "ทุกการอนุมัติต้องมีโมดัลบอกผลลัพธ์" — โมดัลพวกนั้นต้องผ่านชุดนี้ทั้งหมด

### 4.11 Label in Name — 2.5.3 (A)

**accessible name ต้องมีข้อความป้ายที่ตาเห็น อยู่ในนั้น** เหตุผลคือคนที่สั่งงานด้วยเสียงพูดตามป้ายที่เห็น ถ้าชื่อไม่ตรง สั่งไม่ติด

- แนวปฏิบัติที่ดี: ให้ข้อความป้ายอยู่ **ต้น** ชื่อ
- ผ่าน: ปุ่มเขียน "ส่ง" → `aria-label="ส่ง"` หรือปล่อยให้ชื่อมาจากข้อความในปุ่ม
- ผ่าน: ช่องป้าย "วันที่" ชื่อ "วันที่ (วว/ดด/ปปปป)"
- **ตก**: ปุ่มเขียน "ส่ง" แต่ `aria-label="ยืนยันการส่งคำร้อง"` (ป้ายที่เห็นไม่อยู่ในชื่อ)
- **ตก**: ป้ายอยู่ในชื่อแต่สลับลำดับคำ
- **ตก**: ปุ่มไอคอนล้วนที่ไม่มีชื่อเลย

**กฎใช้งาน** — ถ้ามีป้ายที่ตาเห็นอยู่แล้ว **หลีกเลี่ยง `aria-label`** เพราะมันจะไปทับชื่อ ทำให้เกิดคำสั่งที่มองไม่เห็น

### 4.12 Dragging Movements — 2.5.7 (AA)

**นิยามการลาก** — pointer จับ element ตอน down-event แล้ว element (หรือภาพแทนตำแหน่ง) ตามไปจนถึง up-event

**ต้องทำได้ด้วย single pointer โดยไม่ต้องลาก** เว้นแต่จำเป็นจริง หรือเป็นของ user agent (scroll, pull-to-refresh)

| องค์ประกอบ | ทางเลือกที่ต้องมี |
|-----------|------------------|
| บอร์ด kanban | เลือกการ์ด → เมนู "ย้ายไปคอลัมน์..." |
| slider | คลิกบนราง / ช่องกรอกตัวเลข / ปุ่มลูกศร |
| แผนที่ | ปุ่มเลื่อนทิศทาง |
| รายการเรียงลำดับได้ | ปุ่มขึ้น/ลง |
| คอลัมน์ตารางที่ลากปรับกว้างได้ | ต้องมีวิธีอื่นปรับ |

### 4.13 ฟอร์มและข้อผิดพลาด — 3.3.1 · 3.3.2 · 3.3.3 · 3.3.4

- **3.3.1 (A)** — ระบุช่องที่ผิด **เป็นข้อความ** (สีแดงอย่างเดียวตกทั้ง 3.3.1 และ 1.4.1)
- **3.3.2 (A)** — ทุกช่องมีป้าย และมีคำแนะนำรูปแบบเมื่อจำเป็น
- **3.3.3 (AA)** — ถ้าระบบรู้วิธีแก้ ต้องเสนอ ("รูปแบบวันที่ต้องเป็น วว/ดด/ปปปป")
- **3.3.4 (AA)** — งานที่มีผลผูกพัน/การเงิน/ลบหรือแก้ข้อมูล ต้องมีอย่างน้อยหนึ่งใน: ย้อนกลับได้ · ตรวจสอบข้อมูลก่อนส่ง · มีขั้นยืนยันที่ตรวจทานและแก้ได้

> ระบบเราเข้าข่าย 3.3.4 เต็ม ๆ ทั้ง QT/SO/สัญญา/การชำระเงิน — โมดัลยืนยันที่บอกผลลัพธ์ก่อนกดคือทางที่ถูกอยู่แล้ว

### 4.14 การยืนยันตัวตน — 3.3.8 (AA)

**ห้ามบังคับ "cognitive function test"** ในทุกขั้นของการยืนยันตัวตน — ได้แก่ การจำ (รหัสผ่าน ลำดับอักขระ รูปแบบ) การถอดข้อความ การสะกด การคำนวณ การแก้ปริศนา

**ผ่านได้ถ้ามีอย่างน้อยหนึ่งข้อ**
1. **Alternative** — มีวิธียืนยันตัวตนอื่นที่ไม่ใช่การทดสอบการรู้คิด
2. **Mechanism** — มีตัวช่วยทำแทนได้ (**password manager กรอกอัตโนมัติได้ + วางได้**)
3. **Object Recognition** — แค่ให้จำวัตถุทั่วไป (CAPTCHA รูปรถ/สัตว์)
4. **Personal Content** — ให้ระบุเนื้อหาที่ผู้ใช้เคยให้ไว้เอง

**สรุปปฏิบัติ**
- รหัสผ่านธรรมดา **ผ่าน** ตราบใดที่ไม่บล็อกการวาง (paste) และไม่ขวาง autofill
- **บล็อก paste ในช่องรหัสผ่านหรือ OTP = ตก**
- OTP ต้องวางได้
- 2FA ด้วย biometric / hardware key / OS auth **ผ่าน** (ไม่ใช่การทดสอบการรู้คิด)
- CAPTCHA ตัวอักษรบิด **ตก** (ตัวเลือกเสียงที่ยังต้องถอดข้อความก็ไม่ช่วย)

### 4.15 Redundant Entry — 3.3.7 (A)

ข้อมูลที่ผู้ใช้กรอกไปแล้วใน **กระบวนการเดียวกัน** ถ้าต้องใส่ซ้ำ ต้อง **เติมให้อัตโนมัติ** หรือ **ให้เลือกได้**

- ข้อยกเว้น: จำเป็นจริง (เช่น แบบทดสอบความจำ) หรือเพื่อความปลอดภัย (ตั้งรหัสผ่านใหม่)
- ขอบเขต: ภายใน session เดียว ข้ามโดเมนได้ถ้าเป็นกระบวนการเดียวกัน
- ตัวอย่างที่ผ่าน: ติ๊ก "ที่อยู่จัดส่งเหมือนที่อยู่ใบกำกับ" · ฟอร์มที่ error แล้วยังคงค่าที่กรอกไว้ · ขั้นที่ 3 เติมค่าจากขั้นที่ 1 ให้แก้ได้
- ทั้ง "เติมอัตโนมัติ" และ "ให้เลือกจากรายการ" นับว่าผ่านเท่ากัน

> ระบบเรามีเส้นงานหลายขั้นเยอะมาก (คำร้อง → ทะเบียน · Deal → QT → SO) ข้อนี้แทบเป็นกฎออกแบบของเราอยู่แล้ว

### 4.16 Consistent Help — 3.2.6 (A)

ถ้ามีช่องทางช่วยเหลือปรากฏหลายหน้า ต้องอยู่ **ลำดับสัมพัทธ์เดิม** เทียบกับเนื้อหาอื่น

ชนิดที่นับ: (1) ข้อมูลติดต่อคน (2) ช่องทางติดต่อคน เช่น แชต/ฟอร์ม (3) ตัวช่วยตัวเอง เช่น FAQ (4) ระบบติดต่ออัตโนมัติ เช่น แชตบอต

**ไม่ได้บังคับว่าต้องมีความช่วยเหลือ** — บังคับแค่ว่าถ้ามี ต้องอยู่ที่เดิม (ตำแหน่งบนจอเปลี่ยนตามความกว้างได้ แต่ลำดับใน DOM ต้องคงที่)

### 4.17 Content on Hover or Focus — 1.4.13 (AA)

tooltip / popover / เมนูที่โผล่จาก hover หรือ focus ต้องครบสามอย่าง

1. **Dismissible** — ปิดได้ด้วย Esc โดยไม่ต้องย้ายเมาส์/โฟกัส
2. **Hoverable** — ลากเมาส์เข้าไปบนตัวป๊อปอัปได้โดยมันไม่หาย
3. **Persistent** — อยู่จนกว่าผู้ใช้จะเลื่อนออก / ปิด / ข้อมูลไม่เกี่ยวข้องแล้ว (ห้ามหายเองตามเวลา)

## 7. เช็กลิสต์ใช้กับ SS System

ลำดับจากผลกระทบมากไปน้อย สำหรับเว็บแอปภายในที่เป็นตาราง/ฟอร์มหนัก

**คอนทราสต์และสี**
- [ ] ข้อความทุกชิ้นบนพื้นครีม/พื้นเข้ม ≥ 4.5:1 (ข้อความรอง/placeholder โดนบ่อยสุด)
- [ ] ป้ายสถานะที่ใช้สี ต้องมีข้อความ/ไอคอนกำกับด้วย ไม่ใช่สีล้วน (1.4.1)
- [ ] เส้นขอบ input · checkbox · ตัวคั่นตาราง ≥ 3:1 ถ้ามันคือตัวบ่งชี้เดียว (1.4.11)
- [ ] เส้น/แท่งในกราฟผลงานขาย ≥ 3:1 และไม่พึ่งสีล้วนแยกชุดข้อมูล

**คีย์บอร์ดและโฟกัส**
- [ ] เดินทั้งหน้าด้วย Tab ได้ ไม่มี trap (โมดัล, dropdown, date picker)
- [ ] `:focus-visible` ชัด ≥ 2px และคอนทราสต์ ≥ 3:1 ทั้งธีมสว่างและมืด
- [ ] แถบเมนูข้าง/หัวตารางที่ sticky ต้องไม่บังสิ่งที่โฟกัสจนมิด (2.4.11) — ใช้ `scroll-padding`
- [ ] ทุกอย่างที่คลิกได้ต้องเป็น `<button>`/`<a>` จริง ไม่ใช่ `<div onclick>` (F42, 2.1.1)

**เป้ากดและการลาก**
- [ ] ปุ่มไอคอนในแถวตาราง ≥ 24×24 หรือมีระยะห่างพอ (2.5.8)
- [ ] ที่ใดลากได้ ต้องมีปุ่ม/เมนูทำแทน (2.5.7)

**ตารางและ layout**
- [ ] ตารางข้อมูลใช้ `<th scope>` + `<caption>` ไม่ใช่ div grid (1.3.1)
- [ ] ตารางกว้าง ๆ ใส่ container เลื่อนแนวนอน ส่วนตัวกรอง/แบ่งหน้า/หัวเรื่องรอบข้างไหลลงได้ที่ 320px (1.4.10)
- [ ] ทดสอบด้วย CSS text-spacing แล้วไม่มีข้อความขาด/ทับ (1.4.12) — ระวังกล่องความสูงตายตัว + สระไทย

**ฟอร์ม**
- [ ] ทุก input มี `<label for>` จริง · placeholder ไม่ใช่ label
- [ ] ข้อความ error ผูกกับช่องด้วย `aria-describedby` และเป็นข้อความ ไม่ใช่กรอบแดงอย่างเดียว (3.3.1)
- [ ] ค่าที่เคยกรอกในเส้นงานเดียวกัน เติมมาให้ (3.3.7)
- [ ] `autocomplete` ในช่องข้อมูลส่วนบุคคล (1.3.5)
- [ ] ช่องค้นหามี `autoComplete="off"` (กติกาภายในเรา ไม่ขัดกับ 1.3.5 เพราะไม่ใช่ข้อมูลของผู้ใช้เอง)

**ข้อความสถานะ**
- [ ] toast / "บันทึกแล้ว" / "พบ N รายการ" / ตัวเลขกระดิ่ง อยู่ใน live region ที่มีอยู่ตั้งแต่โหลดหน้า (4.1.3)
- [ ] โมดัลอนุมัติ: `role="dialog"` + `aria-modal` + โฟกัสเข้า/วน/Esc/คืนโฟกัส

**โครงสร้าง**
- [ ] `<html lang="th">` และข้อความอังกฤษในเอกสาร EN มี `lang="en"` (3.1.1/3.1.2)
- [ ] `<title>` แต่ละหน้าไม่ซ้ำและบอกเรื่อง (2.4.2)
- [ ] มี `<main>` เดียว · `<nav>` มีชื่อ · มี skip link ข้ามเมนู (2.4.1)
- [ ] ไอคอนหนึ่ง entity หนึ่งแบบเหมือนกันทั้งเว็บ (3.2.4 — กติกาภายในเราตรงกับเกณฑ์นี้พอดี)
