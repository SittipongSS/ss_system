# แผนออกแบบ "ตารางเข้า service / ตารางผลิต"

สองโมดูลแยกกัน + ปฏิทินรวมหนึ่งหน้า — ต่อยอดจากไทม์ไลน์โครงการและของเข้า PM/RM ที่มีอยู่แล้ว

- เขียน: 2026-07-30
- ต่อยอดจาก: `lib/pm/schedule.js` (เอนจินไทม์ไลน์), `lib/pm/deliveries.js` (ของเข้า mig 0176/0177), `docs/cross-department-requests-plan.md`
- มติผู้ใช้ 2026-07-30: service = **เข้าไซต์ลูกค้าดูแลระบบกระจายกลิ่น** · ตารางผลิตละเอียดระดับ **วัน × ไลน์ + กำลังผลิต** · **แยกโมดูล แต่มีปฏิทินรวมให้ดู** · งานผลิต 1 ใบ **จองไลน์เดียว** · ช่างอยู่ **ฝ่ายใหม่ `TS` (Technic Service)** เห็นข้อมูล **ทีม SV ทั้งหมด** · ของที่ใช้หน้างาน **บันทึกอย่างเดียว ไม่ตัดสต็อก** · นัดเก็บ **เวลาจริง** (ไม่มี `slot`) + ไซต์มี **ช่วงเวลาที่ให้เข้า**
- สถานะ: **สายบริการจบครบ S-1→S-5 (merged) · P-1 + P-2 จบ (mig 0189 รอรันบน prod) · ถัดไป P-3 บอร์ด วัน × ไลน์**

## 0. ปัญหาที่แก้ — ระบบรู้ว่า "ต้องผลิต" แต่ไม่รู้ว่า "ผลิตวันไหน ที่ไหน"

ของที่มีอยู่แล้วในระบบวันนี้:

| ชั้น | ที่อยู่ | ตอบคำถามอะไรได้ |
|---|---|---|
| ไทม์ไลน์โครงการ | `lib/pm/schedule.js` + `project_tasks` | ขั้นตอนไหนควรเสร็จสัปดาห์ไหน (กริดรายสัปดาห์ W1–W5) |
| ขั้นผลิตในแม่แบบ | `templates.js` — `เบิกของเข้าไลน์ผลิต` 7 วัน → `ผลิตสินค้า` 3 วัน → `ส่งมอบของให้คลัง` | "ช่วงผลิตกินเวลาประมาณเท่าไร" |
| ของเข้า PM/RM | `material_deliveries` (mig 0176/0177) + `productionReadiness()` | **ผลิตได้เมื่อไหร่** (ของครบเมื่อไหร่) |

**สิ่งที่ไม่มีเลย:**

1. **ไลน์ผลิตไม่มีตัวตนในระบบ** — ขั้น `ผลิตสินค้า 3 วัน` เป็นแค่แท่งบน Gantt ไม่ผูกกับเครื่อง/ไลน์ไหน ไม่มีใครรู้ว่าวันที่ 5 ส.ค. มีงานจ่อกี่ใบ
2. **กำลังผลิตไม่ถูกนับ** — ถ้า SO 4 ใบทุกใบมีขั้น "ผลิตสินค้า" ทับสัปดาห์เดียวกัน ไทม์ไลน์ทั้ง 4 ใบเขียวหมด ทั้งที่โรงงานทำได้ใบเดียว → **แผนโกหกเงียบ ๆ** (ปัญหาเดียวกับ milestone "สั่งซื้อสาร" ที่เคยเป็นกล่องเปล่าก่อน mig 0176)
3. **งาน service ไม่มีที่อยู่เลย** — ทีม `SV` (Services) มีอยู่ใน `TEAMS` และลีดมี `serviceInterest = 'diffuser'` แต่หลังปิดการขายแล้ว **ไม่มีตารางไหนเก็บว่าไปติดตั้งที่ไหน ต้องกลับไปเติมน้ำหอมเมื่อไหร่** · `customers` มีที่อยู่ช่องเดียว → ลูกค้าที่มี 12 สาขาเก็บไม่ได้ตั้งแต่ต้น
4. ความละเอียดของไทม์ไลน์คือ **สัปดาห์** (`weekOfDay`, `cellKey`) — งาน service กับตารางผลิตต้องการ **วัน** และงาน service ต้องการ **ช่วงเช้า/บ่าย** ด้วย → ใช้กริดเดิมไม่ได้

> ⭐ **ตัวเชื่อมที่สำคัญที่สุดมีอยู่แล้ว:** `productionReadiness(deliveriesForSalesOrder(rows, soId))` ตอบว่า "ของครบแล้ว — เริ่มผลิตได้" ตารางผลิตที่ออกแบบนี้คือ **ปลายทางของข้อมูลชิ้นนั้น** ไม่ใช่ระบบใหม่ที่ไม่รู้จักกัน

## 1. ขอบเขต — 3 ส่วน

**มติผู้ใช้ 2026-07-30:** A และ B เป็น **ระบบของตัวเองในตัวสลับระบบ ไม่ใช่เมนูใต้ "บริหารงานขาย"**
→ เส้นทางจึงอยู่นอก `/pm` (ซึ่งเป็น project management ของฝ่ายขาย) และมีรายการของตัวเองใน `config/systems.js`

| ส่วน | เส้นทาง | เจ้าของ | สาระ |
|---|---|---|---|
| **A. ตารางผลิต** | `/production` | PC (วางแผน) · PD (ทำจริง) | บอร์ด วัน × ไลน์ผลิต + กำลังผลิตต่อวัน |
| **B. ตารางเข้า service** | `/service` | ทีม SV | ไซต์ → เครื่อง → รอบบริการ → นัดเข้า |
| **C. ปฏิทินรวม** | `/schedule` | ผู้บริหาร · SA | อ่านอย่างเดียว ซ้อนสองโมดูลในปฏิทินเดียว |

**A กับ B เป็นคนละโมดูล คนละตาราง คนละสิทธิ์** — ไม่ยัดเป็นตาราง `jobs` เดียวกัน เพราะหน่วยของงานคนละชนิดจริง ๆ (ผลิต = จำนวนชิ้น × ไลน์ × วัน · service = จุดหมาย × ช่าง × ช่วงเวลา) การยัดรวมจะได้ตารางที่ครึ่งหนึ่งของคอลัมน์เป็น NULL เสมอ — ซึ่งเป็นอาการเดียวกับที่ทำให้ต้องรื้อ 3 เมนูคำร้องข้ามฝ่าย

**C ไม่มีตารางของตัวเอง** — เป็น view ที่ query สองโมดูลแล้ว normalize เป็นรูปทรงเดียว (`{date, kind, title, owner, href, tone}`) ในไฟล์ pure ไฟล์เดียว ไม่มีการ copy ข้อมูล

## 2. หลักการที่ยึด (มาจากบทเรียนที่ระบบนี้เจ็บมาแล้ว)

1. **แผนคือค่าที่คำนวณได้ ไม่ใช่ตารางสำเนา** — การกระจายงานลงรายวันคำนวณจาก (วันเริ่ม, จำนวน, อัตราต่อวัน, วันหยุด) แบบเดียวกับ `autoCellsForTask()` และให้ override ได้แบบ `cellsOverride` · **ไม่สร้างตาราง booking รายวัน** เพราะสำเนาที่ไม่มีใครอัปเดตตามคือที่มาของบั๊กภาษี 4 สูตร
2. **เตือน ไม่บล็อก** — จองเกินกำลังผลิตได้ (โรงงานจริงมี OT) แต่ต้องเห็นสีแดงทันที · ระบบที่บล็อกจะถูกเลี่ยงไปทำนอกระบบ แล้วตารางก็ตายทั้งใบ
3. **ทุกวันที่นับผ่านปฏิทินทำงานจริง** — ใช้ `holidaySet()` + `isBusinessDay()` ที่มีอยู่ ห้ามนับ 7 วันดิบ ⚠️ **วันหยุด 2027 ยังไม่มีใน DB** (`THAI_HOLIDAYS` hardcode ถึง 2026) ตารางผลิตที่ข้ามปีจะเพี้ยนเงียบ ๆ — ต้องใส่ก่อนเปิดใช้
4. **สร้าง/แก้ ใช้ฟอร์มเดียวกัน** (กฎ `AGENTS.md`) — `ProductionJobForm`, `ServiceVisitForm`, `ServiceSiteForm` แต่ละตัวมีไฟล์เดียว ต่างกันได้แค่ props
5. **เหตุผลลงเธรด ไม่ลงคอลัมน์** — เลื่อนนัด/เลื่อนคิวผลิตต้องกรอกเหตุผล และเหตุผลนั้นลง `entity_updates` (append-only) ไม่ใช่คอลัมน์ `rescheduleReason` ที่รอบถัดไปเขียนทับจนไม่มีใครได้อ่าน
6. **หน้าที่ตอบคำถามเดียวต้องอ่านได้ใน 3 วินาที** — หน้า SO ตอบ "ผลิตวันไหน" · หน้าไซต์ตอบ "ครั้งหน้าเข้าเมื่อไหร่" · ไม่ต้องเปิดบอร์ดใหญ่

## 3. โมดูล A — ตารางผลิต

### 3.1 แนวคิด 3 ชั้น

```
ความต้องการ (demand)        →  งานผลิต production_jobs   ← มาจาก SO line
กำลัง (capacity)            →  ไลน์ผลิต production_lines + วันปิด/ปรับกำลัง
แผน (plan)                  →  คำนวณ: job × line × วันเริ่ม × อัตรา = โหลดรายวัน
```

**ชั้น "แผน" ไม่มีตาราง** — `lib/pm/productionPlan.js` (pure) คำนวณจาก 2 ชั้นบน

### 3.2 ตารางใหม่ (migration 0186 · P-1 + 0189 · P-2)

```sql
-- ไลน์ผลิต — master data ระดับ settings
production_lines (
  id text PK,
  code text NOT NULL UNIQUE,        -- 'MIX-01' | 'FILL-02'
  name text NOT NULL,               -- 'ไลน์ผสม 1'
  kind text NOT NULL,               -- 'mix' | 'fill' | 'pack' | 'other'
  "capacityPerDay" numeric,         -- กำลังผลิตต่อวันทำการ (หน่วยตาม unit)
  unit text,                        -- 'ชิ้น' | 'กก.'
  "isActive" boolean NOT NULL DEFAULT true,
  "sortOrder" integer NOT NULL DEFAULT 0,
  ...ผู้สร้าง/เวลา
)

-- วันที่ไลน์ทำงานไม่ปกติ (ซ่อมบำรุง / เพิ่มกะ) — override กำลังเป็นรายวัน
production_capacity_days (
  id text PK,
  "lineId" text NOT NULL REFERENCES production_lines(id) ON DELETE CASCADE,
  date date NOT NULL,
  "capacityPerDay" numeric NOT NULL CHECK (>= 0),   -- 0 = ปิดไลน์วันนั้น
  reason text,
  UNIQUE ("lineId", date)
)

-- งานผลิตหนึ่งใบ = ผลิตสินค้าตัวหนึ่ง จำนวนหนึ่ง เพื่อ SO ใบหนึ่ง
production_jobs (
  id text PK,
  code text UNIQUE,                 -- PB-YYMMXXXX (RPC next_entity_number scope 'PB')
  -- logical link ข้ามโมดูล (แพตเทิร์นเดียวกับ material_deliveries) — ไม่ใส่ FK ไป projects
  "projectId" text, "dealId" text,
  "salesOrderId" text REFERENCES sales_orders(id) ON DELETE SET NULL,
  "salesOrderLineId" text,
  "productId" text REFERENCES products(id) ON DELETE SET NULL,
  "fgCode" text, "productName" text,      -- snapshot เสมอ
  qty numeric NOT NULL CHECK (qty > 0),
  unit text,
  "dueDate" date,                   -- ต้องเสร็จก่อนวันไหน (จาก SO / ไทม์ไลน์)
  -- ── ชั้นแผน ── (มติ §10.1: งานหนึ่งใบจอง "ไลน์เดียว")
  "lineId" text REFERENCES production_lines(id) ON DELETE SET NULL,
  "plannedStart" date,
  "ratePerDay" numeric,             -- ว่าง = ใช้ capacityPerDay ของไลน์
  "dayOverrides" jsonb NOT NULL DEFAULT '{}'::jsonb,   -- {"2026-08-04": 0}
  -- ── สถานะจริง ──
  status text NOT NULL DEFAULT 'draft'
    CHECK (status IN ('draft','planned','in_progress','done','cancelled')),
  "actualStart" date, "actualFinish" date, "qtyProduced" numeric,
  "ownerId" text, "ownerName" text,       -- PC ผู้วางแผน
  note text,
  ...ผู้สร้าง/เวลา
  CONSTRAINT production_jobs_dates_sane CHECK (ทุก date BETWEEN '2000-01-01' AND '2100-12-31')
)
```

> ⚠️ `CREATE INDEX IF NOT EXISTS` เทียบแค่ชื่อ ไม่เทียบนิยาม — ถ้าแก้นิยาม index ต้อง `DROP` ก่อน แล้วยืนยันด้วย `pg_indexes` หลังรัน (บทเรียน mig 0181→0182)

### 3.3 `lib/pm/productionPlan.js` — ตรรกะล้วน (มีเทสต์)

| ฟังก์ชัน | คืนอะไร |
|---|---|
| `spreadJob(job, line, { holidays })` | `[{date, qty}]` — กระจาย `qty` ลงวันทำการจาก `plannedStart` ตาม `ratePerDay` เคารพ `dayOverrides` |
| `jobFinishDate(job, line, opts)` | วันสุดท้ายที่งานจบ = ใช้ตอบบนหน้า SO |
| `lineLoad(jobs, lines, range, opts)` | `Map<lineId-date, {planned, capacity, pct, jobs[]}>` — เนื้อของบอร์ด |
| `overloadedDays(load)` | วันที่ `planned > capacity` → แถบแดง |
| `readinessConflict(job, readiness)` | `plannedStart < readiness.lastDue` → **"วางผลิตก่อนของมาถึง"** |
| `dueRisk(job, finish)` | `finish > dueDate` → "จบช้ากว่ากำหนดส่ง N วัน" |

**สองอันล่างคือหัวใจ** — ระบบไม่ได้แค่วาดตาราง แต่ตอบว่าแผนนี้เป็นไปได้ไหม โดยดึงจาก `deliveries.js` ที่มีอยู่แล้ว

### 3.4 งานผลิตเกิดขึ้นยังไง

- **SO อนุมัติ** → สร้าง `production_jobs` สถานะ `draft` อัตโนมัติ **หนึ่งใบต่อ 1 SO line ที่มี `productId`** (บรรทัดบริการ/ค่าออกแบบฉลากไม่มี `productId` → ไม่สร้าง)
- PC เปิดคิว `draft` แล้ว **รวม/แตก/แก้จำนวน** ได้ก่อนวางลงไลน์ (ผลิตรวมล็อตเป็นเรื่องปกติ)
- วางลงไลน์ + ใส่ `plannedStart` → สถานะ `planned`
- ⚠️ **ห้ามสร้างงานผลิตอัตโนมัติจาก QT** — QT ยังไม่ใช่คำสั่ง จะได้คิวขยะที่ไม่มีใครกล้าลบ

### 3.5 หน้าจอ

| หน้า | สาระ |
|---|---|
| `/production` **บอร์ด** | แกนตั้ง = ไลน์ · แกนนอน = วัน (4–8 สัปดาห์) · แต่ละช่องแสดง % กำลังที่ใช้ + ชิปงาน · ช่องเกิน 100% เป็นแถบ danger · เสาร์-อาทิตย์/วันหยุดเทาทึบ |
| `/production` **คิว** | ตารางงาน `draft`/`planned` เรียงตาม `dueDate` + คอลัมน์ "ของครบ?" (จาก `productionReadiness`) — คิวนี้คือหน้าที่ PC เปิดจริงทุกเช้า |
| การ์ดบนหน้า **SO** | "ผลิต: 12–14 ส.ค. · ไลน์ผสม 1" หรือ "ยังไม่ได้วางคิวผลิต" + ปุ่มไปวาง |
| การ์ดบนหน้า **โครงการ** | งานผลิตทุกรอบของโครงการ (คอนเซปเดียวกับพาเนลของเข้า: โครงการเห็นทุกรอบ ดีลเห็นเฉพาะรอบตัวเอง) |

**ความสัมพันธ์กับไทม์ไลน์:** ขั้น `ผลิตสินค้า` บน Gantt **ไม่ถูกแทนที่** แต่ได้ป้ายสรุปห้อยแบบเดียวกับ `deliveryStepBadge()` ("วางคิวแล้ว 12–14 ส.ค.") และเมื่องานผลิต `done` ให้เสนอปิดขั้นนั้น — ไม่ปิดให้เอง เพราะ PD เป็นคนยืนยัน

## 4. โมดูล B — ตารางเข้า service

### 4.1 แนวคิด 4 ชั้น

```
ที่ไหน   →  service_sites    (ลูกค้า 1 ราย มีได้หลายจุด — customers มีที่อยู่ช่องเดียว ใช้ไม่พอ)
อะไร     →  service_assets   (เครื่องกระจายกลิ่นแต่ละตัว + กลิ่นที่ใช้)
ทุกเมื่อไหร่ → service_plans (รอบบริการ: ทุก N สัปดาห์)
เข้าจริง  →  service_visits  (นัดหนึ่งครั้ง = หนึ่งแถวบนตาราง) + service_visit_items (ของที่ใช้)
```

### 4.2 ตารางใหม่ (migration 0187 · S-1 + 0188 · S-2)

  -- ข้อจำกัดถาวรของไซต์: ห้างเปิด 10:00 · โรงแรมห้ามเข้าช่วงเช็คอิน · โรงงานหยุดพัก 12:00-13:00

service_assets (

### 4.3 `lib/service/rounds.js` — ตรรกะล้วน

| ฟังก์ชัน | คืนอะไร |
|---|---|
| `plannedDates(plan, {from, to, holidays})` | วันที่ควรเข้าในช่วง — วันที่ตกวันหยุด **เลื่อนไปวันทำการถัดไป** |
| `ensureVisits(plan, existing, horizonDays = 90)` | นัดที่ต้อง gen เพิ่ม (ไม่ซ้ำของเดิม) |
| `nextAfterDone(plan, visit)` | นัดถัดไปนับจาก **วันที่ทำจริง** ไม่ใช่วันที่นัดไว้ — ถ้าเข้าช้า 5 วัน รอบถัดไปต้องขยับตาม |
| `dayLoad(visits, {perPersonPerDay})` | โหลดรายคนรายวัน → เตือนเมื่อช่างคนเดียวถูกนัด 6 จุดในวันเดียว |
| `zoneSplit(visits)` | จัดกลุ่มตามโซนในวันเดียวกัน — วันที่วิ่งข้ามโซนขึ้นป้ายเตือน |
| `refillStatus(asset, ctx)` ✅ | สถานะน้ำหอม 5 แบบ — `unknown` (ข้อมูลไม่พอ ไม่เดา) · `covered` (มีนัดก่อนหมดแล้ว) · `overdue` · `soon` (≤14 วัน) · `ok`<br>⚠️ ของที่**แห้งไปแล้ว**ยังเป็น `overdue` แม้มีนัดรออยู่ — นัดที่มาหลังวันหมดไม่ได้แปลว่าไม่มีปัญหา ลูกค้าดมไม่ได้กลิ่นไปแล้วหลายวัน<br>⚠️ ตัวตั้ง = วันเข้าเติมล่าสุด**ของไซต์** (ช่างเข้าครั้งเดียวเติมทุกเครื่อง) · เครื่องที่ติดตั้งทีหลังใช้ `installedAt` แทน · นับเฉพาะนัดที่**ปิดงานแล้ว** ไม่งั้นวันหมดเลื่อนออกไปเรื่อย ๆ ทั้งที่ขวดแห้ง |
| **`accessConflict(visit, site)`** | เวลานัดหลุดช่วงที่ไซต์ให้เข้า (`accessFrom`–`accessTo`) หรือชนวันที่ไซต์ไม่ให้เข้า (`accessDays`) → **เตือน ไม่บล็อก** (ลูกค้าอนุโลมเป็นครั้ง ๆ ได้) · นัดที่ยังไม่ใส่เวลาไม่ถือว่าผิด |
| **`overlaps(visits)`** | นัดของช่าง**คนเดียวกัน**ที่เวลาทับกัน — ของเดิมทำไม่ได้เพราะ เช้า/บ่าย หยาบเกิน · นัดที่ไม่มีเวลาชนกับใครไม่ได้ (ไม่รู้เวลา = ไม่ตัดสิน) |
| `visitMinutes(visit)` | ความยาวนัดเป็นนาที — ใช้วางความสูงชิปบนปฏิทินและรวมชั่วโมงงานต่อวัน |

> **ทำไม horizon 90 วัน ไม่ gen ทั้งปี:** นัดที่ gen ไว้ 12 เดือนล่วงหน้าคือ 12 แถวที่จะถูกเลื่อนทุกเดือนแล้วไม่มีใครกล้าลบ · gen สั้น + ต่อรอบเมื่อปิดงานจริง ทำให้ตารางสะท้อนของจริงเสมอ

## 6. สิทธิ์ — ฝ่ายใหม่ `TS` (Technic Service)

> ⭐ **มติผู้ใช้ 2026-07-31: สองระบบนี้เป็นคนละทีมปฏิบัติงาน** — แผนการผลิตคือ **PD** (กับ PC ที่วางแผนของเข้า) · ธุรกิจบริการคือ **TS** · ช่างไม่ต้องเห็นตารางโรงงาน และคนโรงงานไม่ต้องเห็นนัดเข้าไซต์ · ล็อกไว้ด้วย 
> ⚠️ cap ทั้งสองชุดอยู่ที่ role  ซึ่ง PC/PD/WH/QC/TS ใช้ร่วมกัน — **ตัวกั้นจริงคือ*ฝ่าย*** ที่เขียนใน  /  · ลืมแคบเมื่อไหร่ สองระบบรั่วหากันทันทีโดยไม่มีอะไรฟ้อง

**มติผู้ใช้:** ช่างหน้างานอยู่ **ฝ่าย `TS`** ซึ่งเป็น *ฝ่ายปฏิบัติงาน* ที่รับงานต่อจาก **ทีม `SV` (ธุรกิจบริการ)** ที่ขาย
→ `TS` เป็น **department** ไม่ใช่ team · ตรงกับแพตเทิร์นที่มีอยู่แล้วของ `PC`/`PD`/`WH`/`QC` (role `staff` + department แยก)

| สิ่งที่ต้องแก้ | ที่ไหน |
|---|---|
| `DEPARTMENTS` += `'TS'` + label ไทย "ฝ่ายเทคนิคบริการ" | `lib/permissions.js` |
| `DEPARTMENT_ROLES.TS = ['staff']` | เดียวกัน |
| `TEAMS` **ไม่แตะ** — `SV` (Services) ยังเป็นทีมขายธุรกิจบริการเหมือนเดิม | — |

capability ใหม่ 4 ตัว: `production:view` `production:edit` `service:view` `service:edit`

| ใคร | ได้อะไร | ขอบเขตข้อมูล |
|---|---|---|
| `staff` department **PC / PD** | `production:view` + `production:edit` | ทั้งหมด — **ไม่เห็นธุรกิจบริการเลย** |
| `staff` department **TS** (ช่าง) | `service:view` + `service:edit` · **ไม่มี `production:view`** | **ทุกไซต์/นัดของทีม SV** (มติผู้ใช้ — ไม่ใช่แค่นัดที่ตัวเองถูกมอบหมาย เพราะช่างสลับกันไปแทนกันเป็นเรื่องปกติ) |
| sales roles ทุกตัว | `production:view` · `service:view` | ตาม scope ทีมเดิม — SA ตอบลูกค้าได้ว่าผลิตวันไหน โดยไม่ต้องแก้ตาราง |
| `senior_ae`/`ae`/`ac` **team SV** | `service:edit` | ทีม SV เป็นเจ้าของสัญญาบริการ |
| `admin` / `ae_supervisor` | ทุกอย่าง · `executive` อ่านอย่างเดียว | ทั้งหมด |

> ⚠️ **บทเรียนตรงที่ต้องไม่ทำซ้ำ:** PC/PD/TS ไม่มี role ของตัวเอง ถือ role `staff` เหมือนกันหมด — ถ้ากั้นด้วย `pmEditScope` **คนที่รู้เรื่องจริงจะเป็นคนเดียวที่แก้ไม่ได้** (เกิดมาแล้วกับ `/api/pm/my-work` ที่ PC ไม่เคยเห็นคิวตัวเอง) · ต้องเช็ค **department** ตรง ๆ แบบเดียวกับ `canEditDeliveries()` และ `costing:*`
>
> ⚠️ **ช่างต้องไม่ได้ cap ขายติดมา** — นี่คือเหตุผลที่ `TS` เป็น department แยก ไม่ใช่ team ใต้ SA: ถ้าช่างถือ role `ae` เพื่อให้มีทีมได้ จะเห็นดีล/ใบเสนอราคา/มูลค่าทั้งทีมทันที (กฎเดิม: ย้ายคนข้ามกลุ่มห้ามรับ cap ของกลุ่มปลายทาง)

## 8. เธรดความเคลื่อนไหว

ทั้ง `production_job` และ `service_visit` เข้าเธรดกลาง `entity_updates` (mig 0163) — ตารางนี้ polymorphic ไม่มี FK และ **ไม่มี CHECK ที่ `entityType`** ชนิดใหม่ประกาศในโค้ดที่ `lib/master/updateTypes.js` เท่านั้น จึงเพิ่มได้โดย**ไม่ต้อง migration**

## 10. มติที่ปิดแล้ว + ข้อค้าง

### 10.1 ✅ งานผลิต 1 ใบ **จองไลน์เดียว**
`production_jobs` ถือ `lineId` เดียว ไม่แตก `production_job_steps` · หน่วยของงานยึด **หน่วยของไลน์ที่จอง** (`production_lines.unit`) — ถ้าไลน์คิดเป็นกิโลแต่ SO สั่งเป็นชิ้น ให้ PC กรอก `qty` ตามหน่วยไลน์ และแสดงจำนวนของ SO ไว้ข้าง ๆ เป็นข้อมูลอ้างอิง

> ถ้าวันหนึ่งต้องจองสองขั้น (ผสม→บรรจุ) ทางออกที่**ไม่ต้องรื้อ**คือออกงานผลิตสองใบผูก SO line เดียวกัน — โครงรองรับอยู่แล้วเพราะ `salesOrderLineId` ไม่ unique

### 10.2 ✅ ของที่ใช้หน้างาน = **บันทึกอย่างเดียว**
`service_visit_items` ไม่ตัดสต็อก ไม่ออกบิล · เป็นหลักฐานว่าเติมกลิ่นอะไรไปเท่าไร เพื่อ (ก) ตอบลูกค้าย้อนหลัง (ข) ป้อน `refillDue()` ให้ประเมินรอบถัดไปแม่นขึ้น
⚠️ **ห้ามเผลอทำเป็นครึ่งทาง** — ถ้าไม่ตัดสต็อกก็อย่ามีช่อง "คงเหลือ" ให้คนเข้าใจผิดว่าระบบรู้ยอด

### 10.3 ✅ ช่วงเวลาเข้าไซต์ — เก็บ **เวลาจริง** ทั้งสองชั้น
**มติผู้ใช้ 2026-07-30:** ใส่ช่วงเวลาเข้าไซต์ · แยกเป็นสองเรื่องที่ไม่ใช่อันเดียวกัน

| ชั้น | คอลัมน์ | คือ |
|---|---|---|
| **ไซต์** | `accessFrom` / `accessTo` / `accessDays` | ไซต์ **ยอมให้เข้า**ช่วงไหน — ข้อจำกัดถาวร กรอกครั้งเดียวใช้ตลอด |
| **นัด** | `startTime` / `endTime` (+ `actual*`) | นัด**ครั้งนี้**เข้ากี่โมง |

ความสัมพันธ์: `accessConflict()` เทียบสองชั้นแล้ว**เตือน ไม่บล็อก** — ลูกค้าอนุโลมเป็นครั้ง ๆ ได้ ระบบที่บล็อกจะถูกเลี่ยงไปนัดนอกระบบ

> 🪤 **ยุบ `slot` ทิ้ง** — เดิมออกแบบไว้เป็น เช้า/บ่าย/เต็มวัน · พอมีเวลาจริงแล้วการเก็บทั้งคู่ = **ข้อมูลชิ้นเดียวสองแหล่ง** ที่เพี้ยนหากันแน่นอน (นัด 13:30 แต่ `slot='am'` ค้างอยู่ ใครถูก?) · "เช้า/บ่าย/เต็มวัน" กลายเป็น **ปุ่มลัดในฟอร์ม** ที่เติมเวลาให้แทน — ได้ความเร็วเท่าเดิมโดยไม่มีแหล่งที่สอง
>
> ⚠️ **เวลาว่างได้** (`NULL`) = "นัดวันนั้น ยังไม่ระบุเวลา" ซึ่งเป็นสถานะจริงที่เกิดบ่อย · ตัวตรวจทุกตัว (`overlaps`, `accessConflict`) ต้อง**ไม่ตัดสินแถวที่ไม่มีเวลา** — ไม่รู้เวลา ไม่ใช่ ผิด

### 10.4 ⏰ วันหยุด 2027 — **งานคน ต้องทำก่อนเปิดใช้**
`THAI_HOLIDAYS` hardcode ถึง 2026 · ตาราง `holidays` มีแล้วแต่ต้องกรอก — **ตารางผลิต/รอบ service ที่ข้ามปีจะคำนวณผิดเงียบ ๆ** (ไม่มี error ให้เห็น แผนแค่เพี้ยน)
