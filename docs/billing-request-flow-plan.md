## 0. สรุปสั้นที่สุด

สายงาน "ขอใบวางบิลจากบัญชี" **ถูกออกแบบครบและเขียนโค้ดไปแล้วครึ่งหนึ่ง** แล้วถูกปิดเก็บ
ด้วยมติ ม-87 (*"ตอนนี้สนใจแค่ RD"*) · หลังจากนั้นอีก 5 วัน สายการเงินอีกครึ่งกลับถูกสร้าง
ขึ้นมาจากอีกทาง — งวดชำระ SO (`0245`) และขั้นบัญชีตรวจใบ (`0250`) — **โดยไม่มีเอกสารฉบับไหน
รู้ว่าอีกฉบับเดินไปแล้ว**

⇒ วันนี้มีสองครึ่งที่ยังไม่ต่อกัน:

| ครึ่งที่มีแล้ว | ครึ่งที่ยังขาด |
|---|---|
| งวดชำระ SO + SA แจ้ง/บัญชีรับรอง (`0245`) | **ไม่มีทางขอเอกสารจากบัญชี** — ปิดด้วยธง `legacy` |
| ขั้นบัญชีตรวจใบ `financeStatus` (`0250`) | **ไม่มีสัญญาบริการ** ⇒ สายบริการยังไม่มีที่แขวนงวด |
| โมดูล `/finance` + role `finance` + ฝ่าย `FN` | **ไม่มีคิวคำร้องของบัญชี** |

⭐ **ข้อเสนอทั้งฉบับสรุปเป็นประโยคเดียว:**
> ตารางงวดชำระตัวเดียว สองเจ้าของ (ใบสั่งขาย · สัญญาบริการ) ·
> คำร้อง `billing_doc` ชนิดเดียวเป็นทางออกเอกสารของทั้งสองสาย ·
> ด่านเข้าไซต์อ่านจากตารางงวดตัวเดิม ไม่นับเงินเอง

## 1. สิ่งที่ตรวจแล้วว่ามีจริงบนโค้ดวันนี้

### 1.1 กำแพงทั้งสามของแผนธุรกิจบริการ §9 — **พังครบแล้ว**

| # | กำแพงเดิม | สถานะวันนี้ |
|---|---|---|
| 1 | ไม่มีฝ่ายบัญชีใน `DEPARTMENTS` | ✅ `FN` อยู่ครบ (`permissions.js:83`) |
| 2 | `dept_requests.dept CHECK (dept IN ('RD','PC'))` | ✅ ผ่อนแล้วรับ `FN` (mig `0212`) |
| 3 | `workflow_template_steps.role` ไม่มี `TS` | ✅ เพิ่มแล้ว (mig `0192`) |

⇒ **PR `G-1` ของแผนธุรกิจบริการเสร็จสมบูรณ์แล้ว** ไม่ต้องทำซ้ำ

⚠️ **แต่มติข้อ 2 ของแผนนั้นเพี้ยนจากของจริง** — แผนเขียนว่า role ชื่อ `accountant`
โค้ดที่ลงจริงใช้ `finance` (มติผู้ใช้ 2026-08-13: *"ไม่อยากใช้คำว่า Staff"*) ·
`ROLES` มี `finance` · `DEPARTMENT_ROLES.FN = ['finance']` (ตัด `staff` ออก 2026-08-28 — ดู [role-per-department.md](role-per-department.md))
⇒ ต้องแก้บรรทัดนั้นในแผนเดิม ไม่งั้นคนอ่านจะไปสร้าง role ที่สอง

### 1.2 สายงาน "สองลายเซ็น" ของแผน §5 — **สร้างแล้ว แต่สร้างบนใบสั่งขาย**

`sales_order_installments` (mig `0245`) ยกสายงานจากมติ 2026-08-01 มาตรง ๆ:

```
pending ──[SA/AC กด "ลูกค้าจ่ายแล้ว" + แนบหลักฐาน]──> reported
              ↑                                        │
              └──────[บัญชีตีกลับ + เหตุผล]────────────┤
                                                       ↓
                                     [บัญชีคอนเฟิร์ม] confirmed
```

คอลัมน์ครบตามที่แผนออกแบบไว้ — `seq · label · percent · amount · dueDate · status ·
reportedBy*/paidOn/evidence · confirmedBy* · rejectedReason`

🔴 **ขาดคอลัมน์เดียวเทียบกับแผน: `billingRequestId`** ซึ่งเป็นตัวเชื่อมไปคำร้อง

⭐ **ยอดมาจาก snapshot ของ `quotations.paymentPlan` ตอนอนุมัติใบ** ไม่ใช่ตอนสร้างร่าง ·
`type:'full'` = หนึ่งงวด 100% ไม่ใช่ศูนย์งวด

### 1.3 ขั้นบัญชีตรวจใบ (mig `0250`) — ของใหม่ที่แผนเดิมไม่มี

แผนธุรกิจบริการ §5 เขียนว่า *"ในระบบวันนี้ SO ยังไม่มีขั้นบัญชี … แผนนี้จะเป็นที่แรก"*
— **ไม่จริงแล้ว** · มีก่อนแล้วด้วยเส้นทางอื่น และตัดสินไว้ดีกว่าที่แผนคาด:

`sales_orders.financeStatus` เป็น **แกนคู่ขนาน ไม่ใช่สถานะกลางทาง** เพราะ
`status='approved'` ปลดล็อก 12 จุดทั่วระบบ ⇒ แทรกสถานะกลางเมื่อไร ของ 12 อย่างหยุดรอบัญชี

### 1.4 คำร้อง `billing_doc` — สร้างครบแล้ว ปิดไว้ด้วยธงเดียว

### 1.5 R-1 ของแผนรื้อคำร้อง — ทำแล้ว

## 2. 🔴 ข้อค้นพบที่เปลี่ยนรูปแผน — บัญชีมีสามกริยา ไม่ใช่หนึ่ง

ตอนนี้ระบบมีสองด่านบัญชีที่หน้าตาคล้ายกันมาก และกำลังจะมีอันที่สาม
ถ้าไม่ตั้งชื่อให้ต่างกันตั้งแต่วันนี้ **คนกดจะสับสนภายในสัปดาห์แรก**

| กริยา | ตอบคำถามอะไร | เก็บที่ไหน | กดกี่ครั้ง |
|---|---|---|---|
| **ตรวจใบ** | *เอกสารใบนี้ถูกต้องไหม* (ที่อยู่ออกบิล · เลขภาษี · เครดิต) | `sales_orders.financeStatus` (`0250`) | ครั้งเดียวต่อใบ |
| **ออกเอกสาร** | *ออกใบวางบิล/ใบกำกับให้หน่อย* | 🆕 คำร้อง `billing_doc` | กี่ครั้งก็ได้ |
| **รับรองงวด** | *เงินงวดนี้เข้าจริงไหม* | `sales_order_installments.status` (`0245`) | ครั้งเดียวต่องวด |

⭐⭐ **สามอันนี้ห้ามรวมเป็นสถานะเดียว** — ของจริงเดินสลับกันได้ทุกลำดับ:
ออกใบวางบิลก่อนลูกค้าจ่าย · จ่ายก่อนขอใบกำกับ · ขอใบเสร็จหลังจ่ายไปแล้วสองเดือน

🪤 **กับดักที่ต้องเขียนกันไว้ในโค้ด**
- **ปิดคำร้อง ≠ งวดถูกรับรอง** — ออกใบวางบิลแล้วไม่ได้แปลว่าเงินเข้า
- **งวด `confirmed` ≠ คำร้องปิด** — บางงวดไม่มีใครขอเอกสารเลย (มติเดิม: *"บางทีขอ บางทีไม่ขอ"*)
⇒ `billingRequestId` **nullable และไม่มีตรรกะไหนบังคับให้มีค่า**

### 3.1 ⭐ ตารางงวดตัวเดียว สองเจ้าของ — ไม่สร้างตารางที่สอง

**ห้ามสร้าง `service_contract_installments` แยก** แม้แผนเดิมจะเขียนชื่อนั้นไว้
(เขียนตอนที่ยังไม่มี `sales_order_installments`) — สร้างแยกเมื่อไรได้ของสี่ชุดที่ต้องเพี้ยนหากัน:
สอง API เขียน · สองด่านสิทธิ์ · สองโมดัลยืนยัน · สองที่นับ "ค้างชำระ"

⇒ ตรงกับข้อห้ามที่ `request-hub-rebuild-plan.md` R-2 เขียนไว้เอง: **"ห้ามสร้างกลไกที่สอง"**
และตรงกับกฎข้อ 3 ของ `module-ownership-rule.md` (ทางเขียน · ด่านสิทธิ์ · จอยืนยัน ต้องมีชุดเดียว)

**รูปที่เสนอ** — เพิ่มคอลัมน์เจ้าของที่สอง ไม่เปลี่ยนชื่อตาราง:

```sql
ALTER TABLE public.sales_order_installments
  ALTER COLUMN "salesOrderId" DROP NOT NULL,
  ADD COLUMN "serviceContractId" text
      REFERENCES public.service_contracts(id) ON DELETE CASCADE,
  ADD CONSTRAINT installment_one_owner CHECK (
    ("salesOrderId" IS NOT NULL)::int + ("serviceContractId" IS NOT NULL)::int = 1
  );
```

| ทางเลือก | ทำไมไม่เอา |
|---|---|
| ตารางที่สอง | สี่ชุดที่ต้องเพี้ยนหากัน (ข้างบน) |
| `ownerType` + `ownerId` แบบ polymorphic | เสีย FK จริงทั้งสองข้าง — โรคเดียวกับ `ON DELETE SET NULL` ที่ R-5 เพิ่งบันทึกไว้ |
| ✅ **สองคอลัมน์ + CHECK เลือกหนึ่ง** | FK จริงทั้งคู่ · DB บังคับเจ้าของเดียว · API เดิมไม่พัง |

⚠️ **ชื่อตารางจะไม่ตรงกับเนื้ออีกต่อไป** — ยอมรับและคอมเมนต์กำกับ ดีกว่า `ALTER TABLE RENAME`
บนตารางที่มีเงินจริงและมี route/เทสต์อ้างชื่ออยู่หลายจุด · เปลี่ยนชื่อทีหลังได้เสมอ

### 3.2 สัญญาบริการ — สองสถานะแยกกัน

ตามมติ `service-field-operations.md` ข้อ 11 · ของจริงในชีต 64% ค้างที่ *"รอลูกค้าส่งสัญญา"*

| ช่อง | มาจากไหน | กฎ |
|---|---|---|
| `docStatus` | คนกรอก | `pending_customer` · `received` · `not_started` |
| `serviceStatus` | **คำนวณจาก `startDate`/`endDate` เสมอ** | ห้ามเก็บเป็นคอลัมน์ |
| `billingCycle` | `monthly \| quarterly \| yearly \| custom` | gen งวดตอนสร้าง **แล้วแก้รายงวดได้** |

🪤 **ห้าม import คอลัมน์ "ระยะเวลา (ปี)" จากชีต** — ขัดกับตัวเองแล้ว (Dapper ช่วงวันเดียวกัน
ใส่ `0.25` กับ `1`) · คำนวณจากวันที่เสมอ · ปีเป็น พ.ศ. ปนกับ ค.ศ. ต้องมีเทสต์ทั้งสองแบบ

### 3.3 ⭐ งวดชำระเกิดตั้งแต่ร่าง SO — ได้ ถ้าย้ายที่หยุดยอด

**คำถามผู้ใช้ 2026-08-14:** *"งวดชำระ gen ตั้งแต่ร่าง SO เลยได้มั้ย"*

**ได้** — กลไกรองรับอยู่แล้ว `ensureInstallments` เป็น idempotent และถูกเรียกจากสองทาง
อยู่ก่อนแล้ว (อัตโนมัติตอนอนุมัติ · ปุ่ม "เริ่มติดตามการชำระ" ของใบเก่า) ·
ตัวที่ห้ามไว้คือด่านบรรทัดเดียวใน `installments/route.js:66`
พร้อมเหตุผลที่เขียนกำกับไว้:

> *"ยอดยังเปลี่ยนได้จนกว่าจะอนุมัติ — สร้างงวดก่อนหน้านั้นยอดต่องวดจะผิดเงียบ ๆ"*

⭐ **เหตุผลนั้นถูก แต่แก้ได้โดยไม่ต้องเลื่อนเวลาสร้าง** — ปัญหาไม่ใช่ "สร้างเร็วไป"
แต่คือ **"snapshot ครั้งเดียวแล้วไม่มีใครมาทับ"** ⇒ ย้ายจุดที่หยุดยอด ไม่ใช่จุดที่สร้างแถว

| ช่วง | `percent` / `amount` | `dueDate` · `label` · `note` |
|---|---|---|
| ร่าง / รออนุมัติ / ตีกลับ | **คำนวณใหม่ทับทุกครั้งที่ยอดใบเปลี่ยน** | ของ SA · แก้ได้ · **ต้องรอดจากการทับ** |
| ⭐ **ตอนอนุมัติ** | เขียนทับครั้งสุดท้ายจากยอดจริง แล้ว **`frozenAt = now()`** | คงเดิม |
| หลังอนุมัติ | ล็อก ห้ามแก้ (กติกาเดิม) | แก้ได้ตามเดิม |

**ทำไมถึงคุ้ม** — `dueDate` เป็นช่องที่ **QT ไม่มี** และ SA ต้องกรอกเองทีละงวด
(คอมเมนต์ `0245` เขียนไว้เอง: *"ของจริงมีงวดที่ผูกกับเหตุการณ์ (หลังติดตั้ง) ไม่ใช่ผูกกับวัน"*)
⇒ วันนี้ไม่มีแถวให้กรอกจนกว่าใบจะอนุมัติ ⇒ **ใบผ่านด่านอนุมัติไปโดยไม่มีกำหนดชำระสักงวด**
แล้วต้องหวังว่ามีคนย้อนกลับมาใส่ · การกรอกวันคือสิ่งที่ควรทำ**ตอนร่าง** เพราะเป็นตอนที่ SA
กำลังคุยเงื่อนไขกับลูกค้าอยู่พอดี

🪤 **สามกับดักที่ต้องปิดพร้อมกัน — ไม่ปิดข้อไหนก็พังทั้งข้อ**

1. **ทะเบียนการชำระของบัญชีต้องกรองเฉพาะแถวที่ `frozenAt` แล้ว**
   `/finance/payments` เป็นทะเบียนเงินจริง · ปล่อยงวดของใบร่างเข้าไป = บัญชีเปิดมาเจอ
   คิวเงินที่ยังไม่มีอยู่จริง และตัวเลขรวมทั้งหน้าผิดทันที
2. **ปุ่ม "ลูกค้าจ่ายแล้ว" ยังต้องรอ `frozenAt`** — งวดร่างเป็นของสำหรับวางแผน ไม่ใช่ของให้แจ้ง
   (แจ้งบนยอดที่ยังขยับได้ = หลักฐานผูกกับตัวเลขที่จะถูกเขียนทับ)
3. **การเขียนทับต้องไม่แตะแถวที่ `status != 'pending'`** — เข็มขัดเส้นที่สอง เผื่อวันหลัง
   มีใครเปิดข้อ 2 · ชนเมื่อไรให้ **หยุดแล้วขึ้นข้อความ ไม่ใช่ทับเงียบ**

**ที่ลงจริง** (mig `0259`)

| ของ | ที่ไหน |
|---|---|
| `frozenAt` + **backfill แถวเดิมทั้งหมด** | mig `0259` — ทุกแถวที่มีอยู่เกิดตอนอนุมัติ จึง freeze แล้วโดยนิยาม · ไม่ backfill = เงินที่บัญชีรับรองไปแล้วหายจากทะเบียน |

### 3.5 ⭐ ผลลัพธ์ของบรรทัด — เลขที่เอกสาร (B-3 · ปิด R-6 ของหัวข้อนี้)

`request-hub-rebuild-plan.md` R-6 เขียนไว้ว่า *"ต้นทางทำครบแล้ว (`needs`) แต่ปลายทาง
ยังไม่มี"* ⇒ ปิดคำร้องแล้วไม่มีอะไรตกผลึก · ของหัวข้อนี้ ขาออกคือ **เลขที่เอกสาร**

| | ยอดที่ขอ (B-2) | เลขที่เอกสาร (B-3) |
|---|---|---|
| อยู่ที่ | **ใบ** (`dept_requests`) | **บรรทัด** (`dept_request_items`) |
| เพราะ | หลายเอกสารขอบนยอดก้อนเดียว | 1 บรรทัด = 1 เอกสาร = 1 เลขที่ |

⭐⭐ **สองอย่างนี้อยู่คนละที่โดยตั้งใจ ไม่ใช่ความไม่สม่ำเสมอ** — ของจริงขอใบวางบิลกับ
ใบกำกับภาษีในคำร้องเดียว ได้เลขที่คนละเลข คนละวันครบกำหนด แต่ยอดเดียวกัน

- ถามในโมดัล **"ส่งเอกสาร"** (ก้าว `ready`) ซึ่งเป็นจังหวะที่บัญชีออกเอกสารจริง —
  ที่เดียวกับที่แนบไฟล์อยู่แล้ว (ม-90: *"flow การส่งเอกสาร ต้องเป็นแบบเดียว"*)
- **เลขที่บังคับ · วันครบกำหนดไม่บังคับ** — ใบเสร็จออกหลังรับเงินแล้ว ไม่มีกำหนดชำระ
- ⚠️ **ไม่มี FK ไม่ unique** — เลขมาจากระบบบัญชีข้างนอก (Express) ที่เราไม่ได้เป็นเจ้าของ ·
  บังคับ unique = ระบบนี้ปฏิเสธความจริงของระบบบัญชี (ใบกำกับที่ยกเลิกออกเลขซ้ำได้)
- ⚠️ **ด่านต้องอ่าน `lineKind` จากแถวจริง ไม่ใช่จาก body** — รับจาก client เมื่อไรก็
  ข้ามด่านได้ทันที · และ **ห้ามลามไปรูปร่างอื่น** (เอกสารของ RD ไม่มีเลขที่ให้กรอก
  บังคับหมดเมื่อไร ฝ่ายอื่นกดส่งของไม่ได้เลยสักแถว)

🔴 **ผลตามมาที่เปลี่ยนลำดับของทั้งแผน — คำร้องเกิดก่อนงวดเสมอ**

ของจริง: ลูกค้าขอใบวางบิล 50% **ก่อนผลิต** ⇒ ขอตั้งแต่ตอนที่ยังมีแค่ QT ·
ส่วนงวดชำระเกิดจาก SO ซึ่งอาจยังไม่ถูกสร้างด้วยซ้ำ

⇒ **ห้ามผูกอัตโนมัติ** — ตอนงวดเกิด ให้หน้าใบสั่งขายโชว์
*"คำร้องขอเอกสารของใบเสนอราคานี้ (N ใบ)"* แล้วให้ SA กดแนบเข้ากับงวดเอง
เดาจาก % ที่ใกล้เคียงเมื่อไร จะได้ใบวางบิลไปแขวนผิดงวดโดยไม่มีใครรู้

**ที่ลงจริงใน B-5** (mig `0260`) — `sales_order_installments.billingRequestId`

| ทางเข้า | ใช้เมื่อไร |
|---|---|
| *"ขอใบวางบิลงวดนี้"* | ยังไม่เคยขอ — เปิดคำร้องใหม่พร้อมเติม QT + ยอดของงวดให้แล้ว |
| *"แนบคำร้องที่ขอไว้แล้ว"* | ขอไปแล้วตั้งแต่ตอนมีแค่ QT — เลือกจากรายการของใบเสนอราคาเดียวกัน |
| *"ถอดคำร้องออกจากงวด"* | แนบผิด หรือคำร้องถูกลบไปแล้ว |

**สามข้อที่ handler ตรวจจากแถวจริง** (เชื่อ id ที่ส่งมาไม่ได้):
ต้องเป็น `billing_doc` · ต้องเป็นคำร้องของ **ใบเสนอราคาเดียวกับใบสั่งขายนี้** ·
**หนึ่งคำร้องแขวนได้งวดเดียว** (ยอดอยู่ที่ใบคำร้อง ไม่ใช่รายบรรทัด ⇒ แขวนสองงวด = นับซ้ำ)

⚠️ **แนบได้แม้งวดคอนเฟิร์มแล้ว** ต่างจากการแก้กำหนดชำระ — ของจริงขอใบเสร็จ *หลัง*
เงินเข้าเป็นเรื่องปกติ · ปิดตรงนี้เมื่อไร ใบเสร็จจะไม่มีที่ให้แขวน
⚠️ **งวดร่างก็แนบได้** ต่างจากการแจ้งชำระ — คำร้องมักเกิดก่อนใบอนุมัติด้วยซ้ำ

```
          │    4. วันนัดอยู่ในช่วงที่ไซต์ยอมให้เข้า           [TS]
          │
          ├─ ครบ ─▶ scheduled ─▶ in_progress ─▶ done / partial / unable
          └─ ไม่ครบ ─▶ หัวหน้าข้ามได้ พร้อมเหตุผลบังคับ + ลงบันทึก
```

⭐ **ข้อ 2 อ่านจากตารางงวดตัวเดียวกับสายขาย** — ด่านไม่นับเงินเอง ไม่มีสูตรของตัวเอง
⇒ วันไหนกติกา "เลยกำหนด" เปลี่ยน แก้ที่เดียว

**นิยาม "เลยกำหนด"**: เลย `dueDate` แล้ว **และ** ยังไม่ `confirmed` · **ไม่มี grace period**
(`reported` ที่บัญชียังไม่กด = ยังนับว่าค้าง)

**บล็อกระดับสัญญา ไม่ใช่ระดับลูกค้า** — ลูกค้ารายเดียวมีหลายสัญญาเป็นเรื่องปกติ

## 7. 🪤 กับดักที่บันทึกไว้ให้รอบนี้

- **สามกริยาของบัญชีต้องใช้คำต่างกันบนจอ** — ตรวจใบ · ออกเอกสาร · รับรองงวด (§2)
- **`reported` ไม่ปลดด่าน** — ปลดเมื่อ `confirmed` เท่านั้น ไม่งั้น SA แจ้งเองปลดเอง = ไม่มีด่าน
- **ไม่ backfill** — ใบที่อนุมัติก่อน `0250` มี `financeStatus = NULL` แปลว่า "ออกก่อนมีขั้นบัญชี"
  ไม่ใช่ "รอบัญชี" · กติกาเดียวกันใช้กับงวดของสัญญาที่ import เข้ามา
- **ปุ่มนอกเอกสารต้นทางต้องเห็นหลักฐานชุดเดียวกัน** — โมดัลยืนยันต้องโชว์ไฟล์แนบ วันจ่ายจริง
  และผู้แจ้ง **และเตือนเมื่อไม่มีไฟล์แนบ** (เงื่อนไขที่ทำให้กฎข้อ 3 ยอมให้มีปุ่มหลายจอ)
- **หัวข้อคำร้องไม่มี CHECK ที่ DB โดยเจตนา** — เพิ่ม/เปิดหัวข้อ แก้ไฟล์ทะเบียนอย่างเดียว
  ห้ามออก migration
- **เพิ่มหน้าใหม่ต้องลง `OPEN_PAGES` ของ proxy** ไม่งั้นโดนเด้ง
- **แนบไฟล์ต้องต่อครบ 5 จุด** รวม `PARENT_TABLE` ของ proxy `/file` (ตกจุดนี้ = 403 เงียบ)
- **ลิสต์ชนิดเอกสารของ FN ห้ามรวมกับของ RD** — รวมเมื่อไร คำร้องขอเอกสารของ RD จะมี
  "ใบกำกับภาษี" โผล่ ซึ่ง RD ออกให้ไม่ได้
- **`AC` ในข้อความแชทไม่ใช่ฝ่ายบัญชี** — เป็น role `ac` = Account Coordinate ในฝ่ายขาย
