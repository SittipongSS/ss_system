ผู้ใช้จริง ใช้กับฟอร์มใหม่ทุกฟอร์มในทุกโมดูล

## 1. ลำดับคำถาม

**หลัก: เรียงตามลำดับที่คนคิด ไม่ใช่ตามลำดับที่ตารางฐานข้อมูลเก็บ**

1. **ตัวกำหนดบริบทอยู่บนสุด** — ช่องที่เลือกแล้ว *เปลี่ยนความหมายหรือชุดตัวเลือกของช่อง
   อื่น* ต้องถามก่อน เพราะมันคือคำถามที่คนตอบได้อยู่แล้วในหัว
   - ฟอร์มดีล: **ประเภทดีล** (SCENT/NPD/RE-ORDER) อยู่บนสุด — มันเลือก template ไทม์ไลน์
   - ฟอร์มคำร้อง: **ฝ่ายผู้รับ → หัวข้อ** มาก่อนทุกอย่าง เพราะ "คนเปิดคำร้องคิดจาก
     *จะถามใคร* ก่อน *ถามเรื่องอะไร* เสมอ" (มติ 2026-08-04) — ของเดิมกลับหัว
     (เลือกหัวข้อแล้วระบบเดาฝ่าย) ทำให้ฝ่ายผู้ตอบกลายเป็นผลข้างเคียงที่ผู้ใช้ไม่เห็น

2. **ช่องที่ขึ้นต่อกันวางติดกัน** — ลูกค้า → แบรนด์ (แบรนด์เป็นของลูกค้ารายนั้น)
   ผู้ใช้จะได้เห็นทันทีว่าทำไมช่องขวายังกดไม่ได้

3. **ช่องที่โผล่/หายตามเงื่อนไข ต้องอยู่ *ใต้* ตัวที่ทำให้มันโผล่** — วางไว้เหนือเมื่อไร
   ผู้ใช้จะเจอช่องงอกขึ้นมาเหนือจุดที่ตัวเองกำลังมองอยู่ (กติกาในฟอร์มคำร้อง: ช่องจากธง
   `needs` ทั้งหมดอยู่ใต้ช่องหัวข้อ)

4. **ความรับผิดชอบอยู่ท้าย** — "ใครรับผิดชอบ" เป็นคำถามหลังจากรู้แล้วว่างานคืออะไร
   ฟอร์มดีลจึงวาง **ผู้รับผิดชอบ (AE) ล่างสุด** (มติ 2026-08-08)

5. **สองขั้นเมื่อฟอร์มเปลี่ยนรูปทั้งชุด** — ถ้าคำตอบของคำถามแรกทำให้ช่องข้างล่างสลับ
   หน้าตาทั้งชุด ให้ถามให้จบก่อนแล้วค่อยกางฟอร์ม ไม่ใช่กางไว้ตั้งแต่ต้นแล้วเปลี่ยนรูป
   ใต้มือคนอ่าน (ฟอร์มคำร้อง: เลือกฝ่าย+หัวข้อ → กด "กรอกฟอร์ม…" → ฟอร์มกาง และ
   ช่องหัวข้อถูกล็อก ปุ่ม "เปลี่ยนฝ่าย/หัวข้อ" เป็นทางเดียวที่แก้ได้ พร้อมเตือนว่าจะล้างฟอร์ม)

6. **ห้ามให้เลย์เอาต์เป็นตัวกำหนดลำดับ** — อย่าปล่อยช่องไหลตาม grid แม่: พอจำนวนช่อง
   เปลี่ยนตามเงื่อนไข (เช่นช่องที่ซ่อนตามสิทธิ์) parity จะพลิกแล้วคู่ที่ควรอยู่ด้วยกัน
   เลื่อนหลุดคนละบรรทัด ฟอร์มดีลจึงจับคู่เองด้วย `pairRows` และช่องที่เหลือเดี่ยวกินเต็มแถว
   แทนการทิ้งรูไว้ข้าง ๆ

**คู่ที่ต้องอยู่แถวเดียวกัน = ของที่อ่านคู่กัน** (มูลค่า | วันที่ปิด · วันที่เริ่ม | วันที่สิ้นสุด ·
ลูกค้า | แบรนด์) — ไม่ใช่ "ช่องไหนเหลือก็จับคู่ไป"

## 2. การกรอก

**ค่าที่ระบบรู้อยู่แล้ว ห้ามให้คนพิมพ์ซ้ำ**
- ขึ้นเป็น **ช่องเส้นประ อ่านอย่างเดียว** (`.deal-derived` / `.derived` ในฟอร์มคำร้อง)
  ไม่ใช่ดรอปดาวน์ที่จางลง — ดรอปดาวน์จางอ่านเหมือน "ช่องที่แก้ได้ในสถานะอื่น" ซึ่งไม่มีวันจริง
- ตัวอย่าง: ลูกค้า/ดีล/ขั้นไทม์ไลน์ ที่เติมจากใบสั่งขาย · ชื่อผู้รับผิดชอบของ AE ที่ล็อกเป็นตัวเอง
- เปิดให้เลือกซ้ำเมื่อไร จะมีวันที่ค่าสองทางขัดกันแล้วไม่มีอะไรบอกว่าอันไหนถูก

**ไม่มีค่าตั้งต้นให้กับสิ่งที่เป็นการตัดสินใจ**
- ประเภทดีลเคย default เป็น NPD เงียบ ๆ → ได้ template ผิดประเภทโดยไม่มีใครรู้ (แก้ 2026-07-21)
- FC% เคย default 50 (= ออกใบเสนอราคาแล้ว) ทั้งที่ดีลใหม่ยังเป็นลีด (แก้ 2026-08-05)
- สถานะเคย default `lead` → ดีลเกิดที่ลีดทั้งที่คนสร้างไม่เคยตัดสินใจ (แก้ 2026-08-08)
- **default ได้เฉพาะเมื่อ flow ตัดสินให้แล้วจริง ๆ** เช่นเปิดดีลจากลีด = `qualified`
  (ลีดผ่านคัดกรองมาแล้วโดยนิยาม) หรือค่าที่มาจากบริบทที่กดเข้ามา (เปิดจากหน้าโครงการ)

**ผลของการเลือกต้องเห็นก่อนกด**
- แถบขั้นสถานะโชว์ FC% ใต้ทุกขั้น → เห็นว่าเลือกขั้นไหนได้กี่เปอร์เซ็นต์ ก่อนจะเลือก
  (และทำให้ช่อง FC แยกหายไปได้ทั้งช่อง)
- ใต้ช่องวันที่คาดปิดบอกเดือน FC ที่จะได้ · ใต้ช่องดีลเก่าบอกว่ายอดจะตกเดือนไหน

**ช่องบังคับ**
- ดอกจันอยู่ **บรรทัดเดียวกับป้าย** — ห่อป้ายทั้งก้อนไว้ใน element เดียว (`.deal-field-label`)
  🐞 เคยพัง: `.deal-field` เป็น flex column ทำให้ text node กับ `<span>*</span>` แตกเป็น
  คนละ flex item แล้วดอกจันตกไปคนละบรรทัด (ผู้ใช้ส่งภาพมา 2026-08-08)
- **ด่านตรวจรวมข้อความเดียว** บอกทุกช่องที่ขาดในครั้งเดียว ไม่ใช่ให้กดแล้วเจอทีละช่อง
- ปุ่มที่กดไม่ได้ **ต้องบอกเหตุผลติดปุ่ม** — จางเฉย ๆ คือสิ่งที่ทำให้คนคิดว่าระบบพัง
  แล้วไปหาสาเหตุผิดที่ (กฎเดียวกับ `requestFormBlocker`)
- เงื่อนไขที่ปุ่มรู้แต่ฟอร์มไม่รู้ = ห้ามมี ใช้ตัวตรวจตัวเดียวกันทั้งสองที่

**ป้ายช่องเปลี่ยนตามโหมดได้ ถ้าความหมายของค่าเปลี่ยนจริง**
- ดีลเก่าจากระบบเดิม + สถานะ Won → "มูลค่าคาดการณ์/วันที่คาดการณ์ปิด" กลายเป็น
  **"มูลค่าที่ปิด/วันที่ปิด"** เพราะมันคือของจริงจากระบบเดิม ไม่ใช่การคาดการณ์
- **คีย์ในฟอร์มคงเดิม server เป็นคน map** — ไม่แตกช่องใหม่ให้ต้องดูแลสองทาง
- ข้อความ error ต้องเรียกชื่อช่อง**ตามที่ตาเห็นบนจอตอนนั้น**

**โหมดผ่าน props ไม่ใช่คนละไฟล์** (กฎ AGENTS.md) — `probabilityMode` · `alreadyWon` ·
`lockedOwner` · `showProject` · `lockKind` · `deferAttachments` ทั้งหมดคือโหมดของ
component เดียว การมีฟอร์ม "สร้าง" กับ "แก้" คนละไฟล์คือจุดที่ระบบเพี้ยนหากันทุกครั้ง

**ล็อกดีกว่าซ่อน เมื่อผู้ใช้ไม่มีสิทธิ์เปลี่ยน**
- ผู้รับผิดชอบของ ae/senior_ae = โชว์ชื่อตัวเองแบบล็อก ไม่ใช่ซ่อนช่องทิ้ง — คนต้องเห็นว่า
  ดีลจะไปอยู่กับใคร
- ฝ่ายที่ยังไม่เปิดใช้ในฟอร์มคำร้อง = แสดงจางและกดไม่ได้ ไม่ใช่ซ่อน "ตัวเลือกที่ไม่มีสิทธิ์
  ต้องเห็นว่ามีอยู่ ไม่งั้นคนจะไปหาที่อื่น"

**ค่าอิสระที่มีคำตอบซ้ำ ๆ ให้ชิปลัด** — วันที่คาดปิดมีชิป สิ้นเดือนนี้ / +30 วัน / สิ้นไตรมาส
เพราะช่องนี้เป็นตัวกำหนดเดือน FC · ชิปที่ไม่ตรงบริบทต้องหายไป (โหมดดีลเก่าเป็นวันในอดีต
จึงไม่โชว์ชิปวันอนาคต)

### ข้อความยาว — ทรงเดียวทั้งระบบ (มติผู้ใช้ 2026-08-12 · IS-26080006 · IS-26080018)

**เกณฑ์ตัดสินว่าเป็นช่องยาวไหม: เพดานตัวอักษร ไม่ใช่ความรู้สึก** — เกิน ~200 ตัวอักษร
หรือเป็นข้อความพรรณนา/ที่อยู่/เหตุผล = `Textarea` · ชื่อ/รหัส/ตัวเลข = `Input`
🐞 `Mood & Tone` กับ `ที่อยู่จัดส่งตัวอย่าง` เพดาน 500 ตัวอักษรแต่วางเป็นช่องบรรทัดเดียว
สูงแถวเดียว (`--ctl-h`) ⇒ ผู้ใช้พิมพ์แล้วเห็นทีละท่อน อ่านย้อนสิ่งที่เพิ่งพิมพ์ไม่ได้ (ผู้ใช้แจ้งเอง)

**ขนาดมาจากกติกาชุดเดียว — อย่าเขียน `min-height` ที่หน้าใดหน้าหนึ่ง**

| เรื่อง | กติกา |
|---|---|
| พื้นขั้นต่ำ | **3 บรรทัดเสมอ** — `rows` ขอมากกว่าได้ ขอให้เตี้ยกว่าไม่ได้ |
| ตอนพิมพ์ | โตตามเนื้อหาเอง (`field-sizing: content`) จนถึงเพดาน 40vh แล้วเลื่อนในกล่อง |
| ผู้ใช้ขยายเอง | ลากมุมล่างได้เสมอ (`resize: vertical`) — ลากแล้วความสูงติดตัวทับการโตอัตโนมัติ |
| ฟอนต์ | ฟอนต์ปกติ · `variant="data"` (mono) **เฉพาะ JSON/ล็อกจริง ๆ** |

🐞 **ประวัติที่ทำให้ต้องเขียนกฎนี้ไว้** (ตรวจ 2026-08-12): `rows` ไม่เคยมีผลเลยเพราะ CSS
ตั้ง `height` ตายตัวทับ ⇒ 20 จุดที่เขียน `rows={2..8}` ได้ความสูงเท่ากันหมด · แล้วอีก
4 หน้าเขียน `min-height` ของตัวเองทับ (78 · 88 · 92 · 110px) · และเพราะกล่อง `data`
สูงกว่ากล่องฟอร์มอยู่ 20px คนเลยหยิบมันไปใช้กับ **ข้อความไทย 21 จุด**
(เหตุผลที่ยกเลิก · สิ่งที่ลูกค้าบอก · บรีฟกลิ่น · รายละเอียดคำร้อง) ⇒ ประโยคไทยไปอยู่ใน
ฟอนต์ mono ทั่วระบบโดยไม่มีใครตั้งใจ · ผู้ใช้สรุปอาการเองว่า "long text ใช้ดีไซน์ไม่เหมือนกัน"

⚠️ นิยามจริงอยู่ที่ `textarea.premium-input` + `.textarea-premium` ใน `globals.css`
และ `--ta-rows` ที่ `components/ui/Textarea.js` ประกอบให้ — **แก้ที่นั่นที่เดียว**

### แนบไฟล์ — ทางเข้าเดียว สามวิธี (มติผู้ใช้ 2026-08-12 · IS-26080013)

**ช่องที่ตอบได้หลายข้อ — ถามข้อที่ตามมา *หลัง* คำตอบ ไม่ใช่กางไว้ตั้งแต่ต้น**
(มติผู้ใช้ 2026-08-11 · ช่อง "ทีม" ของหน้าตั้งค่าผู้ใช้)
พอติ๊กได้หลายข้อ มักมีคำถามชั้นสองตามมาว่า "แล้วข้อไหนเป็นตัวหลัก" — ช่อง **ทีมหลัก**
โผล่เมื่อเลือกตั้งแต่ 2 ทีมขึ้นไปเท่านั้น เพราะเลือกทีมเดียวคำถามนี้ไม่มีคำตอบอื่นให้ตอบ
กางไว้ตลอดเวลา = ช่องที่คนต้องอ่านแล้วข้ามทุกครั้งโดยไม่ได้ตัดสินใจอะไร
⚠️ และเมื่อติ๊กตัวที่เป็น "ตัวหลัก" ออก ค่าตัวหลักต้องเลื่อนตามทันที ห้ามค้างเป็นค่าที่
ไม่อยู่ในชุดที่เลือกแล้ว (บังคับที่ `resolveTeamAssignment` ซึ่งฟอร์มกับ API ใช้ร่วมกัน)

**ช่องที่ถามเฉพาะบางคน — เกณฑ์คือ "มีคำตอบให้เลือกจริงไหม" ไม่ใช่ "สิทธิ์ถึงไหม"**
(มติผู้ใช้ 2026-08-11) ช่อง "ทีมเจ้าของงาน" ในฟอร์มดีล/ลูกค้า/คำร้อง/ทะเบียน โผล่เฉพาะ
ตอนเจ้าของงานอยู่ตั้งแต่ 2 ทีม — คนทีมเดียวไม่เห็นเลย เพราะทีมนั้นคือคำตอบเดียวอยู่แล้ว
· กางไว้ให้ทุกคน = ช่องที่คนส่วนใหญ่ต้องอ่านแล้วข้ามทุกครั้งโดยไม่ได้ตัดสินใจอะไร
⚠️ **ค่าตั้งต้นที่โชว์ต้องเป็นค่าเดียวกับที่ server จะบันทึกจริง** — ฟอร์มดีลถอยไป
"ทีมหลักของเจ้าของ" ตรงกับ `attributionTeam` ฝั่ง server · ถอยคนละทางเมื่อไร ชิปจะชี้
ทีมหนึ่งแล้วงานไปลงอีกทีมเงียบ ๆ ซึ่งไม่มีอะไรบนจอฟ้อง

**เกณฑ์ตัดสินที่ใช้จริง**

- **นับตัวเลือก**: ≤6 และไม่โต = กางให้เห็น · เกินนั้นหรือโตตามข้อมูล = ช่องค้นหา
- **ความยาวป้าย**: ชื่อคนไทยเต็ม ๆ หรือป้ายยาวกว่าประมาณ 20 ตัวอักษร ใส่ชิปแล้วแตกบรรทัด
  → ใช้ช่องค้นหา (เหตุผลที่ผู้รับผิดชอบ AE **ไม่ใช่** ชิป ทั้งที่ทีมหนึ่งมีไม่กี่คน)
- **สองชั้นหรือไม่**: มีการจัดกลุ่มตามธรรมชาติ + คนจำ "ชื่อของ" ได้แต่ไม่จำว่าอยู่กลุ่มไหน
  → `TwoPanePicker` · ห้ามทำเป็น "สองช่องเรียงกัน" ที่บังคับให้ตอบชั้นบนก่อน
- **ต้องลงเซลล์ตารางได้ไหม**: ถ้า pattern เดียวกันต้องใช้ทั้งในฟอร์มและในเซลล์ตาราง
  ต้องเป็น **ช่องเดียว** — เหตุผลที่หมวดสินค้าไม่ใช้ "แผ่นเลือกหมวดหลัก + ช่องค้นหมวดรอง"
  ทั้งที่สวยกว่าในฟอร์ม: มันเป็น 2 คอนโทรล ลงเซลล์ตารางไม่ได้ แล้วจะได้ของสองเวอร์ชัน
  ที่ต้องคอยดูแลให้ตรงกันตลอดไป
- **ธง ≠ ช่องเลือก**: อะไรที่เป็น "โหมด" ให้เป็นสวิตช์ ไม่ใช่ checkbox ลอย หรือค่าหนึ่งใน dropdown

**กติกาที่ห้ามละเมิด**

1. **หนึ่ง pattern มีทรงเดียว** — ถ้าต้องมีสองทรงเพราะบริบทต่าง แปลว่าเลือก pattern ผิด
2. **สัญญาของผู้เรียกห้ามเปลี่ยนตอนเปลี่ยนคอนโทรล** — `ProductCategorySelect` เปลี่ยนจาก
   ดรอปดาวน์กลุ่มแบนเป็นแผงสองชั้นโดยผู้เรียก 3 จุดไม่ต้องแตะเลย เพราะ props/`onChange`
   คงรูปเดิมเป๊ะ · เปลี่ยนรูป meta เมื่อไรพังเงียบทั้งสามที่
3. **primitive อยู่ที่ `components/ui/` เท่านั้น** — หน้าไหนเขียนคอนโทรลเองแปลว่ากำลังจะ
   เกิดเวอร์ชันที่สอง (`audit:ui` + ratchet บังคับอยู่แล้ว)
4. **ตัวเลือกที่ตัดออกต้องบอกว่าตัดเพราะอะไร** — ลิสต์ที่กรองแล้วต้องมี `emptyText` ที่ตอบ
   คำถาม "ทำไมใบของฉันไม่อยู่ในลิสต์" ไม่ใช่ "ไม่พบรายการ" เฉย ๆ · ลิสต์ที่ตัดที่ 200 แถว
   ต้องบอกว่ายังมีอีกกี่รายการ

## 4. กระบวนการตัดสินใจ (เวลาจะเพิ่ม pattern ใหม่)

1. **หาญาติในระบบก่อนสร้างใหม่** — ก่อนออกแบบโมดัลชุดใหม่ ไปดูหน้าเปิดคำร้อง RD ก่อน
   แล้วพบว่าปุ่มเลือกฝ่ายกับชิป PDR คือของเดียวกับที่กำลังจะทำ ⇒ ยกเป็น primitive กลาง
   แทนที่จะได้ภาษาที่สอง · เช่นเดียวกับ `TwoPanePicker` ที่มีอยู่แล้วตั้งแต่มติ 2026-08-06
2. **ทำตัวเลือก 2–3 แบบให้ผู้ใช้เลือกก่อนลงโค้ด** (กติกาถาวรของ design v2 ข้อ 2) —
   ลง `/settings/design-preview` หรือ artifact · ห้ามเขียน pattern ใหม่ในหน้าโดยตรง
3. **เคาะแล้วลง primitive + โทเคน → หน้าค่อยเรียกใช้**
4. **เปิดของจริงให้ดูก่อนปิดงาน** — ทุกครั้งที่ผู้ใช้ต้องตัดสินเรื่องหน้าตา ให้เห็นของจริง
   บนหน้าจอจริง อย่าอธิบายเป็นตัวหนังสือแล้วเดาแทนเขา
5. **เอกสาร + เทสต์ในคอมมิตเดียวกับโค้ด** — มติที่ไม่มีเทสต์ล็อกจะไหลกลับภายในไม่กี่เดือน
