## 1 · สายสหมิตรวันนี้เดินยังไง

ลูกค้าเดียว (AR-109) ทีม KA · ทุกอย่างเริ่มจากรอบพยากรณ์ที่ลูกค้าส่งมา ไม่ใช่จากดีลที่ AE เปิดเอง

1. **นำเข้ารอบ FC** — อัปไฟล์ .xlsx ได้แค่พรีวิว ไม่เขียนฐาน (`api/sahamit/forecast/import/route.js`)
   แล้วบันทึกเป็นรอบใน `sahamit_forecast_rounds` + `sahamit_forecast_lines` (สินค้า × เดือน × จำนวน)
2. **สร้างดีล** — หน้า `/sahamit/forecast` แท็บ "รายเดือน (สร้างดีล)" ติ๊กบรรทัด เลือก AE และเดือน
   ที่คาดได้ PO ⇒ **1 บรรทัด = 1 ดีล** เขียน `sales_deals` ตรง ๆ ด้วย service-role
   (`forecast/rounds/[id]/create-sales-deal/route.js:122-160`)
3. **รอบใหม่เข้ามา** — ดีลของรอบเก่าที่รหัส FG ทับกัน ถูกปิดเป็น `lost` พร้อมป้าย superseded
4. **PO ลูกค้ามาจริง** — กรอกมือทั้งใบ ไม่มีอัปโหลด ไม่มีที่แนบไฟล์ PO (`api/sahamit/po/route.js`)
5. **สร้างโครงการ PM จาก PO ก่อน** เป็นเงื่อนไขบังคับ ไม่งั้น settle ไม่ผ่าน
6. **settle-deal** ทำ 6 อย่างในคำขอเดียว — ยุบดีล FC เป็น **ดีลรวมใบเดียวต่อ PO** (`SHM_PO <เลขที่>`)
   · ออกใบเสนอราคาให้อัตโนมัติ · ย้ายตารางเชื่อม · ปิดดีลต้นทางเป็น `lost`
7. **Won → Actual เหมือนสายปกติทุกประการ** — รับใบเสนอราคา = Won → ออกใบสั่งขาย →
   **อนุมัติใบสั่งขาย = Actual** (trigger mig 0110) · ที่ใบสั่งขายต้องกรอกเลข PO และแนบไฟล์ PO ใหม่อีกรอบ
8. **ท่อคู่ขนานที่ไม่บรรจบ** — แท็บ "PO เทียบ FC" กระทบยอดด้วยตัวเลขเงินของโมดูลเอง
   (`lib/sahamit/dashboard.js`) ไม่เคยเทียบกับใบเสนอราคา/ใบสั่งขายเลย

## 2 · ต่างจากสายปกติตรงไหน

| | สายปกติ | สหมิตร |
|---|---|---|
| ดีลเกิด | AE กรอกฟอร์ม ผ่านด่านบังคับ ได้รหัส `DL-` | ระบบสร้างให้ เขียนตารางตรง **ข้ามด่านทั้งชุด · ไม่มีรหัส** |
| หมวด/สินค้า | เลือกหมวด + กรอกตารางมูลค่ารายหมวด | ไม่เขียน `categoryCode` ไม่มี `valueItems` เก็บรหัส FG ไว้ใน `metadata` |
| เดือนรับของ | `endDate` ของดีล | ไม่เขียน `endDate` ใช้ `metadata.demandMonth` แทน |
| มูลค่า | ราคาขาย | **จำนวน × `costPrice` (ราคาผลิต)** (`lib/sahamit/server.js:105-107`) |
| ปิด Won | รับใบเสนอราคา | รับใบเสนอราคาเหมือนกัน แต่ใบถูก "ผลิตให้" จากบรรทัด PO |
| Actual | ใบสั่งขายอนุมัติ | **เหมือนกันเป๊ะ** — PO ไม่เคยเป็น Actual |
| ลบดีล | ลบได้ | **ลบไม่ได้** ถ้ามี `metadata.sahamitPoId` |
| ดีลที่เลิกใช้ | `lost` = แพ้จริง | ยืม `lost` มาแปลว่า "ถูกยุบ/ถูกแทนที่" ต้องมีข้อยกเว้นไล่ตามทุกจอ |

## 3 · จุดที่ต้องรื้อ (เรียงตามผลกระทบ)

1. **6.7 ล้านกองอยู่ที่ "ไม่ระบุหมวด" ในรายงาน FC และดีลไม่มีวันสิ้นสุด** — เพราะตอนสร้างดีล
   ไม่เคยเขียน `endDate` / `categoryCode` / `valueItems` ทั้งที่ **มีรหัส FG อยู่ใน `metadata` ครบ**
   (27 ดีลวันนี้) · รหัส FG อุ้มหมวดไว้ในตัวอยู่แล้ว (ดู [fc-excel-report] ในความจำ + `forecastBreakdown.js`)
2. **ดีลสหมิตรค้นด้วยรหัสไม่เจอ** — `code` เป็น null ถาวรเพราะเขียนแถวตรงโดยไม่ผ่านตัวออกเลข
3. **แก้รอบ FC แล้วกดสร้างดีลซ้ำได้เต็ม ๆ** — ป้าย "สร้างดีลแล้ว" หายไปเอง ตัวกันซ้ำหลุด
4. **เลข PO และไฟล์ PO ต้องพิมพ์ซ้ำที่ใบสั่งขาย** ทั้งที่ PO อยู่ในระบบแล้ว ไม่มี prefill ไม่มีตรวจว่าตรงกัน
5. **"ขายได้เท่าไร" ได้สองคำตอบ** — หน้าสหมิตรใช้ จำนวน × ราคาผลิต ของ PO · หน้าขายใช้ใบสั่งขาย
   ที่อนุมัติ · ไม่มีจุดกระทบยอดระหว่างสองเลข
6. **ดีลขึ้นว่า "แพ้" ทั้งที่แค่ถูกยุบหรือถูกรอบใหม่แทน** — ไม่มีสถานะ "ยุบ/แทนที่" จริง
7. **แบ่งส่ง/รวม PO แก้จำนวนบรรทัดที่ออกใบไปแล้วได้เงียบ ๆ** — ด่านล็อกมีเฉพาะเส้น PATCH
   เส้น split/merge ไม่ได้เรียกด่านเดียวกัน
8. **หน้าที่มีของแต่กดไม่ได้** — `/sahamit/review` ไม่มีทางเข้าจากเมนู · การล็อกช่อง FC มี API ครบ
   แต่ไม่มีจอ ผู้ใช้เห็นธง "แก้ช่องที่ล็อก" แต่คุมต้นเหตุไม่ได้
9. **คำบนจอสอนขั้นตอนที่ระบบเลิกรับแล้ว** และชื่อเมนู "ของเข้า (สหมิตร)" ไม่ตรงกับหัวหน้าจอ
10. **โค้ดตายที่ยังยิงได้** — `sync-sales-planning` (เขียนคีย์เดือนผิดชื่อ) · flag `sahamitRisk`
    ที่ไม่มีใครอ่าน · เส้น `pred-ack` / `flags`

## 4 · แตะแล้วเสี่ยง — อ่านก่อนลงมือทุกครั้ง

- **`metadata.demandMonth`** เป็นตัวเดียวที่รายงาน FC ใช้ตัดสินเดือนของดีลสหมิตร
  ⇒ เปลี่ยนชื่อหรือย้ายช่อง = ดีลสหมิตรตกเดือนผิดทั้งกอง
- **`metadata.sahamitPoId`** — ทุก query ที่โยง PO กับดีลอ่านคีย์ JSON ตัวนี้ ไม่ใช่ FK
  ⇒ แตะแล้วท่อขาดเงียบ ๆ
- **การยืม stage `lost` แทน "ถูกยุบ"** — ถอดออกโดยไม่มีสถานะรองรับ = ดีลที่ถูกยุบกลับมานับเป็นแพ้
  และ FC ถูกนับซ้ำ
- **ราคาที่ใช้คือ `costPrice`** — ทั้งมูลค่าดีลและราคาบนใบเสนอราคาที่ออกไปแล้วผูกกับตัวนี้
- **การหักยอดตอน partial merge** เป็นจุดเดียวในระบบที่ทำแบบนี้ และชนกับตัว resolve ที่มา FC (mig 0337)
- **backfill รหัส `DL-` หรือ `endDate` ย้อนหลัง** = ตัวเลขรายงานเดือนเก่าขยับทันที
  · **ฐาน dev คือฐาน production และไม่มีถังขยะ** ⇒ ต้องซ้อมกับข้อมูลที่สร้างเองแล้วลบทิ้ง
- **`sahamit_forecast_lines` ไม่มี unique (roundId, fgCode, month)** ⇒ นำเข้าซ้ำทำให้ยอดถูกนับทบ
  โดยไม่มีอะไรฟ้อง
