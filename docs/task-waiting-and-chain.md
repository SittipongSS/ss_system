# งานติดตาม: สถานะ "รอคนอื่น" + งานต่อเนื่อง

> สถานะ: **รอตรวจ** · เขียนพร้อมโค้ด 2026-08-17 (mig 0266)
> ขอบเขต: `personal_tasks` (หน้า `/pm/tasks` + `/pm/tasks/[id]`) เท่านั้น —
> ขั้นตอนไทม์ไลน์ (`project_tasks`) ไม่เปลี่ยน

## 1. ปัญหาที่แก้

**ก. ป้ายเกินกำหนดโผล่เฉพาะตอนกด "กำลังทำ"**
`getUrgencyInfo` ในหน้า `/pm/tasks` ตัดจบตั้งแต่ `status === "Pending"` แล้วคืนคำว่า
"ยังไม่เริ่ม" ⇒ งานที่ยังไม่เริ่มและเลยกำหนดไปแล้วขึ้นสีเทาเงียบ ๆ ต้องเปลี่ยนสถานะ
เป็น "กำลังทำ" ก่อนถึงจะเห็นว่าเลยกำหนด

ที่แย่กว่าคือระบบ**ขัดกันเอง**อยู่แล้ว: การ์ด "ต้องรีบ" (`isUrgent`) และ KPI
(`taskKpi.tallyTask`) นับงาน Pending ที่เลยกำหนดมาตั้งแต่ต้น — เลขบนการ์ดบอกว่ามี
แต่กดเข้าไปในตารางแล้วหาไม่เจอว่าใบไหน

**ข. สถานะ 3 ค่าไม่ครอบคลุมงานจริง**
งานที่ส่งออกไปแล้วรอลูกค้า/ฝ่ายอื่นตอบ ไม่ใช่ "กำลังทำ" (ไม่มีอะไรอยู่ในมือเรา)
และไม่ใช่ "รอดำเนินการ" (แปลว่ายังไม่ได้เริ่ม) — เลือกผิดทั้งสองทาง
และงานที่ต่อกันเป็นสาย ("จบใบนี้ค่อยเริ่มใบหน้า") ไม่มีที่เก็บความสัมพันธ์เลย
ทั้งที่ขั้นตอนไทม์ไลน์มี `predecessors` + ตัวไล่สถานะอัตโนมัติมานานแล้ว

## 2. มติผู้ใช้ (2026-08-17)

1. เพิ่มสถานะเดียวคือ **"รอคนอื่น"** (`Blocked`) — ไม่เพิ่ม "พักไว้/ยกเลิก"
2. งานต่อเนื่องผูกกันจริงและ **ปลดล็อกอัตโนมัติ** เมื่อใบก่อนหน้าปิด ·
   ต้องสร้างงานต่อเนื่องจากงานที่มีอยู่ได้ (เชื่อมได้ทั้งไปข้างหน้าและย้อนหลัง)
3. ตอนรอคนอื่น **นาฬิกาเกินกำหนดเดินต่อ** — เดดไลน์คือเดดไลน์ ไม่ว่ารออะไร
   แต่ต้อง **แยกสีและแยกยอด** จากงานที่ค้างอยู่ในมือเราเอง

## 3. สิ่งที่ลงโค้ด

### 3.1 กติกาสี (ที่เดียว: `taskUrgency` ใน `lib/pm/derived.js`)

| สถานการณ์ | สี | ป้าย |
|---|---|---|
| เลยกำหนด · งานอยู่ในมือเรา | แดง | `เลยกำหนด N วัน` |
| เลยกำหนด · รอคนอื่นอยู่ | ม่วง | `เลยกำหนด N วัน · รอคนอื่น` |
| เหลือ ≤3 วัน | เหลือง (ม่วงถ้ารอคนอื่น) | `เหลือ N วัน` |
| ยังไม่เริ่ม ไม่มีกำหนด | เทา | `ยังไม่เริ่ม` |

**ทุกสถานะที่ยังไม่ปิดอ่านวันกำหนดเสมอ** — เทสต์ที่ตรึงข้อนี้ไว้คือ
`lib/pm/taskUrgency.test.mjs` (เคสแรกคือบั๊กเดิมตรง ๆ)

### 3.2 แยกยอด

- การ์ดบนหน้ารายการ: `งานทั้งหมด · กำลังทำ · ต้องรีบ · รอคนอื่น · เสร็จแล้ว`
  — **"ต้องรีบ" ไม่รวมงานที่รอคนอื่น** (เร่งเองไม่ได้) ส่วนการ์ด "รอคนอื่น"
  มีบรรทัดรองบอกว่าในนั้นเลยกำหนดไปกี่ใบ
- KPI (`taskKpi`): `overdue` ยังนับรวมเหมือนเดิม (เดดไลน์ไม่หยุดเดิน) แต่เพิ่ม
  `waiting` กับ `overdueWaiting` แยกไว้ให้อ่านได้ว่าใบไหนเจ้าตัวเร่งเองไม่ได้
- ป้ายตัวเลขบนเมนู (`myTasksTodoCount`): **ไม่นับงานที่รอคนอื่น** — เมนูบอก
  "งานที่รอฉันทำ" ถ้ากดเข้าไปแล้วทำอะไรไม่ได้ คนจะเลิกเชื่อเลขนั้น

### 3.3 สถานะ "รอคนอื่น"

- ต้องระบุ **"รออะไร/รอใคร"** เสมอ (ด่านซ้ำทั้งฝั่งฟอร์มและ API) — ข้อความนี้ไป
  โผล่ในคิวของคนอื่นด้วย จึงต้องอ่านรู้เรื่องโดยไม่ต้องรู้จักงานนั้นมาก่อน
- เก็บ `blockedReason` + `blockedSince` · ออกจากสถานะนี้ = ล้างทั้งคู่
- ขึ้นเธรดงานเป็นอัปเดตชนิด `blocked` (คู่กับ `late` ที่มีอยู่แล้ว)

### 3.4 งานต่อเนื่อง

- `predecessorId` — **หนึ่งงานมีใบก่อนหน้าได้ใบเดียว**, มีใบถัดไปกี่ใบก็ได้
  (อ่านกลับด้านจากคอลัมน์เดียวกัน) · จงใจไม่ทำกราฟเต็มแบบ `project_tasks`
  เพราะงานติดตามเป็นสายเส้นเดียว ไม่ใช่แผนงานที่ต้องคำนวณ critical path
- ปุ่ม "สร้างงานต่อเนื่อง" อยู่ทั้งในแถวของหน้ารายการและหัวหน้ารายละเอียด
  ก๊อปบริบทของใบก่อนหน้ามาให้ (ดีล/โครงการ/หมวด/ผู้รับผิดชอบ)
- ผูกกับใบที่ยังไม่ปิด → งานใหม่เริ่มที่ "รอคนอื่น" พร้อมเหตุผลอัตโนมัติ
  `รองาน "X" ให้เสร็จก่อน`
- ปิดใบก่อนหน้า → ใบถัดไปที่ยัง `Blocked` เด้งกลับเป็น **"รอดำเนินการ"**
  (ไม่กระโดดไป "กำลังทำ" — คนต้องกดเริ่มเอง กติกาเดียวกับ `lib/pm/status.js`)
  พร้อมบันทึกในเธรดว่าปลดล็อกเพราะใบไหน
- กันผูกวน: ห้ามผูกกับตัวเอง และไล่สายขึ้นไป 20 ชั้นกันวงรอบ

## 4. กับดักที่ต้องรู้

- **สถานะ `Blocked` ใช้กับงานติดตามเท่านั้น** — `StatusSelect` จึงรับชุดสถานะเป็น
  prop (`PERSONAL_TASK_STATUSES` vs `PROJECT_TASK_STATUSES`) ค่าตั้งต้นเป็นชุด 3 ค่า
  ของไทม์ไลน์ เพราะสถานะของมันถูกไล่อัตโนมัติจากกราฟ predecessor ที่ไม่รู้จัก `Blocked`
- `taskProgressPct('Blocked') === 50` เท่ากับ "กำลังทำ" โดยตั้งใจ (งานที่รอคนอื่นคือ
  งานที่เดินไปแล้วครึ่งทาง ไม่ใช่งานที่ถอยหลัง)
  ⚠️ คอมเมนต์เก่าใน `TaskFormModal` บอกว่าค่านี้ "ไปโผล่บนความคืบหน้าโครงการ" — **ไม่จริง**
  ตรวจแล้ว 2026-08-17: ใช้ที่เดียวคือตัวเลข % ใต้แถบขั้นในฟอร์ม ส่วนความคืบหน้าโครงการ
  นับจาก "ขั้นตอนที่ Completed / ทั้งหมด" (`getProgress`) ไม่ได้อ่านค่านี้เลย
- ด่านสิทธิ์ "แก้ได้เฉพาะสถานะ" นับ `blockedReason` เป็นชุดเดียวกับ `status`
  (`STATUS_FIELDS`) ไม่งั้นผู้รับผิดชอบที่ไม่ใช่ผู้ดูแลงานจะเลือก "รอคนอื่น" ไม่ได้เลย
  ทั้งที่เป็นคนที่รู้ว่าติดอะไรอยู่
- `predecessorId` ผูกได้ตอน**สร้าง**เท่านั้นในรอบนี้ (API รองรับ PATCH แล้ว แต่ยังไม่มี
  ตัวเลือกบนฟอร์มแก้ — ตั้งใจ ไม่ใช่ลืม)
- ด่านของ PATCH เทียบว่า **ลิงก์เปลี่ยนจริงไหม** ไม่ใช่แค่ "มีคีย์ predecessorId ในคำขอ" —
  ถ้าเทียบแค่คีย์ client ที่ส่งทั้งแถวกลับมาจะดึงงานที่คนปลดไปทำแล้ว กลับเข้าสถานะ
  "รอคนอื่น" เงียบ ๆ (เจอตอน scrutinize ก่อน merge)
- ลบงานที่มีใบต่อเนื่อง → ปลดล็อกใบที่ยังติด + ตัด `predecessorId` ให้ทุกใบก่อนลบ
  (ลิงก์เป็น logical ไม่มี FK ไม่ทำเองแล้วงานจะค้างรอ "งานที่ไม่มีอยู่แล้ว")

## 6. ป้ายเมนู "งานของฉัน" กับหน้ารายการ — **แก้แล้ว** (ตรวจตัวเลข M9 · 2026-10-20)

- เดิม: ป้ายเลขบนเมนูไม่นับงาน "รอคนอื่น" แต่หน้ารายการเปิดมาโชว์งานทั้งหมดรวมงานที่รอ
  ⇒ เลขบนเมนู **น้อยกว่า** จำนวนแถวที่เห็น (ยอมรับไว้ก่อนพร้อมทางแก้ที่เลือกไว้แล้ว: ลิงก์ไปหน้ารายการพร้อมตัวกรอง
  ไม่ใช่เอางานที่รอกลับเข้าไปนับ)
- ตอนนี้: ทำตามทางแก้นั้น — ป้ายยังไม่นับงานที่รอ (เจตนาเดิม "งานที่รอฉันทำ") แต่เมนูมี `countHref`
  `/sa/tasks?count=tasks` ⇒ เปิดที่ขอบเขต "ของฉัน" · แท็บ "ต้องทำ" · ตัวกรองสถานะ `todo`
  (ชิป "กรอง: รอฉันลงมือ (ไม่รวมรอคนอื่น) ×") และ **ล้างตัวกรองอื่นทุกตัว** (คำค้น · หมวด · ผู้รับ · ดีล/โครงการ)
  ⇒ เลขบนป้าย = เลขบนแท็บ "ต้องทำ" = แถวในตาราง
- ตัวตัดสินตัวเดียว `isMyTodoTask` (`lib/pm/taskListFilter.js`) — ป้ายเมนู (`myTasksTodoCount`) กับตัวกรอง `todo`
  ของคิวเรียกตัวเดียวกัน · หน้าอ่าน `count` ด้วย `useSearchParams` แล้วถอดออกจาก URL ทันที ⇒ กดป้ายซ้ำขณะอยู่หน้านี้
  ก็ติดทุกครั้ง · กด × ที่ชิป = กลับไปสถานะทั้งหมด
- เลขบนแท็บบทบาท (ต้องทำ · มอบหมายโดยฉัน · ทั้งหมดของฉัน) นับ **พร้อมตัวกรองอื่นทุกตัว** (รวมการ์ดสถานะ · ดีล ·
  คำค้น · หมวด) ⇒ เลขบนแท็บ = แถวหลังกดแท็บ (ตรวจตัวเลข M8 — เดิมนับงานค้างของฉันทั้งหมดไม่สนตัวกรอง)

## 7. ลิงก์จากหน้าดีล/หน้าโครงการ → คิวงาน (มติเจ้าของ 2026-10-20 · ตรวจตัวเลข M8b · M8c · M8d)

- **"งานของดีล X" มีนิยามเดียว** — `dealId = X` หรือ (`projectId = โครงการของ X` และ `dealId` ว่าง = งานเดิมที่ผูกผ่าน
  ไทม์ไลน์เก่า) · `lib/pm/dealTaskLink.js` (`dealTaskOrFilter` ฝั่ง DB · `isDealTask` ฝั่ง JS — เทสต์แปลสตริงจริงแล้วเทียบทีละแถว)
  🐞 เดิมหน้าดีลโหลด `projectId = P` เฉย ๆ ⇒ งานของ **ดีลพี่น้อง** ในโครงการเดียวกันปนเข้าการ์ด "x/y เสร็จ" ตารางงาน และฟีดอัปเดตงาน
- **ปุ่ม "เปิดคิวงาน" บนหน้าดีล** (`/sa/tasks?dealId=X`) เปิดคิวที่ **ขอบเขตกว้างสุดที่คนนั้นมีสิทธิ์** + มุมมอง "ทั้งหมดของฉัน"
  + งานค้าง · ล้างคำค้น/หมวด/ผู้รับ/การ์ดสถานะที่ค้าง · คงชิปดีล (`dealQueueLanding` · แบบเดียวกับคำร้องจากหน้าดีล H1)
  ⇒ การ์ดมีป้าย **"ค้าง n"** ที่ server นับด้วยตัวตัดสินเดียวกับคิวตอนมาถึง บนแถวที่ขอบเขตนั้นโหลดได้จริง
  (`lib/pm/taskScope.js` — ตัวโหลดขอบเขตตัวเดียวกับ `/api/pm/my-work`) · role ที่มีแค่ "ของฉัน" (WH/QC/PC …) ได้เลข
  เฉพาะงานที่คิวของตัวเองโชว์ได้ (ป้ายเขียนว่า "ของคุณค้าง n") · ไม่มีสิทธิ์ดูคิว = ไม่มีป้าย · อ่านขอบเขตหรืองานของดีลไม่ได้
  = ไม่มีป้าย (ไม่ใช่ "ค้าง 0" — รีวิว 20/10)
- **ปุ่ม "เปิดหน้างาน" บนหน้าโครงการ** พาชุดที่เลือกไปด้วยเสมอ (ไม่ตก `/sa/tasks` เปล่าแล้ว) และคิวต้องได้ **งานชุดเดียวกับ
  ตารางงานของหน้าโครงการ** (`projectSelectionPasses` · เทสต์ไปกลับครบ 8 ตัวเลือก) — หน้าโครงการแยก "งานกลางโครงการ" (ไม่มี
  `dealId`) เป็นตัวเลือกของตัวเอง ส่วน `?dealId=` ของคิวรวมงานกลางมาให้ (`isDealTask`) ⇒ ลิงก์พาธง `central` ไปด้วย:
  ไม่ได้เลือก = `?projectId=P` · ดีล + งานกลาง = `?dealId=a,b` · ดีลอย่างเดียว = `?dealId=a,b&central=none`
  (ชิป "กรอง: ไม่รวมงานกลางโครงการ ×") · งานกลางอย่างเดียว = `?projectId=P&central=only` (ชิปโครงการต่อท้าย "· เฉพาะงานกลางโครงการ")
  🐞 รีวิว 20/10: เลือกดีล A อย่างเดียวบนหน้าโครงการเห็น 2 งาน กดแล้วคิวขึ้น 3 (งานกลางติดมา) · เลือกเฉพาะงานกลางได้ทั้งโครงการ
  ⚠️ ธงมีผลคู่กับตัวกรองของลิงก์เท่านั้น (`none`↔ดีล · `only`↔โครงการ · คู่ผิดถูกทิ้งทั้งตอนสร้างและตอนอ่าน — `readTasksQueueLink`)
  ไม่เคยกรองทั้งคิวลำพัง (งานส่วนตัวที่ไม่ผูกดีลไม่ใช่ "งานกลางโครงการ")
- **กดย้อนกลับมาที่ลิงก์ (`?dealId=`/`?projectId=` ยังอยู่ใน URL)** = ตั้งแค่ชิปดีล/โครงการ/ธงจาก URL · ขอบเขต มุมมองบทบาท การ์ดสถานะ
  คำค้น หมวด ผู้รับ = ค่าที่ `useStickyState` คืนให้ (มติ 2026-08-25 "ย้อนกลับ = กลับไปที่เดิม" · มุมมองบทบาทจำแบบ sticky ด้วยแล้ว)
  🐞 รีวิว 20/10: เดิมลงทั้งชุด `dealQueueLanding` ทุกครั้งที่เมานต์ ⇒ กรอง "เสร็จแล้ว"/พิมพ์ค้นหา → เปิดงาน → ย้อนกลับ = ตัวกรองหาย
