# จัดทีมเอง ไม่ต้องรอแอดมิน — ออกแบบหน้าและหลัง

**สถานะ: รอตรวจ** — ออกแบบ 2026-08-28 · ยังไม่เริ่มเขียนโค้ด · มี 3 ข้อที่ต้องให้ผู้ใช้เคาะก่อน (§7)

- โจทย์จากผู้ใช้ 2026-08-28: *"อยากย้ายการจัดทีมออกมาเป็นของแต่ละระบบแทน ให้ Supervisor
  หรือหัวหน้า หรือผู้ช่วยตั้งเองได้ไม่ต้องรอแอดมิน และแยกเฉพาะฝ่ายได้ด้วย"*
  หน้าใหม่ต้อง **ดูรายชื่อ + ย้ายคนข้ามทีม · สร้าง/ปิดทีมเอง · ตั้งหัวหน้าทีม**
- ตรวจของจริงก่อนออกแบบ: 6 มุม (โค้ด · ฐานข้อมูล · เอกสารมติ) 2026-08-28

## 1. ของจริงวันนี้ — สามข้อที่เปลี่ยนรูปงานทั้งหมด

| # | ข้อเท็จจริง | ที่มา |
|---|---|---|
| 1 | **"ทีม" ไม่ใช่ข้อมูล** เป็นค่าคงที่ 3 ตัวในโค้ด และไม่มีตาราง `teams` ในฐานเลย | `permissions.js:162` · ไม่มี migration ไหนสร้างตารางนี้ |
| 2 | **สังกัดของคนอยู่ใน Supabase Auth `app_metadata`** ไม่ใช่ตารางแอป — เขียนได้เฉพาะ service role ผ่าน `/api/users` ซึ่งกั้นด้วย `users:manage` = **role `admin` เท่านั้น** และ cap นี้ **จงใจ grant ไม่ได้** | `proxy.js:319` · `permissions.js:302-320,471-478` |
| 3 | **`TS` เป็นฝ่าย ไม่ใช่ทีม โดยเจตนา** — ทีมมีได้เฉพาะ role ฝ่ายขาย ถ้าจับช่างเป็นทีมต้องให้ role `ae` แล้วช่างจะได้ cap ขายมาทั้งชุด | มติ 2026-07-31 · `permissions.js:124-129,184` |

รหัสทีมยังถูกก๊อปเป็น **ข้อความเปล่า** ลง 20 คอลัมน์ใน 19 ตาราง + อยู่ในกุญแจของ unique index
3 ตัว + มี `CHECK (teamKey IN ('ODM','KA','SV'))` ที่ mig 0128 + มีรายการทีมซ้ำอีก 4 ชุด
ในโค้ด (`SALES_TEAMS` · `TEAM_ORDER` · `TEAM_LABELS` ที่ก๊อปมือไว้ในหน้าวางเป้า)
ซึ่ง**เรียงลำดับไม่ตรงกับตัวแม่ด้วยซ้ำ**

⇒ "สร้างทีมเองได้" ไม่ใช่การเพิ่มหน้าจอ แต่คือการ **ยกทีมขึ้นเป็นทะเบียน** ก่อน

## 2. แยกสองแกนที่วันนี้ปนกันอยู่ในคำเดียว

> **ทีมขาย ≠ ทีมปฏิบัติงาน** — นี่คือข้อเสนอหลักของแผนนี้

| | **ทีมขาย** (ของเดิม) | **ทีมปฏิบัติงาน** (ของใหม่) |
|---|---|---|
| ตอบคำถาม | ยอดนี้เป็นของทีมไหน · ใครเห็น/แก้แถวนี้ได้ | ใครทำงานกลุ่มไหน · วันนี้ใครคู่กับใคร |
| ผูกกับ | `app_metadata.team/teams` → ขอบเขตสิทธิ์ | สมาชิกในตาราง ไม่แตะสิทธิ์เลย |
| ใครมี | เฉพาะ role ฝ่ายขาย (ODM/KA/SV) | ฝ่ายไหนก็มีได้ (TS · PD · WH …) |
| ปิดทีม | กระทบยอดย้อนหลัง (ต้องเก็บรหัสไว้อ่าน) | ไม่กระทบข้อมูลเก่า |

**ทำไมต้องแยก** — ถ้าจับช่าง TS เข้า `app_metadata.teams` เพื่อให้ "มีทีม" ช่างต้องถือ
role `ae` (กติกา `TEAM_ROLES`) แล้วจะได้สิทธิ์เห็นดีล/ใบเสนอราคา/มูลค่าทั้งทีมขายติดมาด้วย
ซึ่งขัดมติ 2026-07-31 ตรง ๆ · การแยกแกนทำให้ TS มีทีมได้โดยไม่ต้องแตะระบบสิทธิ์เลยสักบรรทัด

## 3. หลังบ้าน

### 3.1 ตารางใหม่สองใบ

```sql
-- ทะเบียนทีม (แทนค่าคงที่ TEAMS)
create table public.teams (
  code        text primary key,          -- 'ODM' · 'KA' · 'SV' · 'TS-A' …
  name        text not null,             -- ป้ายที่คนอ่าน
  department  text not null,             -- เจ้าของทีม: SA · TS · PD …
  kind        text not null,             -- 'sales' | 'crew'   ← แกนที่ §2 แยกไว้
  "leadId"    text, "leadName" text,     -- หัวหน้าทีม (ยังไม่มีที่ไหนในระบบวันนี้)
  "isActive"  boolean not null default true,
  "sortOrder" integer not null default 100,
  note        text
);

-- สมาชิกทีมปฏิบัติงาน (kind='crew' เท่านั้น — ทีมขายยังอ่านจาก app_metadata)
create table public.team_members (
  "teamCode" text not null references public.teams(code) on delete restrict,
  "userId"   text not null,
  "userName" text,
  "joinedAt" date,
  primary key ("teamCode", "userId")
);
```

⚠️ **ทีมขายไม่ย้ายที่เก็บ** — `app_metadata.team/teams` ยังเป็น source of truth ของขอบเขต
สิทธิ์เหมือนเดิม เพราะทุกด่านสิทธิ์อ่านมันแบบ sync ตอน render · ย้ายไปตารางแปลว่าทุกการเช็ค
สิทธิ์ต้องยิง DB (ADR 0015 ทั้งฉบับตั้งอยู่บนของเดิม) ⇒ ตาราง `teams` ทำหน้าที่
**ทะเบียนชื่อ/ป้าย/หัวหน้า/ลำดับ** ส่วนการเป็นสมาชิกของสายขายยังอยู่ที่บัญชีผู้ใช้

### 3.2 สิทธิ์ — cap ใหม่ที่แคบ ไม่ใช่แจก `users:manage`

`users:manage` เปิดสร้าง/ลบบัญชี/รีเซ็ตรหัสผ่านมาด้วยทั้งชุด และถูกกันไม่ให้ grant ไว้
ด้วยเหตุผล SECURITY ที่เขียนกำกับ ⇒ **ห้ามแตะ** · ของใหม่คือ

```js
// permissions.js
'team:manage'   // จัดทีมของฝ่ายตัวเอง — ไม่ใช่จัดการบัญชี
```

- ถือโดย: `ae_supervisor` (ทีมขาย) + คนที่ได้ **per-user grant** (`GRANTABLE_CAPS`)
  ⇒ "ผู้ช่วย" ที่ผู้ใช้พูดถึง = คนที่หัวหน้าขอให้แอดมินติ๊ก grant ให้ครั้งเดียว จบ
- **ขอบเขต = ฝ่ายของตัวเอง** — `canManageTeams(user, department)` คืน true เมื่อ
  `departmentOf(user) === department` (admin ข้ามได้)
- สิ่งที่ cap นี้ **ทำไม่ได้**: สร้าง/ลบบัญชี · เปลี่ยน role · เปลี่ยนฝ่าย · รีเซ็ตรหัส ·
  แก้ `extraCaps` — สี่อย่างนี้ยังเป็นของแอดมินเหมือนเดิม

### 3.3 API

| เส้น | ทำอะไร | ด่าน |
|---|---|---|
| `GET /api/teams?department=TS` | ทะเบียนทีม + จำนวนสมาชิก | `team:manage` หรือ `users:view` |
| `POST /api/teams` | สร้างทีม (code ออกจากชื่อ + ฝ่าย) | `team:manage` ของฝ่ายนั้น |
| `PATCH /api/teams/[code]` | เปลี่ยนชื่อ · หัวหน้า · ลำดับ · ปิดใช้งาน | เดียวกัน |
| `PUT /api/teams/[code]/members` | ย้ายคนเข้า/ออก **ทีมปฏิบัติงาน** | เดียวกัน |
| `PATCH /api/users/[id]/team` | ย้าย **ทีมขาย** (เขียน app_metadata) | `team:manage` + ฝ่ายต้องตรง + role ปลายทางต้องเป็น `TEAM_ROLES` |

⚠️ เส้นสุดท้ายเป็นเส้น **ใหม่ที่แคบ** ไม่ใช่เปิด `/api/users/[id]` เดิมให้กว้างขึ้น —
เส้นเดิมเขียน role/department/extraCaps ได้ด้วย ซึ่งไม่ควรอยู่ในมือหัวหน้าทีม

### 3.4 ปิดทีม ≠ ลบทีม

รหัสทีมถูกก๊อปเป็นข้อความลง 19 ตาราง และอยู่ในกุญแจ unique index ⇒ **ลบไม่ได้**
`isActive=false` แปลว่า: ไม่ขึ้นในดรอปดาวน์ให้เลือกใหม่ · ยังอ่านป้ายได้ทุกที่ที่อ้างถึง ·
ยังกรองรายงานย้อนหลังได้ · ปิดไม่ได้ถ้ายังมีสมาชิกหรือมีงานเปิดค้าง (บอกจำนวนตอนกด)

### 3.5 ย้ายทีมแล้วอะไรค้าง — ต้องบอก ไม่ใช่เงียบ

คู่มือปัจจุบันบอกว่าย้ายทีมมี **4 ขั้น** และ 3 ขั้นเป็นงานมือ: แก้บัญชี → แก้ทีมของดีล
ที่ยังเปิดทีละใบ → ย้ายเป้าเดือนอนาคต → กดถอนสิทธิ์เอกสารร่วม
⇒ ปุ่ม "ย้ายทีม" ที่แก้แค่ `app_metadata` จะทิ้งดีล/เป้า/สิทธิ์ไฟล์ค้างที่ทีมเดิมโดยไม่มีอะไรฟ้อง

**ดีไซน์**: กดย้ายแล้วขึ้นโมดัลสรุปผลข้างเคียงก่อนยืนยัน (แพตเทิร์น `approvalPrompt`)

> ย้าย ต้า จาก KA → SV
> · ดีลที่ยังเปิดอยู่ **7 ใบ** ยังนับเป็นของ KA — ไปแก้ทีละใบที่หน้าดีล
> · เป้าเดือน ก.ย.–ธ.ค. **4 เดือน** ยังอยู่ใต้ KA
> · เอกสารร่วมที่แชร์ไว้ **12 ไฟล์** ยังเปิดได้ — กดถอนสิทธิ์ที่หน้าผู้ใช้
> [ ] รับทราบว่าต้องตามเก็บสี่อย่างนี้เอง

⚠️ ดีลเดือนเก่ารายงานใต้ทีมเดิม **ถูกต้องแล้ว** ไม่ต้องย้อนแก้

## 4. หน้าบ้าน

### 4.1 อยู่บ้านไหน

ตามกฎ module-ownership (เมนู = งานที่ฝ่ายนั้นทำ · ตัดที่ `visible` ไม่ใช่ที่ `cap`):

| ฝ่าย | เส้นทาง | เมนู |
|---|---|---|
| ขาย | `/sa/teams` | ใต้ระบบบริหารงานขาย |
| บริการ | `/service/teams` | ใต้ธุรกิจบริการ |

**หน้าเดียวกัน component เดียวกัน** ต่างกันแค่ `department` ที่ส่งเข้าไป — ไม่ใช่สองไฟล์
ที่จะเพี้ยนหากันภายในสองเดือน (กฎ AGENTS.md ข้อแรกของ repo) · แอดมินยังเห็นทุกฝ่าย
ผ่าน `/settings/teams` ที่ใช้ component เดิมอีกทีโดยไม่ล็อกฝ่าย

### 4.2 โครงหน้า

```
จัดทีม · ฝ่ายบริการ                                   [+ สร้างทีม]
────────────────────────────────────────────────────────────────
[การ์ดทีม]  ทีม A — เขตกรุงเทพตะวันออก        หัวหน้า: ต้า
            4 คน · BKK-E, BKK-N
            ┌ สมาชิก ────────────────────────────────────┐
            │ ต้า (หัวหน้า)   · เข้าทีมเมื่อ 1 ส.ค. 2026  │
            │ เบส            · …                    [ย้าย]│
            └───────────────────────────────────────────┘
[การ์ดทีม]  ทีม B — ปริมณฑล                    หัวหน้า: —  ⚠ ยังไม่ตั้งหัวหน้า
            2 คน

[แถบล่าง]  ยังไม่อยู่ทีมไหน 3 คน   ← ถังนี้ต้องมีเสมอ
```

**กติกาที่ยึด**
- ทีมเป็น **การ์ด** ไม่ใช่แถวตาราง — สมาชิกอ่านเป็นกลุ่ม ไม่ใช่รายการยาว
- **ถัง "ยังไม่อยู่ทีมไหน" ต้องมีเสมอ** แม้ว่าง — ถังที่หายไปคือคนที่หายไปจากสายตา
  (โรคเดียวกับแดชบอร์ดที่เคยตัดถัง null ทิ้งจนยอดรวมไม่ตรง)
- ย้ายคน = ปุ่ม "ย้าย" บนแถวสมาชิก แล้วเลือกทีมปลายทางเป็น **ไทล์** (ตัวเลือกน้อย)
  ⚠️ **ไม่ใช่ลากวาง** — ลากวางบนมือถือทำไม่ได้ และการย้ายคนควรมีจังหวะยืนยัน
- ตั้งหัวหน้า = เลือกจากสมาชิกในทีมนั้นเท่านั้น (หัวหน้าที่ไม่ได้อยู่ในทีมคือข้อมูลที่ผิด)
- ทีมที่ปิดแล้วยุบเป็นแถวเดียวใต้สุด กดขยายดูได้ ไม่หายไปจากจอ

### 4.3 สิ่งที่หน้านี้ **ไม่มี** โดยตั้งใจ

- ❌ ปุ่มสร้าง/ลบบัญชีผู้ใช้ · เปลี่ยน role · รีเซ็ตรหัสผ่าน — ยังเป็นของแอดมินที่ `/users`
- ❌ ตัวสลับ "ทีมที่กำลังทำงานอยู่" — เคยตัดสินว่าตกไปแล้ว (ADR 0015:92) เพราะลืมสลับ
  แล้วยอดเข้าผิดทีมเงียบ ๆ
- ❌ การให้สิทธิ์ตามการเป็นสมาชิกทีมปฏิบัติงาน — ทีม crew **ไม่แตะสิทธิ์เลย**
  ถ้าวันหนึ่งอยากให้แตะ ต้องเป็นมติใหม่ ไม่ใช่ผลข้างเคียง

## 6. กับดักที่ต้องเขียนเทสต์ดัก

1. เทียบทีมด้วย `===` แทนการตัดกันของชุด — เคยพลาดมาแล้วสองรอบ
2. `null` เทียบ `null` แล้วผ่าน ⇒ ใบไร้ทีมกลายเป็นใบสาธารณะ
3. ปิดทีมแล้วป้ายในรายงานย้อนหลังกลายเป็นรหัสดิบ
4. ~~เพิ่มทีมใหม่แล้วลืม `CHECK` ของ `commercial_presets`~~ — **ไม่ใช่กับดักจริง**: `mig 0149` ถอดคอลัมน์ `teamKey` ทิ้งไปแล้วตอนรื้อคลังเงื่อนไขการค้าเป็น "คลังตามชนิด" (ตรวจตอนรัน mig 0311 แล้วล้มที่ 42703 · ข้อมูลเดิมมาจากการอ่าน mig 0128 โดยไม่ได้ไล่ต่อ)
5. `sortOrder` ในทะเบียนไม่ตรงกับ `TEAM_ORDER` ในโค้ด ⇒ รายงานเรียงคนละแบบกับหน้าจัดทีม
6. หัวหน้าทีมถูกย้ายออกจากทีมแล้วยังค้างเป็นหัวหน้า

## 7. สามข้อที่ต้องให้ผู้ใช้เคาะก่อนเริ่ม

1. **แยกสองแกนตาม §2 ไหม** — ทีมขาย (ผูกสิทธิ์/ยอด) กับทีมปฏิบัติงาน (จัดคน) เป็นคนละของ
   · ถ้าไม่แยก ต้องยอมรับว่าช่างจะได้ cap ขายติดมา ซึ่งขัดมติ 2026-07-31
2. **"ผู้ช่วย" คือใคร** — ข้อเสนอคือ per-user grant `team:manage` ที่แอดมินติ๊กให้ครั้งเดียว
   (ไม่มีแนวคิด "ผู้ช่วย" เป็น role ในระบบวันนี้)
3. **ย้ายทีมแล้วดีล/เป้าที่ค้าง** — ข้อเสนอคือ *บอกให้ครบแล้วให้คนไปตามเก็บเอง*
