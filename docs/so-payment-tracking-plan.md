# งวดชำระบนใบสั่งขาย — SA แจ้ง บัญชีคอนเฟิร์ม

สถานะ: **เสร็จสมบูรณ์** — หลังบ้าน + หน้าจอขึ้นใช้งานจริงแล้ว (ตรวจล่าสุด 2026-08-27)
เจ้าของงาน: บริหารงานขาย (SA) × ฝ่ายบัญชีและการเงิน (FN)

> **คำสั่งตั้งต้นจากผู้ใช้ 2026-08-13:** *"SO ต้องเอาเรื่องการชำระมาด้วย เรามีการทำงวดชำระไว้ด้วยนิ
> จาก QT ก็ดึงมาใช้ เพื่อเป็นการติดตามว่าชำระครบยัง · ลำดับก็คือ SA ส่งเรื่อง จบที่บัญชีตรวจสอบ
> คล้าย ๆ ลำดับการอนุมัติ SO"*

## นี่ไม่ใช่ของใหม่ — มีมติไว้แล้วตั้งแต่ 2026-08-01

[service-business-system-plan.md §5](service-business-system-plan.md) บันทึกมติผู้ใช้ไว้ว่า
*"SA ต้องกดว่าลูกค้าจ่ายแล้ว บัญชีต้องคอนเฟิร์ม"* พร้อมสถานะครบชุด และเขียนกำกับไว้ว่า

> ⇒ **ขั้นบัญชีที่ผู้ใช้อธิบายเป็นกระบวนการจริงที่ยังไม่เคยลงระบบ** แผนนี้จะเป็นที่แรก ·
> ถ้าใช้ได้ดี ค่อยพิจารณาย้อนไปใส่ให้ SO ทีหลัง

และหัวข้อคำร้อง FN ก็จอดรอเรื่องนี้อยู่ — `lib/requests/kinds/fn/billingDoc.js` เขียนไว้ตรง ๆ ว่า

> ⏳ ของจริงต้องอ้างใบสั่งขาย/งวดจ่ายด้วย แต่ `sales_orders` ยังไม่มีขั้นบัญชีเลย ⇒ รอบนี้ผูกแค่
> โครงการ+ดีล · **ห้ามเดาโครงสร้างงวดจ่ายล่วงหน้า** — ออกแบบพร้อมของจริงตอนมีที่เก็บ

**ตรวจแล้ว 2026-08-13: ทั้ง `service_contract_installments` และตารางสัญญาบริการ ยังไม่มีในรีโป**
⇒ งานนี้เป็น **ที่แรก** ที่ลงขั้นบัญชีจริง · สถานะและกติกาต้องยกมาจากมติ 2026-08-01 ทั้งชุด
ไม่ใช่คิดใหม่ ไม่งั้นพอทำสัญญาบริการทีหลังจะได้สองชุดที่เพี้ยนหากัน

## สายงาน — ยืมรูปเดียวกับที่ตัดสินไว้

```
งวด:  pending ──[SA/AC กด "ลูกค้าจ่ายแล้ว" + แนบหลักฐาน]──> reported
                     ↑                                        │
                     └────[บัญชีตีกลับ + เหตุผล]───────────────┤
                                                              ↓
                                              [บัญชีคอนเฟิร์ม] confirmed ✅
```

⚠️ **`reported` ไม่นับว่าชำระแล้ว — นับเมื่อ `confirmed` เท่านั้น**
ไม่งั้น SA แจ้งเองนับเอง = เท่ากับไม่มีด่าน (กติกาเดียวกับที่ห้าม `reported` ปลดด่านเข้าไซต์)

เทียบกับสายอนุมัติ SO ที่ผู้ใช้บอกว่า "คล้าย ๆ กัน" — **คล้ายแต่ไม่ใช่ตัวเดียวกัน**:

| | อนุมัติ SO | ชำระเงิน |
|---|---|---|
| หน่วยที่เดิน | ทั้งใบ | **รายงวด** — งวด 1 confirmed ขณะงวด 2 ยัง pending ได้ |
| ผู้ตรวจ | AE Supervisor (SA) | **ฝ่ายบัญชี (FN)** — คนละฝ่าย |
| เกิดขึ้นเมื่อ | ก่อนนับ Actual | หลังอนุมัติ ยาวไปจนปิดงาน |
| ผลเมื่อผ่าน | ยอดเข้า Actual | งวดนั้นปิด · ครบทุกงวด = ใบนี้ชำระครบ |

⇒ ห้ามยัดเข้า `sales_orders.status` เดิม — เป็นคนละแกน เดินพร้อมกันได้

## ที่เก็บ

งวดของ SO เป็น **snapshot จาก QT ตอนสร้างใบ** เหมือนที่รายการสินค้าเป็น snapshot อยู่แล้ว
ต้นทางคือ `quotations.paymentPlan` (jsonb) ที่มีอยู่แล้ว:

```jsonc
{ "type": "full" | "installment",
  "paymentMethod": "โอน" ,
  "installments": [ { "no": 1, "label": "มัดจำ", "percent": 30, "amount": 19260, "note": null } ] }
```

ตารางใหม่ — หนึ่งแถวต่อหนึ่งงวด (ห้ามเก็บเป็น jsonb เพราะแต่ละงวดมีสถานะ ผู้กด เวลา และไฟล์แนบของตัวเอง):

```
sales_order_installments
  salesOrderId · seq · label · percent · amount        ← snapshot จาก QT
  dueDate                                              ← กรอกที่ SO (QT ไม่มีวันรายงวด)
  status: pending | reported | confirmed | rejected
  reportedById/Name/At · evidence[]                    ← SA / AC
  confirmedById/Name/At                                ← FN
  rejectedReason · rejectedById/Name/At                ← FN
```

**สร้างงวดตอนไหน** — ตอนใบถูก **อนุมัติ** ไม่ใช่ตอนสร้างร่าง
เหตุผล: ยอดยังเปลี่ยนได้จนกว่าจะอนุมัติ · สร้างก่อนแล้วยอดต่องวดจะผิดเงียบ ๆ
`type: "full"` = **หนึ่งงวด 100%** ไม่ใช่ศูนย์งวด (ไม่งั้นใบจ่ายครั้งเดียวจะไม่มีอะไรให้ติดตามเลย)

| ทำอะไร | ใคร | ด่าน |

🔴 **จุดที่ต้องตัดสินก่อนเขียนโค้ด** — ระบบวันนี้ไม่มี role บัญชี มีแต่ **department `FN`**
ที่ถือ role `staff` (`permissions.js` · `DEPARTMENT_ROLES.FN = ['staff']`) — ⚠️ ยกเลิก role `staff` ไปแล้ว 2026-08-28 ([role-per-department.md](role-per-department.md))
และ FN โผล่ในระบบแค่สองที่: `REQUEST_ANSWER_DEPARTMENTS` กับหัวข้อคำร้อง `billing_doc`
⇒ ต้องเพิ่ม predicate ใหม่ (เช่น `canConfirmPayment(user)` = department FN หรือ admin)
**อย่าใช้ role `staff` ล้วนเป็นด่าน** — staff กระจายอยู่ 6 ฝ่าย (PC/PD/WH/RD/QC/TS/FN)
กด confirm ได้หมดทั้งที่ไม่ใช่บัญชี

## หน้าตาบนหน้า SO

การ์ดใหม่ในคอลัมน์ซ้าย ต่อจาก "ข้อมูลบนเอกสาร" — **แยกจากเส้นเดินงานผลิต** เพราะคนละแกน
(ผลิตเดินไปทางของ · ชำระเดินไปทางเงิน) และสรุปหนึ่งบรรทัดขึ้นการ์ดยอดสุทธิในรางขวา:

```
ชำระแล้ว 2/3 งวด · ฿38,520 จาก ฿64,200 · เหลืองวดที่ 3 ครบ 30/09/2026
```

แต่ละงวดหนึ่งแถว: ป้ายสถานะ · ชื่องวด · % · จำนวนเงิน · กำหนดชำระ · ปุ่มตามสิทธิ์
งวดที่ `rejected` ต้องขึ้นเหตุผลของบัญชีเป็นข้อความ ไม่ใช่ป้ายเปล่า (กฎเดียวกับ SO ที่ถูกตีกลับ)

## ของที่ต้องระวัง

- **ยกเลิกอนุมัติ / ออก Rev.** — ใบที่มีงวด `confirmed` แล้วต้องยกเลิกอนุมัติไม่ได้ (หรือได้แต่ต้อง
  ถามบัญชีก่อน) กติกาเดียวกับที่ตอนนี้บล็อกด้วยใบยื่นสรรพสามิต (`filingState.filing`)
- **ยกเลิก SO** — งวดที่คอนเฟิร์มแล้วคือเงินที่รับมาจริง ห้ามหายไปเงียบ ๆ พร้อมใบ
- **ผลรวมต้องเท่ายอดใบ** — `computeInstallments` ในลิบเดิมโยนเศษปัดไปงวดสุดท้ายอยู่แล้ว ใช้ตัวเดิม
  ห้ามคำนวณใหม่ (`lib/sales/paymentPlan.js`)
- **ชื่อคนที่บันทึกไว้เป็นหลักฐาน ห้ามซิงก์ตามบัญชีผู้ใช้ทีหลัง** — `reportedByName` / `confirmedByName`
  เป็น snapshot ของ "ใครกด ณ ตอนนั้น" (กฎเดียวกับ `approvedByName`)

## มติผู้ใช้ 2026-08-13

1. **ผู้คอนเฟิร์ม = ฝ่าย FN + Admin** — ด่านอ่านจาก **department `FN`** ไม่ใช่ role
   ⇒ ผู้ใช้ FN ที่มีอยู่วันนี้ใช้ได้ทันที ไม่ต้อง migrate ข้อมูลผู้ใช้
   พร้อมกันนั้นเพิ่ม role ชื่อ **`finance` — "บัญชีและการเงิน (Finance)"** เพราะผู้ใช้ระบุว่า
   *"ไม่อยากใช้คำว่า Staff"* · คน FN เดิมที่ถือ `staff` ยังผ่านด่านเหมือนเดิม
   (ด่านดูฝ่าย ไม่ได้ดูชื่อ role) — ย้าย role ทีหลังได้โดยไม่กระทบสิทธิ์
2. **วันครบกำหนด = SA กรอกเองทีละงวด** — ไม่คำนวณจาก `paymentDueDate` ให้อัตโนมัติ
   เพราะของจริงมีทั้งงวดผูกกับเหตุการณ์ (หลังติดตั้ง) ไม่ใช่ผูกกับวัน
3. **ใบเก่าที่อนุมัติไปแล้ว: สร้างงวดทีหลังได้เป็นรายใบ** — ปุ่ม "เริ่มติดตามการชำระ" บนใบที่
   อนุมัติแล้วแต่ยังไม่มีงวด · ไม่ generate ย้อนหลังทั้งระบบ (งวดที่จ่ายไปแล้วจะขึ้น pending
   ทั้งหมดแล้วต้องไล่กดย้อน = งานเพิ่มที่ไม่มีใครขอ)

## 🔴 Actual = ยอดเต็มของใบ ไม่ใช่ยอดที่เก็บเงินได้

> **ยืนยันกับผู้ใช้ 2026-08-13:** *"Actual ที่นับยอดให้ SA เป็นยอดเต็ม 100% นะ ถึงจะแบ่งจ่ายใน SO"*

ตรวจสายในโค้ดครบแล้ว — **งวดชำระไม่แตะ Actual เลย และแตะไม่ได้ด้วยโครงสร้าง**

| จุด | ของจริงในโค้ด |
|---|---|
| ตอนสร้าง SO จาก QT | `actualAmount = GREATEST(0, "totalAmount" - "vatAmount")` = ยอดเต็มก่อน VAT (mig 0107:202) |
| รวมเข้าดีล | `sum("actualAmount") WHERE status = 'approved'` — ดูทั้งใบ ไม่รู้จักงวด (mig 0107:87) |
| trigger ที่ปลุกการรวม | `AFTER … UPDATE OF status, "actualAmount", "orderDate", "dealId" ON sales_orders` — **ไม่ได้ฟังตารางงวดเลย** (mig 0107:126) |
| ตัวอ่านฝั่งแอป | `salesOrderActual(order)` = `approved ? actualAmount : 0` เต็มจำนวน |

⇒ SA ได้ยอดเต็ม 100% ตั้งแต่ใบอนุมัติ · แบ่งจ่ายกี่งวดก็ตาม Actual ไม่ขยับ
งวดชำระเป็น **แกนติดตามการเก็บเงิน** ล้วน ๆ

**กันไหลกลับ:** `salesOrderPayments.js` ไม่ export อะไรที่ชื่อ `actual*` และมีเทสต์ยืนยันว่า
`paymentRollup` ไม่มีคีย์ชื่อ `actual`/`won` หลุดออกมา — ถ้าวันหน้ามีคนต่อสายให้สองฝั่งคุยกัน
จะพังที่เทสต์ก่อนขึ้น prod

⚠️ **สิ่งที่เปลี่ยนจริงมีอย่างเดียว: จังหวะที่ Actual ถูก *ถอน* ได้** — ปุ่ม "ยกเลิกอนุมัติ"
กับ "ยกเลิก SO" ถูกบล็อกเมื่อมีงวดที่บัญชีคอนเฟิร์มแล้ว (ยอดเงินไม่เปลี่ยน แต่ถอยใบไม่ได้)
รูปเดียวกับที่ใบยื่นสรรพสามิตบล็อกอยู่แล้ว · **ยังไม่มีทางออกให้ใบที่ต้องออก Rev. ทั้งที่รับเงินมาแล้ว**
— เป็นข้อที่ต้องตัดสินตอนเจอเคสจริง (ทางเลือก: ให้บัญชีถอนคอนเฟิร์มก่อน · หรือเปลี่ยนจากบล็อกเป็นเตือน)

## ⚠️ หลักฐาน Won ≠ หลักฐานการชำระ — ตรวจแล้ว ไม่ต้องเพิ่มด่านที่ SO

คำถามผู้ใช้ 2026-08-13: *"SO จะยื่นอนุมัติได้ต้องแนบหลักฐานพร้อมใส่วันที่ ถึงจะยื่นได้ ถูกมั้ย"*

**ด่านนั้นมีอยู่แล้ว แต่อยู่ที่ QT ไม่ใช่ SO** — `validateWonEvidence` (mig 0102) บังคับตอนกด Won:
ประเภทเอกสาร (สลิป / PO / เอกสารยืนยันการสั่งซื้อ) + วันที่เอกสาร + ไฟล์ ≥1 และถ้าไม่ใช่สลิป
ต้องระบุกำหนดชำระด้วย · SO สร้างได้เฉพาะจาก QT ที่ `status='accepted'` และ **accept route
คือประตูเดียว**ที่ตั้งสถานะนั้นได้ (ตรวจ writer ทุกตัวแล้ว)
⇒ SO ทุกใบมีหลักฐาน+วันที่ตั้งแต่ก่อนถูกสร้าง · เพิ่มด่านซ้ำตอนยื่นอนุมัติ = เงื่อนไขที่ไม่มีทางไม่ผ่าน

🔴 **แต่คนละเรื่องกับหลักฐานการชำระ** — PO ที่ลงนามแล้วคือหลักฐานว่า *สั่งซื้อ* ไม่ใช่ว่า *จ่ายเงิน*
ถ้านับ PO เป็น "ชำระแล้ว" ยอดค้างรับผิดทั้งระบบ ⇒ สิ่งที่ขาดจริงคือ **ทำให้เห็น** (เอาประเภท+วันที่
ของหลักฐาน Won ขึ้นหัวการ์ดการชำระ) ไม่ใช่ด่านใหม่

## ตัดสินแล้ว: งวดที่คอนเฟิร์มแล้ว **บัญชีถอนได้** (มติผู้ใช้ 2026-08-13)

เดิมเป็นข้อค้าง — ใบที่มีงวด `confirmed` ยกเลิกอนุมัติ/ออก Rev. ไม่ได้เลย และไม่มีทางถอย
ผู้ใช้ตัดสินว่า **ให้บัญชีถอนคำรับรองของตัวเองได้** (`action: 'unconfirm'`)

⭐ **ถอนแล้วกลับไป `reported` ไม่ใช่ `pending`** — คำแจ้งของฝ่ายขายและหลักฐานยังอยู่ครบ
สิ่งที่ถูกถอนคือ **คำรับรองของบัญชี** ไม่ใช่การแจ้งของ SA · ถอยไป `pending` เมื่อไรเท่ากับ

      พรีวิวบังคับลบ (ใบเสนอราคา/ใบสั่งขาย) บอก blocked ตั้งแต่พรีวิว
    - ใบบริการที่ยกเลิก: บัญชีรับรองงวด reported ที่ไม่มีช่วงครอบได้ (ไม่มีนัดช่างอ่านใบที่ยกเลิก) ⇒ คืนเงินต่อได้ ไม่ใช่ทางตัน
    - ใบที่ถูกตีกลับ (`rejected`) แนบสลิป/ใบกำกับได้ (มติ D3 — ใบ Rev. ที่ถูกตีกลับถืองวดเงินที่ย้ายมา) · ยามไล่ทุกสถานะของใบ
    - โมดัลรับรองเงินพูดตามสถานะใบ (ยกเลิก = เงินค้าง · ย้อนการอนุมัติ/ยังไม่อนุมัติ = Actual นับเมื่อใบอนุมัติ) · คิวรับรองติดป้าย "ใบยกเลิกแล้ว"
    - งวดที่คืนเงินแล้วไม่ใช่ "เก็บแล้ว" ทุกจอ (แผง · ลิสต์ SO · ทะเบียน · ตัวกรองใบกำกับ) · ใบยกเลิก: งวดโมฆะไม่ใช่ค้างรับ/เลยกำหนด
      (`installmentVoid` ตัวเดียวทั้งระบบ) · ไม่วาดแผน QT เมื่อไม่มีงวด · สถานะระดับใบในทะเบียนมี "ใบยกเลิก/ถูกแทนแล้ว"
    - ข้อความยกเกินยอดใบบอกทางที่มีจริง (คืนเงินได้ทั้งงวดเท่านั้น) · โมดัลยกเงินรู้ว่าแถวของใบที่ยกเลิกเปลี่ยน (ไม่ 409 วน) ·
      งวดที่ยกมาจาก QT อื่นเห็นคำร้องวางบิลของตัวเอง
  - **ร่างที่ QT ถูกถอด Won + ด่านกู้คืน (23/09 · เคส SO-26080039-0)** — `รอตรวจ`
    - ที่มา: ยกเลิกใบ → ถอด Won ของ QT-26080037-4 → ออก QT-5 → admin **กู้คืน**ใบเดิมเป็นร่าง → SO-26080043-0 ออกจาก QT-5
      ⇒ ดีลเดียวมี SO สองใบ · บัญชีรับรองสลิปเดียวกันทั้งสองใบ (ด่านกันสร้างซ้ำดูแค่ QT ใบเดียวกัน) · Actual ไม่ซ้ำ (ร่างนี้ยื่นไม่ได้ — QT ไม่ใช่ accepted)
    - กู้คืน (admin) ต้องผ่าน `salesOrderRestoreBlock`: QT ยัง Won + ไม่มีใบอื่นของ QT เดียวกันที่ยังใช้งาน (route อ่านสด · ปุ่มบอกเหตุ)
    - ร่าง/รออนุมัติ/ตีกลับ ที่ QT ไม่ใช่ Won: งวดเหลือ ถอนคำรับรอง/ตีกลับ/ดึงกลับ/ล้างใบกำกับ (`pipelineInstallmentLock`) ·
      ทะเบียนบัญชีปิดปุ่มรับรอง/บันทึกใบกำกับของแถวนั้นพร้อมเหตุ (`ledgerRowLock`) · ร่าง Rev. (มติ D3) ใช้ QT เดิมที่ยัง Won ⇒ ไม่โดน
    - prod 23/09: โดนล็อกใบเดียวคือ SO-26080039-0 · ทางเก็บกวาดของบัญชียังเปิดอยู่ (ถอนคำรับรอง → ตีกลับ → AE Sup ยกเลิกใบ)

## ขั้นบัญชีปิดใบ (mig 0250 · มติผู้ใช้ 2026-08-13 · **สลับลำดับ 2026-08-30 → mig 0321**)

> *"ต้องเพิ่มขั้นตอนใน SO ให้บัญชีอนุมัติใบด้วยหลัง AE Sup อนุมัติ"*

🔴 **เป็นคนละแกนกับ `status` ไม่ใช่สถานะกลางทาง** — ตรวจแล้ว `status = 'approved'` เป็น
ตัวปลดล็อก **12 จุดทั่วระบบ**: trigger นับ Actual เข้าดีล (0107:126) · เปิดคำร้องพัฒนากลิ่น ·
งานผลิตงอกอัตโนมัติ · สร้างใบยื่นสรรพสามิต · คิว handoff ฝ่ายกฎหมาย · ลายน้ำเอกสารพิมพ์ ·
การสร้างงวดชำระ (0245) ⇒ แทรกสถานะกลางเมื่อไร ของทั้ง 12 อย่างหยุดรอบัญชีไปด้วยหมด

**มติผู้ใช้: ยอด Actual เข้าตอน AE Sup อนุมัติเหมือนเดิม บัญชีไม่แตะ**

```
(ใบยังไม่อนุมัติ / ใบที่ออกก่อนมีขั้นนี้ / ใบยอด 0) = NULL
   │ [AE Sup อนุมัติ ⇒ status='approved' · Actual เข้าทันที]
   ▼
pending ──[เก็บเงินครบทุกงวด]──> (บัญชีกดปิดใบได้) ──> approved ■ = ปิดใบ
```

### 🔄 สลับลำดับ: บัญชีย้ายไปท้ายวง (มติผู้ใช้ 2026-08-30 · mig 0321)

> *"อยากลำดับ การอนุมัติ SO ใหม่ด้วย AE sup > การชำระ (ครบงวด) > บัญชี อนุมัติใบ = ปิดใบ"*
> *"ไม่มีตีกลับตอนท้ายแล้ว มี แค่ ตีกลับ ระหว่างงวด เพราะ บางที อาจอัพโหลดไฟล์ผิด"*

**ของเดิมไม่ใช่ลำดับ มันคือสองแกนที่ไม่เคยคุยกัน** — ลำดับ "AE Sup → บัญชีตรวจ → เก็บเงิน"
เป็นแค่การเรียงหมุดบนราง ไม่มีโค้ดจุดไหนบังคับ ⇒ วัดบนฐานจริง 2026-08-30 พบ **13 ใบ
จาก 35 ใบที่บัญชีอนุมัติแล้ว ยังเก็บเงินไม่ครบ** (บางใบยังไม่ได้สักบาท)
⇒ งานนี้จึงไม่ใช่ "สลับตำแหน่ง" แต่คือ **สร้างด่านที่ไม่เคยมี**

- ปุ่มของบัญชี = **ปิดใบ** (ขั้นสุดท้ายจริง ๆ) ปลดล็อกเมื่อ **ทุกงวดเป็น `confirmed`**
  · ตัวตัดสินตัวเดียว `salesOrderFullyPaid()` ที่ทั้งปุ่ม ด่าน API และคิวบัญชีถามตัวเดียวกัน
  · ไม่ส่ง `installments` เข้าด่าน = **ปฏิเสธ** ไม่ใช่ปล่อยผ่าน (ผู้เรียกที่ไม่มีบริบทงวด
  ไม่ควรเป็นคนตัดสินใจปิดใบ) ⇒ คิวบนทะเบียนจึงต้องคิดที่ server พร้อมงวด
- **ถอด `finance_reject` + `finance_resubmit` ออก** — การตีกลับที่ของจริงต้องใช้คือ
  *รายงวด* (แนบสลิปผิด/ยอดไม่ตรง) ซึ่งมีอยู่แล้วที่ `installmentActionError`
  · และปุ่มตีกลับตอนท้ายจะกดไม่ได้ตลอดกาลอยู่ดี เพราะใบที่เก็บครบถูก `paymentLockReason`
  ล็อกจากการยกเลิก/ย้อนอนุมัติไปแล้ว
- 🪤 `finance_resubmit` เคยมีอีกหน้าที่คือปุ่ม **"ส่งให้บัญชีตรวจ"** ของใบเก่า (`NULL`)
  — **วัดก่อนถอด**: ใบ `approved` + `financeStatus IS NULL` มี 19 ใบ และ **ทั้ง 19 ใบยอด 0**
  ซึ่งกติกาใหม่ถือว่าปิดตั้งแต่ AE Sup อนุมัติ ⇒ ไม่มีใบไหนต้องใช้ปุ่มนั้นอีก
- **mig 0321 ถอน 13 ใบนั้นกลับเป็น `pending`** (มติผู้ใช้: ให้บัญชีกดใหม่ตอนเก็บครบ)
  · ลายเซ็นเดิมใน `document_signature_evidence` ไม่ถูกลบ · ค่าเดิมทุกช่องลง `audit_logs.before`
- ⚠️ **ยังไม่แตะ `status` และ Actual** เหมือนเดิม — เหตุผลเดียวกับ 12 จุดข้างบน

**สิ่งที่บัญชีตรวจ** (ต่างจากคอนเฟิร์มงวดชำระซึ่งตอบว่า *เงินงวดนี้เข้าจริงไหม*):
ข้อมูลลูกค้า/ที่อยู่ออกบิล/เลขผู้เสียภาษี · เงื่อนไขการชำระ งวด กำหนดชำระ ·
ยอดเงิน/ส่วนลด/VAT · เครดิตและวงเงินของลูกค้า

⚠️ **ไม่ backfill** — ใบที่อนุมัติก่อน mig 0250 ได้ `financeStatus = NULL` แปลว่า
"ออกก่อนมีขั้นนี้" ไม่ใช่ "รอบัญชี" · ตั้ง pending ย้อนหลังเมื่อไร บัญชีจะเปิดมาเจอคิวค้าง
ทั้งกองที่ไม่มีใครตั้งใจสร้าง (ขั้นนี้จึงไม่โผล่บนรางก้าวของใบเก่าเลย)

🔴 **แต่ "ไม่ backfill" ไม่เท่ากับ "เข้าคิวไม่ได้"** — รอบแรกปล่อยไว้แบบนั้นจริง ๆ แล้วพัง:
`financeStatus` ถูกตั้งเป็น pending **เฉพาะตอนกดอนุมัติ**เท่านั้น และตอนทดสอบจริงพบว่า
**ทุกใบในระบบ (7/7) อนุมัติไปหมดแล้ว** ⇒ ไม่มีใบไหนเข้าคิวบัญชีได้เลยสักใบ
ฟีเจอร์ใช้ได้แต่กับ SO ที่จะสร้างใหม่เท่านั้น · แก้ด้วยปุ่ม **"ส่งให้บัญชีตรวจ"** ที่ AE Sup/Admin
กดทีละใบ (ใช้ `finance_resubmit` ตัวเดียวกับตอนถูกตีกลับ ป้ายเปลี่ยนตามสถานะ)
⇒ คนตัดสินใจว่าใบไหนควรเข้าคิว ไม่ใช่เทเข้าคิวทั้งกองด้วย migration
(แพตเทิร์นเดียวกับปุ่ม "เริ่มติดตามการชำระ" ของงวดชำระที่มีให้ใบเก่าอยู่แล้ว)

🐞 **กับดักที่เจอตอนแก้:** ด่านกันสองคนกดชนใช้ `.eq('financeStatus', before.financeStatus)`
ซึ่งกับค่า NULL กลายเป็น `col = null` = ไม่จริงเสมอ ⇒ อัปเดตไม่ติดเงียบ ๆ ต้องแยกไปใช้
`.is(col, null)` เมื่อค่าเดิมว่าง

⚠️ ~~**ส่งตรวจใหม่เป็นของฝั่งขาย**~~ — คำสั่งนี้ถอดออกแล้ว 2026-08-30 (ดูหัวข้อสลับลำดับ)
เหลือไว้ตรงนี้เพราะเหตุผลเดิมยังใช้กับด่านอื่น: **คนกดตีกลับต้องไม่ใช่คนกดส่งเข้าคิวเอง**
