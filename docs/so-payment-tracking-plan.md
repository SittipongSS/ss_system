# งวดชำระบนใบสั่งขาย — SA แจ้ง บัญชีคอนเฟิร์ม

สถานะ: **รอดำเนินการ** (ร่างเพื่อขอมติ · 2026-08-13)
เจ้าของงาน: บริหารงานขาย (SA) × ฝ่ายบัญชีและการเงิน (FN)

> **คำสั่งตั้งต้นจากผู้ใช้ 2026-08-13:** *"SO ต้องเอาเรื่องการชำระมาด้วย เรามีการทำงวดชำระไว้ด้วยนิ
> จาก QT ก็ดึงมาใช้ เพื่อเป็นการติดตามว่าชำระครบยัง · ลำดับก็คือ SA ส่งเรื่อง จบที่บัญชีตรวจสอบ
> คล้าย ๆ ลำดับการอนุมัติ SO"*

## นี่ไม่ใช่ของใหม่ — มีมติไว้แล้วตั้งแต่ 2026-08-01

[service-business-system-plan.md §5](service-business-system-plan.md) บันทึกมติผู้ใช้ไว้ว่า
*"SA ต้องกดว่าลูกค้าจ่ายแล้ว บัญชีต้องคอนเฟิร์ม"* พร้อมสถานะครบชุด และเขียนกำกับไว้ว่า

> ⇒ **ขั้นบัญชีที่ผู้ใช้อธิบายเป็นกระบวนการจริงที่ยังไม่เคยลงระบบ** แผนนี้จะเป็นที่แรก ·
> ถ้าใช้ได้ดี ค่อยพิจารณาย้อนไปใส่ให้ SO ทีหลัง

และหัวข้อคำร้อง FN ก็จอดรอเรื่องนี้อยู่ — `lib/requests/kinds/fn/billingDoc.js` เขียนไว้ตรง ๆ ว่า

> ⏳ ของจริงต้องอ้างใบสั่งขาย/งวดจ่ายด้วย แต่ `sales_orders` ยังไม่มีขั้นบัญชีเลย ⇒ รอบนี้ผูกแค่
> โครงการ+ดีล · **ห้ามเดาโครงสร้างงวดจ่ายล่วงหน้า** — ออกแบบพร้อมของจริงตอนมีที่เก็บ

**ตรวจแล้ว 2026-08-13: ทั้ง `service_contract_installments` และตารางสัญญาบริการ ยังไม่มีในรีโป**
⇒ งานนี้เป็น **ที่แรก** ที่ลงขั้นบัญชีจริง · สถานะและกติกาต้องยกมาจากมติ 2026-08-01 ทั้งชุด
ไม่ใช่คิดใหม่ ไม่งั้นพอทำสัญญาบริการทีหลังจะได้สองชุดที่เพี้ยนหากัน

## สายงาน — ยืมรูปเดียวกับที่ตัดสินไว้

```
งวด:  pending ──[SA/AC กด "ลูกค้าจ่ายแล้ว" + แนบหลักฐาน]──> reported
                     ↑                                        │
                     └────[บัญชีตีกลับ + เหตุผล]───────────────┤
                                                              ↓
                                              [บัญชีคอนเฟิร์ม] confirmed ✅
```

⚠️ **`reported` ไม่นับว่าชำระแล้ว — นับเมื่อ `confirmed` เท่านั้น**
ไม่งั้น SA แจ้งเองนับเอง = เท่ากับไม่มีด่าน (กติกาเดียวกับที่ห้าม `reported` ปลดด่านเข้าไซต์)

เทียบกับสายอนุมัติ SO ที่ผู้ใช้บอกว่า "คล้าย ๆ กัน" — **คล้ายแต่ไม่ใช่ตัวเดียวกัน**:

| | อนุมัติ SO | ชำระเงิน |
|---|---|---|
| หน่วยที่เดิน | ทั้งใบ | **รายงวด** — งวด 1 confirmed ขณะงวด 2 ยัง pending ได้ |
| ผู้ตรวจ | AE Supervisor (SA) | **ฝ่ายบัญชี (FN)** — คนละฝ่าย |
| เกิดขึ้นเมื่อ | ก่อนนับ Actual | หลังอนุมัติ ยาวไปจนปิดงาน |
| ผลเมื่อผ่าน | ยอดเข้า Actual | งวดนั้นปิด · ครบทุกงวด = ใบนี้ชำระครบ |

⇒ ห้ามยัดเข้า `sales_orders.status` เดิม — เป็นคนละแกน เดินพร้อมกันได้

## ที่เก็บ

งวดของ SO เป็น **snapshot จาก QT ตอนสร้างใบ** เหมือนที่รายการสินค้าเป็น snapshot อยู่แล้ว
ต้นทางคือ `quotations.paymentPlan` (jsonb) ที่มีอยู่แล้ว:

```jsonc
{ "type": "full" | "installment",
  "paymentMethod": "โอน" ,
  "installments": [ { "no": 1, "label": "มัดจำ", "percent": 30, "amount": 19260, "note": null } ] }
```

ตารางใหม่ — หนึ่งแถวต่อหนึ่งงวด (ห้ามเก็บเป็น jsonb เพราะแต่ละงวดมีสถานะ ผู้กด เวลา และไฟล์แนบของตัวเอง):

```
sales_order_installments
  salesOrderId · seq · label · percent · amount        ← snapshot จาก QT
  dueDate                                              ← กรอกที่ SO (QT ไม่มีวันรายงวด)
  status: pending | reported | confirmed | rejected
  reportedById/Name/At · evidence[]                    ← SA / AC
  confirmedById/Name/At                                ← FN
  rejectedReason · rejectedById/Name/At                ← FN
```

**สร้างงวดตอนไหน** — ตอนใบถูก **อนุมัติ** ไม่ใช่ตอนสร้างร่าง
เหตุผล: ยอดยังเปลี่ยนได้จนกว่าจะอนุมัติ · สร้างก่อนแล้วยอดต่องวดจะผิดเงียบ ๆ
`type: "full"` = **หนึ่งงวด 100%** ไม่ใช่ศูนย์งวด (ไม่งั้นใบจ่ายครั้งเดียวจะไม่มีอะไรให้ติดตามเลย)

## สิทธิ์

| ทำอะไร | ใคร | ด่าน |
|---|---|---|
| เห็นงวด | ทุกคนที่เห็น SO ใบนั้น | scope เดิมของ SO |
| กรอก/แก้วันครบกำหนด | SA (`salesplan:edit`) | เดิม |
| กด "ลูกค้าจ่ายแล้ว" + แนบหลักฐาน | SA / AC เจ้าของงาน | เดิม |
| คอนเฟิร์ม / ตีกลับ | **ฝ่ายบัญชี (department `FN`)** | 🔴 **ยังไม่มีด่านนี้ในระบบ ต้องสร้าง** |

🔴 **จุดที่ต้องตัดสินก่อนเขียนโค้ด** — ระบบวันนี้ไม่มี role บัญชี มีแต่ **department `FN`**
ที่ถือ role `staff` (`permissions.js` · `DEPARTMENT_ROLES.FN = ['staff']`)
และ FN โผล่ในระบบแค่สองที่: `REQUEST_ANSWER_DEPARTMENTS` กับหัวข้อคำร้อง `billing_doc`
⇒ ต้องเพิ่ม predicate ใหม่ (เช่น `canConfirmPayment(user)` = department FN หรือ admin)
**อย่าใช้ role `staff` ล้วนเป็นด่าน** — staff กระจายอยู่ 6 ฝ่าย (PC/PD/WH/RD/QC/TS/FN)
กด confirm ได้หมดทั้งที่ไม่ใช่บัญชี

## หน้าตาบนหน้า SO

การ์ดใหม่ในคอลัมน์ซ้าย ต่อจาก "ข้อมูลบนเอกสาร" — **แยกจากเส้นเดินงานผลิต** เพราะคนละแกน
(ผลิตเดินไปทางของ · ชำระเดินไปทางเงิน) และสรุปหนึ่งบรรทัดขึ้นการ์ดยอดสุทธิในรางขวา:

```
ชำระแล้ว 2/3 งวด · ฿38,520 จาก ฿64,200 · เหลืองวดที่ 3 ครบ 30/09/2026
```

แต่ละงวดหนึ่งแถว: ป้ายสถานะ · ชื่องวด · % · จำนวนเงิน · กำหนดชำระ · ปุ่มตามสิทธิ์
งวดที่ `rejected` ต้องขึ้นเหตุผลของบัญชีเป็นข้อความ ไม่ใช่ป้ายเปล่า (กฎเดียวกับ SO ที่ถูกตีกลับ)

## ของที่ต้องระวัง

- **ยกเลิกอนุมัติ / ออก Rev.** — ใบที่มีงวด `confirmed` แล้วต้องยกเลิกอนุมัติไม่ได้ (หรือได้แต่ต้อง
  ถามบัญชีก่อน) กติกาเดียวกับที่ตอนนี้บล็อกด้วยใบยื่นสรรพสามิต (`filingState.filing`)
- **ยกเลิก SO** — งวดที่คอนเฟิร์มแล้วคือเงินที่รับมาจริง ห้ามหายไปเงียบ ๆ พร้อมใบ
- **ผลรวมต้องเท่ายอดใบ** — `computeInstallments` ในลิบเดิมโยนเศษปัดไปงวดสุดท้ายอยู่แล้ว ใช้ตัวเดิม
  ห้ามคำนวณใหม่ (`lib/sales/paymentPlan.js`)
- **ชื่อคนที่บันทึกไว้เป็นหลักฐาน ห้ามซิงก์ตามบัญชีผู้ใช้ทีหลัง** — `reportedByName` / `confirmedByName`
  เป็น snapshot ของ "ใครกด ณ ตอนนั้น" (กฎเดียวกับ `approvedByName`)

## มติผู้ใช้ 2026-08-13

1. **ผู้คอนเฟิร์ม = ฝ่าย FN + Admin** — ด่านอ่านจาก **department `FN`** ไม่ใช่ role
   ⇒ ผู้ใช้ FN ที่มีอยู่วันนี้ใช้ได้ทันที ไม่ต้อง migrate ข้อมูลผู้ใช้
   พร้อมกันนั้นเพิ่ม role ชื่อ **`finance` — "บัญชีและการเงิน (Finance)"** เพราะผู้ใช้ระบุว่า
   *"ไม่อยากใช้คำว่า Staff"* · คน FN เดิมที่ถือ `staff` ยังผ่านด่านเหมือนเดิม
   (ด่านดูฝ่าย ไม่ได้ดูชื่อ role) — ย้าย role ทีหลังได้โดยไม่กระทบสิทธิ์
2. **วันครบกำหนด = SA กรอกเองทีละงวด** — ไม่คำนวณจาก `paymentDueDate` ให้อัตโนมัติ
   เพราะของจริงมีทั้งงวดผูกกับเหตุการณ์ (หลังติดตั้ง) ไม่ใช่ผูกกับวัน
3. **ใบเก่าที่อนุมัติไปแล้ว: สร้างงวดทีหลังได้เป็นรายใบ** — ปุ่ม "เริ่มติดตามการชำระ" บนใบที่
   อนุมัติแล้วแต่ยังไม่มีงวด · ไม่ generate ย้อนหลังทั้งระบบ (งวดที่จ่ายไปแล้วจะขึ้น pending
   ทั้งหมดแล้วต้องไล่กดย้อน = งานเพิ่มที่ไม่มีใครขอ)

## ที่ยังไม่ตัดสิน (ตัดสินตอนเจอของจริง)

- **แก้งวดบนใบที่อนุมัติแล้ว** — รอบแรกให้ SA แก้ `dueDate` ได้เสมอ แต่แก้ยอด/`%` ไม่ได้
  (ยอดเป็น snapshot ของ QT) · ถ้าของจริงต้องแก้ยอดด้วย ค่อยออกแบบขั้นขออนุมัติทีหลัง
