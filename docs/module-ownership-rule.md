## กฎสามชั้น — ของอะไรอยู่โมดูลไหน (มติผู้ใช้ 2026-08-13)

> *"จะมีเรื่องโครงการ ดีล ใบเสนอราคา ใบสั่งขาย ที่แทบทุกฝ่ายใช้ร่วมกัน หรือว่าเอาคอนเซป
> ความรับผิดชอบใครเริ่มฝ่ายนั้น และข้อมูลนั้นใครใช้ค่อยดึงมา"* — **ใช่ ตามนั้น**

| ชั้น | คืออะไร | ตัวอย่างวันนี้ |
|---|---|---|
| **1 · โมดูลของฝ่าย** | **งานของฝ่าย** — คิวที่ต้องลงมือ + มุมมองที่ฝ่ายนั้นถามเอง | `/rd` คิวคำร้อง · `/finance` ทะเบียนการชำระ |
| **2 · โมดูลเจ้าของเอกสาร** | เอกสารอยู่ที่เดิมตลอดชีวิต ฝ่ายอื่น**เข้ามาอ่าน/ลงมือเฉพาะขั้นของตน** | `/sa` ดีล · โครงการ · QT · SO |
| **3 · ฐานข้อมูล** | ข้อมูลหลักที่ทุกฝ่ายใช้ร่วม ไม่ว่าใครเป็นคนผลิต | `/database` ลูกค้า · สินค้า · กลิ่น/สูตร · **ไซต์บริการ/ทะเบียนเครื่อง** |

**เส้นแบ่งที่ใช้ตัดสิน**

1. **ใครเริ่มเอกสาร คนนั้นเป็นเจ้าของที่เก็บ** — เอกสารไม่ย้ายบ้านตามคนที่มาทำงานกับมัน
2. **ขั้นของฝ่ายอื่น = คอลัมน์เพิ่มบนเอกสารเดิม ไม่ใช่เอกสารใหม่**
3. **โมดูลของฝ่าย = มุมมอง + คิว ไม่ใช่ที่เก็บ** — ที่เก็บและ**ด่านตรวจ**อยู่กับเอกสารต้นทาง
   *(แก้ 2026-08-13: **จอกดได้มากกว่าหนึ่งจอ** แต่ต้องเป็นปุ่มที่เรียก API ตัวเดียวกัน
   เปิดโมดัลตัวเดียวกัน และเห็นหลักฐานชุดเดียวกัน — ดูข้อ 3 ท้ายหัวข้อนี้)*
4. **ข้อมูลที่ฝ่ายหนึ่งผลิตแต่ทุกฝ่ายใช้ ⇒ ชั้น 3 ไม่ใช่ชั้น 1** (= กฎข้อ 6 ข้างล่าง)
5. **เมนู = "งานที่ฝ่ายนี้ทำ" ไม่ใช่ "ทุกอย่างที่เขาอ่านได้"** (= กฎข้อ 7 ข้างล่าง)

### ที่มาของข้อ 4 รอบสอง — ทะเบียนไซต์/เครื่องย้ายเข้าฐานข้อมูล (มติผู้ใช้ 2026-09-17)

ทะเบียนไซต์บริการกับทะเบียนเครื่องเกิดใต้ `/service` เพราะฝ่าย TS เป็นคนดูแล — แต่มันคือ
**ข้อมูลหลักที่ทุกฝ่ายใช้ร่วม** ตรงตามชั้น 3 ทุกตัวอักษร (ทรงเดียวกับทะเบียนกลิ่น/สูตรที่ RD
ผลิตแต่ทุกคนเปิดอ่านได้) · อาการที่ฟ้องว่าอยู่ผิดชั้น:

- ฝ่ายขายตอบลูกค้าไม่ได้ว่า "ตอนนี้มีเครื่องกี่เครื่อง ตั้งที่ไหนบ้าง" — ต้องถาม TS ทุกครั้ง
- หน้าลูกค้าใน `/database` โชว์ไซต์ของลูกค้าอยู่แล้ว **แต่กดเข้าไปดูต่อไม่ได้** (403)
- ใบสั่งขาย · ใบคำร้องประเมินพื้นที่ · คิวงานเข้าใหม่ อ้างสองทะเบียนนี้อยู่ทุกวัน

**ย้าย**: `/service/sites*` → `/database/sites*` · `/service/assets*` → `/database/assets*`
(เส้นทางเก่าเหลือเป็นตัวเด้ง ลิงก์ที่ส่งกันไว้ไม่ตาย)

**สิทธิ์**: อ่าน = `canViewServiceRegistry` (กว้างเท่าทะเบียนสินค้า/ลูกค้า) · **เขียนไม่ขยับ**
= `canEditService` (TS + แอดมิน) · ไซต์ยังเกิดสองทางเดิมเท่านั้น (ใบคำร้องประเมินพื้นที่ ·
ปุ่มเพิ่มไซต์ย้อนหลัง) ⇒ ไม่มีปุ่ม "สร้างไซต์" ลอย ๆ ตามมติ UAT 2026-08-30

**รอบสอง (มติผู้ใช้ 2026-09-24): "ฐานข้อมูล ไซต์ เครื่อง เปิดให้ผู้ใช้ที่เข้าระบบฐานข้อมูลได้เห็นได้เลย"**
— รอบแรกเปิดแค่เส้นของตัวไซต์ แต่หน้า `/database/sites/[id]` โหลด **รอบบริการ + นัดของไซต์** คู่กัน
แล้วล่มทั้งหน้าเมื่อตัวใดไม่ผ่าน ⇒ ทุกตำแหน่งนอก TS (ขาย · RD · บัญชี · โรงงาน · ผู้บริหาร) เจอ Forbidden
- `GET /api/service/plans?siteId=` · `GET /api/service/visits?siteId=` = **ด่านทะเบียนเมื่อระบุไซต์** ·
  ไม่ระบุไซต์ (คิว/ปฏิทินทั้งระบบ) ยังเป็นของ TS · คนนอก TS ได้แค่ตัวนัด ไม่ได้ภาระงาน/บริบทด่าน (จ่ายถึง · สัญญา)
- หน้าไซต์: รอบ/นัดโหลดไม่ได้ = แจ้งในการ์ดนั้น ไม่ล่มทั้งหน้า
- แท็บพื้นที่บริการบนหน้าลูกค้า (`/api/service/customers/[id]/zones`) = ด่านทะเบียน · ลิงก์เข้าหน้าไซต์เปิดตามด่านทะเบียน
- ลิงก์ "ใบส่งงาน" (`/service/visits/[id]` = หน้าทำงานของ TS) บนหน้าทะเบียน โชว์เฉพาะคนที่เปิดได้จริง
- ยาม: `lib/service/registryReadAccess.test.mjs`

**รอบสาม (มติผู้ใช้ 2026-09-24): "ใบส่งงานเปิดให้ฝ่ายขายดูได้ด้วย"** — ฝ่ายขายทุกตำแหน่ง
(`isSalesRole`) **อ่าน** ใบส่งงาน `/service/visits/[id]` ได้ · ไม่ใช่การเปิดโมดูลบริการให้ฝ่ายขาย
- ด่าน `canViewVisitReport` = `canViewService` + ฝ่ายขาย · ใช้ทั้งฝั่ง API และลิงก์บนหน้าทะเบียน (ไซต์ · โซน · เครื่อง)
- API: เฉพาะ `GET /api/service/visits/[id]` (`requireVisit({ report: true })`) · PATCH/DELETE และเส้นย่อย
  (`/items` · `/assets`) ยังเป็นด่านฝ่ายบริการ ⇒ ฝ่ายขายแก้/ปิดงาน/ลบนัดไม่ได้
- เปลือกเมนู: ฝ่ายขายเปิดใบ = คงเปลือกเดิม (ฐานข้อมูล) ไม่สวมเปลือกบริการที่เขาไม่มีเมนู ·
  ปุ่มย้อนกลับพาไปหน้าไซต์ในฐานข้อมูล · การ์ดประเมินพื้นที่พาไปใบคำร้อง `/requests/[id]` แทนจอประเมินของ TS
- รูป/ลายเซ็นในใบเปิดผ่าน `GET /api/service/visits/[id]/file?i=<ลำดับ>|sig=1` — **ด่านเดียวกับใบ**
  (`requireVisit({ report: true })`) · server หยิบ URL จากแถวของนัดแล้วสตรีมจาก Drive เอง ไม่รับ Drive id จาก query
  🐞 เดิมจอลิงก์ `webViewLink` ของ Drive ตรง แต่ตอนอัปไม่มีการให้สิทธิ์รายไฟล์ ⇒ เปิดได้แค่สมาชิก Shared Drive
  (2 ราย · มติ #1274 ห้ามเพิ่มพนักงาน/แชร์ทั้งโดเมน) ติดทั้ง TS และฝ่ายขาย · แก้ก่อนมีนัดไหนปิดงานพร้อมรูป
  · แผ่นปิดงาน: ไฟล์ที่เพิ่งอัป (ยังไม่บันทึก) เปิดจากไบต์ในเครื่อง · ตัวตัดสิน `lib/service/visitFiles.js` · ยาม `visitFiles.test.mjs`
- หน้าอื่นใต้ `/service` (จัดคิว · งานวันนี้ · ประเมินพื้นที่) ยังเป็นของ TS เหมือนเดิม

**เมนูอยู่สองที่ หน้าเดียว URL เดียว** — TS ใช้สองหน้านี้เป็นเครื่องมือรายวัน ไม่ใช่ข้อมูล
อ้างอิงนาน ๆ ครั้ง ⇒ เมนูฝ่ายบริการยังมีทางลัดชี้ URL ใหม่ ผ่าน `ADOPTED_SHARED_PATHS.service`
(กลไกเดียวกับที่เมนูบัญชียืมใบเสนอราคา/ใบสั่งขายไปไว้ในเมนูตัวเอง) คู่กับกฎข้อ 9
"เปลือกเมนูเดินตามคนดู" ⇒ TS เปิดแล้วเห็นเปลือกบริการ ฝ่ายขายเปิดแล้วเห็นเปลือกฐานข้อมูล
🪤 **ห้ามก๊อปหน้า** — สองเมนูชี้ไฟล์เดียวกัน ถ้าแยกไฟล์เมื่อไรมันจะเพี้ยนหากันตามบทเรียน
"ปุ่มแก้ไขต้องเปิดฟอร์มตัวเดียวกับตอนสร้าง"

### ที่มาของข้อ 2 — ขั้นบัญชีตรวจใบ (mig 0250)

เคยคิดจะแทรกสถานะกลางใน `sales_orders.status` — **ตรวจแล้วทำไม่ได้** เพราะ
`status = 'approved'` ปลดล็อก **12 จุดทั่วระบบ** (Actual · งานกลิ่น · งานผลิต · ใบยื่นภาษี ·
handoff · ลายน้ำ · งวดชำระ) ⇒ แทรกเมื่อไร ทั้ง 12 อย่างหยุดรอบัญชี
**ทางที่ใช้จริง: คอลัมน์ `financeStatus` เป็นคนละแกน เดินพร้อมกันได้**

### ที่มาของข้อ 3 — งวดชำระ (mig 0245)

งวดเก็บใต้ `sales_order_installments` ผูกกับใบ · `/finance/payments` เป็น **มุมมองรวมข้ามใบ**

**เดิมตั้งไว้ว่าอ่านอย่างเดียว — แก้แล้ว (มติผู้ใช้ 2026-08-13)** ผู้ใช้สั่งให้ยกคิว
"รอคุณรับรอง" ขึ้นมาไว้บนหน้าทะเบียนและกดได้จากตรงนั้น เพราะบัญชีเปิดหน้านี้ค้างไว้
ทั้งวันอยู่แล้ว การบังคับให้เด้งไปทีละใบคือการนับคลิกเพิ่มเปล่า ๆ ไม่ได้เพิ่มความปลอดภัย

สิ่งที่กฎข้อ 3 **หวงจริง ๆ** ไม่ใช่จำนวนจอที่มีปุ่ม แต่คือสามอย่างนี้ ซึ่งยังต้องมีชุดเดียว:

| ต้องมีชุดเดียว | ของจริงในโค้ด |
| --- | --- |
| ทางเขียน | `PATCH /api/sales-planning/sales-orders/[id]/installments` — คิวเรียกเส้นเดิม |
| ด่านสิทธิ์ | `payments:confirm` ที่ `proxy.js` + guard ในตัว handler |
| จอยืนยัน | `InstallmentConfirmDialog` — การ์ดบนใบกับคิวใช้ component เดียวกัน |

⚠️ **เงื่อนไขที่ทำให้เปิดปุ่มนอกเอกสารต้นทางได้** — ความเสี่ยงที่ยกไว้ตอนตัดสินคือ
*"คนกดจะมองไม่เห็นหลักฐานที่แนบมากับงวดซึ่งอยู่บนใบ"* ⇒ โมดัลต้องโชว์ไฟล์หลักฐาน
วันจ่ายจริง และผู้แจ้ง ก่อนให้กด และ**เตือนเมื่อไม่มีไฟล์แนบ**
ผลพลอยได้: การ์ดบนใบ SO เดิมถามยืนยันโดยไม่โชว์อะไรเลย ตอนนี้โชว์ด้วย

⇒ อ่านกฎข้อ 3 ว่า **"ด่านเดียว"** ไม่ใช่ "จอเดียว" · จอที่สองที่เรียกด่านเดิมคือมุมมอง
ส่วนจอที่สองที่มี API/สิทธิ์/โมดัลเป็นของตัวเอง คือของที่กฎนี้ห้าม
⚠️ เปิดทางเขียนที่หน้ารวมด้วยเมื่อไร = ด่านสองชุดที่เพี้ยนหากัน และคนกดคอนเฟิร์มจะ
มองไม่เห็นหลักฐานที่แนบมากับงวดซึ่งอยู่บนใบ

## ทำไม

โจทย์ตั้งต้นของระบบคำร้อง (ม-1 ใน [requests-rd-decision-log.md](requests-rd-decision-log.md)):

> *"จะมีโมดูลระบบแยกของแต่ละฝ่าย ฝ่ายจัดซื้อ ฝ่ายวิจัยและพัฒนา ฝ่ายบัญชีและการเงิน
> **เพื่อที่แต่ละฝ่ายจะได้ขยายระบบได้**"*

ระบบคำร้องคือ **รอยต่อระหว่างฝ่าย** ไม่ใช่ระบบของฝ่ายใดฝ่ายหนึ่ง — เอางานประจำวันของฝ่าย
หนึ่งไปวางในโมดูลของอีกฝ่าย = ฝ่ายนั้นขยายระบบตัวเองไม่ได้ และคนใช้ต้องจำว่างานของตัวเอง
อยู่ใต้เมนูของใคร

## วิธีใช้

**1 · หน้าจออยู่ในโมดูลของฝ่ายที่ลงมือทำ**
คิวของ RD อยู่ `/rd/requests` ไม่ใช่แท็บใน `/requests` ของฝ่ายขาย ·
`lib/requests/modules.js` ถือลิสต์ `DEPTS_WITH_OWN_MODULE` ที่ตัดฝ่ายซึ่งมีโมดูลของตัวเอง
ออกจากคิวรวม — เพิ่มชื่อฝ่ายที่เดียว ทั้งสองจอตามเอง

**2 · ใบคำร้องยังเป็นจอเดียวสำหรับสองฝั่ง** (ม-31)
`/requests/[id]` ไม่แยกตามฝ่าย — **ปุ่มย้ายตามคนดู** เท่านั้น
แยกที่ *คิว* ไม่แยกที่ *ใบ* · แยกใบเมื่อไรก็ได้สองก้อนที่เพี้ยนหากันในสามเดือน

**3 · ทุกระบบต้องมีแถบเมนูของตัวเอง**
ระบบใน `config/systems.js` ต้องมีกลุ่มเมนูคู่กันใน `AppLayout.allGroups`
ไม่มีกลุ่ม = `menuItems` ว่าง = ผู้ใช้เข้าระบบมาแล้วไม่มีทางไปหน้าอื่นเลย

**4 · เส้นทางใหม่ต้องลงทะเบียนใน `OPEN_PAGES`** (`webapp/src/proxy.js`)
default-deny — ไม่ลงทะเบียน = ฝ่ายเจ้าของโมดูลถูกเด้งกลับ `/home` เงียบ ๆ
และ **แอดมินไม่มีวันเจอบั๊ก** เพราะผ่านตั้งแต่บรรทัดแรกของ `lockedOut`

**5 · การ์ดระบบขึ้นกับ *ฝ่าย* ไม่ใช่ role** (ม-48)
`departmentOf(user) === 'RD'` ไม่ใช่ `canAnswerRequestsFor` — ตัวหลังให้ `isSuperuser`
ผ่านหมด ซึ่งรวมหัวหน้าฝ่ายขาย ⇒ หัวหน้าฝ่ายขายจะได้การ์ดระบบ R&D ทั้งที่ไม่ใช่บ้านของเขา

**6 · ฐานข้อมูลเป็นของกลาง เจ้าของทะเบียนเป็นของฝ่าย** (ม-30)
ทะเบียนกลิ่น/สูตรอยู่ `/database` เพราะเป็นข้อมูลกลาง — **RD เขียน ฝ่ายอื่นอ่าน**
*"มันก็เป็นฐานข้อมูลกลางนะ แค่มาจาก RD"*

**7 · เมนู = "งานที่ฝ่ายนี้ทำ" ไม่ใช่ "ทุกอย่างที่เขาอ่านได้"** (มติ 2026-08-13)
ฝ่ายบัญชีเคยเห็นเมนูใต้ "บริหารงานขาย" ครบทั้งชุดเพราะถือ `salesplan:view` ซึ่ง
**ไม่เคยมีใครตัดสิน — มันติดมากับ cap** · ตัดเหลือเอกสารที่เขาต้องเปิดจริง
(ใบเสนอราคา · ใบสั่งขาย · คำร้อง) ผ่าน `worksInSalesPipeline()`

| เมนู | FN | เหตุผล |
|---|---|---|
| ใบสั่งขาย | ✅ | ขั้นบัญชีอยู่บนใบนี้ |
| ใบเสนอราคา | ✅ | แผนชำระ ยอด และ VAT ที่ต้องตรวจอยู่บน QT |
| คำร้อง | ✅ | ตอบคำร้องเอกสารการเงิน (`REQUEST_ANSWER_DEPARTMENTS` มี FN) |
| แดชบอร์ดยอดขาย · งานของฉัน · ดีล · โครงการ | ❌ | งานของฝ่ายขายล้วน ๆ |

⚠️ **ตัดที่ `visible` ไม่ใช่ที่ `cap`** — cap คุมสิทธิ์อ่านซึ่งยังต้องเปิด (กดลิงก์จากใบ
ไปดีล/โครงการยังต้องเข้าได้) และ view scope ยังเป็น `'all'` ตามที่ต้องใช้ตรวจใบ
⚠️ **ไม่แตะ RD ซึ่งกว้างเท่ากัน** — ของ RD เป็น**มติที่ตัดสินไว้แล้ว**
(`salesPlanningViewScope`: *"rd ต้องเห็นดีล/โครงการทุกทีมเพื่อมีบริบทเต็มตอนตอบข้อสอบถาม
จากฝ่ายขาย"*) ส่วนของ FN เป็นผลพลอยได้ ⇒ **สองอย่างนี้ไม่เหมือนกัน อย่ายุบเป็นกฎเดียว**

**8 · ปลายทางของการ์ดระบบต้องเป็นหน้าที่อยู่ในเมนูของคนคนนั้น**
ไม่งั้นกดการ์ดแล้วไปยืนบนหน้าที่แถบเมนูไม่ไฮไลต์อะไรเลย · FN กด "บริหารงานขาย" แล้วลงที่
`/sa/sales-orders` ไม่ใช่แดชบอร์ดยอดขาย (ล็อกไว้ใน `config/systems.test.mjs`)

**9 · เปลือกของเอกสารร่วมเดินตาม *คนดู* ไม่ใช่ตาม URL** (มติผู้ใช้ 2026-08-22)

> *"วิจัยและพัฒนา กับ การเงินและบัญชี พอกดเข้าไป บ้างอย่างมันรูทเข้าไปที่บริหารงานขาย
> ซึ่งอยากให้แต่ละฝ่ายทำงานเฉพาะของโมดูลตัวเอง โดยให้ส่วนข้อมูลกลางเดียวกัน"*

กฎข้อ 1–8 ถูกทั้งหมด แต่มีรูโหว่ที่ **เปลือก**: `systemForPathname()` รู้จักแต่ URL
⇒ ใบสั่งขายหนึ่งใบมีคนเปิดสามฝ่าย แต่แมปเป็นเปลือกเดียวคือ "บริหารงานขาย" เสมอ

| ก่อน | หลัง |
|---|---|
| FN กดใบจากทะเบียนการชำระ → เปลือกสลับเป็นงานขาย เมนู `/finance/*` หายจากจอ | เปลือกยังเป็น "บัญชีและการเงิน" เมนูบ้านตัวเองอยู่ครบ |
| RD กดใบคำร้องจากคิว → เปลือกสลับเป็นงานขาย | เปลือกยังเป็น "วิจัยและพัฒนา" |
| เดินผ่านหนึ่งครั้ง `ss:last-system` ถูกเขียนทับถาวร ⇒ การ์ด "ทำงานต่อ" และ `/notifications` `/account` พาไปบ้านฝ่ายขายตามไปหมด | เขียนเฉพาะระบบที่คนคนนั้นเข้าถึงได้จริง |

**สิ่งที่ไม่เปลี่ยนเลย** — route · API · ด่านสิทธิ์ · โมดัล · ที่เก็บเอกสาร
(กฎข้อ 3 "ด่านเดียว" ยังอยู่ครบ · ไม่มีการโคลนใบหรือคิวตามข้อห้าม ม-31/ม-34)

**ของจริงในโค้ด**

| ชิ้น | ที่ | หน้าที่ |
|---|---|---|
| `homeSystemForUser()` | `lib/permissions.js` | ฝ่าย → บ้าน (RD→`rd` · FN→`finance` · อื่น→`null`) **คู่กับด่านของโมดูลเสมอ** ไม่งั้นได้เปลือกที่ไม่มีกลุ่มเมนู |
| `ADOPTED_SHARED_PATHS` | `config/navigation.js` | เส้นทางที่ฝ่ายนั้น "รับไปทำงานในบ้านตัวเอง" |
| `SHARED_DOC_ITEMS` | `components/AppLayout.js` | นิยามเมนูเอกสารร่วม **ประกาศครั้งเดียว** ใช้ได้หลายกลุ่ม |
| `sharedItemBelongsInGroup()` | `config/navigation.js` | เมนูเอกสารร่วมขึ้นได้ **กลุ่มเดียวต่อคน** เสมอ |

⚠️ **RD/FN ไม่มีเมนูคิวรวม "คำร้อง" ในโมดูลตัวเอง** (มติผู้ใช้ 2026-08-22:
*"บัญชี กับ RD ไม่มีที่ต้องเปิดเอง มีแต่ SA ที่ต้องเปิดมาหา"*) ⇒ แท็บ "ที่ฉันเปิด"
ของคิวรวมว่างเปล่าตลอดกาลสำหรับเขา · ใบคำร้องที่เขาเปิดจากคิวฝ่ายจึงไฮไลต์ที่
**"คิวคำร้อง"** โดยให้ `match` ของเมนูนั้นกิน `/requests/[id]` ด้วย
⇒ เมนูที่ครอบเส้นทางที่รับมา **เป็นเมนูของฝ่ายเองก็ได้ ไม่จำเป็นต้องเป็นรายการเอกสารร่วม**

⚠️ **รับเส้นทางมาแล้วต้องมีเมนูคู่กันเสมอ** (= กฎข้อ 8) — ไม่งั้นยืนบนหน้าที่แถบเมนู
ไม่ไฮไลต์อะไรเลย · `config/navigation.test.mjs` มี ratchet คุมคู่นี้แล้ว

⚠️ **ดีล · โครงการ · แดชบอร์ด · งานของฉัน ไม่ถูกรับไปบ้านใคร** — กฎข้อ 7 ตัดสินแล้วว่า
ไม่ใช่เมนูของ FN ส่วน RD เปิดดูเพื่อ *บริบทตอนตอบคำร้อง* ไม่ใช่งานประจำ ⇒ ยังเป็น
เปลือกงานขายตามเดิม กดจากลิงก์บนใบได้เหมือนเดิมทุกอย่าง

⚠️ **ผลที่ตามมา: ฝ่ายบัญชีไม่มีการ์ด "บริหารงานขาย" อีกแล้ว** — เอกสารสี่ชนิดของเขา
(ใบเสนอราคา · ใบสั่งขาย · สัญญา · คำร้อง) ย้ายเข้ากลุ่มเมนูของ `/finance` หมดแล้ว
การ์ดจึงเหลือศูนย์รายการ · **ไม่ได้เสียเมนูใดเลย ไม่ได้เสีย cap ใดเลย** — ตัดที่ `visible`
เหมือนกฎข้อ 7 เป๊ะ ๆ

### RD ตามมาเป็นฝ่ายที่สอง (มติผู้ใช้ 2026-08-29)

> *"ระบบวิจัยและพัฒนา ควรโชว์ SO ที่เกี่ยวข้องในโมดูลด้วยมั้ย และควรปิดระบบบริหาร
> งานขายไม่ให้ RD เข้าไป คล้าย ๆ FN ทำงานเฉพาะบัญชีและการเงิน"*

| | ก่อน | หลัง |
|---|---|---|
| การ์ด/เมนู "บริหารงานขาย" ของ RD | ภาพรวม · ดีล · โครงการ · งานของฉัน | ไม่มีการ์ด (เหมือน FN) |
| ใบสั่งขายที่ฝ่ายต้องดู | กดจากลิงก์บนใบคำร้องทีละใบ | เมนู **"ใบสั่งขายที่เกี่ยวข้อง"** ใน `/rd` |
| `ADOPTED_SHARED_PATHS.rd` | `['/requests']` | `+ /sa/sales-orders` · `/sales-planning/sales-orders` |

**ทำไมสองข้อนี้ต้องมาคู่กัน** — ปิดเมนูงานขายโดยไม่ให้ที่ดูใบสั่งขายในบ้านตัวเอง
= ฝ่ายเหลือทางเดียวคือเปิดทีละใบจากคำร้อง · และรับเส้นทางใบสั่งขายเข้าบ้านโดยไม่มีเมนู
คู่กัน = ผิดกฎข้อ 8 ทันที (เจอจริงตอน UAT: กดใบจากคิวแล้วเปลือกสลับไป "บริหารงานขาย"
ซึ่งเป็นระบบที่เขาไม่มีกลุ่มเมนูอีกแล้ว = แถบว่าง)

⚠️ **"ใบสั่งขายที่เกี่ยวข้อง" ไม่ใช่ทะเบียนใบสั่งขาย** — หน้านี้แสดงเฉพาะใบที่คำร้องของ
ฝ่ายอ้างถึงจริง (15 ใบจาก 99 ใบทั้งระบบ ณ วันทำ) · เอกสารยังเป็นของฝ่ายขายตามชั้น 2
และ server ไม่ส่งราคาต่อหน่วย/ยอดรวมมาให้เลย — ตัดที่ payload ไม่ใช่ซ่อนที่จอ

⚠️ **ตัวตัดสินเปลี่ยนจาก "ชื่อฝ่าย" เป็น "มีบ้านของตัวเองไหม"** — `worksInSalesPipeline`
กับการ์ด `salesplan` เคยเขียน `!== 'FN'` / `!== 'finance'` ตรง ๆ ⇒ ฝ่ายที่สามจะตกหล่น
ตอนนี้ทั้งคู่ถาม `homeSystemForUser(user) === null` ซึ่งเป็นตัวเดียวกับที่เลือกเปลือก
