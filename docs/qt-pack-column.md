## ทำไม

มติเจ้าของ 08/10/2026: รายการหมวด **02-001** (ระบบกระจายกลิ่น SDS) ในใบเสนอราคาต้องมีคอลัมน์ **"แพ็ค/เดือน"** และ

```
จำนวนเงินของรายการ = แพ็ค × จำนวน × ราคา   แล้วหักส่วนลดรายการตามเดิม
ตัวอย่าง: 2 แพ็ค × 12 เดือน × ฿3,500 = ฿84,000
```

วันนี้ฝ่ายขายคูณเองแล้วพิมพ์ผลลงช่องจำนวน (เช่น 172 = 43 สาขา × 4 เดือน) — ตัวเลขบนใบจึงอ่านไม่ออกว่าขายกี่แพ็คกี่เดือน
และตาราง "งานบริการ" ของใบสั่งขายต้องถามซ้ำอีกรอบ

## กฎเงินของบรรทัด (ที่เดียวของทั้งระบบ)

| | JS — `quoteLineNet` (`lib/salesPlanning.js`) | ฐาน — CHECK `*_line_money_rule` (mig 0407) |
|---|---|---|
| คูณ | `packFactorOf(packQty) × qty × unitPrice` (floating point) | `COALESCE("packQty", 1) * qty * "unitPrice"` (numeric แท้) |
| ปัด | **ครั้งเดียว** หลังคูณครบสามตัว (ห้ามปัดต่อหน่วยแล้วคูณ) | `round(…, 2)` ครั้งเดียว |
| ส่วนลด | คิดจากยอดก่อนลดทั้งรายการ · บาทไม่คูณแพ็ค | ไม่คิดใหม่ — ลบ `"discountAmount"` ที่เก็บไว้ |
| ผล | `lineTotal` | `abs("lineTotal" − ผลข้างบน) <= 0.01` |

- `packFactorOf`: เลขแพ็คที่ใช้ได้ (จำนวนเต็ม 1–9999) นอกนั้น **1** — ว่างและค่าผิดรูปคูณ 1 เสมอ ไม่มีวันเป็น 0 หรือเศษส่วน
  (ห้ามใช้ `toMoney` กับเลขแพ็ค: `toMoney('0', 1)` = 0 · `toMoney('1.5', 1)` = 1.5)
- บรรทัดที่ไม่มีเลขแพ็คได้ยอดเดิม **ทุกบิต** (คูณ 1 ใน floating point ไม่เปลี่ยนค่า)
- ค่าคลาด 0.01 จำเป็นจริง: ผลคูณที่ลงครึ่งสตางค์พอดี JS กับฐานปัดต่างกันได้ 1 สตางค์ (3 × 1.5 × 33.33 → JS 149.98 · ฐาน 149.99)
- **จุดบอดของ CHECK** (จดไว้ในชุดตัวอย่าง): เลขแพ็ค **1** ที่หายระหว่างทางก๊อป (ยอดไม่เปลี่ยน) และยอดที่เพี้ยน 1 สตางค์ — คนเห็นคือยามทางก๊อปกับสคริปต์เทียบ
- **เพดาน**: บรรทัดที่ยอดเกินราว 3 × 10¹³ บาท ฐานปฏิเสธด้วย 23514 (double เก็บสตางค์ไม่ได้แล้ว) — มีผลกับโค้ดรุ่นเดิมด้วยตั้งแต่รัน 0407 · ห่างจากบรรทัดจริงแปดหลัก
- ชุดตัวอย่างเดียวของสองฝั่ง: `webapp/src/lib/sales/quoteLinePackFixtures.json` (rule 20 · stored 9 · typing 19) — ไฟล์ 0407 ตรวจในตัว (§3) และ
  `quoteLinePackRule.test.mjs` เทียบสูตร JS กับนิพจน์ของ CHECK แบบทศนิยมแท้

### กฎของเซิร์ฟเวอร์ (ช่องปิด)

**เซิร์ฟเวอร์ไม่แก้เลขแพ็คเอง** — รับบรรทัดตามที่ส่งมา หรือปฏิเสธคำขอพร้อมข้อความไทยที่บอกเลขรายการ · ไม่ตัดคีย์ทิ้ง ไม่เก็บ `NULL` แทนตัวเลข ไม่คิดยอดใหม่โดยไม่มีตัวเลข
ขณะ `QUOTE_PACK_INPUT_OPEN` เป็น `false` **เลขแพ็คทุกค่าถูกปฏิเสธ (ค่าที่ถูกต้องด้วย)** · `null` / ไม่มีคีย์ / ว่าง ไม่ใช่เลขแพ็ค ผ่านเสมอ
(หลังรัน 0407 ทุกบรรทัดที่ API คืนมี `packQty: null` และจอส่งกลับมาทั้งก้อน)

| ทาง | กฎกัดตรงไหน |
|---|---|
| สร้างใบ (`POST deals/[id]/quotations` · สายสหมิตร) | `createQuotationDraft`: ตัว normalize โยน → 400 · ด่านบนบรรทัดชุดสุดท้าย — ก่อนออกเลขใบ |
| แก้ใบพร้อมบรรทัด (`PATCH quotations/[id]`) | ตัว normalize โยน → 400 — ไม่เรียก RPC |
| แก้แค่ VAT / ส่วนลดท้ายใบ (ส่งบรรทัดที่เก็บไว้กลับไปทั้งก้อน ไม่ผ่านตัว normalize) | ด่าน `linePackIssues(newLines)` หลัง sync ราคา — ด่านเดียวของทางนี้ |
| ออก Rev. (`POST quotations/[id]/revise`) | ตัว normalize โยน → 400 · ด่านบนบรรทัดของฉบับใหม่ — ก่อนสร้างแถวใด ๆ |

ด่านสุดท้ายที่ไม่พึ่ง JS: CHECK สองตัวของฐาน → 23514 → `ยอดของรายการไม่ตรงกับสูตร แพ็ค × จำนวน × ราคา — ยังไม่ได้บันทึก แจ้งผู้ดูแลระบบ`

### ลายนิ้วมือการอนุมัติและฉบับตรึง

canonical JSON เก็บค่า `null` ไว้ ⇒ คีย์ `packQty` ต้อง **ไม่มี** เมื่อบรรทัดไม่มีเลขแพ็ค — ไม่งั้นลายนิ้วมือของใบที่อนุมัติแล้วทุกใบเปลี่ยนพร้อมกัน
เลขแพ็ค 1 ≠ ไม่มีเลขแพ็ค (เอกสารคนละหน้าตา จึงเป็นลายนิ้วมือคนละค่า) · ฉบับตรึงของใบเสนอราคาฝังเนื้อหาเดียวกันจึงได้กฎนี้ไปด้วย
ฉบับตรึงของใบสั่งขายมีรายการคีย์ของตัวเอง — ยังไม่แตะ (งวด PR-2 พร้อมกระดาษ) · ยาม: `approvalFingerprintGolden.test.mjs` (ค่าทองจับก่อนแก้โค้ด)

### ช่องสำหรับเทสต์ (`packInputOpen`) — ไม่ใช่สวิตช์

`normalizeManualLines` · `buildQuotationRevisionContent` · `createQuotationDraft` รับ `packInputOpen` (ค่าตั้งต้น = `QUOTE_PACK_INPUT_OPEN`)
เพื่อให้เทสต์พิสูจน์ว่าเลขแพ็ค (รวมเลข 1) เดินครบทุกทอดขณะ production ยังปิด · **ห้ามมีไฟล์ใน `src/` นอกเทสต์ส่งค่านี้** และ route ไม่มีช่องนี้เลย
(ยามซอร์ส `linePackWritePaths.test.mjs`) — เปิดช่องจริงมีทางเดียวคือแก้ค่าคงที่

สองเส้นทาง (PATCH ใบ · ออก Rev.) ไม่มีช่องสำหรับเทสต์ จึงทดสอบอีกท่า: `linePackRoutes.test.mjs` เรียก **ตัว handler จริง** กับฐานปลอม และ "เปิดช่อง"
ด้วยการจำลองการแก้ค่าคงที่ — resolve hook ของไฟล์เทสต์ห่อ `@/lib/sales/linePacks` ให้สวิตช์เป็นค่าที่สลับได้ (เฉพาะโปรเซสของไฟล์เทสต์นั้น)
⇒ โค้ดของแอปต้อง import `linePacks` ผ่าน `@/lib/sales/linePacks` เท่านั้น (เทสต์เดียวกันยึด)

## ลำดับ deploy ของงวด PR-1

1. ทุกด่านในเครื่องเขียว · แบรนช์อยู่บน `main` ล่าสุด · ตรวจว่าเลข **0407** ยังว่าง (`origin/main` + PR ที่เปิดอยู่)
2. **เจ้าของ ที่ SQL Editor ก่อน merge** ทีละบล็อก: SELECT ตรวจก่อนรัน → เทียบค่าที่คาด (มีเงื่อนไข "อย่ารัน" ข้อไหนเข้า = หยุด) → ทั้งไฟล์ 0407 → SELECT ตรวจหลังรัน
   โค้ดรุ่นที่รันอยู่ใช้ต่อได้ทันทีไม่ต้อง freeze: ไม่มีทางเขียนไหนของมันส่งเลขแพ็ค แถวใหม่ได้ `NULL` และ CHECK รับสิ่งที่มันเขียน
3. CI รันใหม่ → merge → Deploy to production
   (`check:columns` **แดงเฉพาะ** `quotation_lines.packQty` / `sales_order_lines.packQty` จาก `linePackParity.js` จนกว่าจะรัน 0407 — อย่างอื่นแดง = บั๊กจริง)
4. อ่านอย่างเดียว จากโฟลเดอร์ `webapp`: `node --import ./scripts/test-loader.mjs scripts/check-line-pack-parity.mjs` → ต้องจบด้วย `✓ ไม่มีจุดต่าง` (exit 0)
   ใส่จำนวนของรอบก่อน merge ต่อท้าย (`--expect-min-lines=…` `--expect-min-fingerprints=…` — สคริปต์พิมพ์ให้ท้ายผลทุกรอบ) เพื่อให้ "อ่านได้น้อยลง" เป็น exit 1

โค้ดใหม่ขึ้นก่อน migration ก็ไม่พัง (ไม่มีคำขอไหนเอ่ยชื่อคอลัมน์เมื่อไม่มีเลขแพ็ค) แต่ merge ไม่ได้อยู่แล้วเพราะ CI แดง
