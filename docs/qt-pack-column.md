## ทำไม

มติเจ้าของ 08/10/2026: รายการหมวด **02-001** (ระบบกระจายกลิ่น SDS) ในใบเสนอราคาต้องมีคอลัมน์ **"แพ็ค/เดือน"** และ

```
จำนวนเงินของรายการ = แพ็ค × จำนวน × ราคา   แล้วหักส่วนลดรายการตามเดิม
ตัวอย่าง: 2 แพ็ค × 12 เดือน × ฿3,500 = ฿84,000
```

วันนี้ฝ่ายขายคูณเองแล้วพิมพ์ผลลงช่องจำนวน (เช่น 172 = 43 สาขา × 4 เดือน) — ตัวเลขบนใบจึงอ่านไม่ออกว่าขายกี่แพ็คกี่เดือน
และตาราง "งานบริการ" ของใบสั่งขายต้องถามซ้ำอีกรอบ

## กฎเงินของบรรทัด (ที่เดียวของทั้งระบบ)

| | JS — `quoteLineNet` (`lib/salesPlanning.js`) | ฐาน — CHECK `*_line_money_rule` (mig 0407) |
|---|---|---|
| คูณ | `packFactorOf(packQty) × qty × unitPrice` (floating point) | `COALESCE("packQty", 1) * qty * "unitPrice"` (numeric แท้) |
| ปัด | **ครั้งเดียว** หลังคูณครบสามตัว (ห้ามปัดต่อหน่วยแล้วคูณ) | `round(…, 2)` ครั้งเดียว |
| ส่วนลด | คิดจากยอดก่อนลดทั้งรายการ · บาทไม่คูณแพ็ค | ไม่คิดใหม่ — ลบ `"discountAmount"` ที่เก็บไว้ |
| ผล | `lineTotal` | `abs("lineTotal" − ผลข้างบน) <= 0.01` |

- `packFactorOf`: เลขแพ็คที่ใช้ได้ (จำนวนเต็ม 1–9999) นอกนั้น **1** — ว่างและค่าผิดรูปคูณ 1 เสมอ ไม่มีวันเป็น 0 หรือเศษส่วน
  (ห้ามใช้ `toMoney` กับเลขแพ็ค: `toMoney('0', 1)` = 0 · `toMoney('1.5', 1)` = 1.5)
- บรรทัดที่ไม่มีเลขแพ็คได้ยอดเดิม **ทุกบิต** (คูณ 1 ใน floating point ไม่เปลี่ยนค่า)
- ค่าคลาด 0.01 จำเป็นจริง: ผลคูณที่ลงครึ่งสตางค์พอดี JS กับฐานปัดต่างกันได้ 1 สตางค์ (3 × 1.5 × 33.33 → JS 149.98 · ฐาน 149.99)
- **จุดบอดของ CHECK** (จดไว้ในชุดตัวอย่าง): เลขแพ็ค **1** ที่หายระหว่างทางก๊อป (ยอดไม่เปลี่ยน) และยอดที่เพี้ยน 1 สตางค์ — คนเห็นคือยามทางก๊อปกับสคริปต์เทียบ
- **เพดาน**: บรรทัดที่ยอดเกินราว 3 × 10¹³ บาท ฐานปฏิเสธด้วย 23514 (double เก็บสตางค์ไม่ได้แล้ว) — มีผลกับโค้ดรุ่นเดิมด้วยตั้งแต่รัน 0407 · ห่างจากบรรทัดจริงแปดหลัก
- ชุดตัวอย่างเดียวของสองฝั่ง: `webapp/src/lib/sales/quoteLinePackFixtures.json` (rule 20 · stored 9 · typing 19) — ไฟล์ 0407 ตรวจในตัว (§3) และ
  `quoteLinePackRule.test.mjs` เทียบสูตร JS กับนิพจน์ของ CHECK แบบทศนิยมแท้

**เซิร์ฟเวอร์ไม่แก้เลขแพ็คเอง** — รับบรรทัดตามที่ส่งมา หรือปฏิเสธคำขอพร้อมข้อความไทยที่บอกเลขรายการ · ไม่ตัดคีย์ทิ้ง ไม่เก็บ `NULL` แทนตัวเลข ไม่คิดยอดใหม่โดยไม่มีตัวเลข
ขณะ `QUOTE_PACK_INPUT_OPEN` เป็น `false` **เลขแพ็คทุกค่าถูกปฏิเสธ (ค่าที่ถูกต้องด้วย)** · `null` / ไม่มีคีย์ / ว่าง ไม่ใช่เลขแพ็ค ผ่านเสมอ
(หลังรัน 0407 ทุกบรรทัดที่ API คืนมี `packQty: null` และจอส่งกลับมาทั้งก้อน)

## ลำดับ deploy ของงวด PR-1

1. ทุกด่านในเครื่องเขียว · แบรนช์อยู่บน `main` ล่าสุด · ตรวจว่าเลข **0407** ยังว่าง (`origin/main` + PR ที่เปิดอยู่)
2. **เจ้าของ ที่ SQL Editor ก่อน merge** ทีละบล็อก: SELECT ตรวจก่อนรัน → เทียบค่าที่คาด (มีเงื่อนไข "อย่ารัน" ข้อไหนเข้า = หยุด) → ทั้งไฟล์ 0407 → SELECT ตรวจหลังรัน
   โค้ดรุ่นที่รันอยู่ใช้ต่อได้ทันทีไม่ต้อง freeze: ไม่มีทางเขียนไหนของมันส่งเลขแพ็ค แถวใหม่ได้ `NULL` และ CHECK รับสิ่งที่มันเขียน
3. CI รันใหม่ → merge → Deploy to production
   (`check:columns` **แดงเฉพาะ** `quotation_lines.packQty` / `sales_order_lines.packQty` จาก `linePackParity.js` จนกว่าจะรัน 0407 — อย่างอื่นแดง = บั๊กจริง)
4. อ่านอย่างเดียว จากโฟลเดอร์ `webapp`: `node --import ./scripts/test-loader.mjs scripts/check-line-pack-parity.mjs` → ต้องจบด้วย `✓ ไม่มีจุดต่าง` (exit 0)
   ใส่จำนวนของรอบก่อน merge ต่อท้าย (`--expect-min-lines=…` `--expect-min-fingerprints=…` — สคริปต์พิมพ์ให้ท้ายผลทุกรอบ) เพื่อให้ "อ่านได้น้อยลง" เป็น exit 1

โค้ดใหม่ขึ้นก่อน migration ก็ไม่พัง (ไม่มีคำขอไหนเอ่ยชื่อคอลัมน์เมื่อไม่มีเลขแพ็ค) แต่ merge ไม่ได้อยู่แล้วเพราะ CI แดง

### ใบเก่าที่บรรทัดหมวด 02-001 ไม่มีเลขแพ็ค (มติ A4 "เมื่อแก้หรือออก Rev.")

1. เปิดแก้: ช่องว่าง · ยอดที่เก็บไว้ยังโชว์ · บรรทัดคำแนะนำเหนือตาราง (ไม่แดง): `รายการหมวด 02-001 ของใบนี้บันทึกไว้ก่อนมีช่อง “แพ็ค/เดือน” — แยกจำนวนเดิมเป็น แพ็ค × เดือน ให้ยอดเท่าเดิม (เช่น 24 = 2 แพ็ค × 12 เดือน)`
2. กดบันทึกโดยยังไม่กรอก: ไม่ส่งคำขอ · แถวแดง · ข้อความบอกเลขรายการ — แม้แก้แค่ VAT (เซิร์ฟเวอร์ปฏิเสธคำขอนั้นอยู่แล้ว)
3. แยกจำนวน `172` → `43 × 4`: แก้จำนวนเป็น 4 ก่อน = ยอดเป็นขีด + `ยอดเดิม ฿498,800.00` · กรอก 43 = `฿498,800.00` + `43 × 4 × 2,900.00` (ยอดเดิมหายเพราะเท่ากันแล้ว)
4. แยกผิด (แพ็ค 2 แต่จำนวนยัง 24): `฿153,600.00` · `2 × 24 × 3,500.00` · `ยอดเดิม ฿69,600.00` อยู่ใต้กัน
5. โมดัลยืนยันบันทึกของใบแบบนี้บอกผลต่อยอดรวมทั้งสิ้น: `ยอดรวมทั้งสิ้นเท่าเดิม ฿…` หรือ `ยอดรวมทั้งสิ้นเปลี่ยนจาก ฿… เป็น ฿…` (ไม่มีประโยคนี้เมื่อ **จอสัญญายอดไม่ได้** — เซิร์ฟเวอร์คิดราคาใหม่จากทะเบียนตอนบันทึกเสมอ: มีแถวที่ขึ้นคำเตือนราคาทะเบียนขยับ **หรือจอไม่รู้ราคาทะเบียนของสินค้าบนแถว**
   (`masterPriceUncertain` — สินค้าไม่อยู่ในลิสต์ของหน้า: แก้ข้อมูลสินค้าแม้ครั้งเดียวสถานะกลับเป็นรออนุมัติและหลุดจากลิสต์ ซึ่งก็คือตอนที่ราคาเพิ่งถูกแก้)
   🐞 รีวิว 09/10: เดิมดูแค่ราคาขยับที่จอเห็น — ใบ `172 × 2,900` ที่ทะเบียนถูกแก้เป็น 3,100 ได้โมดัล `ยอดรวมทั้งสิ้นเท่าเดิม ฿533,716.00` แล้วเซิร์ฟเวอร์บันทึก `43 × 4 × 3,100` ยอดรวม 570,524)
6. ออก Rev. ของใบแบบนี้: ไม่ถูกกั้น (ก๊อปบรรทัดตามที่เป็น `NULL` ยัง `NULL`) · โมดัลบอกก่อนกด: `ฉบับใหม่ต้องกรอก “แพ็ค/เดือน” ของรายการหมวด 02-001 ก่อนยื่นอนุมัติ` · ร่างฉบับใหม่ถูกด่านทักตอนบันทึก/ยื่น
7. ระบบไม่เดาเลขให้ทุกกรณี — กรอกแพ็ค 1 คงจำนวนที่พับไว้ก็ผ่าน (ยอดเท่าเดิม แต่กระดาษจะอ่านว่า 172 เดือน) · คนตรวจคือคำแนะนำ หน่วย "เดือน" และผู้อนุมัติ จนงวด PR-4

## ยังไม่ได้พิสูจน์ / ต้องระวัง

- เนื้อและสิทธิ์ของสามฟังก์ชันบนฐานจริงอ่านผ่าน PostgREST ไม่ได้ — ด่านคือ SELECT ตรวจก่อนรันของเจ้าของ (anchor เจ็ดตัว = 1 · `bodies = ttt` · `anon = f` · `svc = t`)
- เส้นทาง PATCH และออก Rev.: `linePackRoutes.test.mjs` เรียก **ตัว handler จริง** กับฐานปลอมในหน่วยความจำ ครอบกิ่งที่แตะบรรทัด · ยอด · เลขแพ็ค
  (กิ่งที่อยู่/ผู้ติดต่อ/metadata ไม่อยู่ในเทสต์นี้) · ตัวกลายพันธุ์ 28 ตัวของสองไฟล์นี้ + ตัวสร้างใบ แดงทุกตัว — รวมเก้าตัวของรีวิว 08/10 · **ที่ยังไม่ได้พิสูจน์** คือรอยต่อกับของจริง: คำขอที่ PostgREST สร้างจากแถวที่ส่ง และ RPC บนฐานจริง
  (ฝั่ง SQL พิสูจน์แยกบนฮาร์เนส PGlite · ไม่มีเทสต์ที่ยิงจาก route ถึงฐานจริง เพราะ dev DB = prod DB ห้ามเขียน)
- (งวด PR-1 / PR-2) "ช่องเปิด" ของเทสต์เส้นทางคือการจำลองค่าคงที่ — **งวด PR-3 เปลี่ยนค่าคงที่จริงแล้ว** เทสต์ช่องปิด 16 ตัวถูกย้ายโดยเจตนา (ไม่มีตัวไหนถูกลบ) และตัวจำลองกลับด้าน:
  วันนี้มันใช้รัน **กิ่งปิด** = คำตอบของรุ่น PR-1 / PR-2
- งวด PR-3: รอยต่อ "หน้าจริง → handler จริง → SQL จริง" ถูกปิดด้วยการเล่นซ้ำ ไม่ใช่ด้วยการยิงฐานจริง — คำขอที่หน้าตัวจริงส่ง (สร้าง · บันทึกแยกจำนวน · ออก Rev.) ถูกอัดไว้แล้วป้อน handler ตัวจริง
  บนฐานในหน่วยความจำ และ payload ที่ handler ส่งถูกป้อน SQL ตัวจริงบน PGlite · **ที่ยังไม่ได้พิสูจน์เหมือนเดิม**: คำขอที่ PostgREST สร้างจากแถว และ RPC บนฐานจริง — ใบแพ็คใบแรกของจริงต้องถูกเฝ้าดูแบบอ่านอย่างเดียว (เช็กลิสต์ข้อ 2)
- งวด PR-3: จอพิสูจน์ด้วย bundle ของ **หน้าตัวจริง** ใน Chrome headless กับหลังบ้านจำลองที่ประกอบจากตัวตัดสินตัวจริง — ไม่มี Next router (ใช้ตัวแทนที่เปลี่ยน path / query ในที่) ไม่มี dev server
  ไม่มีการกดบนฐานจริง · พฤติกรรมที่เป็นของ Next เอง (prefetch · การเปลี่ยนหน้าจริง) ไม่ได้ถูกพิสูจน์ · สายสหมิตรและเส้นสร้างใบสั่งขายไม่ได้ถูกรันเป็น handler (ยึดที่ระดับ lib + ยามซอร์ส)
- PostgREST กับ INSERT หลายแถวที่คีย์ไม่เท่ากันไม่ได้ลอง — `withPackColumn` ทำให้ทุกแถวมีคีย์ชุดเดียวกันจึงไม่ต้องตอบคำถามนี้
