## ทำไม

มติเจ้าของ 08/10/2026: รายการหมวด **02-001** (ระบบกระจายกลิ่น SDS) ในใบเสนอราคาต้องมีคอลัมน์ **"แพ็ค/เดือน"** และ

```
จำนวนเงินของรายการ = แพ็ค × จำนวน × ราคา   แล้วหักส่วนลดรายการตามเดิม
ตัวอย่าง: 2 แพ็ค × 12 เดือน × ฿3,500 = ฿84,000
```

วันนี้ฝ่ายขายคูณเองแล้วพิมพ์ผลลงช่องจำนวน (เช่น 172 = 43 สาขา × 4 เดือน) — ตัวเลขบนใบจึงอ่านไม่ออกว่าขายกี่แพ็คกี่เดือน
และตาราง "งานบริการ" ของใบสั่งขายต้องถามซ้ำอีกรอบ

## กฎเงินของบรรทัด (ที่เดียวของทั้งระบบ)

| | JS — `quoteLineNet` (`lib/salesPlanning.js`) | ฐาน — CHECK `*_line_money_rule` (mig 0407) |
|---|---|---|
| คูณ | `packFactorOf(packQty) × qty × unitPrice` (floating point) | `COALESCE("packQty", 1) * qty * "unitPrice"` (numeric แท้) |
| ปัด | **ครั้งเดียว** หลังคูณครบสามตัว (ห้ามปัดต่อหน่วยแล้วคูณ) | `round(…, 2)` ครั้งเดียว |
| ส่วนลด | คิดจากยอดก่อนลดทั้งรายการ · บาทไม่คูณแพ็ค | ไม่คิดใหม่ — ลบ `"discountAmount"` ที่เก็บไว้ |
| ผล | `lineTotal` | `abs("lineTotal" − ผลข้างบน) <= 0.01` |

- `packFactorOf`: เลขแพ็คที่ใช้ได้ (จำนวนเต็ม 1–9999) นอกนั้น **1** — ว่างและค่าผิดรูปคูณ 1 เสมอ ไม่มีวันเป็น 0 หรือเศษส่วน
  (ห้ามใช้ `toMoney` กับเลขแพ็ค: `toMoney('0', 1)` = 0 · `toMoney('1.5', 1)` = 1.5)
- บรรทัดที่ไม่มีเลขแพ็คได้ยอดเดิม **ทุกบิต** (คูณ 1 ใน floating point ไม่เปลี่ยนค่า)
- ค่าคลาด 0.01 จำเป็นจริง: ผลคูณที่ลงครึ่งสตางค์พอดี JS กับฐานปัดต่างกันได้ 1 สตางค์ (3 × 1.5 × 33.33 → JS 149.98 · ฐาน 149.99)
- **จุดบอดของ CHECK** (จดไว้ในชุดตัวอย่าง): เลขแพ็ค **1** ที่หายระหว่างทางก๊อป (ยอดไม่เปลี่ยน) และยอดที่เพี้ยน 1 สตางค์ — คนเห็นคือยามทางก๊อปกับสคริปต์เทียบ
- **เพดาน**: บรรทัดที่ยอดเกินราว 3 × 10¹³ บาท ฐานปฏิเสธด้วย 23514 (double เก็บสตางค์ไม่ได้แล้ว) — มีผลกับโค้ดรุ่นเดิมด้วยตั้งแต่รัน 0407 · ห่างจากบรรทัดจริงแปดหลัก
- ชุดตัวอย่างเดียวของสองฝั่ง: `webapp/src/lib/sales/quoteLinePackFixtures.json` (rule 20 · stored 9 · typing 19) — ไฟล์ 0407 ตรวจในตัว (§3) และ
  `quoteLinePackRule.test.mjs` เทียบสูตร JS กับนิพจน์ของ CHECK แบบทศนิยมแท้

### กฎของเซิร์ฟเวอร์ (ช่องปิด)

**เซิร์ฟเวอร์ไม่แก้เลขแพ็คเอง** — รับบรรทัดตามที่ส่งมา หรือปฏิเสธคำขอพร้อมข้อความไทยที่บอกเลขรายการ · ไม่ตัดคีย์ทิ้ง ไม่เก็บ `NULL` แทนตัวเลข ไม่คิดยอดใหม่โดยไม่มีตัวเลข
ขณะ `QUOTE_PACK_INPUT_OPEN` เป็น `false` **เลขแพ็คทุกค่าถูกปฏิเสธ (ค่าที่ถูกต้องด้วย)** · `null` / ไม่มีคีย์ / ว่าง ไม่ใช่เลขแพ็ค ผ่านเสมอ
(หลังรัน 0407 ทุกบรรทัดที่ API คืนมี `packQty: null` และจอส่งกลับมาทั้งก้อน)

## ยังไม่ได้พิสูจน์ / ต้องระวัง

- เนื้อและสิทธิ์ของสามฟังก์ชันบนฐานจริงอ่านผ่าน PostgREST ไม่ได้ — ด่านคือ SELECT ตรวจก่อนรันของเจ้าของ (anchor เจ็ดตัว = 1 · `bodies = ttt` · `anon = f` · `svc = t`)
- เส้นทาง PATCH และออก Rev.: `linePackRoutes.test.mjs` เรียก **ตัว handler จริง** กับฐานปลอมในหน่วยความจำ ครอบกิ่งที่แตะบรรทัด · ยอด · เลขแพ็ค
  (กิ่งที่อยู่/ผู้ติดต่อ/metadata ไม่อยู่ในเทสต์นี้) · ตัวกลายพันธุ์ 28 ตัวของสองไฟล์นี้ + ตัวสร้างใบ แดงทุกตัว — รวมเก้าตัวของรีวิว 08/10 · **ที่ยังไม่ได้พิสูจน์** คือรอยต่อกับของจริง: คำขอที่ PostgREST สร้างจากแถวที่ส่ง และ RPC บนฐานจริง
  (ฝั่ง SQL พิสูจน์แยกบนฮาร์เนส PGlite · ไม่มีเทสต์ที่ยิงจาก route ถึงฐานจริง เพราะ dev DB = prod DB ห้ามเขียน)
- "ช่องเปิด" ของเทสต์เส้นทางคือการจำลองค่าคงที่ ไม่ใช่การแก้ไฟล์จริง — งวด PR-3 เปลี่ยนค่าคงที่แล้วต้องรันชุดเทสต์ทั้งชุดอีกรอบ (เทสต์ช่องปิดจะต้องถูกย้ายความคาดหวังโดยเจตนา)
- PostgREST กับ INSERT หลายแถวที่คีย์ไม่เท่ากันไม่ได้ลอง — `withPackColumn` ทำให้ทุกแถวมีคีย์ชุดเดียวกันจึงไม่ต้องตอบคำถามนี้
