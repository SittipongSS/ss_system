แบบหน้าจอ (ข้อมูลจริง 25/11): `~/ss-team/mockups/permissions-page/index.html` (เปิดผ่าน launch config `mockups` พอร์ต 4321)

แต่มติข้อ "สิทธิ์ตามตำแหน่งอยู่ในโค้ด" ข้างล่างต้องถูกนำไปพิจารณาตอนเริ่มเฟส 8

## ภาพตอนเริ่ม (วัด 25/11/2026 · main `f2c02424a` + ฐานจริง)

- **สิทธิ์หลัก:** 29 ตำแหน่ง · 14 ฝ่าย · 44 cap อยู่ใน `webapp/src/lib/permissions.js`
  - ตัวเช็ก `can*` / `is*` 53 ตัวแคบลงอีกชั้นตามฝ่าย ทีม และสถานะเอกสาร
  - มีจุดที่เช็ก `role ===` ตรง ๆ 130 จุด
- **สิทธิ์เสริม:** `app_metadata.extraCaps` แจกได้ 7 ตัว (`GRANTABLE_CAPS`)
  - เป็นแค่ช่องติ๊กท้ายโมดัลแก้ผู้ใช้ใน `/users`
  - ไม่มีบันทึกว่าใครให้ เมื่อไร หรือเพราะอะไร
- **บนฐานจริง:** 6 จาก 44 บัญชีถือสิทธิ์เสริม
  - admin 2 คน ถือสิทธิ์ที่ตำแหน่งมีอยู่แล้ว
  - AC 1 คน ถือ `mgmt:*` ซึ่งระบบปิดตั้งแต่ 13/11
  - RD coordinator 2 คน และ Senior AE 1 คน ถือ `ra:view` + `products:margin` ชุดนี้มีผลจริง
- **ด่านที่ถามแค่ตำแหน่ง ทำให้สิทธิ์เสริมไม่มีผล:**
  - `/api/tax/orders/queue` และ `/table` ใช้ `can(user.role, 'ra:view')` แต่จอ `/tax/filings` ใช้ `useCan` ⇒ จอเปิดตารางให้ แต่ API ตอบ 403
  - `customerHubData.js` ใช้ `seesRa`
  - ป้ายนับงานบริหารสองจุด
  - `canSeeProductCost(role)` ไม่มีโค้ดจริงเรียกใช้ แต่ถามแค่ตำแหน่ง จึงเป็นกับดักให้คนหยิบไปใช้

## มติเจ้าของ 2026-11-25 (ถามทีละข้อ)

0. **แนวทาง: ทาง A** — คงสิทธิ์ตามตำแหน่งไว้ในโค้ด **ไม่ย้ายไปฐานข้อมูลให้ติ๊กบนจอ**
   - เหตุผล: สิทธิ์จริงไม่ได้อยู่ที่ cap อย่างเดียว ยังมีตัวเช็กฝ่าย/ทีม 53 ตัว ตารางที่ติ๊กบนจอจึงจะไม่ตรงกับที่ระบบทำจริง
   - และเทสต์ยาม 31 ไฟล์จะตรวจตารางบนจอไม่ได้
1. **ที่อยู่:** รวมเป็นแท็บในหน้า `/users` — *"เป็นเรื่องเดียวกับผู้ใช้งาน เพราะกำหนดสิทธิ์ผู้ใช้ ทั้งรายคน รายตำแหน่ง สิทธิ์หลักสิทธิ์เสริม"*
   - แท็บ: รายชื่อผู้ใช้ · สิทธิ์ตามตำแหน่ง · สิทธิ์เสริมรายคน · ประวัติการให้สิทธิ์
2. **เหตุผล:** บังคับกรอกทุกครั้งที่ให้สิทธิ์เสริม
3. **หมดอายุ:** ต้องเลือกทุกครั้ง ไม่มีค่าตั้งต้น
   - ตัวเลือกคือ "ไม่มีกำหนด" หรือ "ถึงวันที่"
   - ครบวันแล้ว cron ถอดเอง และแจ้งกระดิ่งทั้งคนให้และคนถือ
4. **ช่องติ๊กเดิมในโมดัลแก้ผู้ใช้:** เหลือแค่สรุป (อ่านอย่างเดียว) กับปุ่ม "จัดการสิทธิ์เสริม"
   - การให้สิทธิ์จึงมีทางเดียว ข้ามช่องเหตุผลไม่ได้
5. **ใครเห็น:** แอดมินแก้ได้ · คนถือ `users:view` เห็นทุกแท็บแบบอ่านอย่างเดียว (ไม่มีปุ่มให้/ถอน)

## กติกาที่งวด 1 ตั้งไว้

- **ด่านใดก็ตามที่ถาม cap ใน `GRANTABLE_CAPS`** ต้องถามผ่าน `canUser(user, cap)` (server) หรือ `useCan(cap)` (จอ) เท่านั้น
  - ห้ามใช้ `can(role, cap)` หรือ `capsFor(role).includes(cap)`
  - เทสต์ `src/lib/grantableCapsHonored.test.mjs` แดงทันทีถ้ามีจุดใหม่
- **ระบบที่ปิด (`CLOSED_MODULES`) แจกสิทธิ์ของมันใหม่ไม่ได้** แต่ `sanitizeExtraCaps` ยังเก็บของเดิมไว้
  - วันเปิดระบบกลับ คนที่ยังถืออยู่จะได้สิทธิ์คืนเอง
  - ชื่อระบบอ่านจากส่วนหน้า `:` ของ cap

## งวด 2 — ทะเบียนสิทธิ์เสริม (mig 0440)

- **ของจริงคือตาราง `user_capability_grants`**
  - หนึ่งแถว = หนึ่ง cap ของหนึ่งคน เก็บ เหตุผล · `expiresOn` · คนให้ · เวลาให้ · `warnedAt` · ตราถอน (`revokeKind` = `manual` | `expired`)
  - ถอนแล้ว**ไม่ลบแถว** ประวัติจึงอยู่ครบ
  - unique index บางส่วนทำให้แต่ละคนถือ cap เดียวกันได้ทีละแถว
- **`app_metadata.extraCaps` เป็นสำเนา**
  - `syncExtraCaps` เขียนตามตารางทุกครั้งที่ให้หรือถอน
  - ไม่อ่านตารางทุกคำขอ เพราะ proxy อ่าน `getUser().app_metadata` อยู่แล้ว
  - 🔴 ห้ามเขียน `extraCaps` ตรงที่อื่น: `POST /api/users` มี extraCaps มาจะปฏิเสธ · `PATCH /api/users/[id]` ส่งชุดต่างจากเดิมมาจะปฏิเสธ
- **ตัวตรวจตัวเดียว `validateGrantRequest`** ใช้ทั้ง API และจอ ข้อความ "ยังขาด" บนจอจึงตรงกับที่ API ตีกลับ
  - ต้องเลือกสิทธิ์อย่างน้อยหนึ่งข้อ
  - เหตุผลห้ามว่าง
  - หมดอายุต้องเลือก ไม่มีค่าตั้งต้น
  - ปฏิเสธ cap ที่ตำแหน่งมีอยู่แล้ว · ถืออยู่แล้ว · ระบบปิด · อยู่นอกรายการแจกได้
- **หมดอายุ:** "ถึงวันที่ D" ใช้ได้ถึงสิ้นวัน D ตามปฏิทินไทย
  - งานพ่วงของ cron `close-resolved-issues` (รันทุกวัน 09:00 ไทย) ถอดแถวที่ D < วันนี้
  - เตือนครั้งเดียวเมื่อเหลือ ≤ 3 วัน
  - กระดิ่ง kind `grant_expiring` / `grant_expired` (`GRANT_BELL_KINDS`) ส่งถึงคนถือ (พาไป `/account`) และคนให้ (พาไป `/users`)
- **ย้ายของเดิม:** migration ย้าย cap ที่อยู่ใน `extraCaps` ตอนรัน (25/11 = 3 คน × 2 cap)
  - เหตุผล "ให้ก่อนมีบันทึกเหตุผล" · ผู้ให้ "ไม่มีบันทึก" · ไม่มีกำหนดหมดอายุ
- **ถอดของงวด 1:** `blockedNewGrants` / `blockedGrantError` ถูกถอด ด่านแจกใหม่ของระบบปิดย้ายเข้า `validateGrantRequest`
- **เทสต์:** `src/lib/capabilityGrants.test.mjs` ใช้ฐานจำลอง · ส่วน `grantableCapsHonored.test.mjs` ยืนยันว่า API ผู้ใช้เขียน extraCaps ตรงไม่ได้
- 🛑 **รัน mig 0440 ก่อน merge** — โค้ดงวดนี้อ่าน/เขียนตารางใหม่ ถ้าตารางยังไม่มี จะเป็นแบบนี้:
  - GET `/grants` ตอบ 500 ข้อความไทย
  - หน้าบัญชีไม่โชว์แถวสิทธิ์เสริม (ไม่พัง)
  - cron รายงาน `grantsError` แต่งานอื่นยังทำต่อ

## งวด 3 — แท็บสิทธิ์ในหน้า `/users`

- **ป้ายไทยของทุก cap อยู่ใน `lib/capabilityCatalog.js`**
  - จัดตาม "ระบบ" ที่คนในบริษัทรู้จัก เช่น `sales:*` คือใบยื่นชำระภาษี จึงอยู่หมวดภาษี
  - ทุก cap มีระดับ 1 ดู · 2 ทำงาน · 3 เต็ม
  - `scope` บอกว่าด่านจริงแคบกว่า cap อีกชั้น เช่น "เฉพาะฝ่าย FN"
  - `capabilityCatalog.test.mjs` แดงทันทีที่มี cap ใหม่ในตำแหน่งไหนแต่ไม่มีป้าย หรือมี cap ผีที่ไม่มีใครถือ
- **แท็บสิทธิ์ตามตำแหน่ง (อ่านอย่างเดียว)**
  - ภาพรวม: ตารางตำแหน่ง × 14 ระบบ ใช้ `family="matrix"` ตรึงคอลัมน์ชื่อตำแหน่ง
    - หัวกลุ่มต่อฝ่ายใช้ `TableGroupRow` ย่อ/ขยายได้
    - ระบบที่ปิดอยู่ขึ้นลายขีด
  - ทีละตำแหน่ง: ไล่ทุก cap มี/ไม่มี พร้อมป้าย "ให้รายคนได้"
  - ข้อมูลมาจาก `capsFor(role)` ตรง ๆ ไม่มีตารางให้ดูแลซ้ำ
- **แท็บสิทธิ์เสริมรายคน**
  - แหล่งข้อมูล: `GET /api/users/grants` (ทะเบียนจริง)
  - หนึ่งแถวต่อหนึ่งสิทธิ์ บอกผลจริง: มีผล · ซ้ำกับตำแหน่ง · ระบบปิดอยู่
  - แถบเตือนเมื่อมีสิทธิ์ที่ไม่มีผล
  - แถบแดงเมื่อสำเนาใน `app_metadata` ไม่ตรงทะเบียน (`copyDrift`)
  - ปุ่ม "ให้สิทธิ์เสริม" เปิด `GrantDialog` ตัวเดิมโดยให้เลือกคนก่อน
  - ของที่ย้ายมาจากระบบเดิมขึ้นว่า "ย้ายเข้าทะเบียน" ไม่ใช่เวลาที่ให้จริง
- **แท็บประวัติ:** เหตุการณ์ ให้ · ย้ายของเดิม · ถอน · หมดอายุ เรียงใหม่สุดก่อน
- **มติข้อ 5:** หน้า `/users` เปิดให้ `useCan("users:view") || canManage` · ปุ่มทุกปุ่มยังผูก `canManage` · API อ่านตรวจ `canUser`
  - ⚠️ devBypass ใส่สิทธิ์เสริมไม่ได้ จึงเปิดจอในโหมด users:view ไม่ได้ มีแค่เทสต์รูปโค้ด (`permissionTabs.test.mjs`) คุมอยู่
