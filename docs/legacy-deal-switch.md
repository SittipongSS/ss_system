## 1. มติผู้ใช้ 2026-09-14 ("ตามที่แนะนำ")

1. **Actual มาจากใบสั่งขายที่อนุมัติแล้วเท่านั้น** — trigger `enforce_sales_order_actual_on_deal`
   ถูกแล้ว **ไม่แก้** · ถอดแนวคิด Actual ที่มาแบบ `'legacy'` ออกจากโค้ดแอปทั้งหมด
2. **ยอดที่พิมพ์ 15 ใบ (1,956,850) ย้ายเป็นบันทึกบนหน้าดีล** — `metadata.legacyClosedValue` (ตัวเลข)
   + `metadata.legacyClosedDate` (YYYY-MM-DD = confirmedAt เวลาไทย) อ่านอย่างเดียว
   แล้วล้างยอดที่ยังนับเป็น FC **ยกเว้น** ดีลที่อาจยังผลิตอยู่ (`endDate` ≥ 2026-09-14) —
   ดีลกลุ่มนั้นได้บันทึกแล้ว แต่ยอด FC คงไว้จนเจ้าของยืนยัน (บล็อก B ในคอมเมนต์ท้าย 0359)
3. ดีล ส.ค.–ก.ย. 5 ใบ และข้อมูลผิด 4 ใบ ต้องให้เจ้าของตัดสิน — **ไม่อยู่ในงานนี้** (§6)
4. **สวิตช์ยังอยู่ในฟอร์มสร้างสำหรับทุกคน** แต่เปิดสวิตช์ + Won = **ไม่มีช่องมูลค่า ไม่บังคับตาราง**
   · server ตีกลับ 400 (ข้อความไทย) ถ้าคำขอส่งยอดหรือแถวมูลค่ามา — ห้ามทิ้งเงียบ
   · คำอธิบายบนฟอร์มเลิกสัญญา Actual — บอกว่าเป็นบันทึกงานที่ปิดในระบบเดิม ไม่มีมูลค่า
     ไม่นับ Actual ไม่เข้า FC ยอดขายจริงมาจากใบสั่งขายที่อนุมัติแล้ว
   · ช่องวันที่คงไว้เป็น **"วันที่ปิดในระบบเดิม"** เพราะมีตัวอ่านจริง (§3)
   · สวิตช์กับขั้นอื่น (ไม่ใช่ Won) ทำงานเหมือนเดิม — เดินตามขั้นตอนปกติ
5. client เขียน `legacyClosedValue`/`legacyClosedDate` ผ่าน POST/PATCH ไม่ได้ — server ถอดทิ้ง
   (mig 0359 เป็นคนเขียนคนเดียว)
6. mig 0359 = DML ล้วน · รายชื่อ id ชัดเจน · ด่านรายแถว · รันซ้ำได้ · audit before ก่อนแก้ ·
   ไม่วนทุกดีล · ผู้ใช้รันเองบน SQL Editor

## 3. ช่อง "วันที่ปิดในระบบเดิม" คงไว้เพราะอะไร

ยอดเป็น 0 ก็จริง แต่ `confirmedAt` ยังมีตัวอ่าน:

- `wonMonthOf` (`lib/sales/dashboardMetrics.js`) จัดดีล Won เข้าเดือน: `metadata.wonMonth` → **`confirmedAt`**
  → `poReceivedDate` → `forecastMonth` · ดีลกลุ่มนี้ไม่มี SO ⇒ `wonMonth` ว่าง ⇒ `confirmedAt` ตัดสิน
- เดือนนั้นใช้กับ `wonCount` รายประเภท/คน/ทีม (`api/sales-planning/dashboard`) · ลิ้นชัก "ปิดได้"
  (`DealDrillDownModal`) · `myDashboardTotals` · `targets/history`
- ไม่มีวันนี้ ⇒ `confirmedAt` ว่าง ⇒ ดีลงานเก่าที่คีย์วันนี้ไปนับเป็นดีล Won ของเดือนที่คีย์ ไม่ใช่เดือนที่ปิดจริง

⚠️ **เพิ่มเกินมติ** (ตัดออกได้): ด่านเดียวกันทั้งจอและ server ตีกลับวันที่ปิดที่เลยวันนี้ (เวลาไทย) —
ดีลเก่า Won คืองานที่ปิดไปแล้ว · ที่มา: DL-26080133 มี `confirmedAt` 2026-12-31

## 5. mig 0359 — วิธีรัน

- **ที่ไหน**: Supabase SQL Editor (ผู้ใช้รันเอง)
- **เมื่อไร**: **หลัง deploy** — รันก่อนก็ไม่พัง (ไม่เปลี่ยนสคีมา) แต่ช่วงนั้นหน้าดีลยังไม่แสดงบันทึก
  ยอดของบล็อก A จะหายจากหน้าดีลโดยไม่มีคำอธิบาย และฟอร์มเก่ายังสร้างดีลเก่า Won พร้อมยอดได้
- **ลองก่อน**: เปลี่ยน `COMMIT;` ท้ายข้อ 2 เป็น `SELECT (SELECT count(*) FROM _m0359_note) AS note, (SELECT count(*) FROM _m0359_zero) AS zero; ROLLBACK;`
  — ดูแถวผลลัพธ์ของ SELECT นี้ (คาด note 15 · zero 4 · รอบซ้ำ 0 · 0) · ถ้าด่านไม่ผ่าน DO block จะ RAISE ก่อนถึงบรรทัดนี้
- **ทำอะไร**: ข้อ 1 เขียนบันทึกทั้ง 15 ใบ · ข้อ 2 ล้างบล็อก A 4 ใบ (311,500 · endDate ผ่านไปแล้ว):
  `projectValue` · `forecastManualValue` · ราคาแถวรายหมวด = 0 + แถวประวัติ FC + เธรดดีล
- **ด่าน**: id + รหัส · Won · legacy · ไม่มี SO อนุมัติ · ไม่มีใบเสนอราคา · ยอดและวันที่ตรงกับที่อ่านจาก
  prod 14/09 — ใบไหนเปลี่ยนไป **ยกเลิกทั้งไฟล์** (RAISE EXCEPTION) · ใบที่ **ถูกลบไปแล้ว** ข้ามได้
  (ด่านนับเทียบกับใบในรายชื่อที่ยังอยู่ · ประกาศรหัสที่ข้ามด้วย RAISE NOTICE) — ห้ามแก้ VALUES ในไฟล์
- **รันซ้ำได้**: รอบสองไม่มีแถวเปลี่ยน · audit_logs ไม่เพิ่ม
- **ถอย**: `SELECT "entityType", "entityId", before FROM public.audit_logs WHERE "actorId" = 'migration-0359'`
- **ตรวจหลังรัน**: ข้อ V1–V7 ท้ายไฟล์ · V6 จับดีลเก่า Won ที่สร้างหลังวันทำรายชื่อ (ต้องทำไฟล์ใหม่ ห้ามแก้ 0359 หลังรัน)
- ⚠️ แถวมูลค่ารายหมวดของบล็อก A **ถูกตั้งราคาเป็น 0 ไม่ได้ลบ** — หน้าดีลยังเห็นแถวจำนวน/หมวดราคา 0
  ข้าง ๆ บันทึก · การแบ่งยอดรายแถวเดิมอยู่ใน audit_logs.before เท่านั้น

## 7. สิ่งที่ตั้งใจไม่ทำ

- **ไม่แก้ trigger** และไม่แก้ migration เก่า — คอมเมนต์ใน 0279/0353 ที่อ้างว่า trigger ปล่อยยอดที่กรอกเองยังอยู่
- **ไม่ย้ายยอดเป็น "ยอดขายระบบเดิม" แยกบนภาพรวม** (ทางเลือก ค ในบรีฟ) — ต่อยอดได้ภายหลังเพราะยอดยังเก็บในบันทึก
- บันทึกโชว์เฉพาะหน้ารายละเอียดดีล — ไม่ขึ้นบนรายการดีล/การ์ดดีลบนหน้าลีด
