# มูลค่าคาดการณ์ของดีล = แถวรายหมวดสินค้า

สถานะ: **เสร็จสมบูรณ์** (โค้ด + mig 0264 · ตรวจ 2026-08-17)

## มติ (ผู้ใช้ 2026-08-17)

> *"การสร้างดีล อยากเปลี่ยนมูลค่าคาดการณ์ โดยหมวดสินค้าเลือกหลายรายการได้ และใส่
> จำนวน และราคาต่อหน่วยคาดการณ์ มูลค่ารวมก็ให้คิดอัตโนมัติ"*

คำตอบที่เคาะเพิ่มในรอบเดียวกัน:

| คำถาม | มติ |
|---|---|
| ยอดรวมพิมพ์ทับได้ไหม | **ล็อก คิดจากแถวเท่านั้น** |
| แต่ละแถวกรอกอะไร | หมวด · **ปริมาตร + หน่วยปริมาตร** (mig 0265) · จำนวน · **หน่วยขาย** · ราคา/หน่วย · **หมายเหตุรายแถว** |
| หมวดหลักของดีลมาจากไหน | ผู้ใช้ทักว่า *"workflow template มาจากประเภทดีลนิ"* — ถูกต้อง: template เลือกจาก **ประเภทดีล** (`lib/sales/dealTimelineGen.js`) ส่วน `deals.categoryCode` เป็นแค่ตัว **กรองขั้นตอน** (`categoryOnly` / `categoryExclude` / `flag:excise`) ⇒ ให้ `categoryCode` = **หมวดของแถวแรก** และ server sync ให้เอง ไม่มีช่องหมวดเดี่ยวบนฟอร์มอีก |

## โครงข้อมูล

- `sales_deal_value_items` (mig 0264 · +`volume`/`volumeUnit` ใน mig 0265) —
  `dealId · seq · categoryCode · volume · volumeUnit · qty · unit · unitPrice · amount · note`
  - 🪤 **`unit` กับ `volumeUnit` คนละเรื่องและสลับกันได้ง่ายมาก** (คำเตือนเดียวกับ `lib/master/units.js`):
    `unit` = หน่วย**นับขาย** (ชิ้น · ขวด) ที่คูณกับราคา · `volume`+`volumeUnit` = **ขนาดของหนึ่งหน่วยขาย**
    (100 ml) ซึ่ง **ไม่เข้าสูตรคิดเงิน** ⇒ ฟอร์มโชว์ประโยค `1 ชิ้น = 100 ml` (`packagingSummary`)
    ใต้ช่อง กรอกสลับเมื่อไรอ่านแล้วผิดทันที
  - ปริมาตรไม่บังคับ (งานบริการไม่มีขนาด) แต่กรอกตัวเลขแล้วต้องมีหน่วยเสมอ — CHECK ที่ DB ด้วย
  - CASCADE ตามดีล · unique `(dealId, seq)` · CHECK: `qty > 0` · `unitPrice >= 0` · หมวดเป็นรูป `MM-TTT`
  - **ตารางแถว ไม่ใช่ jsonb** เพราะต้องรวมยอดคาดการณ์ตามหมวดข้ามดีลได้ และ CHECK ระดับคอลัมน์เขียนได้
- `sales_deals.projectValue` **ยังเป็นยอดรวมเหมือนเดิม** — ทั้งระบบ (FC · แดชบอร์ด · ความแม่นยำ FC vs Actual)
  อ่านคอลัมน์นี้ ⇒ ห้ามย้าย · API เขียนทับด้วยผลบวกของแถวทุกครั้งที่บันทึก
- ดีลเก่า **ไม่ backfill** — qty/ราคาต่อหน่วยของอดีตไม่มีใครรู้ · ฟอร์มโชว์ยอดเดิมพร้อมข้อความว่ายังไม่แตกหมวด
  และจะถูกแทนที่เมื่อเพิ่มแถวแรก

## สูตรอยู่ที่เดียว

`src/lib/sales/dealValueItems.js` — ฟอร์มใช้พรีวิว · API ใช้ตอนบันทึก (ห้ามคิดผลรวมเองที่อื่น)

- ปัดเงิน **รายแถวก่อนบวก** — ยอดรวมจึงเท่ากับผลบวกของตัวเลขที่ผู้ใช้เห็นในตาราง
- **ไม่ปัด** `qty` / `unitPrice` — ราคาต่อหน่วยที่มีทศนิยมเกินสองตำแหน่ง (0.335) เป็นของจริงในงานกลิ่น
- `dealValueTotal()` บวกจาก `amount` ของแถวถ้ามี — คิดใหม่จากค่าที่ปัดแล้วจะได้คนละยอดกับที่บันทึกไว้

ฝั่ง server: `src/lib/sales/dealValueItemsRepo.js` (`prepareDealValueItems` ตรวจ+คิดยอดก่อนเขียน ·
`saveDealValueItems` **เขียนทับทั้งชุด** เพราะลำดับแถวมีความหมาย และแถวที่ผู้ใช้ลบต้องหายจริง)

## กับดักที่เจอมาแล้วในงานนี้

1. **โหลดแถวพลาดแล้วคืน `[]`** = ฟอร์มเปิดมาว่าง กดบันทึกทีเดียวล้างแถวจริงทิ้ง ⇒ GET ทั้งสองเส้น
   (`/deals/[id]` · `/deals/[id]/overview`) ต้องตอบ error/warning ไม่ใช่กลืนเป็นลิสต์ว่าง
   หน้ารวมดีลก็ **ไม่เปิดฟอร์มแก้** ถ้าอ่านแถวของใบนั้นไม่สำเร็จ
2. **ยอดรวมกับแถวเขียนคนละคำสั่ง** (PostgREST ไม่มีทรานแซกชันข้ามคำสั่ง) — POST ตอบ `valueItemsWarning`
   (ดีลเกิดแล้ว กดซ้ำจะได้ดีลซ้ำ) · PATCH ตอบ 500 ให้กดบันทึกใหม่ (เขียนทับทั้งชุด กดซ้ำปลอดภัยเสมอ)
3. **`categoryCode` ดิบใน body ต้องไม่ทับหมวดที่มาจากแถว** — ไม่งั้นหมวดของดีลไม่ตรงกับแถวของตัวเอง
4. **อย่ายัด query ใหม่เข้า `Promise.all` เดิมของหน้า overview** — `check:rowcap` อ่านทีละคำสั่งด้วยหน้าต่าง
   14 บรรทัด การเติมบรรทัดที่มี `.limit()` ทำให้คำสั่งข้างเคียงที่ยังไร้ขอบเขตถูกนับว่าปลอดภัย
   (ตัวเลขหนี้ลดเองจาก 169 → 167 ทั้งที่ไม่มีใครแก้อะไร)
5. **CSS ของตารางใหม่ห้ามลอกเลขดิบจาก `QuotationLineItems.module.css`** (17/13/25px) — ชั้นระยะห่าง
   มี ratchet แล้ว (`spacingScale.test.mjs`) · ตารางใหม่ใช้ `TableScroll` เปล่า ๆ ไม่มี
   `premium-glass-table` / `premium-table` ครอบ ตาม ratchet ของ `audit:ui`
